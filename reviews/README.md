# Ревью и планы исправлений

Каждый цикл — папка с датой, внутри два файла:

- **`review.md`** — что найдено на конкретном коммите. После передачи не правится: это фиксация состояния.
- **`plan.md`** — живой документ. Задачи с галочками, таблица решений, возражения, ссылки на коммиты.

Следующий цикл — новая папка рядом, например `2026-11-15/`.

Решения, которые меняют правила, попадают в новую версию правил в [Specification/State_rules](../Specification/State_rules).

## Как работаем

Сейчас работаем с продуктовой частью, поэтому ревью делается ролью «продакт». Полное ревью всеми ролями — перед передачей разработчикам (шаг 6).

Исправления в репозитории делает Claude (Claude Code) по нашим указаниям. В репозитории работают двое, оба пушат прямо в `main`, без pull request.

1. **Ревью.** Запуск в Claude Code: `/im-review продакт`. Результат — `review.md` и `plan.md` в папке с датой. Ревью ничего не исправляет и не коммитит. Готовые ревью и план сразу коммитим и отправляем на GitHub, чтобы их видел коллега.
2. **Согласование плана.** План правим оба, прямо в `plan.md`:
   - решение по вопросу — в таблицу «Решения»: колонки «Решение» и «Кто, дата»;
   - возражение — цитатой под пунктом, с именем: `> Дмитрий: не согласен, потому что…`;
   - перед правкой — `git pull`, после правки — сразу коммит и `git push`. Так правки двух человек в одном файле не конфликтуют.
3. **Задачи для Claude — номерами пунктов из плана.** Что делать, в плане уже записано, описывать заново не нужно. Например:
   - «исправь BUG-01 и DOC-01»;
   - «сделай этап 1»;
   - «внеси решения RULE-01 и RULE-02».

   Пункт из таблицы решений берётся в работу, только когда заполнено поле «Решение». Если решили не так, как предложено в плане, назовите своё решение: Claude впишет его в таблицу и сделает по нему.
4. **Что делает Claude по каждой задаче:**
   - подтягивает свежий `main` с GitHub, чтобы работать по последней версии плана;
   - исправляет;
   - прогоняет самопроверку и проверку ссылок;
   - коммитит и пушит, только если попросить: «исправь BUG-01, закоммить и запушь».

   Коммитов два. Первый — само исправление, сообщение начинается с номера пункта: `BUG-01: Принять — передать payload`. Второй — отметка в плане: `[x]` и номер первого коммита. В один коммит это не уложить: номер коммита появляется только после того, как коммит сделан.

   После push GitHub сам прогоняет проверки. Результат — значок у коммита и вкладка [Actions](https://github.com/soulhome2/IM/actions). Красный крестик — что‑то сломалось, подробности в отчёте.
5. **Повторное ревью** — после пачки исправлений: `/im-review продакт`. Оно смотрит только то, что изменилось с прошлого ревью: какие пункты закрыты и не сломалось ли что‑то новое. Результат — новая папка с датой и новая строка в таблице выше.
6. **Перед передачей разработчикам:**
   - полное ревью всеми ролями: `/im-review`;
   - закрыты все пункты уровня «блокер» и «высокий»;
   - решения из таблиц перенесены в правила, а не остались только в плане.

## Договорённости

- **Номера пунктов постоянные:**
  - `ARCH` — системные причины;
  - `BUG` — прототип;
  - `RULE` — правила;
  - `DOC` — документы;
  - `DATA` — демо-данные;
  - `PROC` — процесс.

  Префикс `D-` не используем: так в `prototype/README.md` нумеруются решения дизайн-кита.
- **У каждого пункта ревью указана важность:** [блокер], [высокий], [средний], [низкий].
- **Коммит начинается с номера пункта:** `BUG-01: Принять — передать payload`.
- **Ссылки в ревью закрепляются на коммит** (`https://github.com/soulhome2/IM/blob/<коммит>/…#L…`), чтобы номера строк не уезжали. Для `.md` нужен `?plain=1`, иначе GitHub не прокрутит к строке.
- **Ревью начинается с автоматических проверок:** `prototype/index.html?selftest` и `python3 tools/check_links.py`. Всё, что они находят, сразу идёт в ревью. Внимательное чтение нужно для остального.
- **Ревью делается по правилам скилла [im-review](../.claude/skills/im-review/SKILL.md).** В Claude Code — команда `/im-review` или просьба «сделай ревью». Порядок, чек‑листы и шаблоны лежат там же и читаются и без Claude. Нашли в ревью новый тип ошибки — добавьте его в [чек‑лист](../.claude/skills/im-review/checklist.md).
- **Ревью смотрит глазами ролей:** архитектор, тестировщик, продакт, UX / оператор, дизайнер, разработчик. По умолчанию — всеми по очереди. Одной ролью — `/im-review продакт` или «посмотри как архитектор». У каждой находки — метка роли.
- **Повторное ревью в тот же день** дописывается в папку этого дня, новая папка не заводится.
- **Новый функционал — вместе с шагом самопроверки** в `prototype/selftest.js`. Иначе следующая правка может его незаметно сломать.
