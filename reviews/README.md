# Ревью и планы исправлений

Каждый цикл — папка с датой, внутри два файла:

- **`review.md`** — что найдено на конкретном коммите. После передачи не правится: это фиксация состояния.
- **`plan.md`** — живой документ. Задачи с галочками, таблица решений, возражения, ссылки на коммиты.

Следующий цикл — новая папка рядом, например `2026-11-15/`.

Решения, которые меняют правила, попадают в новую версию правил в [Specification/State_rules](../Specification/State_rules).

| Дата | Коммит | Ревью | План | Статус |
|---|---|---|---|---|
| 2026-10-01 | `59d3eea` | [review.md](2026-10-01/review.md) | [plan.md](2026-10-01/plan.md) | план на согласовании |

## Договорённости

- **Номера пунктов постоянные:**
  - `BUG` — прототип;
  - `RULE` — правила;
  - `DOC` — документы;
  - `DATA` — демо-данные;
  - `PROC` — процесс.

  Префикс `D-` не используем: так в `prototype/README.md` нумеруются решения дизайн-кита.
- **Коммит начинается с номера пункта:** `BUG-01: Принять — передать payload`.
- **Ссылки в ревью закрепляются на коммит** (`https://github.com/soulhome2/IM/blob/<коммит>/…#L…`), чтобы номера строк не уезжали. Для `.md` нужен `?plain=1`, иначе GitHub не прокрутит к строке.
- **Обсуждение — прямо в `plan.md`.** Возражение пишется цитатой под пунктом, с именем. Итог вносится в таблицу решений.
- **Работаем в `main` без pull request.** Перед правкой плана — `git pull`, после правки — сразу коммит и `git push`. Так правки двух человек в одном файле не конфликтуют.
