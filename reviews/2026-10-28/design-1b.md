# Этап 1б (ARCH-15): одно событие — несколько инцидентов. Проект

Основание — решение пользователя 2026-10-28 в [41-multi-service.md](../../research/integration/41-multi-service.md) («Решение пользователя») и решения № 9, № 10 в [40-plan.md](../../research/integration/40-plan.md). Мнения консилиума — [41-consilium/](../../research/integration/41-consilium/). План работ — [plan-1b.md](plan-1b.md).

Пометка **«Выбор проектировщика»** (В1…В17) — место, где пользователь решения не принимал, а проект выбрал сам. У каждого — отвергнутый вариант. В2, В4, В7, В8 пользователь решил сам 2026-10-28 — они помечены **«решение пользователя»**; подробности внутри них, которые выбрал проект, помечены отдельно. Сводка — в конце.

## 1. Что решено и что в этап не входит

Входит: события проходят через правила (фильтры); каждое подошедшее правило со сценарием создаёт свой инцидент сразу; ключ уникальности «событие + сценарий»; приоритет — от правила; сквозной номер тревоги; соседи знают друг о друге; при «Дубликате» — предупреждение о соседях; «Массовый сбой» на выборке закрывает только свой сценарий; уведомление соседям о ложной тревоге; один звук на тревогу; фильтр очереди по сценарию; нормативы по сценарию.

Не входит: цепочка эскалации по службе и адресация дежурной группе правила (М1) — в §15; вход и токены; редактор правил (в прототипе правила — только из эталонного набора, §17).

## 2. Модель данных

**Правило** (фильтр) — как `incident_rules` сервера МИ: название, приоритет, сценарии, условия. Условия соединены «или», поля внутри условия — «и», каждое поле по желанию — как `incident_rule_conditions` (`source_guid`, `source_type_guid`, `group_guid`, `source_event_type_guid`). В эталонном наборе — новый раздел `rules`:

```json
{ "guid": "80000000-0000-4000-8000-000000000009", "name": "Пожар в торговом центре — медпункт",
  "priority": 100, "createdAt": "2026-09-01T09:00:00Z",
  "scenarios": ["60000000-0000-4000-8000-000000000009"],
  "conditions": [{ "eventTypeId": "fire", "sourceGroupGuid": "30000000-0000-4000-8000-000000000021" }] }
```

Поля условия: `eventTypeId`, `deviceGuid`, `deviceTypeId`, `sourceGroupGuid`. Приоритет — число уровня справочника (§2.5). `createdAt` нужен для последнего шага ранжирования: у сервера МИ у правила только `updated_at` — в `BACKEND.md` записать, что нужен `created_at`.

Правила набора (**В12**): по одному «базовому» правилу на тип события — одно условие, в нём только тип (`80…0001`–`80…0008`, сценарий — нынешний `byEventType`, приоритет — самый частый у типа в наборе: пожар 75, проникновение 75, саботаж 50, праздношатание 25, СИЗ 50, алкоголь 75, разбитие стекла 75, оставленный предмет 75); «Пожар у датчика дыма 2» (`80…000a`: устройство `20000000-0002-4000-8000-000000000002`, приоритет 100, сценарий пожара — пересечение с базовым, ключ даст один инцидент); «Пожар в торговом центре — медпункт» (`80…0009`, выше). Новый сценарий «Медпомощь при пожаре» — `fixtures/scenarios/medical.v1.json`, guid `60000000-0000-4000-8000-000000000009`, три шага. `scenarios.byEventType` переименовать в `scenarios.keys` и добавить `"medical"`: это только имя файла сценария и ключ для тестов, а не выбор сценария (выбирают правила).

**Событие** — запись сервера о присланном источником: `guid` (от источника; повтор приходит с тем же), тип, устройства (первое — источник), время у источника, время прихода, `alarmNumber`, список созданных инцидентов по порядку создания. Прототип хранит события отдельным списком рядом с инцидентами; в эталонном наборе отдельного списка нет — при загрузке сервер собирает события из `eventGuid` и `alarmNumber` инцидентов.

**Номер тревоги** (**В4, решение пользователя**) — номер первого инцидента события: «тревога INC-1847». Своего счётчика и приставки нет. Первый — созданный первым в порядке создания события (§3, шаг 4); у самого первого инцидента номер тревоги равен его собственному номеру. Событие без инцидентов номера тревоги не получает; повтор события — тот же номер. В наборе у 27 инцидентов номер тревоги — свой номер, у соседа `INC-1853` — `INC-1847`.

**Поля инцидента** (API и набор): `eventGuid` — событие, `alarmNumber` — номер его тревоги, `ruleGuid` — правило-победитель (для отчётов; у сервера МИ ссылку на правило вернуть — её убрала миграция 010). У 27 инцидентов набора — свои события `70000000-0000-4000-8000-00000000NNNN` (NNNN — цифры номера), `ruleGuid` — базовое правило типа. Добавляется один сосед: `INC-1853` — «Медпомощь при пожаре», событие и тревога `INC-1847`, новый, приоритет 100, правило `80…0009`.

**Соседи** — инциденты одного события, кроме самого. Это не привязка §11: их не объединяют и не отсоединяют, у каждого свой владелец, сроки и закрытие. Объединить соседей нельзя и так: у них разные сценарии, а объединяют только один (§11.3).

**Статус тревоги** — вычисляется, не хранится, нового состояния машины нет: «открыта», пока открыт хоть один её инцидент; «закрыта», когда закрыты все; «ложная», если все закрыты «Ложной тревогой». В карточке — по инцидентам, видимым смотрящему (**В6**); в отчётах бэкенда — по всем.

## 3. Как событие становится инцидентами

1. Событие уже есть (тот же `guid`) — ничего не создаётся, ответ — прежние инциденты. Если правила поменяли между доставками, повтор ничего не досоздаёт.
2. Правила без сценария отбрасываются. Подошедшие — те, у кого подошло хоть одно условие.
3. Для каждого сценария подошедших правил — один инцидент (**В1**: у правила с двумя сценариями — два инцидента). Правило-победитель среди правил с этим сценарием — по ранжированию §14.5; от него приоритет и `ruleGuid`. Сценарий — последняя версия.
4. Все инциденты события и запись события — одной транзакцией: не создался один — не создаётся ничего. Каждый инцидент проходит переход `create` машины как сейчас. Порядок создания (и номеров `INC-`; первый даёт номер тревоги): чей победитель старше по ранжированию — раньше (решение пользователя 2026-10-28: по точности условия, а не по приоритету правила — номер тревоги может принадлежать не самой срочной службе); сценарии одного правила — по порядку его списка (**Выбор проектировщика** внутри В4; отвергнуто — по порядку сценариев в справочнике). Номер тревоги — номер первого созданного.
5. Не осталось ни одного сценария — инцидентов нет, событие записано как обработанное, номера тревоги нет.

**Ранжирование** (**В2, решение пользователя**: «предложение» §15 принято как правило — в правилах и прототипе; вопрос §15 закрыт). Ранг условия — по самому точному его полю (устройство 3000, тип устройства 2000, группа 1000 + глубина группы в дереве, только тип события — 0; тип события ранга не добавляет); ранг правила — наибольший из подошедших условий; затем приоритет правила; затем раньше созданное; полное равенство — порядок списка правил. Глубина вместо «вложенная точнее родителя» даёт полный порядок: две невложенные группы тоже сравнимы, циклов и «победителя нет» не бывает. Бэкенд исполняет то же — определения раздела `intake` машины.

**Где это записано** (**В3**): смысл выбора — выражениями CEL в машине, как остальные правила (ARCH-07), раздел `intake`; сервер прототипа только собирает данные и вызывает определения.

## 5. «Дубликат» и «Массовый сбой» с соседями

**«Дубликат»** (**В7, решение пользователя**: только предупреждение). Нового поля нет, сервер закрытие «Дубликатом» не отклоняет. Если у инцидента есть соседи, видимые оператору, у варианта «Дубликат» в форме «Закрыть без обработки» — предупреждение: «У этого события есть ещё инциденты ({n}) — это другие службы той же тревоги, а не дубликаты. Закрыть можно, их это не закроет». Без соседей предупреждения нет. Определение §2.2 уточняется: «Та же тревога уже разбирается в другом инциденте; инцидент того же события другой службы — не дубликат». **Выбор проектировщика:** предупреждение — у варианта списка (новое `FieldOption.warning`), показывается, когда вариант выбран; отвергнуто — пояснение всей формы (у формы одно пояснение — первое подходящее, оно занято текстом о шагах).

**«Массовый сбой» на выборке** (**В8, решение пользователя**: закрыть только свой сценарий). «Закрыть без обработки» на панели выборки остаётся доступным; закрываются только отмеченные сценария основного выборки, остальные пропускаются и не меняются. **Основной выборки** — как в §11.3 (`mergePrimary`): свой «В работе», а если таких несколько — самый срочный, при равенстве — появившийся раньше; иначе самый срочный новый, при равенстве — появившийся раньше. **Выбор проектировщика:** если по §11.3 основного нет (отмечены только отложенные, ожидающие принятия, чужие) — тот же порядок по всем отмеченным: самый срочный, затем появившийся раньше, затем меньший номер (`bulkPrimary`); отвергнуто — сценарий, которого в выборке больше всего. Доступность действия считается только по инцидентам своего сценария. Что видит оператор: в форме — «Закроются инциденты сценария «Пожарная тревога»: 2 из 3. Других сценариев — 1, они останутся открытыми»; после действия — уведомление «Не закрыты — другой сценарий: INC-1853»; в ответе сервера `BulkTransitionResult.skipped[]` — `{incidentGuid, number, reasonKey: "workflow.error.selection.other_scenario"}`. Одиночный «Массовый сбой» из строки не меняется.

## 6. Уведомление, звук, видимость

**Ложная тревога у соседа** (**В9**). Закрыт «Ложной тревогой» — каждому открытому соседу запись в журнал «INC-1847 того же события закрыт: Ложная тревога» и уведомление его адресату: владельцу, адресату передачи или участникам дежурной группы на месте с доступом (`recipients`). У нового соседа адресата нет — только запись в журнал; себе — не уведомляется (как BUG-30). Закрытым соседям — ничего. Автозакрытия нет. Событие потока — новое `incident.sibling_closed` получателю: `incident` — его инцидент, `payload` — `{siblingGuid, siblingNumber, closeResultId}`; клиент — всплывающее уведомление.

**Один звук на тревогу** (**В10**). Уведомления адресату (§8.1) и алерты (§9) по инцидентам одной тревоги, пришедшие одному человеку за 10 секунд, — один звук; уведомления остаются отдельными. Решает клиент по `eventGuid` в событии потока, настройки нет. Звука у появления нового инцидента нет и не вводится. В прототипе звука нет вовсе (§17) — правило только в правилах и описании потока.

**Видимость** (§5). Соседи в карточке и число «ещё N» — только видимые смотрящему. Сейчас у соседей одно устройство-источник, поэтому видимость совпадает; правило записано на случай доступа по правилу (§15).

## 7. Контракт (`openapi.json`, CRLF)

- `IncidentSummary`: `eventGuid` (uuid), `alarmNumber` (номер первого инцидента события, вид как у `number`) — обязательные; `ruleGuid` (uuid или null); `siblingCount` — видимые незакрытые соседи (**В5**).
- `IncidentCard`: `alarm` — `{eventGuid, number, status: open|closed, allFalseAlarm, siblings: AlarmSibling[]}`, соседи — все видимые, и закрытые; `ruleName` (**В14**). `AlarmSibling`: `guid`, `number`, `scenarioTitle`, `state`, `badge`, `owner`, `closeResultLabel`.
- `GET /operator/incidents`, `…/counters`, `POST …/selection`: параметр `scenarioGuid` — один или несколько через запятую. Поиск находит и по номеру тревоги.
- `GET /operator/reference/scenarios` — `ScenarioRef[]` `{guid, name}`: сценарии правил и открытых инцидентов, по названию.
- `FieldOption.warning` — `{key, text, vars}` или null: предупреждение варианта. `BulkTransitionResult.skipped[]` — `{incidentGuid, number, reasonKey}`; в описании `…/transitions/{transitionId}/bulk` — правило своего сценария.
- Поток: тип `incident.sibling_closed`, `StreamSiblingClosedPayload`; в таблице потока — строка и правило звука.
- Тестовый стенд: новый `POST /test/events` — `TestEventRequest {eventGuid?, eventTypeId, deviceIds, site?, location?, occurredAt?}`, ответ `TestEventResult {eventGuid, alarmNumber|null, created, incidents: IncidentCard[]}` (инциденты — по порядку создания): `201`, если создан хоть один, иначе `200`. `POST /test/incidents` остаётся — один инцидент в обход выбора (**В11**): `ruleGuid` по желанию, без него — базовое правило типа; `priority` в теле — подмена на прогон, приводится к уровню по §2.5. Каждый вызов — новое событие, номер тревоги — свой номер. Без `priority` приоритет — правила: это следствие **решения пользователя** «приоритет задаёт правило» (№ 9), а не выбор проекта — тестовый инцидент без числа получает 75 у пожара вместо самого низкого.

## 8. Прототип

- `server.js`: `load()` читает `rules`, события набора; `intake(spec)` — алгоритм §3 через определения `intake`; `createIncident` — по правилу; `summary()`/`card()` — новые поля; фильтр `scenarioGuid`, поиск по номеру тревоги; `selectionActions`, общая форма выборки и bulk — `bulk.scope` (основной, свой сценарий, `skipped`); варианты формы — `warning`; `deliver` — `incident.sibling_closed`; маршруты `/test/events`, `/operator/reference/scenarios`.
- `engine.js`: `celIncident` + `eventGuid`; предупреждения вариантов в `form()`; мир — `deviceInGroup`, `groupDepth`.
- `app.js` (минимально): в строке очереди — «тревога INC-1847» рядом с номером, если номер тревоги не свой (**В17**), и чип «событие: ещё N» (не `.chip.linked`; подсказка — номера соседей); в карточке — блок «По этому событию» над шагами (**В15**): «Тревога INC-1847 · открыта», соседи строкой «INC-1853 — Медпомощь при пожаре, Новое», номер — «Посмотреть»; в «Фильтры» — список «Сценарий»; в форме закрытия — предупреждение выбранного варианта; после «Массового сбоя» на выборке — список пропущенных; уведомление `incident.sibling_closed`.

## 10. Отвергнутые варианты

- М1 сразу (адресация группе правила) — пользователь отложил на второй шаг.
- М3 (один инцидент с заданиями служб) — вторая машина внутри первой, ломает «одно состояние — один владелец».
- М4 и «по подтверждению» — служба зависит от памяти оператора; пользователь отказался.
- Ключ «событие + правило» — пересекающиеся правила одного сценария дают дубли.
- Автозакрытие соседей при ложной тревоге — ложное для одной службы не значит ложное для другой.
- Тревога как новое состояние или сущность со своим циклом — статус вычисляется, машина не меняется.
- Соседи как привязка §11 — у привязки другой смысл: один владелец, общий срок.
- Запрет «Дубликата», пока есть соседи, или обязательное поле «Дубликат инцидента» с запретом соседа — пользователь выбрал предупреждение.
- «Массовый сбой» по разным сценариям недоступен — пользователь выбрал закрывать свой сценарий, остальные пропускать.
- Номер тревоги со своим счётчиком (`ALM-…`) — пользователь выбрал номер первого инцидента.
- Ранжирование — открытый вопрос для бэкенда — пользователь принял «предложение» §15 как правило.
- Выбор правила кодом `server.js` — правило жило бы вне машины (ARCH-07).
- Убрать `POST /test/incidents` — переписать 13 вызовов тестов без пользы.
