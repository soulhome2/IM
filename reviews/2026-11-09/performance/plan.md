# Скорость рабочего места оператора на миллионной базе — сведение (агент С)

- **Дата:** 2026-11-10. Входы: [map.md](map.md) (К), [db.md](db.md) (Б), [api.md](api.md) (А), [client.md](client.md) (У).
- Сервер `c3d6b33`, клиент `51226ca` (`feature/im_operator`). Сервер на стенде не трогал, в базу не писал, код не менял.
- Решения человека из обсуждения 2026-11-10 (выше мнений агентов): **списки остаются страницами**; **число на экране зависит от выбранного фильтра** — см. §1.

## 0. Итог в пяти строках

1. Почти всё время базы (95 %) — выборка классов очереди `QueueClasses` (QC, 0,7 с): она читает все ~930 тыс. инцидентов, хотя живых ~600; клиент вызывает её трижды (список, счётчики, дерево) на **каждое** событие SSE.
2. Ожидание в 16–18 с — не сервер: одинаковые GET стоят в цепочке за блокировкой кэша Chrome, «отменённые» запросы без `signal` живут до 30 с, затем уходят пачкой и забивают пул сервера из 16 соединений (закрытие — 7,9 с).
3. Фильтры «Завершённые» и «Все» — 10 с на страницу и ещё ~9 с на место `focusGuid` (итого 19–20 с): это `QueuePage` по всем закрытым, а не QC (перемерено, §1.2).
4. Больше всего даст: в клиенте — `signal` + слияние перечитываний + `no-store` (только клиент); в базе — считать по выбранному фильтру: живые — `state <> 'closed'` + частичный индекс (700 → 5 мс).
5. Для фильтров с закрытыми — отдельная работа над страницей (сортировка по индексу, место фокуса не по всем строкам) и выбор, как давать их число (нужно решение, §5).

## 1. Спорные места и перемеры

### 1.1. Показывает ли клиент число закрытых — прав пользователь, отчёт У (вывод 6, У-4) прав наполовину

- **У прав про `/counters` и дерево:** строка состояния (`shell/StatusBar.tsx:94`) и дерево групп (`groups/GroupsPanel.tsx:347–390, 690`) берут только `counters.open` и `top`. Закрытые там не нужны.
- **У неправ в целом:** под списком «1–8 из N» (`queue/Pager.tsx:90`, `page.total`). На сервере `total` страницы — **сумма классов QC** (`storing/queue_queries.go:97` — «the total of a page is the sum of its classes», `:303–305`). При фильтре «Завершённые»/«Все» N включает закрытые, и считает его та же QC. Ещё числа: у вариантов в окне фильтра (`queue/MultiSelectCombo.tsx:281`, `item.count`) и «найдено N» (`queue/FilterWindow.tsx:265`, `view.count`).
- **Вывод:** убрать закрытые из QC целиком нельзя. Их можно убрать, когда выбранный фильтр их не содержит, — это и есть согласованное направление (§4, этап 2).

### 1.2. «Завершённые»/«Все» — 19–20 с (У) против 0,7 с у QC (Б): обе цифры верны, это разные запросы

Перемер, `curl` напрямую в `:5000`, 3 раза, `pageSize=8`:

| Фильтр | без `focusGuid` | с `focusGuid` |
|---|---|---|
| `open` | 0,68 / 0,69 / 0,67 с | 0,68 / 0,67 / 0,68 с |
| `done` | 9,8 / 10,0 / 10,0 с | 19,3 / 18,8 / 19,5 с |
| `all` | 9,8 / 9,7 / 9,7 с | 19,2 / 19,5 / 19,1 с |

Журнал Postgres за эти 10 мин: медленные выражения — `stmtcache_98207284…` и `stmtcache_1240e211…` (`QueuePage`, варианты сортировки), 9,2–10,2 с каждое. QC в них — те же 0,7 с.

- **Причина:** `QueuePage` (`queue_queries.go:297`) — соединение выбранных классов (`chosen`) со всеми инцидентами и `events`, сортировка ~930 тыс. строк ради `LIMIT 8` (`queuePageSQL`). Место фокуса (`queueFocusSQL`, `:241`) — `row_number() OVER (ORDER BY …)` по всем тем же строкам — второй такой же проход. План с `EXPLAIN` не снимал (догадка по тексту и времени; снять — первым шагом этапа 4).
- Клиент шлёт `focusGuid` почти всегда (выбранный инцидент), поэтому оператор видит 19–20 с.

### 1.3. Где копится очередь — сходятся А и У

А: сервер получает запросы каждого вида по одному, затем пачкой. У: цепочка за блокировкой кэша Chrome на одинаковый адрес (шесть одинаковых `/counters` — лесенкой 0,66…4,0 с; с `no-store` — все 0,8–0,9 с). Пачка через ~30 с — таймер `AbortSignal.timeout(30_000)` (догадка У по совпадению, не проверена под `load.py`). Гипотеза К о пределе шести соединений отпала (HTTP/2).

### 1.4. Закрытие за 7,9 с — пул, не блокировка

К предполагал блокировку; Б не нашёл ожиданий блокировок в базе; А показал: закрытие ждало соединения пула за пачкой из 73 QC (повтор: `/session` ждёт 3,7–3,9 с за 70 одновременными счётчиками). Верна версия А.

### 1.5. `ReadIncidentFamily` — 137 мс (А) или 200–890 мс (Б)

Обе верны: А — среднее по 100+ id в прогоне, Б — медиана/p90 на 11–1000 id по 2 ч журнала и повтор 239 id — 0,7 с. Не N+1 (А): один запрос на страницу `pageSize=100`. В рабочем месте страница 8 — касается `load.py`, обхода адресатов и пачек SSE.

## 4. План по этапам

### Перепроверка 2026-11-10

Оговорки:
- **16–18 с — следствие частых событий.** Они сняты под `load.py`, где два оператора-скрипта работают без пауз и браузер получает плотный поток SSE. Каждое событие добавляет в цепочку ~0,7 с. При редких событиях оператор видит ~0,75 с на обновление, а не 16 с. Насколько срочен этап 1, зависит от настоящей частоты событий — её нужно узнать.
- **Порядок.** Этап 2 даёт выигрыш и в покое, и под нагрузкой, а этап 1 — только под потоком событий. `no-store` (У-1) — только после этапа 2: без него сняв цепочку, клиент сразу забьёт пул сервера тяжёлыми QC.

### Этап 1. Клиент: убрать цепочку и лишние перечитывания (без изменения API)

- **Что:** `~/Work/incident-manager`:
  - У-2: `signal` из TanStack Query в `queryFn` → транспорт (`AbortSignal.any` с таймером);
  - У-3: слияние перечитываний — не больше одного `useReloadAll` в полёте и одно отложенное (300–500 мс) (`state/workplaceStore.ts:261`, `shell/useServerEvents.ts`);
  - У-1: `cache: 'no-store'` в `api/operatorApi.ts:170–179` — только вместе с У-2/У-3 **и после этапа 2**, иначе на сервер пойдёт больше одновременных QC по 0,7 с и пул из 16 соединений кончится (см. перепроверку 2026-11-10 ниже).
- **Сервер (тот же этап):** проверить, что `context` запроса доходит до `pgx` в чтениях очереди (А 2.3) — тогда брошенная выборка освобождает соединение.
- **Выигрыш:** под нагрузкой 16–30 с → ~1 с; QC на пачку событий — в разы меньше; пул перестаёт забиваться (закрытие — 22 мс под пачкой).
- **Проверка:** `load.py 10 60` + запись сети браузера (как у К, `cap.mjs`) — медиана ожидания очереди/счётчиков < 1,5 с, нет `failed` по таймеру 30 с; число QC в журнале Postgres за 10 мин — в разы меньше 2424; тесты клиента; правило 147 («запрос во время загрузки не теряется») — отдельный тест.
- **Перенос данных:** нет.

### Этап 2. База и сервер: считать по выбранному фильтру

- **Что:** `~/Work/incident-manager-server`:
  - миграция 052 — частичный индекс по живым (§3);
  - QC получает состояния выбранного фильтра; фильтр без закрытых — условие `state <> 'closed'` в QC и странице;
  - `/counters` и дерево с числами — **только живые** (на экране только `open` и `top`, §1.1);
  - `PeopleIncidents`, `AddressedIncidents` — дописать `AND i.state <> 'closed'`.
- **Выигрыш:** обычная работа (фильтры «Открытые», «Мои» и т. п.): 0,7 с → ~5 мс на вызов, ~1820 из 1912 с базы за 10 мин прогона; тики 66 → 2,5 мс и 206 → 5 мс.
- **Проверка:** повтор QC и тиков (`EXPLAIN (ANALYZE, BUFFERS)` из db.md, 3 раза), `curl` очереди/счётчиков/дерева 3 раза; тесты сервера на очередь, счётчики, дерево; тест: N в «1–8 из N» и числа окна фильтра совпадают с `count(*)` при фильтре с закрытыми и без; фильтр `customer_guid` и правила доступа — те же тесты.
- **Перенос данных:** нет (индекс `CONCURRENTLY`).
- **Контракт:** если `/counters` перестаёт отдавать классы закрытых — правка `openapi.json` (решение Р-1).

### Этап 3. Фильтр с закрытыми: не пересчитывать на каждое событие

- **Что:** выбрать вариант Р-2. Без решения — уже сейчас можно не перечитывать список с закрытыми по каждому событию SSE, а только по смене фильтра (как в аудите) — это тоже видимое поведение, значит Р-2.
- **Выигрыш:** с 0,7 с QC + страница на событие до одного подсчёта на смену фильтра (или 0,3 мс с таблицей счётчиков).
- **Проверка:** как этап 2 + сверка счётчика с `count(*)` (если таблица).
- **Перенос данных:** для таблицы счётчиков — начальное заполнение в миграции (~1 с на этих данных).

### Этап 4. Страница «Завершённые»/«Все» — 10 + 9 с

- **Что:** `storing/queue_queries.go` — снять `EXPLAIN (ANALYZE, BUFFERS)` `queuePageSQL` и `queueFocusSQL` при закрытых; переписать страницу на проход по индексу в порядке сортировки с `LIMIT` (без сортировки всех строк); место фокуса — не `row_number()` по всем строкам, а подсчёт строк «до» по индексу, либо не искать фокус в фильтрах с закрытыми (решение Р-3).
- **Выигрыш:** 19–20 с → ожидаемо < 1 с (догадка до плана).
- **Проверка:** перемер из §1.2 (3 раза, с фокусом и без); тест сервера на порядок и место фокуса для всех `queueOrderSQL`.
- **Перенос данных:** нет; возможно — новый индекс (§3).

### Этап 5. Защита пула и мелочи сервера

- Семафор на 4–6 одновременных тяжёлых чтений (`appservice/operator/queue.go:32`, `references.go:217`) — чтобы переходы всегда находили соединение (А 2.2). После этапов 1–2 менее важен, но страхует от пачек «Завершённых».
- Переписать `ReadIncidentFamily` (Б-2: CTE + соединение по событию): 0,2–0,9 с → 3–11 мс на 11–1000 id. Перенос не нужен, ответ сверен по md5.
- `ConnMaxLifetime` 5–30 мин, `MaxIdleConns = MaxOpenConns`, постоянный порядок колонок `INSERT` (А 2.6) — < 1 % базы, дёшево.
- Автоочистка `incidents`: `autovacuum_vacuum_scale_factor = 0.02`, `analyze 0.01` (Б §3).
- **Проверка:** `load.py` + 70 одновременных счётчиков и `/session` (тест А): `/session` < 50 мс; Б-2 — `EXPLAIN` 3 раза.
