# Клиент оператора: где копится очередь (агент У)

- **Дата:** 2026-11-10. Клиент `51226ca` (`feature/im_operator`), сборка стенда `~/Work/stand/im-dist`, сервер — уже запущенный `im-events`.
- **Как мерил:** puppeteer + headless Chrome, вход через `dev-login.html`, рабочее место `/im/operator/` во фрейме облака. Скрипты — в scratchpad сессии: `par.mjs` (параллельные одинаковые GET), `par2.mjs` (то же с `cache: 'no-store'`), `act.mjs` (клик → готовый экран, тайминги сети Chrome).
- Каждое число повторено три раза (если не сказано иное). Нагрузку `load.py` **не запускал**, в базу не писал. Во время замеров на стенде шли чужие события SSE (работали другие агенты) — это видно по самопроизвольным `useReloadAll`.

## Главное

1. **Очередь копится в кэше HTTP браузера, а не в сети и не на сервере.** Chrome не пускает в сеть второй GET на тот же адрес, пока не закончен первый (блокировка записи кэша — cache lock). Шесть одинаковых `GET /incidents/counters` из страницы пришли «лесенкой»: **0,66 · 1,3 · 2,0 · 2,6 · 3,3 · 4,0 с**; то же у дерева (`/source-groups?withCounters=true`). Шесть **разных** адресов (счётчики, дерево, очередь ×2) идут параллельно: 0,74 / 0,66 / 0,76 с, затем вторая тройка 1,4 с. С `fetch(..., {cache: 'no-store'})` те же шесть одинаковых — **все за 0,81–0,90 с**. Протокол до шлюза — HTTP/2 (`curl --http2` → `HTTP/2`), то есть предел шести соединений на адрес ни при чём.
2. **Это и есть «сервер видит запросы каждого вида строго по одному».** У каждого вида запроса (`counters`, `tree`, очередь с одним и тем же `focusGuid`) адрес не меняется от события к событию, поэтому все повторы встают в одну цепочку за кэшем. При ~0,75 с на запрос и событиях SSE ~1,3 раза в секунду (карта, §1) цепочка растёт быстрее, чем тает: отсюда 16–18 с ожидания у браузера при 0,75 с на сервере.
3. **Отмена в TanStack Query не отменяет сам запрос.** `useReloadAll` (`state/workplaceStore.ts:261–267`) зовёт `invalidateQueries` для шести ключей; по умолчанию `cancelRefetch: true`, то есть прежний незаконченный запрос «отменяется» и сразу ставится новый. Но ни один `queryFn` не берёт `signal` из контекста (`useQueue.ts:123`, `boot/OperatorContext.ts:38/50/65`), а транспорт ставит свой сигнал только по таймеру — `AbortSignal.timeout(30_000)` (`api/operatorApi.ts:11, 177`). Значит, «отменённый» fetch живёт до ответа или до 30 с, держит блокировку кэша, и новый запрос стоит за ним. Каждое событие SSE добавляет в цепочку ещё по запросу на каждый вид.
4. **Максимум «ровно 30 с» и пачка «73 запроса за секунду через ~30 с» — это таймер транспорта.** Запросы, простоявшие в цепочке 30 с, обрываются `AbortSignal.timeout` (карта: 148 `failed`); как только голову цепочки обрывает таймер, стоящие за ней запросы одновременно уходят в сеть. *Догадка* по совпадению чисел (30 с, пачка после затишья) и по поведению cache lock; в журнале сети под `load.py` не проверял — не запускал запись в базу.
5. **Сервер при этом тянет параллельно:** шесть одинаковых счётчиков с `no-store` — 0,8–0,9 с каждый вместо 0,7 с поодиночке. То есть убрать цепочку в клиенте безопасно, но запросов к QC станет больше одновременно — вместе с этим надо снижать само число перечитываний (п. 7–8).
6. **Счётчики на экране — только число открытых.** По коду (`grep` по `src/operator`): `shell/StatusBar.tsx:94` — `counters.open` в строке состояния; `groups/GroupsPanel.tsx:690` — `counters.open` на кнопке групп, `:691` — `topPriority` узлов; строки дерева — `row.counters.open` и `row.counters.top` (`:347, 365, 388–390`). Выбор фильтра (`QueueToolbar.tsx:120`, `<select>`) чисел не показывает. Числа закрытых и «всех» инцидентов из `/counters` **нигде не выводятся**. Число строк списка («Завершённые», «Все») берётся из `total` страницы очереди (`useQueue.ts:103`), а не из счётчиков. Значит, обоснование из «Что уже сделано» («фильтры „Завершённые“ и „Все“ показывают их число») для клиента оператора не подтверждается: в счётчиках можно не считать закрытые — **нужно решение** (контракт `/counters` отдаёт все классы).
7. **На каждое чужое событие — пять-шесть запросов и три QC** (`useServerEvents.ts` → `now.reload()`), без слияния событий: пачка из N событий даёт N перечитываний. Свои переходы — то же (`forms/useRunTransition.ts:105–116`).
8. **Фильтры «Завершённые» и «Все» — 19–20 с на сервере** (замер ниже): `GET /incidents?filter=done…` — `took 20.2 s` в `im-server.log`. Это не клиент, но это самое долгое действие оператора; передать агенту А/Б.

## Действие → запросы → ожидание → итог

Без `load.py`, на фоне редких чужих событий. «Ожидание сервера» — `receiveHeadersEnd − sendStart` по таймингам Chrome; «итог» — от клика до нужного элемента на экране.

| Действие | Запросы (главные) | Ожидание сервера | Работа браузера | Итог (3 повтора) |
|---|---|---|---|---|
| Вход до первой строки очереди | ~15 (карта §1) | QC ×3 по ~0,75 с параллельно | — | 3,0 / 3,1 с от `dev-login` (вместе со входом облака) |
| Фильтр «Мои», «Открытые» | `GET /incidents?filter=…` (+ иногда перечитывание от события) | 0,68–0,75 с | ≤ 30 мс | 0,71 / 0,72 / 0,77 с (один раз 11 с — запрос встал в цепочку за прежним тем же адресом, п. 1) |
| Фильтр «Завершённые» / «Все» | `GET /incidents?filter=done` / `all` | **20,2 с / 19,1 с** | ≤ 30 мс | 20,2 с / 19,1 с (по одному замеру: дольше не гонял) |
| Открыть карточку | `GET /incidents/{id}` (+ heartbeat) | 12–13 мс | 10–30 мс | 23 / 45 / 38 мс |
| Взять, ответить на шаг, закрыть | — | — | — | не мерил: пишут в базу (см. ниже) |

Вывод: без нагрузки браузер почти ничего не тратит — всё время ответа уходит на QC на сервере. Под нагрузкой к этому добавляется цепочка за кэшем браузера (п. 1–4).

## Находки

### У-1. Одинаковые GET стоят в цепочке за кэшем HTTP Chrome
- **Где:** `api/operatorApi.ts:170–179` (`httpTransport`, `init` без `cache`).
- **Сейчас:** 6 одинаковых `/counters` — 0,66…4,0 с лесенкой; с `no-store` — 0,81–0,90 с все (`par.mjs`, `par2.mjs`, 3 повтора, разброс ±0,1 с).
- **Причина:** cache lock Chrome на одинаковый адрес; ответы сервера без `Cache-Control`.
- **Предложение:** `cache: 'no-store'` в `init` транспорта для GET (или `Cache-Control: no-store` в ответах сервера — это шире, трогает сервер).
- **Выигрыш:** ожидание под нагрузкой с 16–18 с до ~1 с (оценка; под `load.py` не проверено).
- **Цена:** одна строка. Риск: больше одновременных QC на сервере (п. 5) — делать вместе с У-2, У-3.

### У-2. `queryFn` не берёт `signal` — отменённые запросы живут до 30 с
- **Где:** `queue/useQueue.ts:123`, `boot/OperatorContext.ts:38, 50, 65`, `card/useLinked.ts:60`, `OperatorPage.tsx:184`; транспорт — только `AbortSignal.timeout`.
- **Предложение:** прокинуть `signal` из контекста TanStack через `calls.*` в транспорт, сложить с таймером (`AbortSignal.any`). Тогда `cancelRefetch` реально обрывает прежний запрос, сервер (через отмену контекста Go) тоже может бросить выборку.
- **Выигрыш:** нет хвоста брошенных запросов; меньше QC на сервере (карта: 148 брошенных за 10 мин досчитывались).
- **Риск:** в Go отмена контекста должна доходить до `pgx` — проверить агенту А.

### У-3. Перечитывание на каждое событие без слияния
- **Где:** `shell/useServerEvents.ts` (вызов `now.reload()`), `state/workplaceStore.ts:261`.
- **Предложение (без изменения API):** сливать перечитывания: не больше одного `useReloadAll` в полёте и одно отложенное (trailing, 300–500 мс). Решение 147 («запрос во время загрузки не теряется») это сохраняет: отложенное перечитывание случится после текущего. Альтернатива — `cancelRefetch: false` для `counters`/`tree`/`session` + одно отложенное.
- **Выигрыш:** под нагрузкой ~1,3 события/с → не больше ~1 перечитывания в 0,75 с вместо очереди; QC втрое меньше на пачку событий.
- **Риск:** счётчики отстают на доли секунды — видимое поведение почти не меняется, но правило 147 надо сверить — **нужно решение**, если задержка заметна.

### У-4. Счётчики и дерево перечитываются, хотя на экране только `open`
- **Где:** см. п. 6 «Главное».
- **Предложение (требует решения по контракту):** считать на сервере только открытые классы для `/counters` и `withCounters` дерева; или один вызов вместо трёх QC (список + счётчики + дерево из одного прохода) — **изменение API, нужно решение**.

### У-5. `/session` и карточка — на каждое событие
- 3–15 мс каждый, нагрузки почти не дают, но в той же цепочке кэша (одинаковый адрес). После У-1 безвредно.

## Без изменения API / с изменением

- **Без изменения API (только клиент):** У-1 (`no-store`), У-2 (`signal`), У-3 (слияние перечитываний). Порядок: У-2 + У-3, затем У-1.
- **С изменением API или правил (нужно решение):** У-4 — счётчики без закрытых или общий вызов «очередь + счётчики + дерево»; события SSE с дельтой счётчиков вместо перечитывания.
