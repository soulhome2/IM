# Памятка для команды бэкенда

С чего начать операторскую часть МИ и как понять, что она готова. Подробности — в [README машины](README.md), здесь — порядок работы и критерий готовности.

## Что реализовать

| Что | Где описано |
|---|---|
| REST API операторского места — 45 операций, плюс 5 служебных для тестового стенда | [`openapi.json`](openapi.json) — контракт, OpenAPI 3.1; для генератора кода — копия в OpenAPI 3.0 [`openapi.v30.json`](openapi.v30.json) (ниже) |
| Исполнение модели workflow: 6 состояний, 32 перехода, 35 условий, 25 эффектов, таймеры, лимиты, права | [`workflow_schema.v1.json`](workflow_schema.v1.json) — модель как данные; смысл — в [README машины](README.md), «Модель workflow» |
| Смысл условий и эффектов, бейджей, фильтров очереди и правил форм — выражения CEL в машине (ARCH-07) | [`CEL.md`](CEL.md) — язык выражений, факты мира, которые даёт сервер, операции эффектов |
| Правила, из которых всё это следует | [`States rules IM.md`](../State_rules/States%20rules%20IM.md) — действующие правила, ссылки «§N» ведут туда |

Модель — это конфигурация, а не код. Сервер хранит её, исполняет и отдаёт клиенту (`GET /operator/workflow/active`). Переходы, кнопки, формы, бейджи и нормативы клиент берёт оттуда и из ответов сервера. Своей таблицы переходов у клиента нет.

Пример исполнения — встроенный сервер прототипа: [`prototype/server.js`](../../prototype/server.js) и исполнитель модели [`prototype/engine.js`](../../prototype/engine.js). Это JavaScript в браузере, в продукт его не переносят. Он пример, а не источник требований: требования — машина, контракт и правила; если прототип с ними расходится, ошибка в прототипе. Всё, что сервер делает помимо переходов машины — тексты, поток событий, параметры запросов, поля ответов, — описано в контракте и машине. Это проверяют `tools/check_machine.py` (тексты — ключами каталога, каждое событие потока и каждый параметр описаны, сервер их читает) и тесты API (каждый ответ — по схеме контракта) (ARCH-04).

## На что обратить внимание

- **Выражения машины — CEL** ([`CEL.md`](CEL.md), ARCH-07). Смысл всех условий и эффектов записан в машине выражениями; сервер вычисляет их реализацией CEL своего языка (у Google есть для Go, Java, C++, Python). Сервер даёт факты мира из `cel.world` машины — права, доступ, состав групп, состояние оператора, молчание, наборы шагов сценария, последний адресат передачи — и переводит свои данные в типы `cel.types`: пусто — `''` и `0`, время — целые мс. Бейджи, фильтры очереди и правила форм — тоже выражения машины (CEL.md, «Правила интерфейса»): сервер вычисляет их под смотрящего, клиент получает готовое. **Изменение контракта:** у поля формы вместо `required`, `visibleWhen`, `requiredFrom`, `excludes`, `excludeSystemItems`, `optionsFrom`, `defaultWhen`, `defaultFrom` — выражения `requiredExpr`, `visibleExpr`, `optionExpr`, `enabledExpr` + `disabledKey`, `defaultExpr`; у пояснения формы вместо `when` — `expr`; у бейджа вместо `state`, `viewerRole`, `when` и у фильтра очереди вместо `states`, `stateCategories`, `ownership` — `expr`. У доступного действия с формой — новое `fieldRules`: видно ли каждое поле и обязательно ли, таблицей по вариантам поля, от которого это зависит.
- **Факты над множеством инцидентов** (ARCH-12, [`CEL.md`](CEL.md)). Выражения не перебирают все инциденты: им нужны `incidentById`, `linkedOf`, `countMine`, `mineOf`, `groupMembersAt` — факты мира, которые сервер исполняет запросами по индексу (owner+state, linked_to, id). Смысл каждого — выражение `ref` в машине над всеми инцидентами; запрос обязан давать то же, внутри перехода — с изменениями этой транзакции. Загружать все инциденты в каждое вычисление не нужно.
- **Переход атомарен.** Всё меняется одним запросом `POST …/transitions/{transitionId}` в одной транзакции: состояние, владелец, таймеры, журнал. Отдельных `/claim`, `/close` нет и не будет.
- **Версия записи.** Карточка отдаёт `ETag` — поле `version` в кавычках, `"12"`. Переход и ответы сценария приходят с `If-Match`. Нет заголовка — `428`, версия не совпала — `412` с актуальной карточкой в теле.
- **Выборка и повторы** (§14.1, BUG-84). Массовое действие и объединение несут `expectedVersions` — версии отмеченных на момент отметки (их отдают `POST /operator/incidents/selection` и `…/filter` в `versions`). Изменился после отметки — в `failed` с `VERSION_CONFLICT`, у объединения (всё или ничего) — весь запрос `412`. Запросы с `idempotencyKey` сервер помнит 10 минут: повтор с тем же ключом получает прежний ответ и ничего не выполняет снова.
- **Ошибки** операций этого контракта (`/operator/*`) — `application/problem+json` с машинным `code`. Перечень кодов — `Problem.code` в контракте, какое условие даёт какой код — в README машины, «Коды ошибок перехода». Остальные маршруты сервера МИ (API настройки) ошибки отдают по-прежнему — `{key, description}`.
- **Копия контракта для генератора кода — [`openapi.v30.json`](openapi.v30.json).** Генератор сервера OpenAPI 3.1 не понимает, поэтому `tools/build_workflow.py` собирает из `openapi.json` копию в 3.0; руками её не править. В копии нет условной проверки `SelectionRequest` (`if`/`then`): при `mode: explicit` обязателен непустой `incidentGuids`. Её сервер проверяет сам — нет отмеченных, `422 BULK_SELECTION_INVALID`, как во встроенном сервере.
- **Таймеры живут на сервере.** Дедлайны — метки времени. Автоэскалацию, нарушения нормативов и потерю связи выполняет планировщик сервера, клиент только показывает отсчёт. Порядок: если готовы сразу несколько автоматических переходов, первым выполняется тот, чьё условие наступило раньше: таймер — по дедлайну, потеря связи — последний признак активности плюс порог, остальное — в момент проверки; при равенстве — по порядку в машине. Переход, который стал возможен после другого, наступает не раньше него, а переход без таймера — сразу после него (RULE-48). Эффекты считают время от этого момента, после каждого перехода выбор делается заново. Порядок общий для всех инцидентов, а не по инцидентам по очереди: переход одного может открыть переход другого (ARCH-13; `tick` в `engine.js`). Так результат не зависит от того, как часто работает планировщик, и догон после простоя даёт то же, что проверка каждую секунду (README машины, «Переходы»; тесты API «im-fsm: прыжок часов и шаги»). Упрощение: условия без времени — доступ, права, состояние оператора — при догоне берутся на текущий момент, а не на момент наступления; если роли поменялись во время простоя, результат будет «как сейчас».
- **Автоматические переходы и запрос оператора (§14.3, ARCH-10).** Перед запросом оператора, который что-то меняет, сервер выполняет все наступившие переходы по таймеру и системные — в той же транзакции или под той же блокировкой инцидента. Иначе действие между тактами планировщика стирает нарушение: «Взять» через секунду после окна — и нарушения реакции нет (BUG-82). Окно после дедлайна по-прежнему ждёт человека (§10.1, правило 5). После ручного перехода сервер сразу выполняет системные переходы, которые стали возможны (передали вышедшему — его группе, закрыли основной — закрыты привязанные), отдаёт их события в потоке, и ответ показывает инцидент уже после них. Переход при догоне меняет версию записи: запрос с версией, прочитанной до него, получает `412` с актуальной карточкой — так же, как если бы планировщик успел раньше. Встроенный сервер так и делает: одно правило в `handle` (`prototype/server.js`).
- **Поток событий обязателен** — `GET /operator/stream`, SSE. Сообщение без строки `event:`, в `id:` — `id` события, в `data:` — JSON. Сервер досылает пропущенное после `Last-Event-ID`: хранит последние события — не меньше 500 и не меньше чем за 10 минут. Такого `id` уже нет (пропущено больше или сервер перезапускался) — первым сообщением `stream.reset`, клиент перечитывает всё (BUG-102). Поток идёт через шлюз облака, а шлюз буферизует ответ и рвёт соединение, по которому долго ничего не идёт. Поэтому сервер шлёт пустой комментарий (строку `:`) не реже раза в 15 с и ставит заголовки `Cache-Control: no-cache` и `X-Accel-Buffering: no`.
- **Признак активности после простоя** (§14.3, RULE-113). При старте сервиса признак активности всех вошедших операторов — момент старта: простой сервиса — не молчание операторов, догон не откладывает их инциденты «нет связи». Встроенный сервер так считает при загрузке и при `POST /test/reset`.
- **Признак активности.** Клиент шлёт `heartbeat` раз в `session.heartbeatSec`; любой запрос оператора, кроме чтения, — тоже признак активности, даже отказанный (§12.3, RULE-112). Если его нет `idleHoldSec`, инцидент оператора уходит в «Отложен — нет связи», через `idleReleaseSec` — обратно в очередь (§12.3).
- **Идентификаторы.** У инцидентов, устройств, групп устройств, типов событий, планов и сценариев — UUID, номер для показа — `number`. Люди и дежурные группы — строки внешней системы (§5).
- **Арендатор — установка облака.** Один МИ на одну установку облака: `customer_guid` берётся из настроек развёртывания, а не зашитый тестовый.
- **Время события (`occurredAt`)** — когда событие случилось у источника: сервер берёт его от агента, а не пишет время приёма.
- **Одно событие — по инциденту на сценарий (§14.5, ARCH-15).** Событие проходит через правила по разделу `intake` машины: правила без сценария не участвуют; для каждого сценария подошедших правил — один инцидент, ключ уникальности — событие + сценарий (`UNIQUE(event_guid, scenario_guid)`). Правило-победитель сценария — по ранжированию §14.5 (определения `ruleMatches`, `ruleFor`, `ruleBeats` машины): самое точное условие (устройство, тип устройства, группа с глубиной в дереве), затем выше приоритет, затем раньше созданное; приоритет инцидента — правила. Все инциденты события и отметка события — одной транзакцией, каждый — переходом машины `create`; повтор события ничего не создаёт. Номер тревоги — номер первого созданного инцидента (`alarm_number`), правило — `rule_guid` (ссылку на правило, убранную миграцией 010, вернуть); для последнего шага ранжирования у правила нужен `created_at` (сейчас только `updated_at`). Сейчас сервер создаёт по инциденту на каждый сценарий каждого подошедшего условия (`incidentrulecondition/processor.go`, `incident.Service.CreateIncidents`) — это нужно поменять; редактор правил не меняется.
- **Тексты — ключами каталога строк (§14.9).** Записи журнала хранятся ключом и подстановками (`templateKey` + `vars`), причины и ошибки приходят ключом (`reasonKey`, `messageKey`): клиент переводит их на язык оператора по каталогу. Каталог — файл на язык, ключи вида `workflow.<область>.<id>[.<поле>]`, строки в формате ICU MessageFormat.
- **Срок группы (§11.4).** У объединённых один срок — срок закрытия основного (RULE-97). Сервер хранит у привязанного `linked_at` — когда он привязан к нынешнему основному — и `left_group` — из какой группы, с каким `linked_at` и когда вышел. Нарушение основного записывается тем, у кого `linked_at` не позже срока, и вышедшим после срока (окно после дедлайна), с записью в журнал (BUG-73, RULE-98). Вышедшему с остатком срока 0 норматив отмечается сработавшим: при взятии второго нарушения нет.
- **Видимость (§5, `invariants.actorSeesIncident`).** Оператор видит только инциденты доступных ему объектов — по группам доступа его ролей: в очереди, карточке и потоке событий; действует — тоже только над ними, запрос к невидимому — 404. Когда меняются роли или группы доступа, сервер проверяет открытые инциденты, как только узнаёт об изменении: группы доступа — данные МИ, смену ролей он узнаёт при обращении пользователя или при сверке с облаком: `addressee_lost_access` (у владельца или адресата нет доступа) и `addressee_cannot_accept` (адресат больше не может принять). Прежнему владельцу или адресату уходит `incident.access_lost` — только номер, данных инцидента он уже не видит.
- **Приоритет — число из справочника (§2.5).** `Priority` — целое 0–100, больше — срочнее; перечня в контракте нет, уровни — в справочнике МИ, общем для всех схем. **Ломающее изменение:** раньше были строки `critical, high, medium, low`. От источника — число: не из справочника — ближайший уровень не выше; ниже самого низкого или без числа — самый низкий. Самый срочный (счётчик `topPriority`) — уровень с наибольшим числом. Нормативы ссылаются на числа; у уровня без своего норматива — `defaultSec`. Правка — операции `/operator/admin/priorities`, после неё всем — `reference.priorities_changed`.
- **Лимиты (§10.2, §11).** `limits.maxActive`, `maxOnHold`, `maxBulk` — целое от 1; `null` или нет поля — «без ограничения» (тестовый стенд передаёт изменения схемы JSON Merge Patch, а там `null` удаляет поле). Лимит выборки проверяет сервер, а не только клиент: в массовом действии больше `maxBulk` — `422 BULK_SELECTION_INVALID` целиком. Без лимита выборки одно массовое действие может прийти сразу на сотни инцидентов — выполнять его по каждому, как и сейчас, с частичным успехом.
- **Права и роли всех пользователей (§5, §8.1).** Роль в правилах — группа пользователей облака. Передать можно только тому, кто может принять: право `incident:accept` и доступ к объекту, у группы — хотя бы у одного участника. Поэтому МИ нужны права и группы не только вошедшего, но и всех пользователей. Вошедшего — от облака; остальных — служебными запросами к облаку с периодической сверкой: события об изменении прав и групп у облака нет. Как часто сверять — открытый вопрос §15; служебного запроса прав и групп пользователя по id у облака нет — тоже §15.
- **Каталог прав в облаке (§5).** Сервер публикует в облаке права машины под именами из поля `cloud` у каждого права в `permissions` машины — 14 прав, другие не нужны: `incident_manager.incidents.filter.edit` и `incident_manager.incidents.track` из каталога убрать. Право настройки `incident_manager.manage` (`incident:schema:admin`) операторских прав не даёт: проверка права оператора не должна считать его любым правом. UUID прав: у прав, которые уже есть в облаке, UUID прежние; `incident_manager.incidents.assign` (в сервере `PermIncidentsAssign`, `internal/im/model/permission.go`) переименовывается в `incident_manager.incidents.assign.own` **с тем же UUID**; новым правам — новые UUID. Облако хранит в ролях UUID права, а право, которого нет в каталоге, помечает устаревшим (`deprecated`), и при сохранении роли его снимают: с новым UUID право передачи молча пропало бы у всех ролей. У каждого узла каталога — название на английском и русском (`i18n`); у права — его подпись из каталога строк (`labelKey` права машины).
- **Алерты (§9).** Эффект `notify(alerts.target, true)` — внешний: выполняется после транзакции перехода. Получатели — пользователь или участники дежурной группы, кто на месте и с доступом к объекту инцидента; никого — в журнал пишется `alerts.noRecipientLog`. Получателю — событие потока `incident.alert`.
- **Выход из МИ (§12.1).** При `offline` сервер сразу выполняет `owner_signed_out` (свои в работе и отложенные — в очередь) и `addressee_signed_out_*` (адресованные лично — группе или в очередь). После выхода, как на перерыве, — только просмотр: признак `readOnly` у состояния оператора в `session.states`, переходы отклоняются с `403 AGENT_NOT_READY`.
- **«Занят» не хранится (§12.1, RULE-99).** Хранимые состояния оператора — `ready`, `not_ready`, `offline`; начальное — `offline` (`initial`). `busy` — производное (`derived` у состояния машины): в `GET /operator/session` сервер отдаёт его вместо `ready`, когда истинно `derived.expr` — у оператора есть свои инциденты в работе. Смены (`session.transitions`) идут от хранимого: занятый оператор уходит на перерыв и выходит, как из `ready`; хранить `busy` и проверять смену от него нельзя — перерыв и выход занятого получат `409`.
- **Групповая обработка — выборка и объединение, групп нет (§11). Ломающие изменения контракта:**
  - убраны группы сценария (`groupGuid`, `POST /operator/incident-groups`, исключение из группы, режимы выборки `group` и `group_or_each_allowed`, `limits.groupCountsAsOneUnit`), вкладки-фильтры, горячие клавиши (`hotkeys` в схеме, `hotkey` у действий, `preferences.hotkeyOverrides`);
  - карточка больше не несёт список `linked`: привязанные — `GET /operator/incidents/{guid}/linked`, постранично;
  - добавлены: состояние `linked` и категория `linked` (не открытые, в списках нет), переходы `merge`, `detach`, `close_linked`; `POST /operator/incidents/filter` («Выделить по фильтру», «Одинаковый сценарий»); `POST /operator/incidents/merge` (всё или ничего); `DELETE /operator/incidents/{guid}/linked` и `…/linked/{linkedGuid}`; у строки очереди `linkedTo`, `linkedCount`, при поиске — `matchedLinked`;
  - на выборку идут только переходы с `bulk.allowed` — иначе `422 BULK_SELECTION_INVALID`; причина недоступности действия выборки — с номером инцидента (`workflow.error.selection.item`).
- **Сценарии — машина сценариев (§14.5, [`Scenario_machine/`](../Scenario_machine/README.md)). Ломающие изменения контракта:**
  - сценарий — формат редактора сценариев продукта, как его сохраняет редактор в `scenarios.script` (схема — `Scenario_machine/scenario_schema.v1.json`, 2026-10-19); прохождение — формат МИ (раздел 9 спецификации), у редактора его нет: `GET …/scenario` отдаёт `IncidentScenario` — сценарий версии инцидента (`script`), прохождение (`result`, `scenarioResult` — раздел 9 спецификации) и что МИ из него считает: путь, курсор показа, прогресс, `requiredStepsFilled`;
  - вместо `PATCH …/scenario/answers` с набором ответов — `POST …/scenario/answer`: ответ на один шаг, что дальше — решает машина сценариев; `PUT …/scenario/cursor` — только шаг пути, без `move`;
  - убран ручной запуск макроса `POST …/macros/{macroId}`: макрос запускает ответ — макрос исхода (`macro`) — по условиям `run_macro`; в событии `macro.completed` `macroId` — имя макроса;
  - в `IncidentScenario` — `ahead`: шаги впереди по кратчайшему пути до конца, без текущего (RULE-95); считать тем же обходом, что M в прогрессе;
  - инцидент получает сценарий и версию при появлении — последнюю версию сценария своего типа события — и доигрывает на ней; набор «закрытие» выполнен, когда отвечен финальный шаг (`finish: true`);
  - исполнять сценарии — как исполнитель прототипа [`scenario.js`](../../prototype/scenario.js) по профилю МИ (README машины сценариев): условие видит только ответ своего шага, операторы `==`, `!=`, `in` над массивами — как в `jsonLogic.ts` редактора; проверять сценарий при публикации — как `tools/check_scenarios.py` (коды редактора и проверки МИ, в том числе макрос или правила у финального шага — не исполнятся, RULE-96); его тесты — [`tests/scenario.html`](../../tests/scenario.html), стык — тесты API `tests/api-junction.js`.
- **Настройки администратора (§20).** Полный перечень по вкладкам будущей админки — [`SETTINGS.md`](SETTINGS.md), он собран из раздела `adminSettings` машины. Настройки схемы правятся через редактор схемы (§14.6). Группы доступа, дежурные группы, справочник приоритетов, справочные ссылки и связи камер — данные МИ: контракт описывает их чтение (`GET /operator/admin/access-groups`, `…/duty-groups`, `…/camera-links`, `GET /operator/reference/help-links`), запросы правки для вкладки администрирования бэкенд описывает сам. Камеры инцидента — из всех связей его источника, без повторов, первая — главная; у инцидента своего списка нет. Связь камер — многие-ко-многим: название, устройства, камеры (RULE-70); прежняя форма `CameraLink` «устройство → камеры» — ломающее изменение.

## Тестовый стенд

Бэкенд проверяется тем же набором тестов, что встроенный сервер прототипа. Для этого стенду нужны пять служебных операций (тег `test-support`). В боевой сборке их быть не должно.

1. **`POST /test/reset`** загружает эталонный набор — [`fixtures/demo.json`](fixtures/demo.json) и сценарии [`fixtures/scenarios/*.json`](fixtures/scenarios/), строками `scenarios.rows` (`guid`, `version`, `name` — из `scenario`, `script` — файл), как `tools/fixture.py`, — и по умолчанию останавливает часы. Время в наборе абсолютное, при загрузке сдвигается на «сейчас − `capturedAt`». Таймеры заданы моментом запуска, длительность — из модели. Формат набора — README машины, «Тестовый стенд». Поля `workflowPatch` и `fixturePatch` — изменения схемы и набора на один прогон, JSON Merge Patch (RFC 7396): без них стенд не проверит правила, которым нужна другая настройка — выключенная автоэскалация, эскалация по закрытию, другой состав групп.
2. **`POST /test/clock`** сдвигает часы и сразу выполняет всё, что за это время должно сработать.
3. **`PUT /test/operators/{operatorId}/roles`** меняет роли человека посреди прогона, как в продукте смена ролей или групп доступа, и сразу выполняет то, что от этого сработало (§5).
4. **`POST /test/events`** — источник прислал событие: оно проходит через правила (раздел `intake` машины, §14.5) — по инциденту на сценарий подошедших правил, одной транзакцией; повтор того же `eventGuid` ничего не создаёт.
5. **`POST /test/incidents`** — один инцидент в обход выбора правил: по правилу `ruleGuid` или базовому правилу типа, переход машины `create` (RULE-61).
6. **CORS для страницы тестов:** разрешить методы `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, заголовки `Content-Type` и `If-Match` и `credentials`, открыть странице `ETag` (`Access-Control-Expose-Headers`). Страница, открытая с диска, приходит с `Origin: null`.

Прогон: открыть `tests/api.html?api=https://адрес-стенда` в браузере. Тесты проходят сценарии по правилам и случайные прогоны с инвариантами, сверяют каждый ответ со схемами контракта (поля, типы, форматы, обязательные заголовки) и проверяют, что вызвана каждая операция.

Клиентская сторона этого пути уже проверена: те же тесты проходят по сети против встроенного сервера (`python3 tools/check_loopback.py`). Если на стенде что-то падает, причину стоит искать на стороне бэкенда, в CORS или во входе.

## Когда готово

- `tests/api.html?api=…` — все тесты зелёные, строка «Каждая операция контракта покрыта тестами» — тоже.
- Прототип работает с бэкендом: `prototype/index.html?api=https://адрес` — очередь, карточка, переходы, поток событий.

Тесты не проверяют 10 операций: редактор схемы (`/operator/workflow/schemas…`, 7) и правку справочника приоритетов (`/operator/admin/priorities…`, 3) — экранов для них в прототипе нет. Их проверка — отдельно.
