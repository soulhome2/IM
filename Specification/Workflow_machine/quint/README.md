# Формальная модель машины состояний на Quint

`im.qnt` — модель машины [`workflow_schema.v1.json`](../workflow_schema.v1.json) на языке [Quint](https://quint-lang.org). Смысл условий и эффектов — как в исполнителе прототипа [`prototype/engine.js`](../../../prototype/engine.js). Модель не заменяет машину: она проверяет её правила на маленьком мире — 3 инцидента, 2 оператора, 1 дежурная группа — перебором путей, отдельно от кода прототипа.

| Файл | Что это |
|---|---|
| `im.qnt` | Модель: состояние инцидента, переходы — условие `<id>Ok` и действие с эффектами, действия окружения (наступление дедлайнов), инварианты |
| `im_test.qnt` | Сценарии: права и настройки заданы, шаги по порядку, в конце — инварианты |
| [`tools/check_quint.py`](../../../tools/check_quint.py) | Модель не разошлась с машиной: переходы, «откуда» и «куда», условия, эффекты, справочники |

## Зачем и что даёт

Тесты прототипа проверяют выбранные случаи. Модель проверяет сами правила машины: перебирает пути и конфигурации — права, доступ, состав группы, настройки, наступление дедлайнов — и ищет состояние, где нарушен инвариант. Так находятся сочетания, до которых тесты и ручная проверка не доходят.

- **Ошибка в правилах, а не в коде.** Модель не зависит от прототипа: нарушенный инвариант значит, что правило машины допускает такое состояние или модель перенесла его неверно.
- **Контрпример.** `quint run` печатает трассу по шагам — какой переход, кто, над каким инцидентом. Её можно повторить на прототипе.
- **Свойства, которые должны держаться всегда** — раздел «Инварианты»: владелец по состоянию, таймеры, лимиты, уровень эскалации, обработка наступивших дедлайнов.
- **Модель не отстаёт от машины.** `check_quint.py` сверяет её с JSON после каждой правки машины.

Что уже нашла: RULE-93 в [ревью 2026-10-19](../../../reviews/2026-10-19/review.md) — автоэскалация могла адресовать инцидент тому, у кого он уже есть, хотя ручная передача ему запрещена. Адресат получал второй срок реакции без нарушения, а при эскалации по нормативу закрытия старший о просрочке не узнавал. Контрпримеры — за 3–4 шага, оба случая подтверждены на встроенном сервере. Исправлено в `e46edea`, свойства `autoEscalateNotToCurrentAddressee` и `resolutionEscalateNotToCurrentAddressee` — в `inv`.

Машину сценариев модель не проверяет: для неё [`tools/check_scenarios.py`](../../../tools/check_scenarios.py) и формальная проверка скиллом `im-fsm`.

## Как устроен Quint

Quint — язык спецификаций на основе TLA (Temporal Logic of Actions) Лэмпорта: модель вычислений та же, что у TLA+, синтаксис ближе к языкам программирования, есть проверка типов. Состояние — значения переменных (`cfg`, `inc`, `lastAction`), `init` задаёт начальные состояния, `step` — отношение «текущее состояние → следующее»: `inc' = …` — тот же штрих, что в TLA+, `any { … }` — один из переходов на выбор (`\/`), `all { … }` — всё сразу (`/\`), `nondet x = S.oneOf()` — любой элемент множества (`\E x \in S`). Инвариант должен быть истинен в каждом достижимом состоянии. `quint run` — встроенный симулятор: на каждом шаге случайно выбирает значения `nondet` и переход и проверяет инвариант в каждом состоянии трассы. `quint verify` переводит модель в TLA+ для Apalache — символьного проверщика моделей TLA+: через SMT-решатель Z3 он проверяет все трассы до заданной глубины. Модель можно выгрузить в TLA+ (`quint compile --target tlaplus`) и проверять другими инструментами TLA+. Доказательств, как в TLAPS, в Quint нет — только проверка моделей.

## Что моделируется

Ядро — 18 переходов: `create`, `claim`, `accept`, `reject`, `hold`, `resume`, `release`, `transfer`, `takeover`, `close`, `reopen` и переходы по таймерам `auto_escalate`, `escalation_ceiling`, `reaction_overdue`, `resolution_overdue`, `resolution_escalate`, `resolution_ceiling`, `hold_overdue`.

Объединение (§11) — 4 перехода: `merge` («Взять в работу» на выборке — над основным и набором остальных, всё или ничего; основной новый берётся тем же действием, `grouping.takeWith`), `detach`, `close_linked`, `linked_lost_access`. Инцидентов три: основной со своим привязанным объединяется с третьим — так проверяется `relinkToPrimary`. Основным модель берёт любого, кого пропускает `mergePrimaryValid`; правило выбора основного из §11.3 — у сервера, а не у машины, поэтому модель перебирает больше сочетаний, чем допускает интерфейс. `close_linked` и `linked_lost_access` — системные переходы: срочные для всех, пока он возможен, ручные действия и время ждут; наступивший дедлайн самого привязанного — раньше, его переход по таймеру идёт первым (RULE-41).

У группы один срок — срок основного (RULE-97). Свой норматив привязанного на паузе; переход по таймеру, который пишет нарушение, пишет его и каждому открытому привязанному (`applyShared`); отсоединённый получает фазу норматива основного (`copyPrimaryDeadline`). «Срок основного — самый ранний» (`tightenPrimaryDeadline`) в абстрактном времени не различить: в модели срок основного не меняется, это правило проверяют тесты API. Срок группы — срок и привязанного: его ручные действия ждут переход по таймеру основного, а объединение ждёт срабатывания наступившего дедлайна основного — как при `graceSec` = 0. Служебное поле `joinedBreaches` — сколько нарушений было у основного при присоединении; в машине его нет, оно для инварианта `linkedSharesBreaches`.

Видимость (§5, `invariants.actorSeesIncident` машины): действует только тот, у кого есть доступ к инциденту, — условие `sees` у каждого ручного действия; у «Отсоединить» — к основному и привязанному, у «Взять в работу» на выборке — ко всем. Это правило сервера, а не условие перехода: невидимого инцидента нет вовсе. `check_quint.py` требует `sees` у каждого ручного перехода, пока в машине стоит флаг. Права и доступ задаются при старте и не меняются, поэтому без доступа к привязанному адресат основного остаётся после перехвата, принятия или эскалации: тот, кто видит основной, может не видеть привязанный, — тогда `linked_lost_access`.

Состояние оператора (§12, `session` машины): на месте, перерыв, вышел — и молчание по ступеням: связь есть, молчит дольше `idleHoldSec`, дольше `idleReleaseSec`. Меняется действиями окружения — перерыв (с правом `agent:set_not_ready`), возврат, выход, вход, молчание, связь. На перерыве и после выхода — только просмотр (`agentReady` у всех ручных действий). Шесть системных переходов по нему — `system_hold_break`, `system_hold_idle`, `system_release_idle`, `owner_signed_out`, `addressee_signed_out_to_group`, `addressee_signed_out_to_queue` — касаются только инцидентов этого оператора и срочные, как `close_linked`: наступивший дедлайн инцидента — раньше них (RULE-41). Пока системный переход ждёт, состояние операторов не меняется.

Права и доступ задаются при старте и меняются на ходу — действием окружения «сменились роли» (§5): у оператора появился или пропал доступ к инциденту, появилось или пропало право «Принимать». По ним — системные `addressee_lost_access` (у владельца или адресата нет доступа к объекту) и `addressee_cannot_accept` (адресат не может принять), а у привязанных — `linked_lost_access`. Срочные, как остальные системные; видимость `sees` следует за доступом. Модель теперь содержит все переходы машины: `NOT_MODELED` в `check_quint.py` пуст. Состав дежурной группы не меняется.

Сценарий — без графа шагов: у инцидента сценарий (один из двух, задаётся при появлении) и отвеченные шаги (из двух); пройден — отвечены оба, это набор `closing` (§14.5), по нему «Закрыть» разрешает «Обработан». Ответ на шаг — действие модели вне машины, право — как `scenarioEdit` машины: владелец, «В работе», видит инцидент; `check_quint.py` сверяет условия. Объединение — только одного сценария (`sameScenarioAsPrimary`), отвеченное объединяемыми — основному (`copyAnswersToPrimary`). Ветвления, значения ответов, версии сценария, «Назад» и переответ модель не видит — их проверяют `tools/check_scenarios.py` и тесты исполнителя сценариев.

Права, доступ к объектам, состав дежурной группы и настройки (`escalation.enabled`, `escalation.onResolutionOverdue`, `maxActive`, `maxOnHold`) выбираются при старте произвольно, поэтому симуляция перебирает и конфигурации. Уровни эскалации: 1 — человек, 2 — группа, `maxLevel` = 2, как в машине. `maxOnHold` в модели — 1 или без ограничения, чтобы лимит достигался.

Время абстрактное. У таймера фаза: `Before` — дедлайн впереди, `Due` — наступил и ещё не сработал (`timerExpired`), `Fired` — сработал: каждый дедлайн срабатывает один раз (`firedTimers` прототипа). Дедлайн наступает действием окружения `expire*`.

**Пока не моделируется:** окно `manualWinsOverTimer` — без него переход по таймеру срочный: пока он возможен, ручные действия над инцидентом ждут, как при `graceSec` = 0. Не моделируются и журнал, уведомления, внешние команды, `version`, конкретные секунды. Переходы машины вне модели перечислены в `NOT_MODELED` скрипта `check_quint.py`.

## Инварианты

| Имя | Что проверяет |
|---|---|
| `ownerByState` | Владелец по состоянию: `new`, `linked` — ни владельца, ни группы; `pending_acceptance` — ровно одно из двух; `in_progress`, `on_hold` — владелец-оператор без группы; `closed` — владелец — закрывший, у закрытого вместе с основным владельца нет, закрывший — закрывший основной (§2.1, §11.4) |
| `holdReasonIffOnHold` | Причина удержания задана тогда и только тогда, когда `on_hold` |
| `timersByState` | Идёт таймер состояния, `resolution` в `pausedInStates` на паузе, в `closed` ничего не идёт; реакция в `new` / `pending_acceptance` остановлена только после записанного нарушения (RULE-84); сработавшая реакция не идёт дальше; у `linked` свой норматив закрытия не идёт — срок у группы; наступивший дедлайн норматива закрытия не уходит на паузу необработанным |
| `levelBounded` | `0 ≤ escalation_level ≤ maxLevel` (§8.3) |
| `closeResultIffClosed` | Результат закрытия задан тогда и только тогда, когда `closed` (§2.2) |
| `timerTransitionsExclusive` | По инциденту готово не больше одного перехода по таймеру (§14.3) |
| `dueDeadlineHandled` | Наступивший дедлайн идущего таймера кто-то обрабатывает — не теряется молча (§4, §9) |
| `limitsRespected` | В работе у оператора не больше `maxActive`, отложенных вручную — не больше `maxOnHold`: системные удержания откладывают и сверх лимита (§10.2) |
| `pendingAddresseeCanAccept` | У ожидающего принятия адресат может принять — или его сейчас возвращает в очередь системный переход: права меняются (§8.1) |
| `autoEscalateNotToCurrentAddressee`, `resolutionEscalateNotToCurrentAddressee` | Эскалация — по реакции и по нормативу закрытия — не адресует инцидент тому, у кого он уже есть: тому же человеку, той же группе или группе, где принять может только владелец (§8.3, RULE-93) |
| `linkedShape` | У привязанного нет причины удержания и результата закрытия; основной — другой инцидент, сам не привязан и открыт, а закрытый — привязанный сейчас закроется вместе с ним (§11.3, §11.4) |
| `openNotLinked` | Открытый непривязанный ни к чему не привязан: отсоединение и переоткрытие снимают связь (BUG-42) |
| `resolutionBreachHasOwner` | У нарушения норматива закрытия есть чьё: срок группы идёт, только пока основной кто-то ведёт (RULE-97) |
| `linkedSharesBreaches` | Нарушения основного после присоединения — и у привязанного, те же записи (§11.4, RULE-97) |
| `noIncidentWithoutAccess` | Ни один инцидент не остаётся у того, у кого нет к нему доступа: у адресата открытого — доступ к нему, у адресата основного — и к привязанным; иначе сейчас выполняется `addressee_lost_access` или `linked_lost_access` (§5, RULE-71) |
| `systemProgress` | Системный переход не зависает: пока он ждёт, выполним он сам или переход по таймеру, который идёт раньше него (RULE-41) |
| `linkedSameScenario` | Привязанный — того же сценария, что основной (§11.3) |
| `processedOnlyFinished` | «Обработан» своим «Закрыть» — только у пройденного сценария, в том числе за счёт ответов, перенесённых при объединении; закрытый вместе с основным берёт его результат (§2.2, §11.4, §14.5) |
| `agentStateRespected` | Вышедший не держит ни своих в работе и отложенных, ни лично ему адресованных; на перерыве у оператора нет инцидентов «В работе» — или их сейчас снимает системный переход (§8.1, §12) |
| `inv` | Все вместе |


## Как запустить

Нужен Node.js 18 или новее. Без прав администратора — в домашнюю папку:

```bash
# архив Node.js LTS с nodejs.org → ~/.local/opt/node, затем
export PATH=~/.local/opt/node/bin:$PATH
npm i -g @informalsystems/quint
```

Из этой папки:

```bash
quint test im_test.qnt                                   # сценарии, меньше секунды
quint run im.qnt --invariant inv --max-samples=10000     # 10 000 случайных трасс по 20 шагов, меньше минуты
quint run im.qnt --invariant inv --max-steps=40 --max-samples=10000   # по 40 шагов, меньше минуты
quint run im.qnt --invariant inv --max-steps=80 --max-samples=20000   # длиннее, около 1½ минуты
```

Из корня репозитория — без Quint, нужен только Python:

```bash
python3 tools/check_quint.py
```

`quint run` — случайная выборка трасс, а не полный перебор. Полный перебор до заданной глубины — `quint verify im.qnt --invariant inv` через Apalache, ему нужна Java 17 или новее.

## Если инвариант нарушен

`quint run` печатает трассу-контрпример: состояния по шагам, в `lastAction` — какой переход, кто и над каким инцидентом. Повторить — по `--seed` из вывода. Дальше выяснить, где ошибка: в модели (перенесли правило не так — сверить с машиной и `engine.js`) или в машине (правило допускает такое состояние). Ошибку машины правят в `workflow_schema.v1.json`, затем модель и `python3 tools/check_quint.py`.

## Когда меняется машина

`python3 tools/check_quint.py` покажет, что разошлось. Новое условие или эффект, которого нет в таблицах скрипта, — тоже ошибка: дополнить таблицу (`guard_atom`, `effect_token`) и модель. Новый переход — смоделировать или добавить в `NOT_MODELED`.
