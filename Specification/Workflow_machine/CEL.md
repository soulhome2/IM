# Язык выражений машины

Машина [`workflow_schema.v1.json`](workflow_schema.v1.json) называет условия и эффекты переходов по имени: `{"fn": "isOwner"}`. Этот документ описывает, как смысл каждого имени записывается в самой машине — выражением на CEL (Common Expression Language, [cel-spec](https://github.com/google/cel-spec)). Тогда смысл правила записан в одном месте, и по нему работают:

- **прототип** — исполнитель [`prototype/engine.js`](../../prototype/engine.js) вычисляет выражения из машины, своих правил у него нет;
- **бэкенд** — своей реализацией CEL (у Google есть официальные для Go, Java, C++, Python) и тем же порядком исполнения;
- **модель Quint** — [`quint/im.qnt`](quint/im.qnt): типы, значения настроек, определения, условия и эффекты переходов генерируются из машины (`tools/gen_quint.mjs`), руками пишутся мир модели, ядро исполнения, действия окружения и инварианты ([README модели](quint/README.md)).

Решения — [ARCH-07 в плане ревью 2026-10-21](../../reviews/2026-10-21/plan.md). У каждого из 33 условий реестра — `expr`, у каждого из 25 эффектов — `do`, у бейджей, фильтров очереди и форм — свои выражения (раздел «Правила интерфейса»); исполнитель прототипа своих правил не держит. Пока смысл переезжал, прототип вычислял и прежние функции, и выражения, и они совпадали на всех тестах — и у условий (выполнено ли, причина отказа), и у эффектов (поля всех инцидентов, которых коснулся переход, и журнал).

## Где в машине

**Раздел `cel`** машины — всё, чем пользуются выражения: `types` — типы значений, `world` — факты мира с типами параметров и результата, `settings` — какие разделы машины видны выражениям как константы и какого они типа, `definitions` — общие понятия. Таблицы ниже описывают то же словами; источник — машина.

**Определения** — `cel.definitions`: понятия, которые нужны многим условиям и эффектам. У каждого — параметры с типами, тип результата и выражение:

```json
"definitions": {
  "addressee": { "params": { "x": "Incident" }, "returns": "string",
                 "expr": "x.owner != '' ? x.owner : x.assignmentGroup" },
  "canAccept": { "params": { "who": "string", "x": "Incident", "except": "string" }, "returns": "bool",
                 "expr": "isGroup(who) ? members(who).exists(m, m != except && canAcceptPerson(m, x)) : canAcceptPerson(who, x)" }
}
```

Определение вызывается как функция: `canAccept(target, incident, '')`. Определения могут вызывать друг друга, но не по кругу.

**Условия** — в реестре `registries.guards`: к имени, аргументам и `onFail` добавляются `argTypes` и `expr`. Результат — `bool`: истина — условие выполнено. Причина отказа — ключ из `failKeys` (первый) или выражение `failKey`, подстановки в её текст — выражения `failVars`.

Тип аргумента — тип CEL или `setting`: путь к настройке машины (`escalation.enabled`). Путь проверяется при сборке, а в выражение приходит значение настройки. Значение, с которым её сравнивают (`settingIs`), — `dyn` того же типа, что настройка.

`usage` — поля самого условия в переходе, кроме `fn` и `args`, с их типами: так `hasScopedPermission` получает `scopeRule` перехода. `failVars` — словарь «подстановка → выражение» или одно выражение-словарь: так подстановка бывает только у одной из причин (`closeResultAllowed`: `{p}` — только при «нет права»).

```json
{ "fn": "escalationTargetAvailable", "args": ["expected"], "argTypes": { "expected": "bool" },
  "expr": "(size(nextLevels(incident)) > 0) == expected", "onFail": "hide", "failKeys": ["workflow.guard.no_escalation_level"] }
{ "fn": "withinHoldLimit", "args": [], "argTypes": {},
  "expr": "limits.maxOnHold == 0 || size(mineIn(incidents, me, 'on_hold', incident.id)) < limits.maxOnHold",
  "failVars": { "n": "limits.maxOnHold" }, "onFail": "disable", "failKeys": ["workflow.guard.hold_limit"] }
```

**Эффекты** — в реестре `registries.effects`: `args` — имена аргументов по порядку, `argTypes`, `defaults` — значения аргументов, которых в переходе нет, и `do` — список операций (раздел «Операции эффектов»). Тип аргумента эффекта — литерал (`string`, `bool`, `int`): значение из перехода; `setting`; `expr<T>` — выражение CEL в переходе, вычисляется до первой операции: `{"fn": "setOwner", "args": ["personOf(form.targetId)"]}`. Литерал-строка подставляется в пути и выражения как `${имя}`: так `setFlag` и `increment` называют поле инцидента — `{"fn": "setFlag", "args": ["closedAt", "now"]}`.

Переходы не меняются: они ссылаются на слово по имени и передают аргументы по порядку `args` реестра — `{"fn": "escalationTargetAvailable", "args": [true]}`.

**Правила интерфейса** — выражения у бейджей (`badges.rules[].expr`), фильтров очереди (`queueFilters[].expr`), пояснений форм (`forms[].notes[].expr`) и полей форм (`requiredExpr`, `visibleExpr`, `optionExpr`, `enabledExpr`, `defaultExpr`) — раздел «Правила интерфейса».

## Типы

Типы CEL: `bool`, `int`, `string`, `list<T>`, `map<string, T>` и типы ниже. `double`, `timestamp`, `duration`, `bytes` не используются (раздел «Что из CEL можно»).

**Необязательное поле** — `opt<T>`: список из нуля или одного значения. Так строка `overrides` норматива отличает «условия нет» от «уровень 0»: `size(o.escalationLevel) == 0 || o.escalationLevel[0] == x.escalationLevel`. Словарь с целыми ключами — `map<int, T>` (`byPriority`): ключи JSON переводятся в числа.

**Пусто — не `null`.** Пустая ссылка на человека, группу, инцидент или позицию справочника — `''`, пустое время — `0`, лимит без ограничения — `0`. Так же в модели Quint (`NOBODY`). Сервер переводит `null` своих данных в `''` и `0` на входе и обратно — на выходе.

**Время — целые миллисекунды** от начала эпохи (`now`, дедлайны, `closedAt`); длительности в настройках — в секундах или минутах, как в машине, перевод — в выражении (`limits.reopenWindowMin * 60000`).

**`Incident`** — инцидент, как его видит машина. Имена — как в контракте API, где поле там есть:

| Поле | Тип | Что это |
|---|---|---|
| `id` | `string` | `guid` инцидента |
| `number` | `string` | номер для людей, `INC-1847` |
| `eventType` | `string` | id типа события |
| `priority` | `int` | приоритет |
| `occurredAt` | `int` | когда появился, мс — для выбора основного (`mergePrimary`) |
| `state` | `string` | состояние (`states[].id`) |
| `owner` | `string` | владелец — всегда человек |
| `assignmentGroup` | `string` | дежурная группа, пока передачу ей никто не принял |
| `holdReasonId` | `string` | причина удержания |
| `escalationLevel` | `int` | ступень автоэскалации, 0 — не эскалировался |
| `transferCount` | `int` | число ручных передач |
| `closeResultId`, `closeCauseId` | `string` | результат закрытия и причина сбоя |
| `result` | `string` | комментарий при закрытии |
| `closedBy` | `string` | кто закрыл |
| `closedAt` | `int` | когда закрыт |
| `slaBreached` | `bool` | есть хоть одно нарушение |
| `breaches` | `list<Breach>` | нарушения |
| `timers` | `map<string, Timer>` | таймеры по id (`reaction`, `resolution`, `hold`) |
| `linkedTo` | `string` | основной инцидент привязанного |
| `linkedAt` | `int` | с какого момента в группе |
| `leftGroup` | `LeftGroup` | из какой группы и когда вышел |
| `scenario` | `string` | сценарий инцидента — ключ машины сценариев |

**`Timer`** — состояние таймера:

| Поле | Тип | Что это |
|---|---|---|
| `due` | `int` | дедлайн; `0` — не идёт |
| `paused` | `bool` | на паузе с остатком |
| `left` | `int` | остаток на паузе, мс |
| `fired` | `int` | дедлайн, по которому таймер уже сработал; `0` — не срабатывал. Один дедлайн срабатывает один раз (§14.3) |
| `since` | `int` | когда запущен (у `hold`) |

**`Breach`** — `kind` (`string`: `reaction`, `resolution`, `hold`), `at` (`int`: момент нарушения — дедлайн), `owner` (`string`: на кого записано — адресат в этот момент).

**`LeftGroup`** — `primaryId` (`string`), `linkedAt` (`int`), `at` (`int`: когда вышел). Не выходил — `primaryId` = `''`.

**`Form`** — поля формы перехода: `targetId`, `primaryId`, `resultId`, `holdReasonId`, `closeCauseId`, `comment` — все `string`, незаполненное — `''`.

**Настройки** — разделы машины как константы с их полями, по `cel.settings`: имя — раздел машины и его тип, или `{type, from}` — значение по пути (`closeResults` — `reasonCatalogs.close_result.items`). Сейчас `limits`, `session`, `escalation`, `alerts`, `states`, `closeResults`, `timerDefs` (`timers`), `holdReasons` (`reasonCatalogs.hold.items`). Адресат — двумя полями (ARCH-07 в7): у уровня эскалации и получателя алертов `targetKind` (`user` или `group`) и `target` (id) вместо строки `user:petrova`. `null` у лимита — `0`.

## Факты мира

То, что машина не определяет, а читает: данные сервера и машины сценариев. Сигнатуры — `cel.world` машины. Каждый сервер даёт их своими функциями (прототип — `celWorld` в `engine.js` из данных `server.js`); модель Quint — рукописным прологом над своим состоянием.

| Функция | Что значит | В прототипе |
|---|---|---|
| `can(who, perm): bool` | у человека есть право — по его ролям | `permsOf` |
| `access(who, x): bool` | у человека есть доступ к объекту инцидента — по группам доступа его ролей (§5). Только человек: доступ группы — определение `hasAccess` | `hasAccess` для человека |
| `isOperator(id): bool`, `isGroup(id): bool` | id — человек или дежурная группа | |
| `members(g): list<string>` | состав дежурной группы сейчас: люди с её ролями и записанные в неё (§8.1) | `membersOf` |
| `dutyGroups(): list<string>` | дежурные группы по порядку набора | |
| `inSourceGroup(x, g): bool` | устройство-источник инцидента — в группе устройств `g` (нормативы, `overrides`) | `inGroup` |
| `agentState(who): string` | состояние оператора (`session.states[].id`) | `agentState` |
| `idleSec(who): int` | сколько секунд сессия оператора не присылает признак активности (§12.3) | `idleSec` |
| `stepsFilled(x, setId): bool` | набор шагов сценария выполнен — отвечает машина сценариев (§14.5) | `stepsFilled` |
| `lastTransferTarget(who): string` | кому оператор передавал в последний раз (§8.2); не передавал — `''`. Только для формы «Передать» | `defaultTransferTarget` |

Состав фактов — закрытый: новое понятие, которое выводится из этих, — определение в машине, а не функция сервера.

## Что из CEL можно

Только то, что переводится в Quint без исключений. Остальное — ошибка сборки.

| Можно | Пример |
|---|---|
| литералы `bool`, `int`, `string`; списки; словари с ключами-строками | `['in_progress', 'on_hold']`, `{'kind': kind, 'at': deadline}` |
| поле, элемент списка по номеру, элемент словаря по ключу | `incident.timers[timerId].due`, `levels[0]` |
| `==`, `!=`, `<`, `<=`, `>`, `>=`, `&&`, `\|\|`, `!`, `? :`, `+`, `-`, `*` над `int` | |
| `x in list` | `incident.state in ['new', 'pending_acceptance']` |
| `size(list)` | |
| `list.exists(v, p)`, `list.all(v, p)`, `list.filter(v, p)`, `list.map(v, e)` | `members(g).exists(m, can(m, 'incident:accept'))` |
| `cel.bind(v, e, тело)` — имя для промежуточного значения | |
| вызов определения и факта мира | |

| Нельзя | Почему |
|---|---|
| строковые функции: `contains`, `startsWith`, `substring`, `matches`, `size(string)` … | в Quint строки только сравниваются. Если данные приходится разбирать — разложить их в машине на поля (в7) |
| `double`, `timestamp`, `duration`, `bytes`, `/`, `%` | время — целые мс; деления правилам не нужно |
| `has()`, `null`, необязательные поля `?.` | пусто — `''` и `0` |
| `Тип{поле: …}` | не поддерживает cel-js 8.0.0. Составное значение — словарем, ключи сверяются с типом при сборке (в8) |

## Операции эффектов

`do` — список операций, выполняются по порядку. Каждая операция видит результат предыдущих: «после перехода» отдельно не бывает — порядок задаётся порядком операций и порядком эффектов перехода. Все изменения, в том числе других инцидентов, применяются вместе, когда выполнены все эффекты перехода; ошибка любой операции — переход не применяется (§14.1, §14.2).

| Операция | Что делает |
|---|---|
| `{"let": "имя", "value": "выражение"}` | имя для значения до конца `do` |
| `{"set": "путь", "value": "выражение"}` | записывает значение. Путь — от `incident` или имени из `forEach`: `incident.owner`, `e.timers[timerId].due` |
| `{"append": "путь", "value": "выражение"}` | дописывает значение в конец списка: `incident.breaches` |
| `{"if": "выражение", "then": [ … ], "else": [ … ]}` | ветвление; `else` можно не писать |
| `{"forEach": "имя", "in": "выражение-список", "do": [ … ]}` | операции для каждого элемента; изменения — у инцидента этого элемента |
| `{"call": "эффект", "args": { "параметр": "выражение" }}` | эффект реестра — как часть этого: так `stopTimer` таймера со `startsOnce` вызывает `pauseTimer` |
| `{"world": "действие", "args": { … }}` | действие мира, ниже |

Операции таймера — `startTimer`, `stopTimer`, `pauseTimer`, `resumeTimer`, `restartTimer` — не встроенные: это эффекты реестра со своим `do` над полями `Timer`. Их правила — `startsOnce`, `pausable`, отработанный срок (RULE-50), норматив по `overrides` и `byPriority` — записаны в машине, как остальные.

Порядок важен: у `merge` пауза своего норматива привязываемого стоит перед `tightenPrimaryDeadline` — тот сравнивает остаток уже на паузе (раньше это обеспечивал отложенный «после перехода» эффект исполнителя).

**Действия мира** — то, что меняет не поля инцидента, а журнал и внешний мир. Аргументы — выражения CEL. Журнал, курсор и перенос ответов меняют только инцидент перехода или того, кого назвали, и применяются вместе с переходом; остальное — после него. В модель Quint не переводятся, кроме переноса ответов:

| Действие | Аргументы | Что делает | В Quint |
|---|---|---|---|
| `log` | `incident`, `key`; `vars` — подстановки, нет — их считает сервер по инциденту (подстановки `appendLog`, README машины); `actor` — от чьего имени, нет — выполняющий переход; `once` — одна запись на ключ и момент: следующая заменяет подстановки | запись в журнал инцидента | — |
| `notify` | `incident`, `to` — кому (человек или дежурная группа), `recipients` — кто получит, `alert` — это алерт, `emptyLog` — ключ записи, если получить некому | доставка уведомления; некому — запись `emptyLog` в журнал | — |
| `command` | `incident`, `command` | внешняя команда (§14.2, `external`) | — |
| `evict` | `incident`, `who` | открытая у человека карточка — на просмотр | — |
| `setCursor` | `incident` | курсор сценария — на первый незаполненный шаг; считает машина сценариев | — |
| `shareAnswers` | `from`, `to` (id основного), `logKey` | ответы привязанного — в неотвеченные шаги основного, что переносится — решает машина сценариев; перенесено — запись в журнал основного | отвеченные шаги основного — объединение с отвеченными привязанного (пролог) |
| `touch` | `incident` | инцидент изменился не своим переходом — новая версия (нарушение группы) | — |

## Правила интерфейса

Что видит оператор в очереди и в форме перехода, — тоже выражения машины над теми же именами (`me` — смотрящий). Вычисляет их сервер; интерфейс получает готовый результат и выражений не вычисляет.

| Где | Выражение | Тип | Что значит |
|---|---|---|---|
| `badges.rules[]` | `expr` | `bool` | бейдж — первое правило по порядку, чьё выражение истинно; ни одного — подпись состояния (§2.4) |
| `queueFilters[]` | `expr` | `bool` | инцидент в фильтре очереди. В списках — инциденты хотя бы одного фильтра: так привязанные (§11) в списках не видны |
| `queueSort.keys.<порядок>[]` | ключ | `int` | порядок очереди: меньше — выше, следующий ключ — при равенстве, при равенстве всех — по номеру инцидента |
| `cardNotes.rules[]` | `expr` | `bool` | пояснение в карточке — первое подходящее; `actions` — доступные смотрящему действия карточки; нет подходящего — пояснения нет |
| `session.states[].derived` | `expr` | `bool` | производное состояние оператора: показывается вместо хранимого `derived.of` (§12, RULE-99); `me` — оператор, `incident` нет |
| `forms[].notes[]` | `expr` | `bool` | пояснение формы — первое подходящее; `true` — всегда |
| поле формы | `requiredExpr` | `bool` | поле обязательно |
| поле формы | `visibleExpr` | `bool` | поле видно; нет выражения — видно всегда. Невидимое не обязательно и не отправляется |
| поле-список | `optionExpr` | `bool` | вариант `option` предлагается. Сервер проверяет по нему и присланное значение: вне вариантов — `422 FORM_FIELD_INVALID` (ARCH-09) |
| поле-список | `enabledExpr`, `disabledKey` | `bool` | вариант можно выбрать; нет — он виден заблокированным с причиной `disabledKey`, а присланный сервер отклоняет так же |
| поле-список | `defaultExpr` | `string` | значение по умолчанию; `''` — нет. Ставится, только если это доступный вариант |

```json
{ "expr": "incident.state == 'pending_acceptance' && ownership(me, incident) == 'target' && isGroup(addressee(incident))",
  "labelKey": "workflow.badge.pending_acceptance.target.group", "style": "inbox" }
{ "id": "mine", "labelKey": "workflow.filter.mine",
  "expr": "incident.state in ['in_progress', 'on_hold'] && ownership(me, incident) == 'owner'" }
{ "name": "comment", "kind": "text", "requiredExpr": "closeResults.exists(i, i.id == form.resultId && i.commentRequired)" }
```

Варианты поля-списка до отбора — `source`: `transferTargets` — люди и дежурные группы от сервера, `reasonCatalog:<справочник>` — позиции справочника. `requiredExpr` и `visibleExpr` могут читать одно поле-список той же формы (`form.resultId`), а оно само — ни одного: тогда сервер вычисляет их для каждого варианта этого поля и отдаёт таблицей (`AvailableAction.fieldRules`: `dependsOn` и `byValue`, ключ `""` — ничего не выбрано). Интерфейс, пока оператор выбирает, смотрит в таблицу; сервер при выполнении перехода вычисляет выражения сам — по присланным значениям. Варианты, значение по умолчанию и пояснения от значений формы не зависят: они нужны до того, как оператор что-то выбрал.

В модели Quint правил интерфейса нет: они не меняют инцидентов.

## Ядро исполнения

Общий код исполнителя, одинаковый для всех правил: он не знает ни одного условия или эффекта IM. Это порядок проверки (`from`, затем условия по порядку, первое невыполненное и его `onFail`), применение перехода целиком или никак, планировщик переходов по таймеру и окно `manualWinsOverTimer` (§10.1, RULE-41, RULE-63), выполнение на выборке (`bulk`, `merge`; «Отсоединить все» — один переход на всех привязанных, всё или ничего), операции эффектов и мост к данным сервера. Ядро знает два условия по имени — `timerExpired` и `agentIdleFor`: по ним планировщик узнаёт момент перехода (RULE-41); момент перехода по молчанию — не раньше последнего перехода инцидента (RULE-48, BUG-76). Ядро записано дважды — в исполнителе прототипа и в модели Quint; что записи совпадают, проверяет сверка историй модели на исполнителе (`tools/check_quint_replay.mjs`). Нарушение, которое записал бы отменённый в окне переход, ядро записывает тем же эффектом машины — `recordBreach` этого перехода, на момент дедлайна и на адресата до действия. Описано в README машины, раздел «Модель workflow»; в модели Quint — рукописная часть генератора.

## Ошибки сборки

Каждое выражение разбирает и проверяет тот же cel-js и тот же код `prototype/cel-runtime.js`, что у прототипа, — `node tools/check_cel.mjs`, в CI — в шаге «Машина состояний». Ошибка — проверка не проходит:

- неизвестное имя, поле, функция или определение; не тот тип или порядок аргументов;
- результат условия — не `bool`; результат определения — не тот, что в `returns`;
- запрещённое из раздела «Что из CEL можно»;
- ключи словаря не совпадают с полями типа, куда значение записывается (`append` в `breaches` — поля `Breach`);
- путь `set` или `append` ведёт не в поле инцидента или не в список;
- `call` эффекта, которого нет, или эффекта, который вызывает сам себя;
- определения вызывают друг друга по кругу;
- слово реестра без `expr` или `do` (`check_machine.py`);
- аргументы перехода не того типа, что в `argTypes`;
- правило поля формы читает больше одного поля, само поле, не поле-список своей формы или поле, которое само зависит от других; варианты, значение по умолчанию или пояснение читают значения формы; `enabledExpr` без `disabledKey`;
- состояние или категория в выражениях бейджей, фильтров и форм, которых нет в машине (`check_machine.py`).

## Перевод в Quint

Генератор модели (`tools/gen_quint.mjs`) берёт дерево разбора cel-js и переводит его по таблице; типы узлов выводит сам — по типам машины, сигнатурам и литералам:

| CEL | Quint |
|---|---|
| `string`, `int`, `bool` | `str`, `int`, `bool` |
| `list<T>`, `map<string, T>`, `map<int, T>`, `opt<T>` | `List[T]`, `str -> T`, `int -> T`, `List[T]` |
| тип с полями | запись `{ поле: тип, … }` |
| `a && b`, `a \|\| b`, `!a` | `a and b`, `a or b`, `not(a)` |
| `c ? a : b` | `if (c) a else b` |
| `x in l` | `l.foldl(false, (acc, y) => acc or y == x)` |
| `size(l)` | `l.length()` |
| `l.exists(v, p)`, `l.all(v, p)` | `l.foldl(false, (acc, v) => acc or p)`, `l.foldl(true, (acc, v) => acc and p)` |
| `l.filter(v, p)`, `l.map(v, e)` | `l.select(v => p)`, `l.foldl([], (acc, v) => acc.append(e))` |
| `m[k]` у словаря | `m.get(k)` |
| определение | `def имя(параметры): тип = …` |
| условие в переходе | часть `ok_<переход>` — с аргументами этого перехода |
| эффект в переходе | `e_<переход>_<n>(w, c, iid): World` — каждая операция даёт новое значение мира `World`; `forEach` — свёртка по id элементов, их поля читаются из текущего мира; `call` — `ec_<эффект>`; действия мира не меняют инцидентов, кроме `shareAnswers` |
| `cel.bind(v, e, тело)` | `{ val v = e  тело }` |
| `x in m` у словаря | `m.keys().contains(x)` |

Время в модели — те же целые миллисекунды, и нормативы — значения машины: часы идут действием окружения не по шагу, а к ближайшему событию — дедлайну, мигу после него, концу окна `graceSec`, порогу молчания. Поэтому в модели есть и окно после дедлайна.

Руками — части `quint/src/`: факты мира над состоянием модели и `shareAnswers`, ядро исполнения, окружение, инварианты ([README модели](quint/README.md)). Что генератор переводит смысл верно, проверено в пробе ARCH-07.1 (ответы сгенерированных условий и выражений прототипа на одних данных совпадают) и проверяется сценариями модели, повторяющими тесты API.

## Библиотека

Прототип и сборка — `@marcbachmann/cel-js` 8.0.0 (2026-07-07, MIT, без зависимостей). Библиотека — модули ES, а прототип открывается и с диска (`file://`), где браузер их не загружает. Поэтому в репозитории она лежит одним обычным скриптом `prototype/vendor/cel-js/cel.js`, собранным esbuild; версия, хэш архива npm и хэш собранного файла — рядом, в `ORIGIN.md`, как у `json-logic-js`. esbuild нужен только при смене версии.

Чем cel-js отличается от спецификации CEL, если это задевает машину:

- нет записи `Тип{поле: …}` — словарь (в8);
- целые — `BigInt` в JS: мост к данным переводит числа;
- у константы-списка тип элементов теряется (`list<State>` становится `list`): настройки-списки общий код объявляет переменными и подставляет в каждое вычисление;
- значения типов — экземпляры общих классов, а все выражения разбираются в копиях одного окружения (`clone()`): обёртки, которые cel-js создаёт сам, между разными окружениями не узнаются.
