# Язык выражений машины

Машина [`workflow_schema.v1.json`](workflow_schema.v1.json) называет условия и эффекты переходов по имени: `{"fn": "isOwner"}`. Этот документ описывает, как смысл каждого имени записывается в самой машине — выражением на CEL (Common Expression Language, [cel-spec](https://github.com/google/cel-spec)). Тогда смысл правила записан в одном месте, и по нему работают:

- **прототип** — исполнитель [`prototype/engine.js`](../../prototype/engine.js) вычисляет выражения из машины, своих правил у него нет;
- **бэкенд** — своей реализацией CEL (у Google есть официальные для Go, Java, C++, Python) и тем же порядком исполнения;
- **модель Quint** — [`quint/im.qnt`](quint/im.qnt): типы, значения настроек, определения, условия и эффекты переходов генерируются из машины (`tools/gen_quint.mjs`), руками пишутся мир модели, ядро исполнения, действия окружения и инварианты ([README модели](quint/README.md)).

Решения — [ARCH-07 в плане ревью 2026-10-21](../../reviews/2026-10-21/plan.md). У каждого из 35 условий реестра — `expr`, у каждого из 27 эффектов — `do`, у бейджей, фильтров очереди и форм — свои выражения (раздел «Правила интерфейса»); исполнитель прототипа своих правил не держит. Пока смысл переезжал, прототип вычислял и прежние функции, и выражения, и они совпадали на всех тестах — и у условий (выполнено ли, причина отказа), и у эффектов (поля всех инцидентов, которых коснулся переход, и журнал).

## Где в машине

**Раздел `cel`** машины — всё, чем пользуются выражения: `types` — типы значений, `world` — факты мира с типами параметров и результата, `settings` — какие разделы машины видны выражениям как константы и какого они типа, `definitions` — общие понятия. Таблицы ниже описывают то же словами; источник — машина.

**Определения** — `cel.definitions`: понятия, которые нужны многим условиям и эффектам. У каждого — параметры с типами, тип результата и выражение:

```json
"definitions": {
  "addressee": { "params": { "x": "Incident" }, "returns": "string",
                 "expr": "x.owner != '' ? x.owner : x.assignmentGroup" },
  "canAccept": { "params": { "who": "string", "x": "Incident", "except": "string" }, "returns": "bool",
                 "expr": "isGroup(who) ? members(who).exists(m, m != except && canAcceptPerson(m, x)) : canAcceptPerson(who, x)" }
}
```

Определение вызывается как функция: `canAccept(target, incident, '')`. Определения могут вызывать друг друга, но не по кругу.

**Условия** — в реестре `registries.guards`: к имени, аргументам и `onFail` добавляются `argTypes` и `expr`. Результат — `bool`: истина — условие выполнено. Причина отказа — ключ из `failKeys` (первый) или выражение `failKey`, подстановки в её текст — выражения `failVars`.

Тип аргумента — тип CEL или `setting`: путь к настройке машины (`escalation.enabled`). Путь проверяется при сборке, а в выражение приходит значение настройки. Значение, с которым её сравнивают (`settingIs`), — `dyn` того же типа, что настройка.

`usage` — поля самого условия в переходе, кроме `fn` и `args`, с их типами: так `hasScopedPermission` получает `scopeRule` перехода. `failVars` — словарь «подстановка → выражение» или одно выражение-словарь: так подстановка бывает только у одной из причин (`closeResultAllowed`: `{p}` — только при «нет права»).

```json
{ "fn": "escalationTargetAvailable", "args": ["expected"], "argTypes": { "expected": "bool" },
  "expr": "(size(nextLevels(incident)) > 0) == expected", "onFail": "hide", "failKeys": ["workflow.guard.no_escalation_level"] }
{ "fn": "withinHoldLimit", "args": [], "argTypes": {},
  "expr": "limits.maxOnHold == 0 || countMine(me, 'on_hold', incident.id) < limits.maxOnHold",
  "failVars": { "n": "limits.maxOnHold" }, "onFail": "disable", "failKeys": ["workflow.guard.hold_limit"] }
```

**Эффекты** — в реестре `registries.effects`: `args` — имена аргументов по порядку, `argTypes`, `defaults` — значения аргументов, которых в переходе нет, и `do` — список операций (раздел «Операции эффектов»). Тип аргумента эффекта — литерал (`string`, `bool`, `int`): значение из перехода; `setting`; `expr<T>` — выражение CEL в переходе, вычисляется до первой операции: `{"fn": "setOwner", "args": ["personOf(form.targetId)"]}`. Литерал-строка подставляется в пути и выражения как `${имя}`: так `setFlag` и `increment` называют поле инцидента — `{"fn": "setFlag", "args": ["closedAt", "now"]}`.

Переходы не меняются: они ссылаются на слово по имени и передают аргументы по порядку `args` реестра — `{"fn": "escalationTargetAvailable", "args": [true]}`.

**Правила интерфейса** — выражения у бейджей (`badges.rules[].expr`), фильтров очереди (`queueFilters[].expr`), пояснений форм (`forms[].notes[].expr`) и полей форм (`requiredExpr`, `visibleExpr`, `optionExpr`, `enabledExpr`, `defaultExpr`, `warnings[]`) — раздел «Правила интерфейса».

## Типы

Типы CEL: `bool`, `int`, `string`, `list<T>`, `map<string, T>` и типы ниже. `double`, `timestamp`, `duration`, `bytes` не используются (раздел «Что из CEL можно»).

**Необязательное поле** — `opt<T>`: список из нуля или одного значения. Так строка `overrides` норматива отличает «условия нет» от «уровень 0»: `size(o.escalationLevel) == 0 || o.escalationLevel[0] == x.escalationLevel`. Словарь с целыми ключами — `map<int, T>` (`byPriority`): ключи JSON переводятся в числа.

**Пусто — не `null`.** Пустая ссылка на человека, группу, инцидент или позицию справочника — `''`, пустое время — `0`, лимит без ограничения — `0`. Так же в модели Quint (`NOBODY`). Сервер переводит `null` своих данных в `''` и `0` на входе и обратно — на выходе.

**Время — целые миллисекунды** от начала эпохи (`now`, дедлайны, `closedAt`); длительности в настройках — в секундах или минутах, как в машине, перевод — в выражении (`limits.reopenWindowMin * 60000`).

**`Incident`** — инцидент, как его видит машина. Имена — как в контракте API, где поле там есть:

| Поле | Тип | Что это |
|---|---|---|
| `id` | `string` | `guid` инцидента |
| `number` | `string` | номер для людей, `INC-1847` |
| `eventType` | `string` | id типа события |
| `priority` | `int` | приоритет |
| `occurredAt` | `int` | когда появился, мс — для выбора основного (`mergePrimary`) |
| `state` | `string` | состояние (`states[].id`) |
| `owner` | `string` | владелец — всегда человек |
| `assignmentGroup` | `string` | дежурная группа, пока передачу ей никто не принял |
| `holdReasonId` | `string` | причина удержания |
| `escalationLevel` | `int` | ступень автоэскалации, 0 — не эскалировался |
| `transferCount` | `int` | число ручных передач |
| `closeResultId`, `closeCauseId` | `string` | результат закрытия и причина сбоя |
| `result` | `string` | комментарий при закрытии |
| `closedBy` | `string` | кто закрыл |
| `closedAt` | `int` | когда закрыт |
| `slaBreached` | `bool` | есть хоть одно нарушение |
| `breaches` | `list<Breach>` | нарушения |
| `timers` | `map<string, Timer>` | таймеры по id (`reaction`, `resolution`, `hold`) |
| `linkedTo` | `string` | основной инцидент привязанного |
| `linkedAt` | `int` | с какого момента в группе |
| `leftGroup` | `LeftGroup` | из какой группы и когда вышел |
| `scenario` | `string` | сценарий инцидента — ключ машины сценариев |

**`Timer`** — состояние таймера:

| Поле | Тип | Что это |
|---|---|---|
| `due` | `int` | дедлайн; `0` — не идёт |
| `paused` | `bool` | на паузе с остатком |
| `left` | `int` | остаток на паузе, мс |
| `fired` | `int` | дедлайн, по которому таймер уже сработал; `0` — не срабатывал. Один дедлайн срабатывает один раз (§14.3) |
| `since` | `int` | когда запущен (у `hold`) |

**`Breach`** — `kind` (`string`: `reaction`, `resolution`, `hold`), `at` (`int`: момент нарушения — дедлайн), `owner` (`string`: на кого записано — адресат в этот момент).

**`LeftGroup`** — `primaryId` (`string`), `linkedAt` (`int`), `at` (`int`: когда вышел). Не выходил — `primaryId` = `''`.

**`Form`** — поля формы перехода: `targetId`, `primaryId`, `resultId`, `holdReasonId`, `closeCauseId`, `comment` — все `string`, незаполненное — `''`.

**Настройки** — разделы машины как константы с их полями, по `cel.settings`: имя — раздел машины и его тип, или `{type, from}` — значение по пути (`closeResults` — `reasonCatalogs.close_result.items`). Сейчас `limits`, `session`, `escalation`, `alerts`, `states`, `closeResults`, `timerDefs` (`timers`), `holdReasons` (`reasonCatalogs.hold.items`). Адресат — двумя полями (ARCH-07 в7): у уровня эскалации и получателя алертов `targetKind` (`user` или `group`) и `target` (id) вместо строки `user:petrova`. `null` у лимита — `0`.

## Факты мира

То, что машина не определяет, а читает: данные сервера и машины сценариев. Сигнатуры — `cel.world` машины. Каждый сервер даёт их своими функциями (прототип — `celWorld` в `engine.js` из данных `server.js`); модель Quint — рукописным прологом над своим состоянием.

| Функция | Что значит | В прототипе |
|---|---|---|
| `can(who, perm): bool` | у человека есть право — по его ролям | `permsOf` |
| `access(who, x): bool` | у человека есть доступ к объекту инцидента — по группам доступа его ролей (§5). Только человек: доступ группы — определение `hasAccess` | `hasAccess` для человека |
| `isOperator(id): bool`, `isGroup(id): bool` | id — человек или дежурная группа | |
| `members(g): list<string>` | состав дежурной группы сейчас: люди с её ролями и записанные в неё (§8.1) | `membersOf` |
| `dutyGroups(): list<string>` | дежурные группы по порядку набора | |
| `inSourceGroup(x, g): bool` | устройство-источник инцидента — в группе устройств `g` (нормативы, `overrides`) | `inGroup` |
| `deviceInGroup(d, g): bool` | устройство `d` — в группе устройств `g` или во вложенной в неё: условие правила по группе (§14.5, ARCH-15) | `deviceInGroup` в `server.js` |
| `groupDepth(g): int` | глубина группы устройств в дереве — сколько над ней групп, верхняя — 0: ранг условия по группе, вложенная точнее родителя (§14.5) | `groupDepth` в `server.js` |
| `agentState(who): string` | состояние оператора (`session.states[].id`) | `agentState` |
| `idleSec(who): int` | сколько секунд сессия оператора не присылает признак активности (§12.3) | `idleSec` |
| `stepsFilled(x, setId): bool` | набор шагов сценария выполнен — отвечает машина сценариев (§14.5) | `stepsFilled` |
| `lastTransferTarget(who): string` | кому оператор передавал в последний раз (§8.2); не передавал — `''`. Только для формы «Передать» | `defaultTransferTarget` |

**Факты над множеством инцидентов** (ARCH-12). Выражения не перебирают `incidents` сами: список действий считается для каждой строки очереди, и в продукте это была бы загрузка всех инцидентов в каждое вычисление. Множество инцидентов читается только через эти факты, а смысл каждого записан в машине выражением `ref` над `incidents`. Прототип и модель Quint вычисляют `ref` как есть: прототип — `cel-runtime.js`, модель — определением над списком инцидентов. Бэкенд исполняет тот же смысл запросом по индексу. В эффекте `incidents` — с изменениями этой транзакции, и запрос бэкенда видит их же.

| Функция | Что значит (`ref`) |
|---|---|
| `incidentById(id): list<Incident>` | инцидент по id — списком из одного или пустым (`byId(incidents, id)`) |
| `linkedOf(id): list<Incident>` | привязанные к основному `id`, и открытые, и закрытые вместе с ним |
| `countMine(who, state, except): int` | сколько инцидентов человека в состоянии, кроме одного — для лимитов (§10.2) |
| `mineOf(who, state, except): list<Incident>` | те же инциденты списком — для подсказки, кто держит лимит |
| `groupMembersAt(p, at): list<Incident>` | кто был в группе основного `p` в момент `at` (`inGroupAt`, §11.4) |
| `siblingsOf(x): list<Incident>` | соседи — инциденты того же события (`eventGuid`), кроме самого `x`, и открытые, и закрытые (§14.5, ARCH-15) |

Состав фактов — закрытый: новое понятие, которое выводится из этих, — определение в машине, а не функция сервера. Факт над инцидентами вызывается только из условий, эффектов и правил интерфейса, не из определений: у определения нет списка инцидентов.

## Что из CEL можно

Только то, что переводится в Quint без исключений. Остальное — ошибка сборки.

| Можно | Пример |
|---|---|
| литералы `bool`, `int`, `string`; списки; словари с ключами-строками или целыми, каждый ключ-литерал — один раз | `['in_progress', 'on_hold']`, `{'kind': kind, 'at': deadline}` |
| поле, элемент списка по номеру, элемент словаря по ключу | `incident.timers[timerId].due`, `levels[0]` |
| `==`, `!=`, `<`, `<=`, `>`, `>=`, `&&`, `\|\|`, `!`, `? :`, `+`, `-`, `*` над `int` | |
| `x in list` | `incident.state in ['new', 'pending_acceptance']` |
| `size(list)` | |
| `list.exists(v, p)`, `list.all(v, p)`, `list.filter(v, p)`, `list.map(v, e)` — только по списку | `members(g).exists(m, can(m, 'incident:accept'))` |
| `cel.bind(v, e, тело)` — имя для промежуточного значения | |
| вызов определения и факта мира | |

| Нельзя | Почему |
|---|---|
| строковые функции: `contains`, `startsWith`, `substring`, `matches`, `size(string)` … | в Quint строки только сравниваются. Если данные приходится разбирать — разложить их в машине на поля (в7) |
| `double`, `timestamp`, `duration`, `bytes`, `/`, `%` | время — целые мс; деления правилам не нужно |
| `has()`, `null`, необязательные поля `?.` | пусто — `''` и `0` |
| `Тип{поле: …}` | не поддерживает cel-js 8.0.0. Составное значение — словарем, ключи сверяются с типом при сборке (в8) |
| макросы `exists`, `all`, `filter`, `map` по словарю: `incident.timers.exists(k, …)` | они перебирают ключи, а порядок ключей у исполнителей разный. Нужен ключ — элемент по ключу: `incident.timers['reaction']` |
| ключ-литерал в словаре дважды: `{'a': 1, 'a': 2}` | cel-js и cel-go молча берут последний — в машине это опечатка |

Что проверка не видит — известные пределы:

- повтор ключа ловится только у литералов: `{k: 1, 'a': 2}` с `k == 'a'` проходит — значение ключа при сборке неизвестно;
- макрос по словарю ловится по типу получателя из проверки типов. У значения типа `dyn` — значение настройки из аргумента `setting`, `let` от такого значения — тип при сборке неизвестен, и макрос по словарю проходит. У cel-go так же. В машине таких выражений нет.

Таблица проб разрешённой части — [`fixtures/cel-subset.json`](fixtures/cel-subset.json): что собирается и что даёт ошибку. Её проверяют оба исполнителя — `node tools/test_cel.mjs` у прототипа и тест подмножества у сервера (копия того же файла).

## Операции эффектов

`do` — список операций, выполняются по порядку. Каждая операция видит результат предыдущих: «после перехода» отдельно не бывает — порядок задаётся порядком операций и порядком эффектов перехода. Все изменения, в том числе других инцидентов, применяются вместе, когда выполнены все эффекты перехода; ошибка любой операции — переход не применяется (§14.1, §14.2).

| Операция | Что делает |
|---|---|
| `{"let": "имя", "value": "выражение"}` | имя для значения до конца `do`. Значение — снимок на момент `let`: следующие `set` его не меняют (PROC-44 в4, как в модели Quint) |
| `{"set": "путь", "value": "выражение"}` | записывает значение. Путь — от `incident` или имени из `forEach` по списку инцидентов: `incident.owner`, `e.timers[timerId].due` |
| `{"append": "путь", "value": "выражение"}` | дописывает значение в конец списка: `incident.breaches` |
| `{"if": "выражение", "then": [ … ], "else": [ … ]}` | ветвление; `else` можно не писать |
| `{"forEach": "имя", "in": "выражение-список", "do": [ … ]}` | операции для каждого элемента; изменения — у инцидента этого элемента. Элемент-инцидент — инцидент черновика транзакции по id: его запись видна `incident`, если это он же, и дальше в том же эффекте |
| `{"call": "эффект", "args": { "параметр": "выражение" }}` | эффект реестра — как часть этого: так `stopTimer` таймера со `startsOnce` вызывает `pauseTimer` |
| `{"world": "действие", "args": { … }}` | действие мира, ниже |

Операции таймера — `startTimer`, `stopTimer`, `pauseTimer`, `resumeTimer`, `restartTimer` — не встроенные: это эффекты реестра со своим `do` над полями `Timer`. Их правила — `startsOnce`, `pausable`, отработанный срок (RULE-50), норматив по `overrides` и `byPriority` — записаны в машине, как остальные.

Порядок важен: у `merge` пауза своего норматива привязываемого стоит перед `tightenPrimaryDeadline` — тот сравнивает остаток уже на паузе (раньше это обеспечивал отложенный «после перехода» эффект исполнителя).

**Действия мира** — то, что меняет не поля инцидента, а журнал и внешний мир. Аргументы — выражения CEL. Журнал, курсор и перенос ответов меняют только инцидент перехода или того, кого назвали, и применяются вместе с переходом; остальное — после него. В модель Quint не переводятся, кроме переноса ответов:

| Действие | Аргументы | Что делает | В Quint |
|---|---|---|---|
| `log` | `incident`, `key`; `vars` — подстановки, нет — их считает сервер по инциденту (подстановки `appendLog`, README машины); `actor` — от чьего имени, нет — выполняющий переход; `once` — одна запись на ключ и момент: следующая заменяет подстановки | запись в журнал инцидента | — |
| `notify` | `incident`, `to` — кому (человек или дежурная группа), `recipients` — кто получит, `alert` — это алерт, `emptyLog` — ключ записи, если получить некому; `about` — уведомление о другом инциденте: закрытом «Ложной тревогой» соседе (`notifySiblings`, ARCH-15) | доставка уведомления; некому — запись `emptyLog` в журнал | — |
| `command` | `incident`, `command` | внешняя команда (§14.2, `external`) | — |
| `evict` | `incident`, `who` | открытая у человека карточка — на просмотр | — |
| `setCursor` | `incident` | курсор сценария — на первый незаполненный шаг; считает машина сценариев | — |
| `shareAnswers` | `from`, `to` (id основного), `logKey` | ответы привязанного — в неотвеченные шаги основного, что переносится — решает машина сценариев; перенесено — запись в журнал основного | отвеченные шаги основного — объединение с отвеченными привязанного (пролог) |
| `touch` | `incident` | инцидент изменился не своим переходом — новая версия (нарушение группы, запись о закрытом «Ложной тревогой» соседе); после транзакции всем, кому он виден, — событие потока `journal.appended` | — |

## Правила интерфейса

Что видит оператор в очереди и в форме перехода, — тоже выражения машины над теми же именами (`me` — смотрящий). Вычисляет их сервер; интерфейс получает готовый результат и выражений не вычисляет.

| Где | Выражение | Тип | Что значит |
|---|---|---|---|
| `badges.rules[]` | `expr` | `bool` | бейдж — первое правило по порядку, чьё выражение истинно; ни одного — подпись состояния (§2.4) |
| `queueFilters[]` | `expr` | `bool` | инцидент в фильтре очереди. В списках — инциденты хотя бы одного фильтра: так привязанные (§11) в списках не видны |
| `queueSort.keys.<порядок>[]` | ключ | `int` | порядок очереди: меньше — выше, следующий ключ — при равенстве, при равенстве всех — по номеру инцидента |
| `cardNotes.rules[]` | `expr` | `bool` | пояснение в карточке — первое подходящее; `actions` — доступные смотрящему действия карточки; нет подходящего — пояснения нет |
| `session.states[].derived` | `expr` | `bool` | производное состояние оператора: показывается вместо хранимого `derived.of` (§12, RULE-99); `me` — оператор, `incident` нет |
| `forms[].notes[]` | `expr` | `bool` | пояснение формы — первое подходящее; `true` — всегда |
| поле формы | `requiredExpr` | `bool` | поле обязательно |
| поле формы | `visibleExpr` | `bool` | поле видно; нет выражения — видно всегда. Невидимое не обязательно и не отправляется |
| поле-список | `optionExpr` | `bool` | вариант `option` предлагается. Сервер проверяет по нему и присланное значение: вне вариантов — `422 FORM_FIELD_INVALID` (ARCH-09) |
| поле-список | `enabledExpr`, `disabledKey` | `bool` | вариант можно выбрать; нет — он виден заблокированным с причиной `disabledKey`, а присланный сервер отклоняет так же |
| поле-список | `defaultExpr` | `string` | значение по умолчанию; `''` — нет. Ставится, только если это доступный вариант |
| поле-список | `warnings[]`: `expr`, `textKey`, `vars` | `bool`; `vars` — словарь «подстановка → выражение» | предупреждение варианта `option` — первое, чьё `expr` истинно (`FieldOption.warning`), подстановки в текст `textKey` — значения выражений `vars`; нет подходящего — `null`. Выбрать вариант оно не мешает, сервер его не отклоняет; интерфейс показывает предупреждение выбранного варианта под полем. Пример — «Дубликат» при видимых соседях (§2.2, ARCH-15) |

```json
{ "expr": "incident.state == 'pending_acceptance' && ownership(me, incident) == 'target' && isGroup(addressee(incident))",
  "labelKey": "workflow.badge.pending_acceptance.target.group", "style": "inbox" }
{ "id": "mine", "labelKey": "workflow.filter.mine",
  "expr": "incident.state in ['in_progress', 'on_hold'] && ownership(me, incident) == 'owner'" }
{ "name": "comment", "kind": "text", "requiredExpr": "closeResults.exists(i, i.id == form.resultId && i.commentRequired)" }
```

Варианты поля-списка до отбора — `source`: `transferTargets` — люди и дежурные группы от сервера, `reasonCatalog:<справочник>` — позиции справочника. `requiredExpr` и `visibleExpr` могут читать одно поле-список той же формы (`form.resultId`), а оно само — ни одного: тогда сервер вычисляет их для каждого варианта этого поля и отдаёт таблицей (`AvailableAction.fieldRules`: `dependsOn` и `byValue`, ключ `""` — ничего не выбрано). Интерфейс, пока оператор выбирает, смотрит в таблицу; сервер при выполнении перехода вычисляет выражения сам — по присланным значениям. Варианты, их предупреждения, значение по умолчанию и пояснения от значений формы не зависят: они нужны до того, как оператор что-то выбрал.

В модели Quint правил интерфейса нет: они не меняют инцидентов.

## Ядро исполнения

Общий код исполнителя, одинаковый для всех правил: он не знает ни одного условия или эффекта IM. Это порядок проверки (`from`, затем условия по порядку, первое невыполненное и его `onFail`), применение перехода целиком или никак, планировщик переходов по таймеру и окно `manualWinsOverTimer` (§10.1, RULE-41, RULE-63), выполнение на выборке (`bulk`, `merge`; «Отсоединить все» — один переход на всех привязанных, всё или ничего), операции эффектов и мост к данным сервера. Ядро знает два условия по имени — `timerExpired` и `agentIdleFor`: по ним планировщик узнаёт момент перехода (RULE-41); момент перехода по молчанию — не раньше последнего перехода инцидента (RULE-48, BUG-76). Ядро записано дважды — в исполнителе прототипа и в модели Quint; что записи совпадают, проверяет сверка историй модели на исполнителе (`tools/check_quint_replay.mjs`). Нарушение, которое записал бы отменённый в окне переход, ядро записывает тем же эффектом машины — `recordBreach` этого перехода, на момент дедлайна и на адресата до действия. Описано в README машины, раздел «Модель workflow»; в модели Quint — рукописная часть генератора.

## Ошибки сборки

Каждое выражение разбирает и проверяет тот же cel-js и тот же код `prototype/cel-runtime.js`, что у прототипа, — `node tools/check_cel.mjs`, в CI — в шаге «Машина состояний». Ошибка — проверка не проходит:

- неизвестное имя, поле, функция или определение; не тот тип или порядок аргументов;
- результат условия — не `bool`; результат определения — не тот, что в `returns`;
- запрещённое из раздела «Что из CEL можно», в том числе повтор ключа-литерала в словаре и макрос по словарю;
- ключи словаря не совпадают с полями типа, куда значение записывается (`append` в `breaches` — поля `Breach`);
- путь `set` или `append` ведёт не в поле инцидента или не в список;
- корень пути `set` или `append` — не `incident` и не имя `forEach` по `list<Incident>`: значение `let` — снимок, запись в него пропала бы; элемент `forEach` по другому списку (`incident.breaches`) — не инцидент черновика;
- `call` эффекта, которого нет, или эффекта, который вызывает сам себя;
- определения вызывают друг друга по кругу;
- слово реестра без `expr` или `do` (`check_machine.py`);
- аргументы перехода не того типа, что в `argTypes`;
- правило поля формы читает больше одного поля, само поле, не поле-список своей формы или поле, которое само зависит от других; варианты, значение по умолчанию или пояснение читают значения формы; `enabledExpr` без `disabledKey`;
- состояние или категория в выражениях бейджей, фильтров и форм, которых нет в машине (`check_machine.py`).

## Перевод в Quint

Генератор модели (`tools/gen_quint.mjs`) берёт дерево разбора cel-js и переводит его по таблице; типы узлов выводит сам — по типам машины, сигнатурам и литералам:

| CEL | Quint |
|---|---|
| `string`, `int`, `bool` | `str`, `int`, `bool` |
| `list<T>`, `map<string, T>`, `map<int, T>`, `opt<T>` | `List[T]`, `str -> T`, `int -> T`, `List[T]` |
| тип с полями | запись `{ поле: тип, … }` |
| `a && b`, `a \|\| b`, `!a` | `a and b`, `a or b`, `not(a)` |
| `c ? a : b` | `if (c) a else b` |
| `x in l` | `l.foldl(false, (acc, y) => acc or y == x)` |
| `size(l)` | `l.length()` |
| `l.exists(v, p)`, `l.all(v, p)` | `l.foldl(false, (acc, v) => acc or p)`, `l.foldl(true, (acc, v) => acc and p)` |
| `l.filter(v, p)`, `l.map(v, e)` | `l.select(v => p)`, `l.foldl([], (acc, v) => acc.append(e))` |
| `m[k]` у словаря | `m.get(k)` |
| определение | `def имя(параметры): тип = …` |
| условие в переходе | часть `ok_<переход>` — с аргументами этого перехода |
| эффект в переходе | `e_<переход>_<n>(w, c, iid): World` — каждая операция даёт новое значение мира `World`; `forEach` — свёртка по id элементов, их поля читаются из текущего мира; `call` — `ec_<эффект>`; действия мира не меняют инцидентов, кроме `shareAnswers` |
| `cel.bind(v, e, тело)` | `{ val v = e  тело }` |
| `x in m` у словаря | `m.keys().contains(x)` |

Время в модели — те же целые миллисекунды, и нормативы — значения машины: часы идут действием окружения не по шагу, а к ближайшему событию — дедлайну, мигу после него, концу окна `graceSec`, порогу молчания. Поэтому в модели есть и окно после дедлайна.

Руками — части `quint/src/`: факты мира над состоянием модели и `shareAnswers`, ядро исполнения, окружение, инварианты ([README модели](quint/README.md)). Что генератор переводит смысл верно, проверено в пробе ARCH-07.1 (ответы сгенерированных условий и выражений прототипа на одних данных совпадают) и проверяется сценариями модели, повторяющими тесты API.

## Векторы

Бэкенд вычисляет те же выражения своей реализацией CEL. Что смысл у него тот же, что у прототипа, проверяют **векторы**: «вход + мир → ответ» вычислений исполнителя прототипа. Бэкенд повторяет каждый вектор своим исполнителем и сверяет ответ (PROC-44).

**Откуда.** Файл [`fixtures/cel-vectors.json`](fixtures/cel-vectors.json) лежит в репозитории и собирается командой `node tools/cel_vectors.mjs --update` (решение PROC-44 в2). Векторы берутся из двух мест (в1):

- **запись** — тесты API на исходной машине, `tests/api.html?celVectors=1`. Часы и случайные числа зафиксированы. Пишется каждое вычисление условия, правила интерфейса, определения (и вызванного из другого выражения) и эффекта. В файл идёт не больше 30 векторов на имя и не больше 5 на один ответ;
- **синтетика на границах** — случаи, которых запись не даёт: дедлайн ровно сейчас, порог молчания, лимит отложенных, окно переоткрытия, порядок у `mergePrimary` и `recipients`, остаток таймера, `null` на входе, ошибки вычисления. У вектора синтетики есть поле `case` — название случая.

**Ошибки вычисления** в записи не встречаются: тесты API идут по правильным данным. Поэтому все векторы с `expect.error` — синтетика, сейчас их 7, в каждом виде вычислений:

| Вид | Случай | Что ломается |
|---|---|---|
| условие | `timerExpired ['nope']` | нет ключа в `incident.timers` |
| условие | `withinHoldLimit` без `scope.incidents` | факт с `ref` (`countMine`), а списка инцидентов нет |
| эффект | `restartTimer ['reaction', 'now * now']` | переполнение `int64` в выражении аргумента |
| эффект | `pauseTimer ['nope']` | `timerDef('nope')` — элемент `[0]` пустого списка |
| правило интерфейса | `queueSort.keys.reaction_deadline.0` у инцидента без таймера `reaction` | нет ключа в `incident.timers`: данные сервера неполные |
| определение | `timerRuns(x, 'nope')` | нет ключа в `incident.timers` |
| определение | `leftOf` со строкой `'abc'` в параметре `now: int` | не тот тип на входе |

Каких ошибок в векторах нет и почему:

- **Дробное число на входе `int`.** В векторе бывают только целые. Прототип дробную часть отбрасывает, а строку из цифр читает как число; бэкенд в обоих случаях даёт ошибку. Это проверяет свой тест бэкенда, а запись векторов следит, чтобы таких входов не было.
- **Переполнение от входа, а не от выражения.** Входы векторов — безопасные целые, до 2^53. Произведения в машине — настройка или аргумент на 1000 (`sec * 1000`), и из безопасных целых до 2^63 они не доходят. Поэтому переполнение есть только в выражении аргумента (`now * now`). cel-js проверяет переполнение у `+`, `-`, `*`, как cel-go. У унарного минуса не проверяет: `-x` при наименьшем `int64` cel-go даёт ошибку, cel-js — нет. Из безопасных целых туда не попасть.
- **Значение больше 2^53 в ответе.** Такой ответ — правильный `int64`, но в вектор его не записать. В машине таких нет.

`--update` запускает Chrome и идёт около 6 минут. Любая правка машины, даже `$comment`, требует `--update`. Профиль Chrome `--update` держит во временной папке системы; другую папку задаёт `--tmp=папка`, другой Chrome — переменная `CHROME`. `TMPDIR` для этого не подменять: в длинном пути Chrome не может создать свой сокет `SingletonSocket` и падает. `node tools/cel_vectors.mjs --check` работает без Chrome, за секунды; в CI он входит в шаг «Машина состояний». Он проверяет:

- файл собран от этой машины;
- файл не правлен руками;
- каждый вектор повторяется на исполнителе прототипа;
- у каждого условия, эффекта, определения и правила интерфейса машины есть вектор.

**Файл.** Канонический JSON: ключи по алфавиту, без пробелов. Сначала шапка, затем по строке на инцидент пула и по строке на вектор. Векторы упорядочены по `id`.

| Поле | Что |
|---|---|
| `machineSha256` | sha256 байтов `workflow_schema.v1.json`, от которой собраны векторы. Бэкенд сверяет его со своей копией машины |
| `counts` | сколько векторов каждого вида |
| `incidents` | пул: ключ — первые 16 hex sha256 канонического JSON инцидента, значение — `Incident` целиком |
| `skipped` | сколько вычислений запись пропустила: `tapeRepeat` — мир на один и тот же вызов ответил по-разному (ниже, «Лента»), `worldError` — факт мира бросил исключение |
| `vectors` | векторы |
| `format` | `1` |

| Поле вектора | Что |
|---|---|
| `id` | `<kind>:<name>:<первые 10 hex sha256 канонического входа>`; вход — `args`, `use` (если есть), `scope`, `world` |
| `kind` | `guard`, `rule`, `definition`, `effect` |
| `name` | у условия и эффекта — `fn`; у правила интерфейса — ключ правила (`forms.close.fields.comment.requiredExpr`, `queueFilters.mine.expr`, `queueSort.keys.oldest_first.0`); у определения — его имя |
| `case` | только у синтетики: название случая |
| `args` | у условия и эффекта — аргументы из перехода как есть: литералы, пути к настройкам, выражения `expr<T>`. Пропущенный аргумент эффекта уже взят из `defaults`. У определения — значения по `params` |
| `use` | у условия — поля `usage` из записи условия в переходе (`scopeRule`) |
| `scope` | имена верхнего уровня: `me`, `actor`, `surface`, `now`, `deadline` (уже `deadline ?? now`), `form` (`Form` целиком), `incident`, `before` (у эффекта), `option` и `actions` (у правила), `incidents` |
| `world` | лента: `[{"fn", "args", "out"}]` — вызовы фактов мира без `ref` |
| `expect` | `{"value": …}` или `{"error": "текст"}` |

Ответ в `expect.value`:

- **условие** — `null`, если выполнено; иначе `{"key", "vars"?}`: причина отказа и подстановки;
- **правило интерфейса и определение** — значение по объявленному типу;
- **эффект** — `{"incidents": {"<id>": {"$ref": …}}, "actions": [{"action", "args"}]}`: инциденты, в которые писали `set` и `append` (целиком, после эффекта), и действия мира по порядку.

**Значения.**

- Инцидент на входе и в ответе — `{"$ref": "<ключ>"}` в пул.
- Инцидент в аргументах ленты и действий — `{"$incident": "<id>"}`: факты о нём зависят от записи сервера, а не от полей.
- Числа — только безопасные целые.
- `opt<T>` — список из 0 или 1 элемента.
- Ключи `map<int, T>` — строки цифр.
- `null` бывает только в синтетике «пусто на входе» и читается, как `value()` прототипа: `''`, `0`, `false`, `[]`, запись из пустых полей.
- Нет ключа в `scope` — имени нет. Не подставлять пустое значение. Так у определений: `scope` пустой. Так у правил без инцидента — производного состояния оператора `session.states.<id>.derived.expr`: в нём нет `incident`. `incidents` есть, только если вычисление спрашивало список. Нет его, а факт с `ref` вызван — ошибка.

**Как повторяет бэкенд.**

- **Окружение** — из раздела `cel` машины. Факты мира без `ref` отвечают по **ленте**: вызов ищется по `fn` и аргументам, равным по значению. На один вызов — один ответ, сколько бы раз выражение его ни спросило. Вычисление, где мир на один и тот же вызов ответил по-разному, запись в файл не пишет. Их число — в `skipped.tapeRepeat`, `--check` его печатает.
- **Промах.** Вызова нет на ленте — вектор не прошёл, даже если ждали ошибку. Неиспользованная запись ленты — не ошибка.
- **Факты с `ref`** вычисляются выражением `ref` над `scope.incidents` — **пулом** инцидентов вектора.
- **Сравнение** — по значению, с `expect` в каноническом виде. `expect.error` значит: у бэкенда вычисление тоже должно дать ошибку. Текст в `expect.error` — сообщение cel-js или исполнителя прототипа, часто в несколько строк, с указателем на место в выражении. Бэкенд текст **не сравнивает**: сверяется только то, что ошибка есть. Значение вместо ошибки и ошибка вместо значения — расхождение.

Что из этого следует для исполнителя бэкенда:

- **Определения** — функции окружения. Они видят только свои параметры, настройки, факты мира и другие определения; `incident`, `me`, `now` им не видны.
- **`cel.bind`** — расширение CEL, его нужно включить (в cel-go — `ext.Bindings()`).
- **Числа** — `int64` по объявленному типу. Дробное число или строка на входе `int` — ошибка.
- **В `incident.timers`** — все таймеры машины (`timers[].id`). Нет ключа — ошибка (вектор `timerExpired ['nope']`).
- **`idleSec`** — целые секунды, с округлением вниз.
- **В эффектах `incident.state`** — уже новое состояние, `to` перехода.
- **Ошибка вычисления** — ошибка сервера, а не `false` (PROC-44 в3). Переход не применяется, в `/actions` — ошибка, а не «скрыто».
- **`let`** — снимок значения (в4).
- **Элемент `forEach`** — инцидент черновика по id.
- **Повтор ключа-литерала в словаре и макросы по словарю** — ошибка сборки. cel-go их принимает, поэтому нужна своя проверка разрешённой части при загрузке машины («Что из CEL можно»).

## Векторы переходов

Вектор CEL проверяет одно вычисление. Но переход — это больше, чем сумма вычислений: порядок проверок, форма, окно после дедлайна, эффекты нескольких инцидентов на общих черновиках, журнал и его порядок, действия после фиксации. Всё это делает **ядро исполнения** («Ядро исполнения» выше). Что ядро бэкенда делает то же, что ядро прототипа, проверяют **векторы переходов**: «инциденты + лента мира + действие → инциденты, журнал, действия после фиксации». Векторы записаны на ядре прототипа, бэкенд повторяет каждый своим ядром и сверяет итог. Расходится — правится бэкенд, а не вектор.

**Уровень — ядро, а не HTTP.** Вектор — это вызов ядра прототипа (`IMEngine.create` в [`prototype/engine.js`](../../prototype/engine.js)): `run` — один переход, `runAll` — один переход на нескольких инцидентах («Отсоединить все»), `merge` — объединение вместе с «Взять» основного, `create` — появление инцидента. Версий, `If-Match`, кодов HTTP, текстов ответа в векторах нет: это слой HTTP, его проверят тесты API. Переходы по таймеру и системные (`tick` планировщика) — тоже не здесь, их векторы — на этапе 6. Окно после дедлайна у ручного перехода — здесь.

### Откуда

Файл [`fixtures/transition-vectors.json`](fixtures/transition-vectors.json) собирает та же команда, что векторы CEL, `node tools/cel_vectors.mjs --update`, тем же прогоном Chrome. Векторы берутся из двух мест:

- **запись** — тесты API на исходной машине, `tests/api.html?celVectors=1`, часы и случайные числа зафиксированы. [`tests/transition-vectors.js`](../../tests/transition-vectors.js) оборачивает `IMEngine.create` (только ядра исходной машины) и пишет каждый вызов `run`, `runAll`, `merge`, `create`: список инцидентов до вызова, ленту мира и итог. Лента — факты `cel.world` из кадра записи векторов CEL и функции сервера мимо `cel.world` (ниже). Вектор `run`, `runAll`, `create` закрывается на возврате, `merge` — позже (ниже, «Объединение»);
- **синтетика** — случаи, которых запись не даёт. Сейчас их 8, у каждого поле `case` — название случая: «Взять» в окне после дедлайна, на конце окна и «Передать» в окне (таймер продолжается); форма с недопустимым значением и без обязательного поля (3 случая); «Отсоединить все», где второй инцидент не привязан; появление с приоритетом без своего норматива. У инцидентов синтетики id, событие и сценарий — UUID, у каждого инцидента своё событие, номер — `INC-%04d`: такие векторы можно положить в PostgreSQL. Ожидаемое синтетики тоже записано на ядре прототипа, а не написано руками; что каждый случай должен показать (отмена таймера, нарушение, ключ отказа…), проверяет код сборки — не показал, `--update` останавливается.

**Отбор — при записи.** На один `op:name` — не больше 20 векторов, на один исход — не больше 4. Исход — это отказ и его ключ, ошибка или у успеха набор ключей журнала, видов действий после фиксации и есть ли запись `timer_overridden`. Вектор проходит отбор, как только закрыт; не прошедший не хранится, в пул идут только инциденты оставленных. Один и тот же вход с двумя разными ответами — стоп записи (проверяется по всем векторам, и по отброшенным).

**Объединение и `merged_in*`.** Запись о присоединённых основному (`workflow.journal.merged_in` или `merged_in_more`) у прототипа пишет `server.js` после `engine.merge`, своим журналом, а бэкенд — ядро, в той же транзакции. Поэтому вектор объединения ждёт её. На возврате `merge` кадр ленты закрывается и снимается «после», а вектор остаётся открытым. Закрывает его следующий **меняющий** вызов любого обёрнутого ядра — своего или ядра коллеги: `run`, `runAll`, `merge`, `create`, `tick`, `startTimer`, `stopTimer`, `pauseTimer`, `resumeTimer` — или конец записи. Вызовы чтения (`isDone`, `availability`, `badge`…) его не закрывают: `server.js` зовёт `isDone` после объединения раньше, чем пишет `merged_in`. На закрытии у основного может быть одна новая запись — `merged_in*` от `me`: она входит в ожидаемое с пометкой `"server": true`. Любое другое изменение у любого инцидента списка — не ядро: вектор не пишется, счёт `skipped.outsideEngine`.

**Пропуски.** Вызов, который записать честно нельзя, в файл не идёт, но считается в `skipped`:

| Счётчик | Когда |
|---|---|
| `nowChanged` | часы сдвинулись за время вызова |
| `outsideEngine` | изменилось то, чего ядро не отдаёт: отказ или ошибка, после которых что-то изменилось; вызов ядра внутри вызова ядра; у объединения до закрытия — что-то кроме `merged_in*` основного |
| `tapeRepeat` | мир на один и тот же вызов ответил по-разному |
| `worldError` | факт мира или функция сервера бросили исключение |

Все четыре счётчика должны быть 0. Любой не 0 — `--update` останавливается. Перед записью `--update` повторяет оба файла (векторы CEL и переходов) так же, как `--check`; при любом стопе не пишется ни один из двух файлов.

### Формат

Как у векторов CEL («Векторы», «Файл» и «Значения»): канонический JSON, ключи по алфавиту, без пробелов; сначала шапка, затем по строке на инцидент пула и по строке на вектор, векторы — по `id`. Инцидент на входе и в ответе — `{"$ref": "<ключ>"}` в пул, инцидент в аргументах ленты и в действиях — `{"$incident": "<id>"}`, числа — только безопасные целые.

| Поле файла | Что |
|---|---|
| `machineSha256` | sha256 байтов `workflow_schema.v1.json` — то же, что у векторов CEL |
| `format` | `1` |
| `counts` | сколько векторов каждого `op` |
| `incidents` | пул: ключ — первые 16 hex sha256 канонического JSON инцидента, значение — `Incident` машины целиком (`celView` прототипа) |
| `skipped` | счётчики пропусков (выше); все 0 |
| `uncovered` | требования покрытия без вектора, с причиной словами (ниже, «Покрытие»); сейчас `{}` |
| `vectors` | векторы |

| Поле вектора | Что |
|---|---|
| `id` | `transition:<op>:<name>:<первые 10 hex sha256 канонического входа>`; вход — все поля, кроме `id`, `case`, `expect` |
| `kind` | `transition` |
| `op` | `run`, `runAll`, `merge`, `create` |
| `name` | id перехода; у `merge` — переход с `bulk.mode: merge`; у `create` — `create` |
| `case` | только у синтетики: название случая |
| `me` | оператор, от чьего имени работает ядро; он же выполняет переход у `run`, `runAll`, `merge` |
| `now` | время на входе, мс; за вызов не меняется |
| `surface` | где спрашивают (`card`, `queue`) или `""`; у `merge` и `create` — `""` |
| `form` | значения формы как есть (`run`, `runAll`); у `merge` и `create` — `{}` |
| `target` | `run` — `{"id"}`; `runAll` — `{"ids"}`, может быть пустым; `merge` — `{"primaryId", "ids"}`, присоединяемые в порядке вызова, могут быть пустыми; `create` — `{"incident": {"$ref"}}` — новый инцидент до перехода (его `state` — `""`) |
| `incidents` | список инцидентов сервера на входе — `{"$ref"}` в порядке прототипа (ниже, «Пул и порядок списка») |
| `journalAtNow` | `{"<id>": [запись]}` — записи журнала с `at == now` до вызова; только непустые |
| `world` | лента `[{"fn", "args", "out"}]`, на один вызов — одна запись (ниже, «Лента») |
| `expect` | `{"ok": {…}}`, `{"refusal": {…}}` или `{"error": "текст"}` |

**Запись журнала** — `{"actor", "at", "kind", "templateKey", "vars"}`. `kind` — как в ответе API: `dispatcher` и `system` — `system`, остальные — `transition` (у сервера — `model.JournalKindOf`). `vars` — `{}`, если подстановок нет. У записи, которую пишет `server.js` после ядра (`merged_in*`), — ещё `"server": true`. Полей `Transition` и `ID` записи в векторе нет.

`expect.ok` — только то, что ядро прототипа отдаёт:

| Поле | Что |
|---|---|
| `incidents` | `{"<id>": {"$ref"}}` — инцидент после вызова у каждого инцидента списка (и у нового при `create`), который изменился |
| `journal` | `{"<id>": [запись]}` — новые записи журнала по инцидентам, по порядку; только непустые |
| `journalAtNow` | `{"<id>": [запись]}` — записи с `at == now` после вызова у инцидентов, у которых они были до вызова: видно, как `once` заменил подстановки прежней записи |
| `after` | действия после фиксации по порядку: `{"action": "notify", "incident", "recipients", "alert", "about", "actor", "transitionId"}`, `{"action": "evict", "incident", "who", "transitionId", "by"}`, `{"action": "touch", "incident", "actor"}`; `about` — `{"$incident"}` или `""`, `who` и `by` — id или `""` |
| `scenario` | вызовы сценария внутри транзакции по порядку: `{"action": "setCursor", "incident"}`, `{"action": "shareAnswers", "from", "to"}` |
| `external` | `{"<id>": [{"fn", "target"}]}` — внешние эффекты: у `run` и `create` — свой инцидент, у `runAll` — все, у `merge` — только присоединяемые (внешнее основного ядро прототипа не отдаёт); пустые — тоже |
| `facts` | `{"<id>": {"from": {"state", "owner", "addressee", "breaches"}, "to": {…}, "breach"}}` — у инцидентов шагов (у `merge` — присоединяемые и основной, если его взяли); `breaches` — число нарушений, `breach` — вид нового нарушения или `""` |
| `canceled` | только у `run`: `{"<id>": "<переход по таймеру>"}` — срабатывание, которое отменило окно после дедлайна. У `runAll` и `merge` его нет: ядро прототипа его не возвращает, отменённое видно по записи `timer_overridden` |

`expect.refusal` — `{"why": [ключ, подстановки?], "guard"?, "notFrom"?, "code"?, "id"?}`: поля отказа ядра, какие есть (`id` — какой инцидент выборки не прошёл). При записи проверено, что после отказа не изменилось ничего. `expect.error` — текст ошибки вычисления: у прототипа это отказ с ключом `workflow.error.transition_failed`, текст — `why[1].error`.

**Пусто** — `""`, не `null`: в аргументах функций сервера, в `facts`, в действиях (`about`, `who`, `by`, `actor`).

### Покрытие

`--check` требует:

- у каждого ручного перехода машины (`trigger: manual`) и у `create` — вектор `ok` с этим именем, любой `op`;
- у `run`, `runAll` и `merge` — хотя бы по одному отказу;
- хотя бы один вектор `run` с `canceled`.

Синтетика считается. Требование без вектора — провал, если его нет в `UNCOVERED_TRANSITIONS_OK` в `tools/cel_vectors.mjs` с причиной словами. Ключ — имя перехода, `<op>:refusal` (`merge:refusal`) или `run:canceled`; записей не больше трёх, больше — нужна синтетика. Список пишется в поле `uncovered` файла, его читает и тест покрытия бэкенда. Сейчас список пуст: покрыто всё.

### Как повторяет бэкенд

- **Пул и порядок списка.** Инциденты списка берутся из пула в порядке `incidents`. У прототипа это порядок набора и появления (новые — в начало), у сервера — по номеру. Сверка с вектором идёт в порядке вектора; сверка «в памяти = в базе» — в порядке номеров. Сколько векторов дают при этих двух порядках разный итог, бэкенд пишет числом в лог.
- **Журнал до вызова** — только `journalAtNow`. Этого хватает: `once` ищет прежнюю запись только среди записей с `at == now`, а запись `timer_overridden` встаёт перед записями самого вызова, сколько бы записей ни было раньше. Записи `journalAtNow` после вызова у бэкенда — его журнал, с заменами `once` на месте.
- **Лента.** Факты мира без `ref` и функции сервера отвечают по ленте: вызов ищется по `fn` и аргументам, равным по значению; на один вызов — один ответ. Вызова нет на ленте — вектор не прошёл, даже если ждали отказ или ошибку. Неиспользованная запись ленты — только счёт, не провал. Сейчас их 168, все — в векторах `run:close` и `run:transfer`: внутри кадра записи работает код показа сервера прототипа (сводка очереди, кто на месте, кому можно передать), и его вызовы попали на ленту. Повтор с каждой из этих записей, убранной по одной, показал: на итог не влияет ни одна. Бэкенд печатает это число, но не проваливает по нему.
- **Функции сервера на ленте** — с приставкой `ctx.`: `ctx.actorName [id] → имя` (строка или ключ каталога списком), `ctx.progress [инцидент] → {"filled", "total"}`, `ctx.stepNumber [инцидент] → номер шага`, `ctx.shareAnswers [from, to, at] → сколько ответов перенесено`. Варианты поля формы с `source: transferTargets` — факт `transferTargets` той же ленты.
- **Факты с `ref`** вычисляются над списком инцидентов вектора с изменениями этой операции, как в разделе «Факты мира».

**Сравнение.** Одни правила у трёх сверок: повтор на ядре прототипа (`--check`), «вектор против бэкенда» и «бэкенд в памяти против бэкенда в базе».

- **Вид итога** — `ok`, `refusal` или `error` — тот же. Исключение при повторе — расхождение всегда, что бы ни ждал вектор.
- **Отказ.** Отказ есть, ничего не записано. Совпадают поля, которые есть в ожидаемом: `why[0]` — ключ, `why[1]` — подстановки, `guard`, `notFrom`, `code`, `id`.
- **Ошибка.** Бэкенд даёт ошибку, ничего не записано. Это не промах ленты и не конфликт (повтор операции, версия). Текст не сравнивается.
- **Инциденты** — изменённые с любой стороны. Кого сторона не назвала, тот равен исходному (из списка или новый у `create`). Перед сравнением: пусто — нулевое значение типа, в `timers` — все таймеры машины, `since` сравнивается только у `hold` (у остальных — `0` с обеих сторон: прототип хранит `since` только у удержания).
- **Журнал** — по инцидентам, по порядку, поля `actor`, `at`, `kind`, `templateKey`, `vars`. Повтор на ядре прототипа записи с `"server": true` не сравнивает (их пишет `server.js`, а не ядро), бэкенд — сравнивает. Подстановка `closeResultLabel` `[""]` у бэкенда равна `""` у прототипа; таких случаев бэкенд пишет число, оно должно быть 0.
- **`after`** — по порядку. Повтор на ядре прототипа сравнивает и порядок (то же ядро). Сверка «вектор против бэкенда» порядок `after` не сравнивает, только состав; порядок сравнивает сверка «в памяти против в базе». **`scenario`** — по порядку.
- **`external`** — только у инцидентов, для которых он есть в ожидаемом. **`facts`** — у всех названных с любой стороны. **`canceled`** — только у `run`.
- **Пусто:** `null` — `""`, вглубь: в подстановках журнала и отказа, в `external`, `scenario`, `after`, `facts`. Нет подстановок (`nil`) — то же, что `{}`.
- **Числа:** число из JSON и `int64` — одно.
- **Не сравниваются:** версии, поля записи журнала `Transition` и `ID`.
- **В памяти против в базе** — всё выше плюс `canceled` у всех `op`, `Transition` записей журнала и порядок `after`. Не сравниваются место в списке (в памяти — порядок списка, в базе — номер), абсолютные версии (только рост на 1 у изменённых) и `ID` записей журнала; журнал — только записи операции и заменённые `once`.

### Что из этого следует для ядра бэкенда

- **Всё — в одной транзакции перехода.** Где прототип срезает углы в памяти, бэкенд делает по BACKEND.md: нарушение, которое записал бы отменённый окном переход (у прототипа — вторая фиксация после эффектов), записи «некому» (`emptyLog` у `notify`; у прототипа — после фиксации), `merged_in*` (у прототипа — `server.js` после ядра), перенос ответов сценария. Векторы сравнивают итог после всего этого.
- **Порядок записей журнала у инцидента:** `timer_overridden` — первой из записей операции; затем записи эффектов по порядку действий; затем записи «некому» всех шагов — после всех шагов, в порядке `notify`; затем записи окна после дедлайна — нарушение отменённого перехода и его «некому»; `merged_in*` — последней. Так у прототипа, и векторы это сравнивают.
- **Состояние `to` — перед эффектами своего инцидента**, а не всей операции: у «Отсоединить все» второй ещё привязан, пока идут эффекты первого; у объединения основной ещё новый, пока идут эффекты присоединяемых. Шаги операции идут на общих черновиках: второй видит сделанное первым.
- **Факты (`facts`) — после всей операции:** `from` — до операции, `to` — после всех шагов, до окна после дедлайна.
- **Окно после дедлайна — у каждого инцидента шага:** у «Отсоединить все» — у каждого, у объединения — у каждого присоединяемого по переходу объединения и у основного по «Взять».
- **Пустой список — не ошибка.** «Отсоединить все» без привязанных — успех без изменений (есть вектор с `"ids": []`). Объединение без присоединяемых — только «Взять» основного, если он в `from` перехода «Взять» (`grouping.takeWith`), без `merged_in*`; иначе — успех без изменений.
- **Отказ — не ошибка**, а итог: ничего не записано. **Ошибка вычисления — ошибка сервера** («Векторы», PROC-44 в3), тоже без записи.
- **Планировщик** (`tick`, переходы по таймеру и системные) — этап 6, его векторов пока нет.

## Библиотека

Прототип и сборка — `@marcbachmann/cel-js` 8.0.0 (2026-07-07, MIT, без зависимостей). Библиотека — модули ES, а прототип открывается и с диска (`file://`), где браузер их не загружает. Поэтому в репозитории она лежит одним обычным скриптом `prototype/vendor/cel-js/cel.js`, собранным esbuild; версия, хэш архива npm и хэш собранного файла — рядом, в `ORIGIN.md`, как у `json-logic-js`. esbuild нужен только при смене версии.

Чем cel-js отличается от спецификации CEL, если это задевает машину:

- нет записи `Тип{поле: …}` — словарь (в8);
- целые — `BigInt` в JS: мост к данным переводит числа;
- у константы-списка тип элементов теряется (`list<State>` становится `list`): настройки-списки общий код объявляет переменными и подставляет в каждое вычисление;
- значения типов — экземпляры общих классов, а все выражения разбираются в копиях одного окружения (`clone()`): обёртки, которые cel-js создаёт сам, между разными окружениями не узнаются.
