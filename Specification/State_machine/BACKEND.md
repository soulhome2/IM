# Памятка для команды бэкенда

С чего начать операторскую часть МИ и как понять, что она готова. Подробности — в [README машины](README.md), здесь — порядок работы и критерий готовности.

## Что реализовать

| Что | Где описано |
|---|---|
| REST API операторского места — 39 операций, плюс 3 служебные для тестового стенда | [`openapi.json`](openapi.json) — контракт, OpenAPI 3.1 |
| Исполнение модели workflow: 5 состояний, 25 переходов, 27 условий, 19 эффектов, таймеры, лимиты, права | [`workflow.v4.json`](workflow.v4.json) — модель как данные; смысл — в [README машины](README.md), «Модель workflow» |
| Правила, из которых всё это следует | [`States rules IM.md`](../State_rules/States%20rules%20IM.md) — действующие правила, ссылки «§N» ведут туда |

Модель — это конфигурация, а не код. Сервер хранит её, исполняет и отдаёт клиенту (`GET /operator/workflow/active`). Переходы, кнопки, формы, бейджи и нормативы клиент берёт оттуда и из ответов сервера. Своей таблицы переходов у клиента нет.

Образец исполнения — встроенный сервер прототипа: [`prototype/server.js`](../../prototype/server.js) и исполнитель модели [`prototype/engine.js`](../../prototype/engine.js). Это JavaScript в браузере, в продукт его не переносят, но по нему видно, как понимать каждое условие и эффект.

## На что обратить внимание

- **Переход атомарен.** Всё меняется одним запросом `POST …/transitions/{transitionId}` в одной транзакции: состояние, владелец, таймеры, журнал. Отдельных `/claim`, `/close` нет и не будет.
- **Версия записи.** Карточка отдаёт `ETag` — поле `version` в кавычках, `"12"`. Переход и ответы сценария приходят с `If-Match`. Нет заголовка — `428`, версия не совпала — `412` с актуальной карточкой в теле.
- **Ошибки** — `application/problem+json` с машинным `code`. Перечень кодов — `Problem.code` в контракте, какое условие даёт какой код — в README машины, «Коды ошибок перехода».
- **Таймеры живут на сервере.** Дедлайны — метки времени. Автоэскалацию, нарушения нормативов и потерю связи выполняет планировщик сервера, клиент только показывает отсчёт. Порядок: если готовы сразу несколько автоматических переходов, первым выполняется тот, чьё условие наступило раньше: таймер — по дедлайну, потеря связи — последний признак активности плюс порог, остальное — в момент проверки; при равенстве — по порядку в машине. Переход, который стал возможен после другого, наступает не раньше него, а переход без таймера — сразу после него (RULE-48). Эффекты считают время от этого момента, после каждого перехода выбор делается заново. Так результат не зависит от того, как часто работает планировщик, и догон после простоя даёт то же, что проверка каждую секунду (README машины, «Переходы»; тест API «Порядок автоматических переходов»). Упрощение: условия без времени — доступ, права, состояние оператора — при догоне берутся на текущий момент, а не на момент наступления; если роли поменялись во время простоя, результат будет «как сейчас».
- **Поток событий обязателен** — `GET /operator/stream`, SSE. Сообщение без строки `event:`, в `id:` — `id` события, в `data:` — JSON. Сервер досылает пропущенное после `Last-Event-ID`.
- **Признак активности.** Клиент шлёт `heartbeat` раз в `session.heartbeatSec`. Если его нет `idleHoldSec`, инцидент оператора уходит в «Отложен — нет связи», через `idleReleaseSec` — обратно в очередь (§12.3).
- **Идентификаторы.** У инцидентов, устройств, групп устройств, типов событий, планов и сценариев — UUID, номер для показа — `number`. Люди и дежурные группы — строки внешней системы (§5).
- **Записи журнала** хранятся шаблоном и подстановками (`templateKey` + `vars`): клиент переводит их на язык оператора.
- **Видимость (§5).** Оператор видит только инциденты доступных ему объектов — по группам доступа его ролей: в очереди, карточке и потоке событий. Когда меняются роли или группы доступа, сервер сразу проверяет открытые инциденты: `addressee_lost_access` (у владельца или адресата нет доступа) и `addressee_cannot_accept` (адресат больше не может принять). Прежнему владельцу или адресату уходит `incident.access_lost` — только номер, данных инцидента он уже не видит.
- **Права и роли всех пользователей (§5, §8.1).** Передать можно только тому, кто может принять: право `incident:accept` и доступ к объекту, у группы — хотя бы у одного участника. Поэтому МИ нужны права и роли не только вошедшего, но и всех пользователей; как их получать — открытый вопрос §15.
- **Алерты (§9).** Эффект `notify(alerts.target)` — внешний: выполняется после транзакции перехода. Получатели — пользователь или участники дежурной группы, кто на месте и с доступом к объекту инцидента; никого — в журнал пишется `alerts.noRecipientLog`. Получателю — событие потока `incident.alert`.
- **Выход из МИ (§12.1).** При `offline` сервер сразу выполняет `owner_signed_out` (свои в работе и отложенные — в очередь) и `target_signed_out_*` (адресованные лично — группе или в очередь). После выхода, как на перерыве, — только просмотр: признак `readOnly` у состояния оператора в `session.states`, переходы отклоняются с `403 AGENT_NOT_READY`.
- **Настройки администратора (§20).** Полный перечень по вкладкам будущей админки — [`SETTINGS.md`](SETTINGS.md), он собран из раздела `adminSettings` машины. Настройки схемы правятся через редактор схемы (§14.6). Группы доступа, дежурные группы, справочные ссылки и связи камер — данные МИ: контракт описывает их чтение (`GET /operator/admin/access-groups`, `…/duty-groups`, `…/camera-links`, `GET /operator/reference/help-links`), запросы правки для вкладки администрирования бэкенд описывает сам. Камеры инцидента — связь его источника, у инцидента своего списка нет.

## Тестовый стенд

Бэкенд проверяется тем же набором тестов, что встроенный сервер прототипа. Для этого стенду нужны три служебные операции (тег `test-support`). В боевой сборке их быть не должно.

1. **`POST /test/reset`** загружает эталонный набор [`fixtures/demo.json`](fixtures/demo.json) и по умолчанию останавливает часы. Время в наборе абсолютное, при загрузке сдвигается на «сейчас − `capturedAt`». Таймеры заданы моментом запуска, длительность — из модели. Формат набора — README машины, «Тестовый стенд». Поля `workflowPatch` и `fixturePatch` — изменения схемы и набора на один прогон, JSON Merge Patch (RFC 7396): без них стенд не проверит правила, которым нужна другая настройка — выключенная автоэскалация, эскалация по закрытию, другой состав групп.
2. **`POST /test/clock`** сдвигает часы и сразу выполняет всё, что за это время должно сработать.
3. **`PUT /test/operators/{operatorId}/roles`** меняет роли человека посреди прогона, как в продукте смена ролей или групп доступа, и сразу выполняет то, что от этого сработало (§5).
4. **CORS для страницы тестов:** разрешить методы `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, заголовки `Content-Type` и `If-Match` и `credentials`, открыть странице `ETag` (`Access-Control-Expose-Headers`). Страница, открытая с диска, приходит с `Origin: null`.

Прогон: открыть `tests/api.html?api=https://адрес-стенда` в браузере. Тесты проходят сценарии по правилам и случайные прогоны с инвариантами, сверяют каждый ответ со схемами контракта (поля, типы, форматы, обязательные заголовки) и проверяют, что вызвана каждая операция.

Клиентская сторона этого пути уже проверена: те же тесты проходят по сети против встроенного сервера (`python3 tools/check_loopback.py`). Если на стенде что-то падает, причину стоит искать на стороне бэкенда, в CORS или во входе.

## Когда готово

- `tests/api.html?api=…` — все тесты зелёные, строка «Каждая операция контракта покрыта тестами» — тоже.
- Прототип работает с бэкендом: `prototype/index.html?api=https://адрес` — очередь, карточка, переходы, поток событий.

Тесты не проверяют операции редактора схемы (`/operator/workflow/schemas…`, 7 операций): экрана редактора пока нет. Их проверка — отдельно.
