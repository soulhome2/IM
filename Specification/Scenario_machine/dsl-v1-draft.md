# DSL v1 — Формат сценария Менеджера инцидентов

> Спецификация формата документа `scenarios.script` (JSONB) и runtime-документа
> `incidents.scenarioResult` (JSONB).
>
> Парная исполняемая схема: [`dsl-v1-schema.json`](./dsl-v1-schema.json).
>
> Исходник — черновик архитектора 2026-04-29 (`incident-manager-dsl`, коммит
> `bbe12d5`). 2026-10-19 формат сценария приведён к формату редактора
> сценариев продукта: `incident-manager`, `src/shared/schema/scenario.zod.ts`,
> предпросмотр `src/features/preview/lib/playerEngine.ts`, операторы условий
> `src/shared/lib/jsonLogic.ts` (коммит `1fcfa25`). Что редактор сохраняет, то
> этот формат и есть; каждое отличие от исходника и его причина — строкой в
> [CHANGELOG.md](CHANGELOG.md). Формат прохождения (`scenarioResult`, раздел 9)
> у редактора не описан — его задаёт МИ.
>
> Как МИ исполняет сценарий там, где формат молчит (кто отвечает, когда
> запускается макрос, что с флагами, которые МИ не исполняет), — профиль МИ
> в [README.md](README.md).

## 1. Принципы

### П1. Сценарий не зависит от платформы

Один и тот же `script` показывают веб и мобильные клиенты. В сценарии нет
DOM, CSS, нативных элементов, кода — только смысл: что спросить, какие
варианты, куда дальше.

### П2. В `view` — только смысл

`view.label`, `view.required`, `view.options[]` — да. Цвет, отступы, шрифт —
нет: вид шага задаёт дизайн-система клиента.

### П3. Формат — тот, что сохраняет редактор продукта

Документ сценария создаёт редактор сценариев продукта, и формат совпадает
с его форматом поле в поле: всё, что сохранил редактор, проходит схему
[`dsl-v1-schema.json`](./dsl-v1-schema.json), а документ, который схема
отвергает, редактор не создаст. Расширение формата — сначала в редакторе,
потом здесь.

### П4. Стабильные идентификаторы важнее имён

`step.id`, `option.id`, `list.id` — строки, **не индексы массива**: удаление
варианта не сдвигает ссылки на остальные. Редактор создаёт их через
`nanoid` (буквы, цифры, `_`, `-`).

### П5. У сценария есть свой паспорт

`scenario.id` (guid), `scenario.version`, `scenario.name` — обязательны и
отвечают на три разных вопроса:

| Поле | Отвечает на | Меняется когда |
| --- | --- | --- |
| `id` | «**какой** это сценарий» | никогда; совпадает с `scenarios.guid` сервера |
| `version` | «**какая версия**» | при публикации новой версии |
| `name` | «**как назвать в списке**» | в любой момент, без новой версии |

При загрузке редактор подставляет `id`, `name` и `description` из строки
сервера: кто сценарий, решает сервер, документ это только повторяет.

### П6. Граф объявлен, а не запрограммирован

Переходы — декларативные условия JSONLogic, не код. Безопасно, переносимо,
видно в diff.

### П7. Сервер не разбирает `script`

Сервер хранит `scenarios.script` как непрозрачный JSONB. Проверку формата
делает редактор при сохранении (раздел 11); исполнитель МИ — при загрузке.

## 2. Глоссарий и связь с сервером

| Понятие | В формате | Сервер | Legacy `IM/` |
| --- | --- | --- | --- |
| Сценарий обработки | документ `script` | `scenarios` (таблица) / `scenario` (API) | один из `control_logic` в `Msg` |
| Паспорт сценария | `scenario` (`id`, `name`, `version`, …) | `scenarios.guid`, `name`, `version` | — |
| Триггер срабатывания | (вне сценария) | `incidentRule` + `incidentRuleCondition` | `EventSettings`, `OBJS.*` |
| Связь правило ↔ сценарий | (вне сценария) | `incident_rule_scenarios` | неявно |
| Инцидент | — | `incidents` (`scenario_guid`, `scenario_version`) | `EventData` |
| Прохождение оператора | `scenarioResult` | `incidents.scenario_result jsonb` | `EventData.Works[]` |
| Шаг | `steps[]` | (внутри `script`) | строка в `CTRLS.*.{i}` |
| Тип шага | `step.type` | (внутри `script`) | `control_type` |
| Вариант ответа | `option` | (внутри `script`) | `radio.name.{j}`, `combo.content.{j}` |
| Условный переход | `transitions.rules[].condition` | (внутри `script`) | матрица `logic.{i}.item{j}` |
| Макрос на переходе | `macro: { name, args }` | (внутри `script`) | `macro.{i}` |
| Конец сценария | флаг шага `finish: true` | (внутри `script`) | `is_finish=1` |
| Отчёт | флаг шага `report` | (внутри `script`) | `is_report=1` |
| Текущий ответ на шаг | `scenarioResult.state[stepId].value` | (внутри `scenarioResult`) | из `Works` |
| Журнал действий | `scenarioResult.history[]` | (внутри `scenarioResult`) | сами `Works` |
| Жизненный цикл инцидента | (вне сценария) | машина состояний инцидента | жёстко в коде |

## 3. Что НЕ в сценарии

| Вне сценария | Где живёт | Почему вне |
| --- | --- | --- |
| **Триггеры** (когда запустить сценарий) | `incidentRule` + `incidentRuleCondition` | сервер решает это таблицами правил |
| **Права** (кто что может) | права и группы МИ | сценарий не знает про пользователей |
| **Арендаторы** | `customer_guid` в таблицах сервера | слой выше API |
| **Жизненный цикл инцидента** (новый → в работе → закрыт) | машина состояний инцидента | другой автомат, настраивается отдельно |
| **Сроки и эскалация** | нормативы машины состояний инцидента | сроки — свойство инцидента, а не инструкции |
| **Приоритеты** | справочник приоритетов | справочник, не часть сценария |
| **Источники событий** | `sources`, `source_types`, `source_actions` | приходят из Intellect |
| **Вид** (цвета, шрифты, отступы) | дизайн-система клиента | принцип П2 |
| **Координаты узлов в редакторе** | редактор продукта | для исполнения не нужны |

## 4. Корень документа

```json
{
  "scenario": {
    "id": "0190a1b2-0000-7000-8000-000000000001",
    "name": "Пожарная тревога",
    "description": "",
    "version": 2,
    "createdAt": "2026-10-01T09:00:00Z",
    "updatedAt": "2026-10-03T12:00:00Z",
    "updatedBy": "ivanov",
    "initialStep": "visual"
  },
  "steps": [ … ]
}
```

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `scenario.id` | string | ✓ | guid сценария, тот же, что `scenarios.guid` |
| `scenario.name` | string, не пустая | ✓ | название |
| `scenario.description` | string или null | — | описание; пусто — `""` или `null` |
| `scenario.version` | integer ≥ 1 | ✓ | версия сценария |
| `scenario.createdAt`, `updatedAt` | string, ISO-8601 | ✓ | справочно |
| `scenario.updatedBy` | string или null | — | кто изменил, справочно |
| `scenario.initialStep` | string, не пустая | ✓ | id первого шага |
| `steps` | array of Step | ✓ | все шаги; порядок в массиве не важен |

**Номера версии самого формата нет.** У редактора его нет, поэтому нет и
здесь. Исполнитель узнаёт формат только по тому, проходит ли документ схему;
документ формата, который исполнитель не знает, отвергается проверкой схемы,
а не исполняется частично. Риск — в §15 правил МИ.

## 5. Шаг (`Step`)

Шаг — узел графа сценария. После ответа оператора шаг выбирает переход.

### Общие поля всех шагов

Все обязательны.

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | string, не пустая | идентификатор шага, уникален в сценарии |
| `type` | string | `RadioButton` / `Checkbox` / `Select` / `Comment` / `Image` / `Datetime` / `Message` |
| `title` | string, не пустая | заголовок шага |
| `description` | string | пояснение под заголовком; может быть пустым |
| `revisitable` | boolean | можно ли вернуться на пройденный шаг и изменить ответ |
| `finish` | boolean | шаг последний: ответ на него завершает прохождение (раздел 8) |
| `report` | boolean | флаг отчёта редактора (раздел 8) |
| `multitasking` | boolean | флаг параллельной работы редактора (раздел 8) |
| `view` | object | вид шага, свой у каждого типа (раздел 6) |
| `transitions` | object | куда дальше (раздел 7) |

Редактор продукта создаёт новый шаг с `revisitable: true`, `report: true`,
`finish: false`, `multitasking: false`, `description: ""`.

### Почему `type` — дискриминатор

У каждого из семи типов своя форма `view`: у `RadioButton` — `options[]`,
у `Comment` — `minLength`/`maxLength`, у `Image` — `source`. Дискриминатор
и `oneOf` в схеме гарантируют, что `view` соответствует `type`: бессмыслица
вроде `{ "type": "Comment", "view": { "options": [] } }` не пройдёт.

## 6. Семь типов шагов

Значение по умолчанию (`default` у RadioButton, Checkbox, Select, Comment) —
то, чем поле заполнено, когда шаг открывается. Ответом оно становится, только
когда оператор подтвердит шаг («Далее»); на уже отвеченном шаге показывается
ответ, а не значение по умолчанию.

Что хранится в прохождении после ответа — раздел 9, «Тип шага → тип `value`».

### 6.1. RadioButton

Один вариант из списка.

```json
{
  "id": "verdict", "type": "RadioButton",
  "title": "Классификация", "description": "",
  "revisitable": true, "multitasking": false, "report": false, "finish": false,
  "view": {
    "label": "Что на видео?",
    "required": true,
    "default": null,
    "options": [
      { "id": "real",  "label": "Реальная" },
      { "id": "false", "label": "Ложная" }
    ]
  },
  "transitions": {
    "rules": [
      { "condition": { "==": [{ "var": "value" }, "false"] }, "goto": "note", "macro": null }
    ],
    "default": { "goto": "kind", "macro": { "name": "Оповещение по площадке", "args": {} } }
  }
}
```

| Поле `view` | Тип | Описание |
| --- | --- | --- |
| `label` | string | вопрос |
| `required` | boolean | без выбора шаг не подтвердить |
| `default` | string или null | id варианта, выбранного при открытии шага |
| `options` | array of `{ id, label }` | варианты |

Хранится `option.id`, не индекс.

### 6.2. Checkbox

Несколько вариантов из списка.

| Поле `view` | Тип | Описание |
| --- | --- | --- |
| `label` | string | вопрос |
| `minSelected` | integer ≥ 0 | отметить не меньше; > 0 — шаг обязательный |
| `maxSelected` | integer ≥ 0 или null | отметить не больше; null — без верхней границы |
| `options` | array of `{ id, label, default }` | варианты; `default: true` — отмечен при открытии шага |

Отдельного `required` нет: обязательность — `minSelected` > 0. Отметка
«Подтверждаю» — Checkbox с одним вариантом и `minSelected: 1`.

### 6.3. Select

Несколько выпадающих списков, в каждом можно отметить несколько вариантов.
Подписи у шага нет — у каждого списка своя, над ними — заголовок шага.

```json
"view": {
  "required": true,
  "lists": [
    { "id": "kind",  "label": "Вид",  "options": [{ "id": "smoke", "label": "Дым" }, { "id": "flame", "label": "Огонь" }], "default": [] },
    { "id": "floor", "label": "Этаж", "options": [{ "id": "f1", "label": "1" }, { "id": "f2", "label": "2" }], "default": ["f1"] }
  ]
}
```

| Поле | Тип | Описание |
| --- | --- | --- |
| `view.required` | boolean | в **каждом** списке отмечено хоть одно |
| `view.lists` | array, ≥ 1 | списки |
| `lists[].id`, `label` | string | идентификатор и подпись списка |
| `lists[].options` | array of `{ id, label }`, ≥ 1 | варианты |
| `lists[].default` | array of string | отмеченные при открытии шага; можно не писать — `[]` |

### 6.4. Comment

Текст оператора.

| Поле `view` | Тип | Описание |
| --- | --- | --- |
| `label` | string | подпись поля |
| `default` | string | текст в поле при открытии шага |
| `required` | boolean | пустой текст не принимается |
| `readonly` | boolean | текст только показывается, оператор его не меняет |
| `minLength`, `maxLength` | integer ≥ 0 | длина текста в символах |

Подсказку, что писать, автор кладёт в `description` шага.

### 6.5. Image

Изображение.

| Поле `view` | Тип | Описание |
| --- | --- | --- |
| `label` | string | подпись |
| `source` | `camera` / `map` / `operator` / `fixed` | `camera` — снимок с камеры, `map` — снимок карты, `operator` — файл оператора, `fixed` — готовая картинка |
| `image` | string или null | картинка для `fixed` (адрес или `data:`) |

`required` и числа вложений в формате нет. МИ: шаг необязательный, вложение
одно, `fixed` — только показать `image` (README, профиль МИ). Числовой
`img_type` legacy `IM/` заменён именами: `0=camera, 1=map, 2=operator, 3=fixed`.

### 6.6. Datetime

Дата и время.

| Поле `view` | Тип | Описание |
| --- | --- | --- |
| `label` | string | подпись |
| `required` | boolean | без значения шаг не подтвердить |
| `min`, `max` | string (ISO-8601) или null | границы |

Поле всегда «дата и время»; «только дата» и «только время» в формате нет.
Ответ — момент в UTC (раздел 9).

### 6.7. Message

Сообщение с кнопкой. Своего значения нет: нажатие кнопки и есть ответ.

```json
{
  "id": "report", "type": "Message",
  "title": "Доложите старшему смены", "description": "",
  "revisitable": true, "multitasking": false, "report": false, "finish": true,
  "view": { "label": "Доложил" },
  "transitions": { "default": { "goto": null, "macro": null } }
}
```

| Поле `view` | Тип | Описание |
| --- | --- | --- |
| `label` | string | надпись на кнопке |

## 7. Переходы и условия

### Структура

```json
"transitions": {
  "rules": [
    { "condition": { "==": [{ "var": "value" }, "real"] }, "goto": "zone", "macro": { "name": "Включить сирену", "args": {} } }
  ],
  "default": { "goto": "note", "macro": null }
}
```

| Поле | Описание |
| --- | --- |
| `default` | обязателен: `{ goto, macro }` |
| `rules` | необязателен; только у RadioButton, Checkbox и Select. У остальных типов правил нет — редактор их убирает |
| `rules[].condition` | условие JSONLogic над ответом своего шага; пустое `{}` не срабатывает никогда |
| `goto` | id следующего шага или `null` |
| `macro` | `{ name, args }` или `null` — раздел 8 |

### Алгоритм: первое сработавшее

```pseudo
если step.finish:
    прохождение завершено; переходы шага не читаются
иначе:
    для rule в transitions.rules по порядку:
        если rule.condition не пустое и истинно на контексте шага:
            запустить rule.macro; перейти на rule.goto; стоп
    запустить default.macro; перейти на default.goto
```

Первое сработавшее правило выигрывает, иначе `default`. Параллельных веток нет.

### `goto`

| Значение | Где допустимо | Эффект |
| --- | --- | --- |
| id шага | везде | перейти на этот шаг |
| `null` | только у шага с `finish: true` | следующего шага нет |

`null` у шага без `finish` — ошибка проверки (`GOTO_NULL_WITHOUT_FINISH`).
Остаться на шаге переходом нельзя.

### Что видит условие

Условие вычисляется над ответом **своего** шага. Ответы других шагов, данные
инцидента и оператора условию не видны.

| Тип шага | Контекст | Переменная | Пример условия |
| --- | --- | --- | --- |
| RadioButton | `{ "value": <id варианта> }` | `value` | `{ "==": [{ "var": "value" }, "real"] }` |
| Checkbox | `{ "selected": [<id>…] }` | `selected` | `{ "in": [{ "var": "selected" }, ["smoke"]] }` |
| Select | `{ "<id списка>": [<id>…], … }` | id списка | `{ "in": [{ "var": "kind" }, ["smoke", "flame"]] }` |

Пропущенный шаг (раздел 9): RadioButton — `{ "value": null }`, Checkbox —
`{ "selected": [] }`, Select — `{}`.

### Операторы над отмеченными вариантами

Ответ Checkbox и Select — массив. Стандартный JSONLogic сравнивает массив со
строкой через приведение к строке и даёт неверный результат, поэтому
`==`, `!=` и `in` работают так, как в редакторе продукта (`jsonLogic.ts`);
остальные операторы — стандартные.

| Оператор | Аргументы | Результат |
| --- | --- | --- |
| `==` | массив и не массив (в любом порядке) | значение среди элементов массива |
| `!=` | массив и не массив (в любом порядке) | значения нет среди элементов массива |
| `==`, `!=` | иначе | стандартное нестрогое сравнение |
| `in` | массив `a`, массив `b` | `b` не пуст, `a` не пуст и **все** элементы `b` есть в `a` |
| `in` | не массив `a`, массив `b` | `a` среди элементов `b` |
| `in` | массив `a`, строка `b` | хоть один элемент `a` — подстрока `b` |
| `in` | не массив `a`, строка `b` | `a` (строкой) — подстрока `b` |
| `in` | иначе | ложь |

Примеры: отмечены `["a", "b"]` — `{ "==": [{ "var": "selected" }, "a"] }`
истина; `{ "!=": [{ "var": "selected" }, "a"] }` ложь;
`{ "in": [{ "var": "selected" }, ["a"]] }` истина («отмечено всё из условия»);
ничего не отмечено — `{ "!=": [{ "var": "selected" }, "a"] }` истина.

Конструктор условий редактора пишет: для RadioButton `==`, `!=`; для Checkbox
`in` и его отрицание `{ "!": { "in": … } }` («отмечено» / «не отмечено»); для
Select `==`, `!=`, `in` и отрицание `in`. Условия объединяются через `and`, `or`.

### Разрешённые операторы JSONLogic

| Категория | Операторы |
| --- | --- |
| Доступ к данным | `var` |
| Сравнение | `==`, `!=` (как выше), `>`, `>=`, `<`, `<=` |
| Логика | `and`, `or`, `!` |
| Условный | `if` |
| Массивы | `in` (как выше), `none`, `some`, `all` |
| Отсутствие данных | `missing`, `missing_some` |

Арифметика, строки, `merge` и свои операторы не используются.

## 8. Макрос и флаги шага

### Макрос

У каждого исхода — правила и `default` — не больше одного макроса:

```json
"macro": { "name": "Оповещение по площадке", "args": {} }
```

`name` — имя макроса, `args` — параметры (редактор их хранит, но не меняет).
Макрос запускается, когда срабатывает его исход. Несколько действий —
это один макрос площадки, который делает их сам. У шага с `finish: true`
переходы не читаются, поэтому и макросов на нём нет.

МИ запускает макрос по условиям кнопки «Запустить макрос» машины инцидента
и пишет его в журнал инцидента (README, профиль МИ).

### Флаги шага

| Флаг | Смысл | Как МИ |
| --- | --- | --- |
| `finish` | шаг последний: ответ на него завершает прохождение, переходы шага не читаются. В сценарии хотя бы один такой шаг (`NO_FINISH_STEP`) | прохождение завершено — набор «закрытие» машины инцидента выполнен; инцидент сам не закрывается |
| `revisitable` | `true` — на пройденный шаг можно вернуться и изменить ответ; `false` — после ответа ответ не изменить | `false` — повторный ответ отклоняется |
| `report` | флаг отчёта. В редакторе продукта на экране не показывается, новый шаг получает `true` | не исполняется |
| `multitasking` | шаг доступен параллельно с другими задачами. В редакторе на экране не показывается, новый шаг получает `false` | не исполняется |

Эскалации и назначения в сценарии нет: это решения машины инцидента.

## 9. Прохождение оператора (`scenarioResult`)

Хранится в `incidents.scenario_result jsonb` сервера. Сервер его не разбирает,
редактор продукта его не описывает — формат задаёт МИ, здесь и в
`ScenarioResult` контракта (`openapi.json` машины состояний).

### Структура

```jsonc
{
  "state": {
    "<stepId>": { "value": <значение>, "answeredAt": "2026-10-03T08:30:12Z", "by": "ivanov" }
  },
  "history": [
    { "ts": "2026-10-03T08:30:12Z", "stepId": "verdict", "action": "answer", "value": "real", "by": "ivanov" },
    { "ts": "2026-10-03T08:30:12Z", "stepId": "verdict", "action": "macro", "name": "Включить сирену" },
    { "ts": "2026-10-03T08:30:12Z", "stepId": "verdict", "action": "transition", "to": "zone", "matchedRule": 0 }
  ],
  "attachments": [ … ],
  "currentStepId": "zone",
  "completedAt": null
}
```

| Поле | Назначение |
| --- | --- |
| `state` | **последний** ответ на каждый шаг пути, по `stepId` |
| `history` | журнал всех действий, только дописывается |
| `attachments` | вложения шагов Image (необязательно) |
| `currentStepId` | текущий шаг; после завершения — `null` (куда ставить курсор после завершения, решает МИ — README, профиль МИ) |
| `completedAt` | когда прохождение завершено; null — идёт |

### `state[stepId]`

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `value` | по типу шага | ✓ | ответ; у пропущенного шага — `null` |
| `answeredAt` | ISO-8601 | ✓ | когда ответили или пропустили |
| `by` | string или null | — | кто ответил |
| `skipped` | boolean | — | `true` — шаг пропущен без ответа |

### Пропуск шага

Необязательный шаг можно закрыть без ответа — «Пропустить». Необязательный:
RadioButton, Select, Comment, Datetime с `required: false`; Checkbox с
`minSelected: 0`; Image — всегда. Message пропустить нельзя: нажатие — ответ.

| Состояние шага | `state[stepId]` |
| --- | --- |
| не достигнут | ключа нет |
| отвечен | `{ value, answeredAt, by }` |
| пропущен | `{ value: null, answeredAt, by, skipped: true }`; в `history` — `{ action: "skip" }` |

Пустой ответ — не пропуск: Checkbox с `minSelected: 0` можно ответить `[]`.

### Тип шага → тип `value`

| Тип шага | `value` | Пример |
| --- | --- | --- |
| RadioButton | string — id варианта | `"real"` |
| Checkbox | array of string — id отмеченных | `["smoke", "flame"]` |
| Select | object — `{ <id списка>: [id отмеченных] }` | `{ "kind": ["smoke"], "floor": ["f1"] }` |
| Comment | string — текст | `"Прибыли пожарные"` |
| Image | string — id вложения | `"att-1f3c"` |
| Datetime | string — момент в UTC, ISO-8601 | `"2026-10-03T11:30:00Z"` |
| Message | `null` | `null` |

### `attachments`

Шаг Image хранит в `value` только id вложения, само вложение — в
`attachments[]`:

| Поле | Назначение |
| --- | --- |
| `id` | идентификатор вложения; он же в `state[stepId].value` |
| `stepId` | шаг Image, к которому относится |
| `source` | `view.source` шага: `camera` / `map` / `operator` / `fixed` |
| `mime`, `fileName`, `size`, `sha256` | тип, имя, размер, хеш (необязательно) |
| `capturedAt` | когда приложено |
| `dataBase64` или `storage` | содержимое или где оно лежит (`{ kind: "url", url }`, `{ kind: "s3", bucket, key }`) |

### `history`

| `action` | Поля | Когда |
| --- | --- | --- |
| `answer` | `value`, `by` | оператор ответил или изменил ответ |
| `skip` | `by` | оператор пропустил необязательный шаг |
| `transition` | `to`, `matchedRule` (номер правила или `null` — `default`) | переход на следующий шаг |
| `macro` | `name`, `args` (если не пустые) | сработал макрос исхода |
| `finish` | — | ответ на шаг с `finish: true` завершил прохождение |

`history` не правится — только дописывается. Изменённый ответ — новое
событие `answer` с тем же `stepId`.

### Почему `state` и `history` — два поля

`state` — что ответили сейчас, для пути, прогресса и показа шага; `history` —
кто, что и когда делал, для журнала. Только `history` — пересчитывать ответы
при каждом шаге; только `state` — потерять журнал.

## 11. Что проверяется и кем

### Уровень 1. Схема

[`dsl-v1-schema.json`](./dsl-v1-schema.json) — поля, типы, обязательность,
семь видов `view`. В МИ — `tools/check_scenarios.py` для сценариев набора и
примеров; в продукте ту же роль играет zod-схема редактора.

### Уровень 2. Смысл

Что схема не ловит — проверки редактора продукта (`validation.ts`), те же
коды:

| Код | Что |
| --- | --- |
| `NO_FINISH_STEP` | в сценарии нет шага с `finish: true` |
| `EMPTY_INITIAL_STEP`, `INVALID_INITIAL_STEP` | первый шаг не задан или его нет среди шагов |
| `EMPTY_STEP_ID`, `DUPLICATE_STEP_ID` | id шага пустой или повторяется |
| `EMPTY_STEP_TITLE` | заголовок шага пустой |
| `INVALID_GOTO` | `goto` ведёт на несуществующий шаг |
| `GOTO_NULL_WITHOUT_FINISH` | `goto: null` у шага без `finish` |
| `STEP_NOT_REACHABLE` | шаг не достижим от первого |
| `DUPLICATE_OPTION_ID` | id варианта повторяется в шаге или в списке |
| `CHECKBOX_MIN_EXCEEDS_OPTIONS`, `CHECKBOX_MAX_LESS_THAN_MIN`, `CHECKBOX_MAX_EXCEEDS_OPTIONS` | границы `minSelected` / `maxSelected` |
| `INVALID_CONDITION_OPTION_ID` | условие RadioButton или Checkbox ссылается на несуществующий вариант |
| `INVALID_CONDITION_LIST_KEY` | условие Select ссылается на несуществующий список |

МИ проверяет сверх этого (README, «Проверка»): правила у типа, у которого их
быть не может; условие, которое не срабатывает ни при каком ответе;
`default`, до которого не дойти; значение по умолчанию не из вариантов.

### Уровень 3. Исполнение

Исполнитель МИ: ответ не на текущий шаг пути отклоняется; ответ, который не
подходит к шагу, отклоняется с причиной; условие, которое падает при
вычислении, считается ложным.

## 12. Что отложено

| Что | Зачем |
| --- | --- |
| Номер версии формата | отказывать документу незнакомой версии, а не только незнакомой формы; решение — за командой продукта |
| Условия на ответы других шагов, данные инцидента и оператора | ветвление по приоритету, по прошлым ответам; сейчас условие видит только свой шаг |
| Несколько вложений у Image, обязательный Image | в формате редактора их нет |
| Смысл флагов `report` и `multitasking` | отчёты и параллельная работа МИ |
| Локализация через ключи | несколько языков в одном сценарии |
| Перенос живых инцидентов на новую версию сценария | сейчас инцидент доигрывает на своей версии |

## 13. Зафиксированные решения и открытые вопросы

### 13.1. Решения

#### Р1. `scenarioResult` хранится целиком в `incidents.scenario_result jsonb`

Не выносим `history` в отдельную таблицу событий: на ожидаемых объёмах
(десятки шагов, единицы исправлений) это килобайты на инцидент. Пересмотреть,
если появятся инциденты-долгожители или понадобится SQL-аналитика по событиям;
структура `scenarioResult` при этом не меняется.

#### Р2. Макрос пишется в `history` в момент срабатывания исхода

Запись — намерение, а не подтверждение исполнения. Результат исполнения
макроса МИ получает отдельно (событие `macro.completed` потока событий МИ).

#### Р3. Формат сценария — формат редактора продукта

2026-10-19 формат приведён к тому, что сохраняет редактор продукта
(принцип П3). Отличия от исходника DSL v1 — в [CHANGELOG.md](CHANGELOG.md);
их смысл: конец — флаг шага, а не действие; на исходе один макрос, без
списка действий; условие видит только свой шаг, операторы над массивами —
как в редакторе; `goto: null` — «следующего нет»; Select — несколько списков
с множественным выбором; значения по умолчанию; Datetime без `kind`; Image
без `required` и числа вложений; поля шага и корня — как в редакторе; без
`timers`, `concurrency` и номера версии формата.

### 13.2. Открытые вопросы

#### О1. Номер версии формата

Формат меняется вместе с редактором (уже менялись имена полей), а номера
версии у документа нет. Без него исполнитель не отличит документ старой
формы от испорченного. Решает команда продукта; в МИ — §15 правил.

#### О2. Список сценариев на сервере

`GET /scenarios` отдаёт все сценарии сразу. На сотнях сценариев понадобится
пагинация — вопрос API сервера, не формата.
