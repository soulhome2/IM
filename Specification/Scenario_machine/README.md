# Машина сценариев

Сценарий обработки — пошаговая инструкция оператору под тип события: что подтвердить, как классифицировать, что запустить. Сценарии ведёт отдельная машина состояний — эта. Машина инцидента ([State_machine](../State_machine/README.md)) её не заменяет и в неё не встраивается: две машины соприкасаются только в стыке, §14.5 [правил](../State_rules/States%20rules%20IM.md).

Формат сценария — DSL v1 из `incident-manager-dsl` (решение ARCH-06 в1). Откуда и с какого коммита перенесён — [ORIGIN.md](ORIGIN.md), что менялось после — [CHANGELOG.md](CHANGELOG.md). Источник истины теперь здесь.

## Машина как автомат

Прогон — одно прохождение сценария в одном инциденте: сценарий, его версия, ответы и текущий шаг. Хранится как `scenarioResult` (спецификация, раздел 9): `state` — последний ответ на каждый шаг, `history` — журнал без правок, `currentStepId` — текущий шаг, `completedAt` — время завершения.

| Состояние прогона | Признак |
|---|---|
| идёт | `currentStepId` — шаг, `completedAt` — `null` |
| завершён | сработало действие `finish`: `currentStepId` — `null`, `completedAt` задан |

Событие одно — ответ на шаг. Ответ на обязательный шаг (`view.required`) нельзя оставить пустым; необязательный можно пропустить — пишется `skipped: true`. После ответа переходы шага проверяются сверху вниз, срабатывает первое правило с истинным `when`, иначе `default` (спецификация, раздел 7): выполняются его действия, затем переход на `goto`; `goto: null` — остаться на шаге; действие `finish` завершает прогон. Условия — JSONLogic из белого списка операторов спецификации над `{ state }`.

## Профиль МИ

Как МИ исполняет машину. Формат сценария здесь не меняется: где спецификация молчит или говорит о другой системе, записано, как поступает МИ. Решения — ARCH-06 в [плане](../../reviews/2026-10-19/plan.md), 2026-10-19.

| Вопрос | Как в МИ | Решение |
|---|---|---|
| Идентичность и версия | `guid` и `version` — строки сценария на сервере; `metadata.scenarioGuid` и `metadata.version` в сценарии с ними совпадают. Инцидент ссылается на сценарий и версию, как в контракте сервера (`scenarioGuid`, `scenarioVersion`, `scenarioResult`) | в1 |
| Когда создаётся прогон | при появлении инцидента (`create`); версия — актуальная в этот момент и закреплена за инцидентом. Новая версия сценария открытые инциденты не трогает: они доигрывают на своей, переоткрытый — тоже | в4 |
| Набор обязательных шагов `closing` | выполнен, когда прогон завершён — дошёл до `finish`. Обязательные шаги пройденного пути при этом отвечены: без ответа на них переход не срабатывает. Набор `none` выполнен всегда. Других наборов нет: в формате их не задать | в5 |
| Курсор | на текущем шаге прогона — первом неотвеченном на пройденном пути; у завершённого — на последнем шаге пути | в5 |
| Прогресс «N из M» | N — пройденные шаги пути, M — N плюс кратчайший путь от текущего шага до `finish`. У завершённого N = M. При ветвлении M может меняться | в6 |
| «Назад» и переответ | «Назад» показывает предыдущий шаг пути. Шаг с `editable` (по умолчанию — да) можно переответить, после этого переходы проверяются заново. Если путь пошёл по другой ветке, ответы шагов, выпавших из пути, убираются из `state` и остаются в `history`. Действия перехода при повторном ответе выполняются снова. Шаг с `editable: false` после ответа — только для просмотра | в7 |
| `callMacro` | запуск макроса МИ — внешний эффект с записью в журнал инцидента; только если выполнены условия кнопки «Запустить макрос» машины инцидента (`navActions.run_macro`) | в8 |
| `finish` | завершает прогон. Инцидент не закрывает: итог инцидента — только результат закрытия (§2.2); `resolution` действия не используется | в8 |
| `generateReport` | только запись в `history` | в8 |
| `escalate`, `assign` | не исполняются: ответы сценария на переходы инцидента не влияют (§14.5). Пропускаются с предупреждением; в сценариях эталонного набора запрещены проверкой | в8 |
| `timers`, `concurrency` | не исполняются: нормативы, лимиты и одновременную работу ведёт машина инцидента | в8 |
| Данные инцидента в условиях | нет: в условиях видны только ответы (`state`), как в спецификации, раздел 7. Отвечать разрешает машина инцидента (`scenarioEdit`), запускать макросы — условия `run_macro` | в9 |
| Переоткрытие | прогон сохраняется; курсор — как при «Взять» (`setCursor`) | в10 |
| Объединение (`merge`) | «тот же сценарий» — тот же `guid`, версии могут различаться. В неотвеченные шаги основного переносятся ответы привязанного на шаги с тем же `id` и типом, если значение допустимо в версии основного; путь основного пересчитывается: если текущий шаг основного получил ответ, прогон идёт дальше по перенесённым ответам — в `history` основного это ответы в момент объединения с прежним `by`; макросы и отчёт не повторяются (уже были в привязанном), `finish` — да. Пропущенные шаги не переносятся. У привязанного прогон остаётся историей | в11 |
| Проверка ответа | по типу шага: вариант из списка; у Checkbox — без повторов, число между `minSelected` (у обязательного — не меньше одного) и `maxSelected`; у Comment — обязательный не пустой, длина между `minLength` и `maxLength`; у Datetime — формат по `kind` и границы `min`, `max`; у Image — id вложений этого шага, не больше одного без `allowMultiple`. Comment «только для показа» (`readonly`) ответа не имеет: «Далее» его подтверждает, в `state` — `null`. runner-web пропускал пустой обязательный Comment без `minLength` — в МИ нет | в7 |
| Ответ не на шаг пути | отказ. Ответить можно на текущий шаг и на пройденный шаг пути с `editable` | в7 |
| Шаг без переходов; переход на несуществующий шаг; `default` без `goto` и `finish` | шаг без переходов — конец прогона, как в runner-web. Переход на несуществующий шаг — остаёмся на шаге с предупреждением (runner-web перешёл бы на него и сломал прогон). `default` без `goto` и `finish` — остаёмся, как в runner-web. Все три в сценариях МИ запрещает проверка | в8 |
| Путь | восстанавливается по `history`: ответ на шаг пути и события того же ответа решают, остаётся хвост пути или заменяется. Своего поля для пути в прогоне нет — формат не меняется | в7 |
| Типы шагов | все семь. `Image`: источник `operator` — файл в прогоне (`attachments`, `dataBase64`), `fixed` — картинка сценария, `camera` и `map` — снимок-заглушка прототипа | в15 |

## Стык с машиной инцидента

Связь двух машин — только через функции стыка (§14.5). Исполнитель машины инцидента зовёт их через `ctx` и об устройстве сценария не знает.

| Функция | Направление | Что |
|---|---|---|
| `scenarioEdit` | инцидент → сценарий | можно ли сейчас отвечать на шаги; нельзя — прогон открыт на просмотр |
| `stepsFilled(набор)` | сценарий → инцидент | выполнен ли набор: `closing` — прогон завершён, `none` — всегда |
| `progress` | сценарий → инцидент | «N из M» и номер текущего шага |
| `setCursor` | сценарий → инцидент | курсор на текущий шаг прогона: «Взять», «Принять», «Возобновить», «Перехватить», «Переоткрыть» |
| `shareAnswers` | сценарий → инцидент | ответы привязанного — основному при объединении |
