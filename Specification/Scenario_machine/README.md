# Машина сценариев

Сценарий обработки — пошаговая инструкция оператору под тип события: что подтвердить, как классифицировать, что запустить. Сценарии ведёт отдельная машина состояний — эта. Машина инцидента ([Workflow_machine](../Workflow_machine/README.md)) её не заменяет и в неё не встраивается: две машины соприкасаются только в стыке, §14.5 [правил](../State_rules/States%20rules%20IM.md).

Формат сценария — формат редактора сценариев продукта (`incident-manager`, `scenario.zod.ts`): что сохраняет редактор, то исполняет машина. Описан спецификацией и схемой формата сценария v1, перенесёнными из `incident-manager-dsl` (решение ARCH-06 в1) и 2026-10-19 приведёнными к формату редактора. Откуда и с какого коммита — [ORIGIN.md](ORIGIN.md), что менялось — [CHANGELOG.md](CHANGELOG.md). Формат прохождения (`scenarioResult`) у редактора не описан — его задаёт МИ, здесь.

## Машина как автомат

Прохождение — одно прохождение сценария в одном инциденте: сценарий, его версия, ответы и текущий шаг. Хранится как `scenarioResult` (спецификация, раздел 9): `state` — последний ответ на каждый шаг, `history` — журнал без правок, `currentStepId` — текущий шаг, `completedAt` — время завершения.

| Состояние прохождения | Признак |
|---|---|
| идёт | `currentStepId` — шаг, `completedAt` — `null` |
| завершено | ответ на финальный шаг (`finish: true`): `currentStepId` — `null`, `completedAt` задан |

Событие одно — ответ на шаг. Обязательный шаг нельзя оставить пустым; необязательный можно пропустить — пишется `skipped: true` (какие шаги обязательны — спецификация, раздел 9). Ответ на финальный шаг завершает прохождение, его переходы не читаются. У остальных правила проверяются сверху вниз — только у RadioButton, Checkbox и Select, — срабатывает первое с истинным условием, иначе `default` (спецификация, раздел 7): запускается его макрос, затем переход на `goto`. Условие — JSONLogic из белого списка операторов над ответом своего шага: `{ value }`, `{ selected }` или `{ <id списка>: [...] }`.

## Профиль МИ

Как МИ исполняет машину. Формат сценария здесь не меняется: где спецификация молчит или формат редактора задаёт то, чего МИ не делает, записано, как поступает МИ. Решения — ARCH-06 в [плане](../../reviews/2026-10-19/plan.md) и сведение с форматом редактора ([CHANGELOG.md](CHANGELOG.md)), 2026-10-19.

| Вопрос | Как в МИ | Решение |
|---|---|---|
| Где исполняется | на сервере МИ, как машина инцидента: путь, курсор, прогресс, переходы, макросы и проверку ответа считает сервер, клиент показывает шаги пути и отправляет ответ на один шаг (`POST …/scenario/answer`, README машины инцидента). П7 спецификации («сервер не разбирает `script`») — про хранение сценария на сервере продукта, не про исполнение | решение joynickray 2026-10-20 |
| Идентичность и версия | `guid` и `version` — строки сценария на сервере; `scenario.id` и `scenario.version` в сценарии с ними совпадают. Инцидент ссылается на сценарий и версию, как в контракте сервера (`scenarioGuid`, `scenarioVersion`, `scenarioResult`) | в1 |
| Когда создаётся прохождение | при появлении инцидента (`create`); версия — актуальная в этот момент и закреплена за инцидентом. Новая версия сценария открытые инциденты не трогает: они доигрывают на своей, переоткрытый — тоже | в4 |
| Набор обязательных шагов `closing` | выполнен, когда прохождение завершено — отвечен финальный шаг. Обязательные шаги пройденного пути при этом отвечены: без ответа на них переход не срабатывает. Набор `none` выполнен всегда. Других наборов нет: в формате их не задать | в5 |
| Курсор | на текущем шаге прохождения — первом неотвеченном на пройденном пути; у завершённого — на последнем шаге пути | в5 |
| Прогресс «N из M» | N — пройденные шаги пути, M — N плюс кратчайший путь от текущего шага до финального. У завершённого N = M. При ветвлении M может меняться | в6 |
| Шаги впереди | кратчайший путь от текущего шага до финального, без текущего (`ahead`): тот же обход, что для M, поэтому путь и шаги впереди вместе — M. У завершённого — пусто. Карточка показывает их серым | RULE-95 |
| «Назад» и переответ | «Назад» показывает предыдущий шаг пути. Шаг с `revisitable: true` можно переответить, после этого переходы проверяются заново. Если путь пошёл по другой ветке, ответы шагов, выпавших из пути, убираются из `state` и остаются в `history`. Макрос перехода при повторном ответе запускается снова. Шаг с `revisitable: false` после ответа — только для просмотра | в7 |
| `macro` исхода | запуск макроса МИ — внешний эффект с записью в журнал инцидента и событием `macro` в `history`; только если выполнены условия кнопки «Запустить макрос» машины инцидента (`navActions.run_macro`). На исходе один макрос; несколько действий — составной макрос площадки | в8, CHANGELOG |
| Финальный шаг (`finish: true`) | ответ на него завершает прохождение, переходы и макрос шага не читаются. Инцидент не закрывает: итог инцидента — только результат закрытия (§2.2); карточка переходит на «Итог» — после финального шага, вне сценария: там закрывают с «Обработан» кнопкой «Завершить инцидент», форма не открывается (§7) | в8, в18, решение 2026-10-20, CHANGELOG |
| Флаги `report`, `multitasking` | не исполняются: в редакторе продукта их на экране нет, смысла для МИ у них нет | CHANGELOG |
| Эскалация, назначение, сроки | в сценарии их нет: нормативы, эскалацию, передачу и одновременную работу ведёт машина инцидента | в8, CHANGELOG |
| Данные в условиях | только ответ своего шага (спецификация, раздел 7): ни других шагов, ни данных инцидента. Отвечать разрешает машина инцидента (`scenarioEdit`), запускать макросы — условия `run_macro` | в9 |
| Переоткрытие | прохождение сохраняется; курсор — как при «Взять» (`setCursor`) | в10 |
| Объединение (`merge`) | «тот же сценарий» — тот же `guid`, версии могут различаться. Ответы привязанного переносятся только в шаги пути основного, по мере продвижения (BUG-87): текущий шаг основного получает ответ привязанного на шаг с тем же `id` и типом, если значение допустимо в версии основного, и прохождение идёт дальше; у следующего шага пути ответа нет — перенос кончается. Шаг вне пути или впереди такого разрыва не заполняется: иначе «N из M» и набор «закрытие» расходились бы с пройденным — в `history` основного это ответы в момент объединения с прежним `by`; макросы не повторяются (уже были в привязанном), конец — да. Пропущенные шаги не переносятся. У привязанного прохождение остаётся историей | в11 |
| Проверка ответа | по типу шага: RadioButton — вариант из списка; Checkbox — без повторов, число между `minSelected` и `maxSelected`; Select — объект списков шага, в каждом — варианты этого списка без повторов, у обязательного — в каждом списке хоть один; Comment — обязательный не пустой, длина между `minLength` и `maxLength`; Datetime — дата и время ISO-8601 с часовым поясом (без пояса — отказ `format`), границы `min`, `max`, хранится в UTC до секунды (BUG-72); Image — id вложения этого шага. Comment «только для показа» (`readonly`) ответа не имеет: «Далее» его подтверждает, в `state` — `null` | в7, CHANGELOG |
| Ответ не на шаг пути | отказ. Ответить можно на текущий шаг и на пройденный шаг пути с `revisitable` | в7 |
| Переход на несуществующий шаг; `goto: null` не у финального шага | остаёмся на шаге с предупреждением. Оба в сценариях запрещает проверка (`INVALID_GOTO`, `GOTO_NULL_WITHOUT_FINISH`) | в8 |
| Значения по умолчанию | у шага, на который ещё не отвечали, карточка открывает поле заполненным; ответом оно становится по «Далее» | CHANGELOG |
| Путь | восстанавливается по `history`: ответ на шаг пути и события того же ответа решают, остаётся хвост пути или заменяется. Своего поля для пути в прохождении нет | в7 |
| Типы шагов | все семь. `Image` — необязательный, вложение одно: источник `operator` — файл в прохождении (`attachments`, `dataBase64`), `fixed` — показать картинку `image`, `camera` и `map` — снимок-заглушка прототипа. `Datetime` — всегда дата и время, ответ — момент в UTC | в15, CHANGELOG |

## Проверка

Что не ловит схема — `tools/check_scenarios.py`, для сценариев набора это ошибки:

| Проверка | Откуда |
|---|---|
| `NO_FINISH_STEP`, `EMPTY_INITIAL_STEP`, `INVALID_INITIAL_STEP`, `EMPTY_STEP_ID`, `DUPLICATE_STEP_ID`, `EMPTY_STEP_TITLE`, `INVALID_GOTO`, `GOTO_NULL_WITHOUT_FINISH`, `STEP_NOT_REACHABLE`, `DUPLICATE_OPTION_ID`, `CHECKBOX_MIN_EXCEEDS_OPTIONS`, `CHECKBOX_MAX_LESS_THAN_MIN`, `CHECKBOX_MAX_EXCEEDS_OPTIONS`, `INVALID_CONDITION_OPTION_ID`, `INVALID_CONDITION_LIST_KEY` | редактор продукта (`validation.ts`), те же коды |
| правила у Comment, Datetime, Image, Message — исполнитель их не читает | МИ |
| оператор не из белого списка; `var` — не ответ своего шага | МИ, спецификация, раздел 7 |
| значение по умолчанию — не вариант шага или списка; список Select повторяется | МИ |
| из достижимого шага не дойти до финального | МИ |
| правило не срабатывает ни при каком ответе или заслонено более ранним; `default` не срабатывает — перебором ответов своего шага | МИ (PROC-28) |
| у финального шага макрос или правила — переходы финального шага не читаются, они не исполнятся; редактор продукта их не прячет | МИ (RULE-96) |

## Стык с машиной инцидента

Связь двух машин — только через функции стыка (§14.5). Исполнитель машины инцидента зовёт их через `ctx` и об устройстве сценария не знает.

| Функция | Направление | Что |
|---|---|---|
| `scenarioEdit` | инцидент → сценарий | можно ли сейчас отвечать на шаги; нельзя — прохождение открыто на просмотр |
| `stepsFilled(набор)` | сценарий → инцидент | выполнен ли набор: `closing` — прохождение завершено, `none` — всегда |
| `progress` | сценарий → инцидент | «N из M» и номер текущего шага |
| `setCursor` | сценарий → инцидент | курсор на текущий шаг прохождения: «Взять», «Принять», «Возобновить», «Перехватить», «Переоткрыть» |
| `shareAnswers` | сценарий → инцидент | ответы привязанного — основному при объединении |
