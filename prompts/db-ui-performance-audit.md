# Инспекция скорости: база данных, API и клиент оператора на миллионной базе

- **Дата:** 2026-11-09.
- **Коммиты:** IM `fccc650`, сервер `c3d6b33`, конфигуратор и клиент `51226ca` (ветка `feature/im_operator` у всех трёх).
- **Для кого:** ИИ-агенты с доступом к репозиториям, оболочке и стенду (Claude Code или похожие).
- **Зачем:** найти, что на самом деле тормозит рабочее место оператора на базе в миллион инцидентов — в базе, в API сервера и в клиенте, — и дать план ускорения. Индекс ускоряет чтение, но замедляет каждую вставку и обновление: нельзя ускорить одно, сильно ухудшив другое.
- **Что устаревает:** цифры данных стенда, номера миграций, список уже сделанного. Перед запуском сверить с нынешним состоянием.

## Как запускать

Работы три разных вида: база (планы запросов, индексы, цена записи), API сервера (что делает сервер между запросом и базой) и клиент (что делает браузер). Если всё дать одному агенту, ему не хватит контекста, и он будет поверхностным. Поэтому работа идёт в три этапа, пятью агентами:

1. **Карта нагрузки (К).** Один агент составляет общую карту: какие вызовы API и запросы к базе делает рабочее место при каждом действии оператора и в покое. Карта — основа для остальных, чтобы все трое разбирали одно и то же.
2. **Разбор (Б, А, У).** Три агента, у каждого своя часть:

   | Роль | Часть | Что делает |
   |---|---|---|
   | Б | База | Планы запросов из карты, индексы, цена записи, лишние индексы, варианты кроме индексов |
   | А | API сервера | Время ответа по частям: проверка токена, права, обращения к базе, машина, JSON; транзакции и блокировки, пул соединений, живые обновления |
   | У | Клиент | Повторные запросы, водопады, перерисовки, размер ответов, время от клика до экрана |

   Каждый получает общую часть, свой промпт и карту. Друг друга они не видят.

   **Запускать по очереди, а не одновременно.** Все трое замеряют на одном стенде, и параллельная нагрузка испортит чужие цифры. Читать код можно одновременно, замерять — нет.
3. **Сведение (С).** Один агент получает общую часть, свой промпт, карту и три отчёта. Он сводит их в один план: убирает повторы, сталкивает предложения, которые мешают друг другу, и раскладывает их по этапам.

Результаты — в `reviews/<дата>/performance/`:

| Файл | Агент |
|---|---|
| `map.md` | К |
| `db.md` | Б |
| `api.md` | А |
| `client.md` | У |
| `plan.md` | С |

Порядок папок — [reviews/README.md](../reviews/README.md). Решения из таблицы сведения принимаете вы.

````markdown
### Что за система

МИ принимает события от устройств (датчики, камеры, тревожные кнопки), по правилам создаёт из них инциденты, а операторы ведут инциденты по машине состояний: взял в работу, отложил, передал, закрыл. Рабочее место оператора — очередь инцидентов, карточка инцидента со сценарием шагов, живые обновления по SSE. Администратор работает в конфигураторе: правила, сценарии, аудит, журнал событий.

Жалоба: на базе в миллион инцидентов рабочее место оператора отвечает не мгновенно, с небольшими задержками. Нужно найти все такие места и убрать задержки, насколько получится.

**База стенда.** Postgres в контейнере `ac_db.*`, база `imdb`. Версия старая: нет `gen_random_uuid()`, поэтому сначала выясни версию и что она умеет. Доступ:

```bash
C=$(sg docker -c "docker ps --format '{{.Names}}'" | grep '^ac_db\.')
echo "SELECT 1" | sg docker -c "docker exec -i $C psql -U im -d imdb -tA"   # пользователь сервера
# суперпользователь (настройки, pg_stat_statements, auto_explain): -U postgres
```

Журнал медленных запросов уже включён: `ALTER DATABASE imdb SET log_min_duration_statement = 300`. Читать: `sg docker -c "docker logs --since <время> $C"`. Сервер ходит подготовленными выражениями, поэтому в журнале часто видно только имя `stmtcache_…`, а текст — в строке, где это выражение встретилось первый раз.

**Перед любой записью в базу** сними дамп: `docker exec $C pg_dump -U im imdb | gzip -1 > ~/Work/stand/backup/imdb-before-<что>-<дата>.sql.gz`.

### Данные на стенде

Примерно, на 2026-11-09:

- 100 сценариев;
- около 1,17 млн событий за 180 дней, из них около 970 тыс. с инцидентом;
- около 970 тыс. инцидентов, из них 500 новых, остальные закрыты;

- размер базы около 3,5 ГБ.

Данные синтетические:
- источник, тип и `raw_data` событий взяты по кругу из 168 настоящих событий;
- у инцидентов нет результатов сценария (`scenario_result`), то есть без снимков;
- журнал действий содержит только «взял» и «закрыл» от операторов 1 и 2.

Учитывай это, когда переносишь выводы на настоящую нагрузку. Если для вывода нужны данные другой формы — например, много открытых инцидентов, длинные цепочки слияний или крупные `scenario_result`, — скажи это и опиши, как их получить. Сам не заливай.

Фоновое удаление по сроку хранения стирает старые записи: число строк со временем убывает.

### Ограничения

- Правило поведения меняется в правилах и машине, а не только в коде. Если ускорение меняет видимое поведение — например, приблизительное число вместо точного или задержку счётчиков, — так и пометь: «нужно решение».
- Изменение контракта API — только предложением с пометкой «нужно решение»: контракт меняется в `openapi.json` и правилах.
- Разные организации (`customer_guid`) не должны видеть данные друг друга. Ни одно ускорение не должно обходить этот фильтр.
- Удаление по сроку хранения (§14.11) и аудит (§12.4) должны работать как прежде.
- Не трогай `vendor/`, сгенерированные файлы и архив правил.
- Ничего не коммить.

### Как замерять и писать

- Каждую цифру подтверди замером, который можно повторить: команда или запрос, параметры, время. Догадку пометь как догадку.
- Стенд — виртуальная машина, на ней же облако. Повтори замер не меньше трёх раз и бери среднее значение (медиану). Если разброс большой, напиши об этом.
- Отчёт — один файл Markdown на русском, простыми словами, в файл своей роли (раздел «Как запускать»).
- Находку оформляй так:
  - где: файл и строка или имя запроса;
  - замер «сейчас»;
  - причина по плану запроса или профилю;
  - предложение;
  - ожидаемый выигрыш;
  - цена: для записи, памяти, сложности;
  - риск.
- В конце отчёта — раздел «Что не удалось проверить и почему».
````

## К — карта нагрузки

````markdown
Твоя роль — К: общая карта нагрузки. По ней дальше работают три агента (база, API, клиент), поэтому карта должна быть полной и точной, а не глубокой. Оптимизаций не предлагай.

Перечисли, какие вызовы API и запросы к базе делает рабочее место оператора:

- при входе;
- на очереди в покое, включая опрос и SSE;
- при открытии карточки;
- при каждом действии — взять, ответить на шаг сценария, отложить, передать, закрыть, связать, слить;
- при приходе нового события.

Источники:
- **клиент:** `src/operator/api/queries.ts`, `refetchInterval`, обработчики SSE, сброс кэша `invalidateQueries`;

Отдельно перечисли фоновые задачи сервера: таймеры SLA, эскалации, срок хранения, приём событий. Для каждой укажи, как часто она идёт и какие запросы делает.

Если включаешь `pg_stat_statements`, прогони `load.py` двумя операторами минут на 10. Сними итог (вызовов, суммарно, в среднем) и выключи статистику.

Верни `map.md`:

1. **Таблица:** действие → вызовы API (метод и путь) → запросы к базе на каждый вызов (имя функции в `storing` и коротко суть) → сколько раз → время сейчас.
2. **Фоновые задачи** — такой же таблицей.
3. **Десять самых дорогих запросов** по суммарному времени за прогон.
4. **Расхождения кода с делом:** запрос есть в коде, но не идёт, или идёт чаще, чем ждёшь.
````

## Б — база данных

````markdown
Твоя роль — Б: база данных. Тебе дана карта нагрузки (`map.md`). Разбирай запросы из неё. Запросы, которых в карте нет, но которые ты нашёл в журнале Postgres, добавь и отметь.

1. **Планы.** Для каждого заметного запроса — `EXPLAIN (ANALYZE, BUFFERS)` с настоящими параметрами из журнала. Причину медленности пиши по плану: полный проход по таблице, неподходящий индекс, сортировка на диске, соединение миллиона строк.

   - переписывание запросов;

   - разбиение таблиц по времени;

4. **Блокировки.** Ожидание блокировок под `load.py` (`pg_stat_activity.wait_event`, `pg_locks`): какие запросы ждут и кого.
````

## А — API сервера

````markdown
Твоя роль — А: API сервера в связке с базой. Тебе дана карта нагрузки (`map.md`). Планы запросов и индексы — работа другого агента; ты разбираешь, что делает сервер вокруг базы.

Для каждой операции из карты разложи время ответа на части:

- **Обращения к базе.** Сколько запросов уходит на один вызов API. Нет ли N+1, когда в цикле по строкам читаются названия, права или связанные инциденты. Можно ли собрать их в один запрос или прочитать заранее.
- **Время вне базы:**
  - проверка токена в облаке на каждом запросе: есть ли кэш и сколько она стоит;
  - вычисление прав: правила доступа и дерево групп объектов (`ClosurePairs`);
  - исполнение выражений CEL машины на каждый инцидент списка;
  - сборка и размер JSON.
- **Транзакции.** Сколько держится транзакция перехода и блокировка семьи инцидента. Не идут ли внутри неё сетевые вызовы или тяжёлые вычисления. Что происходит, когда два оператора действуют одновременно.
- **Пул соединений.** Размер пула и не кончается ли он под нагрузкой `load.py`: тогда запросы ждут свободного соединения, хотя база простаивает. Нет ли повторной подготовки выражений.
- **Живые обновления.** Сколько работы сервер делает на одно изменение инцидента для SSE и `stream_events`. Не читает ли он заново очередь или счётчики для каждого подключённого оператора. Как это растёт с числом операторов: замерь на двух и оцени на двадцать.

Замер — по журналу сервера, временным меткам или профилю Go (`pprof`, если подключён; если нет — скажи, как подключить, и подключи только во временной сборке, не в коде репозитория).

Что можно поменять в API, если это даёт выигрыш:
- объединить вызовы, которые клиент всегда делает парой;
- отдавать список без тяжёлых полей;
- условные запросы (`ETag`, версия);
- присылать по SSE изменения вместо сигнала «перечитай».

Верни `api.md`:
- для трёх самых частых действий (открыть очередь, взять, закрыть) — таблица «сеть → проверка токена → права → база (по запросам) → машина → JSON → итог» и сверка суммы со временем, которое видит браузер;
- находки;
- предложения по контракту — отдельным списком, с пометкой «нужно решение».
````

## У — клиент

````markdown
Твоя роль — У: клиент оператора в браузере. Тебе дана карта нагрузки (`map.md`). Сервер и базу не разбирай: твоё — от ответа сервера до готового экрана и то, сколько запросов клиент вообще шлёт.

Найди:
- лишние повторные запросы, например после SSE перечитывается то, что уже пришло;
- водопады: запрос ждёт другой, хотя мог идти сразу;
- перерисовку всей очереди на каждое событие SSE (React Profiler, счётчик отрисовок);
- отсутствие виртуализации длинных списков;
- тяжёлые вычисления при отрисовке;
- размер ответов и разбор JSON (например, `scenario_result` со снимками в списке);
- первую загрузку: размер сборки, время до готового рабочего места.

Замерь время от клика до готового экрана по основным действиям: открыть очередь, сменить фильтр, открыть карточку, взять, ответить на шаг, закрыть. Отдельно покажи, сколько из этого времени ушло на ожидание сервера, а сколько на работу браузера. Замер — puppeteer на стенде (`~/Work/stand/ui-check/`, `lib.mjs`), трассировка производительности Chrome.

Верни `client.md`:
- таблица «действие → запросов → ожидание сервера → работа браузера → итог»;
- находки;
- что можно сделать без изменения API, а что требует его изменения — отдельно.
````

## С — сведение

````markdown
Твоя роль — С: сведение. Тебе даны карта (`map.md`) и три отчёта: база (`db.md`), API (`api.md`), клиент (`client.md`). Новых замеров не делай, кроме проверки спорных цифр. Если цифры двух отчётов о одном и том же расходятся, перемерь сам и запиши, чья верна.

1. **Убери повторы.** Одна и та же проблема, увиденная с разных сторон, — одна находка со ссылками на все отчёты.
2. **Столкни предложения.** Индекс, который ускоряет чтение, но замедляет запись, которую нашёл другой агент. Кэш на сервере, который ломает живые обновления. Изменение API, которое делает ненужной правку клиента. Каждое столкновение — строкой с выбором и причиной.
3. **Отбрось лишнее.** Выигрыш меньше разброса замера — не находка.

Верни `plan.md`:

1. **Итог в пяти строках:** что тормозит больше всего и что даст больше всего выигрыша.
2. **Где теряется время** по трём частым действиям: база, сервер вне базы, браузер — одной таблицей из трёх отчётов.
3. **Индексы:** итоговый список добавить и убрать, баланс для потока 50 событий в секунду.
4. **План по этапам.** Сначала то, что дешевле и даёт больше. У каждого этапа:
   - что сделать и в каком репозитории;
   - ожидаемый выигрыш;
   - как проверить: какой замер повторить и какой тест сервера или клиента должен пройти;
   - нужен ли перенос данных.
5. **Таблица решений** — всё, что помечено «нужно решение»: суть, варианты, твоя рекомендация. Решение принимает человек.
6. **Что не удалось проверить** — из всех отчётов, плюс выводы, которые на синтетических данных могут не подтвердиться.
````
