# Incident Manager (МИ)

Проработка нового приложения **Axxon Incident Manager** — рабочего места оператора для обработки инцидентов от систем видеонаблюдения и охраны. Репозиторий содержит продуктовые документы и работающий прототип интерфейса оператора.

Всё содержимое — материалы этапа проектирования: требования, правила жизненного цикла инцидента и кликабельный прототип для согласования. Production-кода здесь нет.

### Что показывает прототип

Очередь с фильтрами и группировкой по объектам, взятие инцидента в работу, пошаговый сценарий обработки с обязательными шагами, приостановку и возобновление, передачу с выбором адресата, перехват чужого инцидента, групповую обработку, нормативы реакции с обратным отсчётом, перерыв оператора, горячие клавиши, светлую и тёмную темы. Видеомонитор и планы объектов нарисованы примерами прямо в файле, поэтому прототип работает без сервера и без доступа к камерам.

### Как связаны документы

Видение задаёт требования. Правила превращают их в жизненный цикл инцидента. Как правила к этому пришли, видно по архиву: первая версия, её разбор с противоречиями, вторая версия, которая их устраняет, третья, где «Эскалация» и «Перенаправить» слились в одну передачу, четвёртая с закрытием без сценария для массовых сбоев, пятая — одно «Закрыть» с результатом, роли вне МИ и машина состояний как источник истины, шестая — уточнения о владельце и адресате-группе, седьмая — решения открытых вопросов и сценарии отдельной машиной. Пятая, шестая и седьмая — теги `rules-v5`, `rules-v6` и `rules-v7` действующего файла.

Машина состояний — те же правила в виде конфигурации, которую исполняет сервер, и API для клиента. Прототип устроен так же, как продукт: интерфейс разговаривает только запросами из `openapi.json`, а отвечает ему встроенный сервер в той же вкладке (`prototype/server.js`), который исполняет машину (`prototype/engine.js`). Своей таблицы переходов у прототипа нет, поэтому прототип и машина не расходятся, а самопроверка сверяет ответы встроенного сервера со схемами контракта. Когда появится бэкенд, интерфейс подключается к нему адресом `?api=https://…`.

Прототип исполняет машину состояний и соответствует v7. Где он отступает от правил — в §17 правил.

## Термины

Полный словарь с расшифровкой сокращений — в §1 [правил](Specification/State_rules/States%20rules%20IM.md). Коротко: **МИ** — менеджер инцидентов, **SLA** — отведённое время на реакцию и на закрытие инцидента, **сценарий** — пошаговая инструкция обработки под тип события, **передача** — отдать инцидент адресату (своё или чужое — одно действие, разные права), **закрытие без обработки** — закрыть без сценария по праву, **автоэскалация** — системная передача по таймеру, **перехват** — изъятие инцидента у работающего оператора.

## Как посмотреть прототип

Откройте `prototype/index.html` в браузере. Нужен интернет — из сети подгружаются шрифты Inter и Material Symbols; без него всё работает, но иконки будут показаны текстом.

Полезное при первом запуске:

- `?` — список горячих клавиш;
- `F1` — регламент обработки инцидента;
- кнопка солнца в правом верхнем углу — переключение светлой и тёмной темы;
- меню оператора справа сверху — перерыв и предвыбор адресата передачи;
- через 10–30 секунд коллеги начнут разбирать события из очереди — так видно поведение чужих инцидентов и работу перехвата.

## Проверки

- `prototype/index.html?selftest` — самопроверка: прототип сам проходит основные переходы (взять, закрыть, отложить, передать, принять и другие), сверяет ответы встроенного сервера со схемами `openapi.json` и показывает отчёт. Если шаг упал, шаги, которые продолжают работу с его инцидентом, помечаются SKIP с причиной, а остальные выполняются как обычно. После прогона демо-данные во вкладке изменены — для чистого прототипа откройте страницу без `?selftest`.
- `tests/api.html` — тесты API: открывается двойным кликом. Сценарии «запрос → новое состояние, владелец, таймеры, журнал, коды ошибок» по каждому правилу и случайные прогоны с проверкой инвариантов модели; ответы сверяются со схемами `openapi.json`, каждый маршрут встроенного сервера покрыт тестом. Время в тестах управляемое: автоэскалация и нарушения нормативов проверяются без ожидания. Свои зёрна прогонов — `tests/api.html?seeds=1,2,3&steps=300`. Это исполняемая спецификация: тесты ходят только по API, данные сбрасывают и время сдвигают служебными операциями тестового стенда, поэтому тот же набор проверяет бэкенд — `tests/api.html?api=https://адрес-стенда` (README машины, «Тестовый стенд»).
- `python3 tools/build_workflow.py` — собрать `prototype/workflow.js`, `openapi.js` и `fixture.js` из машины, контракта и эталонного набора после их правки. `--check` — проверить, что файлы не отстали (так делает CI).
- `python3 tools/check_machine.py` — целостность машины состояний: переходы ссылаются на существующие состояния, формы, условия, эффекты, права и таймеры, API совпадает с моделью; интерфейс говорит только с API, а код прототипа не знает значений справочников машины по имени; эталонный набор данных цел. Смысл правил не проверяет.
- `python3 tools/check_mutations.py` — правила только в машине: в копии прототипа по одному меняются правила машины, и проверяется, что прототип ведёт себя по-новому. Если нет — правило продублировано в коде прототипа. Около полутора минут.
- `python3 tools/check_code_mutations.py` — мутации кода: в копии по одному портится исполнитель, сервер или интерфейс (строгое сравнение вместо нестрогого, забытая проверка, таймер без остатка), и тесты должны это заметить. Выжившая порча — дыра в тестах. Около минуты.
- `python3 tools/check_i18n.py` — словари перевода: нет лишних ключей, английский и испанский совпадают. `--fix` удаляет лишние.
- `python3 tools/check_links.py` — нерабочие ссылки в документах.
- На GitHub все проверки запускаются на каждый push. Результат — значок у коммита и вкладка Actions.
