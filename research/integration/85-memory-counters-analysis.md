# Анализ: срез живых инцидентов в памяти сервера (кандидат в план 85)

Черновик для решения, не план. Повод — [план 84](84-plan-queue-load.md): после задач 1–3 главный расход базы — дерево групп со счётчиками, 43 % времени базы. Второе место — сам запрос очереди. Оба на каждом вызове проверяют правило доступа у всех живых инцидентов.

## Идея

Сервер держит в памяти **срез живых инцидентов**: по одной маленькой записи на каждый незакрытый инцидент. Срез один раз строится из базы и дальше обновляется по ленте событий (`stream_events`). Дерево, счётчики очереди и классы очереди считаются из памяти, без запросов к базе. Клиент опрашивает их в своём темпе.

## Что даёт

Цифры — из замера плана 84 после задач 1–3, срез s5, ~25 тыс. живых, 50 операторов.

| Что | Сейчас | Из памяти |
|---|---|---|
| Дерево, запрос по источникам | 4 017 вызовов за 4 мин × 93 мс ≈ 375 с базы (43 %) | 0, сумма в памяти за доли мс |
| Классы дерева и счётчиков | из кэша на 2 с | 0 и без устаревания на 2 с |
| Отбор очереди по группе устройств | замыкание дерева в SQL | готовый список источников из памяти |
| Рост стоимости с числом живых | линейный на каждом запросе | один раз при постройке, дальше по событию |

Сам запрос страницы очереди (порядок, страница, поиск) остаётся в базе. Но ему можно передать готовый список видимых инцидентов или источников вместо проверки правила у всех живых — это задача 4 плана 84 (Н-2), и с памятью она становится проще.

## Масштаб: 500 операторов вместо 50

Сегодня стоимость дерева — число операторов × частота опроса × число живых. 500 операторов × раз в 3 с × ~0,2 с на запрос при 45 тыс. живых ≈ 33 ядра базы только на дерево. Со срезом стоимость зависит от того, как часто меняются инциденты, и от числа операторов почти не зависит.

Одного дерева для 500 мало. Запрос страницы очереди тоже растёт с числом операторов: ~32 в секунду при 50, ~300 при 500, и каждый проверяет доступ у всех живых. Поэтому для 500 нужны оба шага на одном срезе: дерево и счётчики из памяти, а страница очереди — по готовому списку видимых.

Прогон на 44 тыс. живых после плана 84: время базы 1 922 с за 4 мин, из них дерево — 818 с (43 %). Ожидание, а не замер: без дерева p95 очереди упадёт примерно вдвое (с 1–2 с до ~0,5–1 с), приём под операторами вырастет к 130–160 событий/с.

## Что хранить

На каждый живой инцидент (~100 байт, 45 тыс. — около 5 МБ):
- guid, клиент;
- источник, тип источника, тип события — из `events`, после вставки не меняются;
- сценарий, приоритет (guid, значение — из справочника);
- состояние, владелец, группа назначения, `linked_to`;
- время события — для отбора и порядка, если понадобится.

Сверху — ячейки для ответа: счётчик по (источник, состояние, владелец, группа назначения, приоритет, сценарий, тип события). Видимость — по кэшу доступа плана 80: какие источники видит группа доступа. «Мои» и фильтры машины — через `QueueFilters` над ячейками, как сейчас над классами.

Закрытые в срез не входят: для них уже есть готовые счётчики `queue_closed_counts`.

## Как обновлять

1. **Постройка.** При старте и по сигналу «перестроить клиента» — один запрос: живые инциденты клиента с ключами события. Строка ленты, после которой срез построен, — курсор.
2. **По ленте.** Читатель ленты (такой же, как поток оператора, `Feed.From`) берёт новые строки после курсора. На каждую строку с guid инцидента одним запросом перечитывает ключи этих инцидентов из базы — пачкой на всю порцию строк, по первичному ключу. Затем: старая ячейка −1, новая +1. Инцидент стал закрытым или удалённым — убрать из среза.
3. **После commit, по порядку.** Лента пишется в той же транзакции под замком клиента, а id строк идёт в порядке коммитов внутри клиента. Откаченная транзакция строки не оставляет.
4. **Разрыв ленты.** `Feed.From` отвечает `ok=false`, если строки курсора нет: обрезка (1 000 строк и час), хранение, сброс. Тогда — полная перестройка клиента.
5. **Сверка.** Раз в несколько минут — полный пересчёт клиента в фоне и сравнение со срезом. Расхождение — в лог и метрику, срез заменяется пересчитанным. Это страховка от путей, которые пропустили.

Полезная нагрузка строк ленты для этого не нужна: в `transitioned` нет группы назначения и связи. Поэтому ключи всегда перечитываются из базы по guid. Это дешевле, чем расширять ленту, и не зависит от типа строки.

## Пути записи и пробелы

Обход сервера (`internal/im`, все записи в `incidents` и ключевые поля `events`):

**Покрыты лентой — строка с guid в той же транзакции:**
- приём событий (`incident.created`, `service/intake/service.go`);
- переходы машины — действия операторов, массовые действия, отсоединение, объединение, планировщик: сроки и эскалации (`Op.InTx`, `appservice/operator/feed.go`);
- `TouchIncidents`, запуски сценариев — ключей не меняют.

**Меняют ключи живого инцидента без строки ленты — надо закрыть:**

| # | Где | Что | Что сделать |
|---|---|---|---|
| 1 | Объединение: эффект `relinkToPrimary` — дети объединяемого получают новый `linked_to` | `transitionRows` (`appservice/operator/feed.go:447`) пишет строку только на **шаги** операции, а меняются все `r.Incidents` | строка `incident.updated` на каждый изменённый инцидент без шага. Это полезно и клиенту: сейчас он об этих детях не узнаёт |
| 2 | Старый API v1 `DeleteIncident` (`storing/incident_queries.go:136`) — единственный писатель `deleted_at` | мягкое удаление без строки | строка в транзакции или убрать маршрут. Проверить, зовёт ли его кто-то |

**Массовые перезаписи — нужен не построчный сигнал, а один «перестроить клиента»:**
- сброс МИ (план 83): лента клиента удаляется целиком;
- сброс и загрузка стенда (`stand/wipe.go`, `stand/load_incidents.go`): инциденты пишутся мимо ленты;
- восстановление настроек из копии: меняет приоритеты, источники, группы, сценарии. `priorities_changed` при этом сейчас не пишется — отдельная мелкая ошибка;
- смена машины (`schema_published`, `Install` на стенде): фильтры и состояния «завершено» другие, ячейки пересчитать;
- смена значения приоритета: инциденты ссылаются на guid, значение — из справочника. По `priorities_changed` перечитать справочник;
- внешние записи — скрипты нагрузки и SQL: только перезапуск или служебный сброс памяти.

Везде, где после этих операций уже вызывается `Access.InvalidateAll()`, тот же хук годится для «перестроить срез».

**Видимость без записи в инциденты** — правила доступа, состав и дерево групп. Кэш доступа плана 80 уже сбрасывается после commit во всех этих местах. Срез хранит только ключи, видимость берётся из кэша доступа в момент ответа, поэтому отдельно ничего не нужно. Что проверить: синхронизация источников агента (`appservice/sync/sync_source.go`) создаёт и удаляет источники без сброса кэша доступа. Если удалённый источник был в группе, это касается и кэша доступа уже сейчас.

## Ограничения

- **Один процесс.** Срез, кэш доступа, дерево групп и машины живут в памяти процесса. Лента общая, поэтому при нескольких процессах каждый читал бы её сам и срез оставался бы верным. А вот сбросы кэша доступа и сигналы «перестроить» — только локальные. Сегодня это и так допущение всего сервера (кэш доступа, классы, ядра), срез его не ухудшает. Запустить несколько процессов можно только после общего механизма сигналов, отдельным решением.
- **Задержка.** Срез отстаёт от базы на время доставки строки ленты — доли секунды в тишине. Под лавиной поток в плане 84 отставал до ~90 с, тогда срез будет отставать так же. Это повод сделать читателя среза отдельным, лёгким: ему не нужны строки для людей, только guid. Или поднять его приоритет.
- **Память.** ~5 МБ на 45 тыс. живых, ~100 МБ на миллион. Срез только для живых, поэтому это потолок с запасом.
- **Старт.** Постройка — один запрос по живым, при 45 тыс. — порядка секунды. До постройки ответы идут запросом, как сейчас.

## Объём и порядок (если делать)

1. Закрыть два пробела ленты (п. 1–2) — отдельно и сразу, это нужно и клиенту.
2. Срез в памяти: постройка, читатель ленты, пачечное перечитывание ключей, разрыв, перестройка по хукам, сверка с метрикой.
3. Перевести дерево на срез. Затем счётчики очереди — кэш классов плана 84 станет не нужен.
4. Запрос страницы очереди по готовому списку видимых — задача 4 плана 84.

**Тесты:** на каждый путь записи — что срез совпадает с пересчётом из базы. Сверка под нагрузкой: прогон как в плане 84, в конце — ноль расхождений.

По объёму — примерно как план 80 (кэш доступа).

## Решено

- 2026-11-13: старый маршрут `DELETE /api/v1/incidents/{guid}` **убрать**. Он удаляет и открытые инциденты мимо машины, без потока и журнала действий, а это против §14.11 правил МИ. Клиент и конфигуратор его не вызывают, вызывает только тестовая очистка `deleteAllIncidents` — ей дать свой путь (стендовый сброс или SQL в тестах). После этого `deleted_at` в рабочем коде никто не ставит.
- 2026-11-13: **сервер МИ — один процесс на базу.** Срез делается так же, как сегодняшние кэши: машина, доступ, дерево, классы. Сигналы «перестроить» — внутри процесса. Несколько процессов на одну базу — отдельное решение и отдельный план, сразу для всех кэшей.
- 2026-11-13: дерево ведёт себя в интерфейсе как сейчас — числа по всем открытым видимым, без фильтров очереди. Ничего нового для оператора срез не добавляет, меняется только то, откуда сервер берёт числа.
