# План работ: операторская часть МИ на локальном стенде

Черновик на вычитку, 2026-10-28; решения по всем 8 вопросам приняты в тот же день (таблица «Решения»). Опирается на исследование ([20-decisions.md](20-decisions.md)) и поднятый стенд ([30-local-stand.md](30-local-stand.md)). Сроков нет — только порядок, объём (S — небольшая доработка, M — заметный модуль, L — большой модуль) и признак готовности.

## Рамки

- Всё делаем сами и локально: облако, сервер МИ, конфигуратор и место оператора — на этой машине.
- Ветки — `feature/im_operator` в IM, `incident-manager-server`, `incident-manager`. Коммиты — по просьбе, push — по просьбе. В `axxoncloudgo` ветки нет; если понадобится править облако — сначала спросить.
- Облако не меняем: шлюз для разработки подменяется только на запущенном стенде.
- Источник правды по поведению — машина (`workflow_schema.v1.json`) и контракт (`openapi.json`) этого репозитория. Прототип — образец: код не переносим, повторяем поведение и проверяем теми же тестами (`tests/api.html?api=…`).
- Отложено: боевые стенды и шлюзы, публичное облако, вопросы безопасности облака (introspect, `/ac/v1`), AxxonData.

## Два потока работ

Бэкенд и фронт можно вести параллельно: у прототипа есть встроенный сервер, который отвечает по тому же контракту. Фронт сначала работает против него, потом переключается на настоящий сервер МИ.

```
Этап 1  Контракт и прототип ───────────────┬──────────────────────────────┐
                                            │                              │
Бэкенд:  2 Каркас API → 3 Данные и событие→инцидент → 4 Исполнитель машины → 5 Сессия, очередь, поток → 6 Таймеры, сценарии, журнал → 7 Справочники, схемы, /test
Фронт:   8 Точка входа /im/operator и вход → 9 Экраны оператора (против встроенного сервера, затем против сервера МИ)
                                                                                        ↘ 10 Видео и карта
```

## Этапы

### 1. Контракт и прототип — IM, S–M

Довести контракт до того, как он будет жить в облаке. Без этого и бэкенд, и фронт строятся на старых допущениях.

- Вход: схема `bearerAuth` (токен облака из `localStorage.accessToken`, обновление через `POST /api/v3/ac-backend/auth/tokens`); `prototype/api.js` — заголовок `Authorization` вместо cookie, повтор после 401.
- Поток событий `/operator/stream`: чтение через `fetch` с `Authorization` вместо `EventSource`; требования к серверу — пустой комментарий раз в 15 с, `X-Accel-Buffering: no`.
- `tools/build_workflow.py` собирает копию контракта в OpenAPI 3.0 (`openapi.v30.json`) — для генератора сервера, который 3.1 не понимает (109 мест).
- Правила §5, §8.1, §15: «роль» = группа пользователей облака; права и группы адресатов — из облака.
- Таблица «14 прав машины ↔ права облака `incident_manager.*`» в `BACKEND.md` (схема «ресурс + `use`»; `filter.edit` и `track` убрать; `manage` — не надмножество операторских прав).
- `BACKEND.md`: как сервер выбирает один инцидент и один сценарий (решение 5б ниже) — снять открытый вопрос §15 правил.

Готово, когда: быстрые проверки из `CLAUDE.md`, самопроверка и `tests/api.html` зелёные; прототип работает с `?api=https://axxonnet.test/api/v1/im-backend` хотя бы до первого ответа 501.

### 2. Каркас операторского API — сервер МИ, M

- Второй сгенерированный пакет из `openapi.v30.json`, маршруты `/operator/*` и `/test/*` на том же gin; общий вход через облако.
- Ответы-ошибки `problem+json` (только на новых маршрутах), `ETag`/`If-Match` → 412/428, идемпотентность по ключу 10 минут.
- Каталог прав сервера — 14 прав машины по таблице этапа 1; облако регистрирует их при старте.
- Быстрые исправления из исследования: принимать только access-токен (не refresh/share); права в `GET /incidents` и `/incidents/{guid}`.
- Нереализованные операции отвечают 501 — прогресс видно по `tests/api.html`.

Готово, когда: `tests/api.html` против стенда проходит вход и получает 501 на остальное; в `/me` видны 14 прав.

### 3. Данные инцидента и «событие → инцидент» — сервер МИ, L

- Таблицы под машину: номер инцидента, состояние, версия записи, владелец/адресат/дежурная группа, таймеры, причины, результат закрытия, связи, журнал, лента событий, сессии, ключи идемпотентности.
- Арендатор = установка: `customer_guid` из настроек вместо зашитого тестового.
- Создание инцидента — переход машины `create`, в одной транзакции с отметкой события; одно событие — один инцидент — один сценарий (§14.5); уникальность по `event_guid`. Исправляет найденные на стенде дубли и 500 на повтор события.

Готово, когда: `agent-emulator replay` даёт очередь как в демо прототипа; повтор события не создаёт второй инцидент и не даёт 500.

### 4. Исполнитель машины — сервер МИ, L

Самая сложная часть: сервер должен исполнять `workflow_schema.v1.json` так же, как `prototype/engine.js`.

- Условия и эффекты на CEL — библиотека `cel-go`; факты мира (`can`, `access`, `members`…) — функции Go; факты над множеством инцидентов — запросы SQL.
- Ядро: порядок проверок, `onFail`, всё-или-ничего, групповые операции, слияние.
- **Новое в IM:** выгрузка эталонных векторов из прототипа «выражение + мир → результат», чтобы сверять Go-исполнитель с JS построчно, а не только через HTTP.

Готово, когда: эталонные векторы совпадают; `tests/api.html` проходит переходы (взять, приостановить, передать, закрыть).

### 5. Сессия, очередь, поток событий — сервер МИ, M

- Сессия оператора: состояния, heartbeat, перерыв.
- Очередь: страницы, фильтры, поиск, сортировка, счётчики, выборки.
- Поток: лента в PostgreSQL, пробуждение через `LISTEN/NOTIFY`, досылка по `Last-Event-ID`, `stream.reset` при потере истории. Шлюз стенда уже без буферизации.

Готово, когда: два окна браузера под разными пользователями видят действия друг друга без перезагрузки.

### 6. Таймеры, сценарии, журнал — сервер МИ, M

- Планировщик автопереходов: нормативы реакции, автоэскалация, молчание оператора.
- Исполнитель сценариев: JSONLogic на Go по образцу Python-проверки, сверка с 1007 случаями `tests/jsonlogic-cases.js`; путь, прогресс «N из M», ответы, обязательные шаги.
- Журнал действий оператора.

Готово, когда: инцидент с нормативом сам эскалируется на стенде; сценарий из конфигуратора проходится по шагам.

### 7. Справочники, схемы workflow, тестовый стенд — сервер МИ, M

- Справочники для оператора: типы, дерево групп с устройствами, приоритеты, группы доступа, дежурные группы, связи камер, ссылки, строки.
- Схемы workflow (8 операций админки): хранение, версии, проверка как `check_machine.py`.
- `/test/*` с управляемыми часами и загрузкой эталонного набора — сборкой с отдельным тегом.

Готово, когда: `tests/api.html?api=…` против стенда зелёный целиком.

### 8. Точка входа оператора — конфигуратор, M

- Вторая точка входа Vite `/im/operator/` в том же репозитории и том же архиве; в шлюзе стенда — свой `location`.
- Один пункт меню облака `/im/`: приложение по правам открывает место оператора или конфигуратор.
- Общий HTTP-клиент для оператора и конфигуратора: обновление токена (одно на все окна), обработка 401, без своего тайм-аута бездействия.
- Общие с конфигуратором: формат сценария, JSONLogic, проигрыватели шагов из `features/preview`.

Готово, когда: `dev-login.html?to=/im/operator/` открывает пустое место оператора, токен обновляется сам, вход держится дольше срока access-токена.

### 9. Экраны оператора — конфигуратор, L

- Очередь, карточка с обработкой по сценарию, передача, приостановка, перерыв, выборка — по прототипу и новой дизайн-системе (`main`, коммит «Дизайн-система и карта экранов интерфейса оператора»).
- Сначала против встроенного сервера прототипа (поведение уже проверено), затем против сервера МИ по мере этапов 3–7.
- Проверки — снимками через `~/Work/stand/ui-check`.

Готово, когда: сценарий из руководства оператора проходится на стенде от события эмулятора до закрытия.

### 10. Видео и карта — сервер МИ и фронт, M

- Связь устройства агента с камерой облака: домен и камера у устройства (поле агента).
- Видеомонитор: по iframe `embedded.html` вебклиента на камеру, живое и архив к моменту события; проба на 4 камеры.
- Планы объектов хранить в МИ (облако их не даст); карта — mapbox с ключом из `/api/v3/ac-backend/settings`.

Нужно: VMS, подключённая к облаку стенда, — иначе видео проверить нечем.

## Риски

- **Объём этапов 3–4.** Исполнитель машины — самое большое и самое рискованное; без эталонных векторов расхождения с прототипом найдутся поздно.
- **Ветка прав облака не в `develop`.** Стенд и сервер МИ опираются на `epic/CLOUD-23284-perms-i18n`; на `develop` сервер не стартует.
- **Свой стенд расходится с боем:** подмена nginx, правило в killswitch, Debian из архива, uploader выключен. Всё записано в [30](30-local-stand.md), но боевую выкладку это не проверяет.
- **Чужой код.** Правим `incident-manager-server` и конфигуратор в своих ветках; к слиянию придётся договариваться с их командами.
- **Временное на стенде** — автоматический вход и токен Bamboo — удалить по окончании.
