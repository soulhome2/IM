Статус: **отложен** (решение 2026-11-20): план 90 — раньше. Выигрыш заметен только на большом посту в пик (около 100 операторов, 1 млн закрытых, лавина, поиск по истории); основная работа оператора — «Открытые», карточка, переходы — из памяти и уже быстрая. Решения не приняты.

**Поправка до работы (решение 3, задача 4).** Живую очередь без поиска и без типа устройства сервер отдаёт из памяти (`LiveSlice`, `answers`) — слот она не берёт. Через `heavyRead` идут только «Все» и «Выполненные», поиск и тип устройства. Поэтому делить слоты по «живые / читает закрытые» бесполезно: сверка и «следующая» на «Все» останутся за подсчётами с поиском. Признак набора — **поиск по истории** (`Search != ""` и область читает закрытые) против всего остального; `readKindOf`, тесты задачи 4 и строку решения 3 переписать так перед началом.

**Цель:** под нагрузкой 100 операторов на базе с 1 млн закрытых лёгкие запросы очереди (сверка страницы, очередь по событию потока, «следующая», «обновить») не ждут за тяжёлыми, поиск по истории отвечает быстрее, база занята не больше 5 ядер. Замер — с постоянным темпом операторов, а не «следующий запрос сразу по ответу».

**Подход:** сначала меняем нагрузку и снимаем новую базовую точку на нынешнем сервере (`de4e19b`). Потом три правки сервера по одной, у каждой — замер на спокойном стенде. В конце — повторный прогон с тем же темпом. Смысл ответов не меняется: старые тесты очереди и поиска — страховка, новые тесты сравнивают новый запрос со старым на одних данных.

**Откуда:** «Итог» и журнал (задача 8) плана [93](93-queue-big-db.md), раздел 7 замера [load-2026-11-20-plan93.md](load-2026-11-20-plan93.md). Что там выяснилось:
- хвост p95 4–8 с — это ожидание одного из 6 слотов тяжёлого чтения (p95 ожидания 3,3 с), а не сами запросы;
- дольше всех слоты держат подсчёты классов, первый по времени базы — подсчёт с поиском по истории (1 544 с за 20 мин, до 5,9 с);
- страница и подсчёт идут парой, и лёгкая страница стоит в той же очереди, что подсчёт с поиском;
- нагрузка замкнутая: чем быстрее сервер, тем больше запросов шлют операторы (переходов в A2 — 2 985, в A2-93b — 5 946), поэтому хвосты двух прогонов сравнивать нельзя.

## Что проверить особо

1. **Подсчёт с поиском = прежний подсчёт.** Инцидент, найденный двумя ветками (номер и тип события), считается один раз; привязанный, найденный поиском, даёт строку основного только если основной виден правилами; удалённое устройство не ищется; фильтры области (тип события, приоритет, узел, тип устройства, состояния) действуют внутри `found`. Тест — в задаче 2.
2. **Права в подсчёте.** Два правила на одну строку не считают её дважды; строка, которую не даёт ни одно правило, не попадает в подсчёт. Тест — в задаче 2.
3. **Узел дерева без устройств и узел в тысячи устройств.** Пустой узел — пустой список и нулевые классы, не ошибка и не вся очередь; большой узел — тот же ответ, что сейчас. Тест — в задаче 3.
4. **Короткое чтение при занятых тяжёлых слотах.** Все слоты «по истории» заняты — короткое чтение идёт сразу; отмена запроса во время ожидания освобождает его место в очереди. Тест — в задаче 4.
5. **Внутри транзакции слот не берётся** — как сейчас в `heavyRead`, для обоих наборов. Тест — в задаче 4.
