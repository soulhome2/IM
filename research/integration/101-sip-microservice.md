## Коротко

SIP подключён к облаку **не так, как МИ**:

- **Интерфейса своего у SIP нет.** Раздел SIP — это страница внутри самого портала (`axxoncloud-ui`, маршрут `/sip`). У МИ отдельное SPA на `/im/`, которое кладётся своим zip.
- **Сервер у SIP свой, но он в монорепо облака.** `sipmanager` — отдельный бинарник и docker-образ `ac/sipmanager`, но код лежит в `axxoncloudgo/sipmanager/` и собирается тем же `Makefile` облака. У МИ отдельный репозиторий и свой деплой.
- **Права SIP прописаны в коде облака.** Пространство `sip` (`sip.view`, `sip.manage`) зашито в каталог прав облака. МИ регистрирует своё пространство `incident_manager` сам при старте.
- **В `develop` облака SIP ещё нет.** Всё живёт в ветке `feature/sipmanager_microservice`; её периодически подтягивают к `develop` (последний раз 2026-10-06). Работает на стенде `sip-test1.axxoncloud.com`.

## Как устроено

```text
Браузер ── портал axxoncloud-ui, страница /sip
   │  REST, Authorization: Bearer <токен портала>
   ▼
nginx  location /api/v1/sipmanager/  →  sipmanager:9010
   │
sipmanager (Go, gin, oapi-codegen)
   ├── backend облака (S2S, без входа):
   │     POST /api/v1/auth/introspect-user-token  — кто пользователь и его права
   │     GET  /ac/v1/users-by-ids, /users-by-permissions[/search], /users/domains/permissions, /domains
   ├── своя Postgres (дерево, панели, аккаунты, подписки, общий доступ)
   ├── Kamailio HTTP API :8080 — создать/удалить абонента, статус
   └── push APNS / FCM на телефоны

Kamailio (SIP INVITE) → POST /api/v1/sipmanager/calls → push абоненту
```

### Что ветка `feature/sipmanager_microservice` меняет в самом облаке

Помимо папки `sipmanager/` (около 17 тыс. строк с моками и миграциями), ветка трогает облако так:

1. **Сборка.** `Makefile` и `local.mk`: бинарник `sipmanager_`, образ `ac/sipmanager`, цели `build-sipmanager`, `redeploy-sipmanager`, генерация кода `gen-bp-sipmanager`.
2. **Compose.** `tools/compose/anticonsul-ac.docker-stack.yml`: сервис `sipmanager` в сети `ac`, порт 9010, общий env-файл облака.
3. **Env.** `tools/env/dev.env`, `local-testing.env`: блок `SIPMANAGER_*` (адрес backend, Kamailio, база, ключи APNS/FCM).
4. **nginx.** `tools/docker/nginx.ssl.conf`, `nginx.vms.conf`, `nginx.anticonsul.conf`: `upstream sipmanager-up` и `location /api/v1/sipmanager/`.
5. **Новые S2S-маршруты backend** (`handler/s2s/init.go`, `model/urls.go`, `user_handler.go`, `service/user`, `store/postgres/user_service_queries.go`):
   - `GET /ac/v1/users-by-ids?id=…`;
   - `GET /ac/v1/users-by-permissions?permission=…`;
   - `GET /ac/v1/users-by-permissions/search?name=…&permission=…`.
   Это те самые «список пользователей по правам» и «пользователи по id», которых не хватало МИ для адресатов передачи ([12, п. 2](12-tenancy-users.md#2-служебные-api-для-адресатов-передачи-и-дежурных-групп)). В `develop` их нет.
6. **Права.** `CanManageSip()`/`CanViewSip()` у глобальной роли. Сами `sip.view`/`sip.manage` уже есть в `develop`: каталог (`model/permissions/catalog.go`, группа `sip`) и перевод старых имён `viewSip`/`manageSip` (`perms_v2.go`).

### Вход и права в sipmanager

- Токен — только из заголовка `Authorization`. Middleware на каждый запрос зовёт `introspect-user-token` и кладёт ответ в контекст.
- Проверка прав — в сервисном слое: `permissions.IsHasPerm(sip.view | sip.manage)` (в ветке облака). В `NEW/sipmanager` проверка ещё старая — булевы `canViewSip`/`canManageSip`, а их introspect облака уже не отдаёт. Значит, отдельный репозиторий **отстал** от ветки облака и сам по себе права не пройдёт.
- Тип токена (access/refresh/share) не проверяется — та же дыра, что описана для МИ ([20, риск 1](20-decisions.md)).
- `POST /calls` (от Kamailio) и `/heartbeat` — без входа пользователя.

### Боевой деплой

В `IT/axxoncloud-deploy` sipmanager упомянут только в `bamboo-specs/Cloud.yaml` — как артефакт сборки `sipmanager.img`. Шаблонов nginx с `/api/v1/sipmanager` для заказчиков там нет. У МИ, для сравнения, в боевом nginx Bezeq уже есть `/api/v1/im-backend` и `/im` ([15, п. 1](15-deploy-configurator.md)).

### Меню

`cloud-menu` знает пункт `sip` (маршрут `/sip`, подпись `page.sip`) и пространство `sip` в правах; пункт виден при `sip.view` или `sip.manage`. Это та же схема, что у `/im/` (пункт виден при любом праве пространства) — только страница открывается внутри портала, а не отдельным приложением.

## Сравнение с МИ

| | SIP (sipmanager) | МИ |
|---|---|---|
| Код сервера | в монорепо `axxoncloudgo`, ветка | свой репозиторий `incident-manager-server` |
| Сборка и образ | `Makefile` облака, `ac/sipmanager` | свой |
| Интерфейс | страница портала `/sip` (код в `axxoncloud-ui`) | своё SPA `/im/` (конфигуратор + `/im/operator/`) |
| Адрес API | `/api/v1/sipmanager/` | `/api/v1/im-backend/` |
| Вход | `introspect-user-token` на каждый запрос | так же |
| Права | `sip.*` зашиты в каталог облака | `incident_manager.*` сервер регистрирует сам (`PUT /ac/v1/global-permissions/catalog`) |
| S2S к облаку | пользователи по id и по правам — **добавлены в своей ветке облака** | только то, что есть в `develop` |
| База | своя Postgres | своя Postgres |
| Внешние системы | Kamailio, APNS/FCM | агенты на объектах, VMS |
| Статус | ветка, стенд `sip-test1`, в `develop` нет | ветки `feature/im_operator`, локальный стенд |

## Что из этого полезно МИ

1. **S2S-маршруты пользователей по правам уже написаны** — в ветке `feature/sipmanager_microservice`. Если их вольют в `develop`, МИ получит адресатов передачи и дежурных без своих обходов. Вопрос команде облака: когда вливают и можно ли забрать эти три маршрута отдельным PR раньше.
2. **Путь «сервис внутри монорепо облака»** — облако его уже применяет (monitoring, configsync, vsaasmanager, sipmanager). Для МИ он не нужен: свой репозиторий уже работает, а монорепо привязало бы выпуски МИ к выпускам облака.
3. **Права:** у SIP облако держит пространство у себя, у МИ — сервис сам. Подход МИ гибче (не нужно править облако при новом праве), но зависит от `PUT …/catalog`, которого нет в `develop` ([10, п. 1](10-permissions.md)).
4. Для [идеи единого агента](100-cloud-agent-concept.md): SIP-абоненты сейчас — телефоны, которые ходят в Kamailio напрямую; агента на объекте у SIP нет. Модуль SIP в агенте понадобится, только если панели или АТС на объекте должны управляться из облака.

## Вывод: что это за сервис и как он ложится в общую концепцию

Проверено на стенде (раздел `/sip` с правами `sip.view` + `sip.manage`) и по коду `axxoncloud-ui/app/components/Sip`, `containers/Sip`, `sipmanager/service`.

### Что раздел SIP умеет на самом деле

- Дерево папок. Папку можно создать, переименовать, перенести, удалить. **Переименовать можно только папку** (`canUpdateNode = node.isFolder`).
- Панель: кнопка «добавить». Номер, пароль и realm сервер генерирует сам. Номер — следующий по порядку, realm — `integrator-<id пользователя>.axxoncloud.local`. Все поля карточки **только для чтения**: у панели нельзя задать ни имя, ни номер, ни пароль, ни модель, ни камеру.
- Аккаунт жителя: то же, плюс email. Больше в карточке ничего нет.
- Статус панели «в сети / не в сети» — ответ Kamailio. На стенде статус берётся из заглушки.
- Общий доступ к панелям и аккаунтам для других интеграторов.

Чего нет совсем:
- **Настроек сервиса в интерфейсе.** Адрес SIP-сервера, Kamailio, ключи APNS/FCM задаются только переменными окружения при деплое.
- Журнала звонков: API есть, экрана нет.
- Открытия двери и видео с панели.
- Связи панели с камерой или устройством облака.
- Связи с доменами, сайтами, деревом устройств.
- Квартир и жильцов как сущностей: аккаунт — это просто email.
- Событий в другие сервисы, в том числе в МИ.

### Состояние разработки

- Ветка `feature/sipmanager_microservice` живёт с июля 2024. Активная разработка шла с 2024-07 по 2025-10 (два разработчика по очереди), после этого — только подтягивания к `develop` (2026-10).
- В `develop` облака не влита. В боевом деплое есть только сборка образа, маршрутов nginx у заказчиков нет.
- Работала на тестовом стенде `sip-test1` для проверки мобильных клиентов: регистрация, вызов, push.
- Копия `NEW/sipmanager` (2026-07) отстала от ветки (старая проверка прав).
- Портал из ветки прав облака (`CLOUD-23284`) пространство `sip` не знает. Раздел открывается только после правки, см. ниже.

### Оценка

Впечатление «полунедоделанного прототипа» верное. По сути это **не админка домофонии, а выдача SIP-учёток**: сервис заводит абонента в Kamailio и будит телефон push-уведомлением при звонке. Для пилота «панель позвонила — телефон зазвонил» этого хватило, для продукта — нет:

1. **Нечего настраивать.** Администратор не задаёт ни одного параметра панели или аккаунта, всё генерирует сервер. Всё, что действительно настраивается (SIP-сервер, push), — в env деплоя, вне интерфейса.
2. **Своё отдельное дерево.** Папки SIP не связаны ни с доменами, ни с сайтами, ни с деревом устройств облака. Панель домофона не видна как устройство, её камера — тоже. Это параллельный мир внутри портала.
3. **Нет сценария эксплуатации.** Нет журнала звонков, двери, состояния линий и ошибок регистрации. Оператору и администратору не на что смотреть после настройки.
4. **Не доведено до основной ветки.** Полтора года на ветке, без деплоя заказчикам; права в портале той ветки, где мы работаем, уже разошлись с SIP.

Внешний вид здесь не главный упрёк. Раздел нарисован стандартными компонентами портала (MUI, как «Устройства» и «Права пользователей»), поэтому выглядит как остальной портал. Отличается как раз МИ: у него своё приложение и свой дизайн. Слабость SIP — в содержании, а не в стиле.

### Как ложится в общую концепцию

- **Техническая схема подключения — та же, что у МИ, и она рабочая.** Отдельный сервис, вход через `introspect-user-token`, права в общем каталоге, свой маршрут в nginx, пункт в общем меню. Это подтверждает, что путь МИ правильный и общий для облака.
- **Продуктово SIP в концепцию не встроен.** Нет связи с устройствами, доменами, событиями. Для домофонии в общей экосистеме (МКД) нужно, чтобы панель была устройством облака с камерой, звонок был событием, а пропущенный или тревожный вызов мог стать инцидентом в МИ. Ничего из этого нет даже в заготовке.
- **Для МИ.** Брать из SIP стоит только три S2S-маршрута пользователей (выше). Интеграция «звонок с панели → событие → инцидент» потребует доработки sipmanager: отдавать событие звонка наружу, сейчас он только шлёт push. Для [единого агента](100-cloud-agent-concept.md) модуль SIP пока не нужен: на объекте у SIP ничего не стоит, панели ходят в Kamailio напрямую.

Что спросить у команды облака:
1. Жив ли проект SIP, будет ли ветка влита в `develop`, кто владелец?
2. Планируется ли панель как устройство облака (с камерой) вместо отдельного дерева?
3. Будут ли события звонков наружу (NATS/вебхук), чтобы МИ мог их принимать?

## SIP на локальном стенде

Поднят 2026-11-26 без пересборки облака: отдельный сервис Swarm `ac_sipmanager` из ветки `feature/sipmanager_microservice`, своя база в `ac_db`, Kamailio — встроенная заглушка, маршрут в nginx стенда. Страница `/sip` портала работает: дерево, панели, аккаунты. Подробности, ограничения и откат — `~/Work/stand/sip/README.md`.

Что пришлось обойти:
- сборка портала на стенде (ASIP-AX1047) не знает пространство прав `sip` и уводит со страницы — в собранный файл прав дописан `sip`;
- поиск интеграторов и общий доступ не работают: им нужны S2S-маршруты, которых нет в backend стенда.
