# План 96. Индексы поиска строит сервер после старта, `pg_trgm` не обязателен

> **Для агентов-исполнителей:** обязательный навык — superpowers:subagent-driven-development (рекомендуется) или superpowers:executing-plans. Шаги — чекбоксы `- [ ]`. Сервер — по superpowers:test-driven-development: сначала тест, он падает, потом код. Решения ниже приняты, их не пересматривать; чего в плане нет — не придумывать, а остановиться и спросить.

Статус: **написан** (2026-11-20), не начат.

**Цель:** сервер МИ стартует и работает и без расширения `pg_trgm`. Есть расширение — индексы поиска строятся сами, в фоне, после старта. Расширение включили позже — достаточно перезапустить сервер. В разделе «Состояние системы», блок «База», видно, используется ли индекс поиска, строится или нет и почему.

**Подход:** в миграции 081 остаётся только попытка включить расширение. Не вышло — предупреждение, а не остановка. Построение двух индексов поиска переезжает из миграции в код сервера: при каждом старте, в фоне, через `CREATE INDEX CONCURRENTLY`. Пока индексов нет, поиск идёт прежним проходом по истории (как до плана 93): находит то же, только медленнее.

**Где:**

  - выбор пути поиска — `internal/im/service/storing/queue_queries.go`, `queueNarrow` (строка `case queueSearchIndexed(scope.Search):`);
  - запуск — `internal/im/infrastructure/infrastructure.go`, `InitInfrastructure`;

  - «Состояние системы» — `internal/im/service/storing/system_status.go`, `internal/im/handler/operator/system_status.go` (`systemDatabase`), копия контракта и сгенерированный `generated/spec.go` (`make vendor-operator-contract gen-api-operator`).
- IM — контракт `Specification/Workflow_machine/openapi.json` (схема `SystemDatabase`, файл в CRLF), правила §20 (блок «База», строка ~1212), прототип `prototype/server.js` и `prototype/app.js` (`systemStatusTable`), `prototype/selftest.js`; этот план, «К выкату» плана [93](93-queue-big-db.md), `README.md` раздела.

## Почему так

Сейчас миграция 081 сначала создаёт `pg_trgm`, потом строит индексы. Если прав на расширение нет, миграция падает, и сервер не стартует. Если сделать её просто «терпимой», она запишется как выполненная без индексов. Потом расширение включат, перезапустят сервер, а индексы не появятся: выполненные миграции сервер не повторяет.

Граница, по которой делим: всё, от чего зависит **смысл** ответа, остаётся в миграциях до старта. В фоне строится только то, что влияет на **скорость**. Индексы поиска — только скорость: с ними и без них поиск находит одно и то же. Это уже проверяют тесты плана 93 («три пути находят одно»).

Время сборки на стенде (план 93, задача 2): 1 млн инцидентов и 1,07 млн событий — 2,96 с и 2,71 с, под лавиной, приём не замедлился.

## Решения

| № | Вопрос | Решение | Почему |
|---|---|---|---|
| 1 | Где создаётся расширение | Только в миграции 081, терпимо: нет прав или нет пакета → `RAISE WARNING` с подсказкой, миграция проходит. Код при старте расширение **не создаёт**, только проверяет, есть ли оно | Создание расширения — изменение схемы, ему место в миграции. Включить позже может администратор базы, у него права есть |
| 2 | Миграция 081 уже выполнена на стенде и в тестовых базах, план 93 запушен | Меняем файл 081 на месте, новую миграцию не заводим. Это безопасно и после пуша: где старая 081 прошла, индексы есть, код их найдёт и ничего не сделает; где она упала (нет прав на `pg_trgm`), она не записана в `im_db_migrations`, и выполнится новая | Сервер сверяет только имена миграций, не их текст (`checkAppliedMigrations`) |
| 3 | Когда строить | При каждом старте, в отдельной горутине, после миграций. Запросы сервер принимает сразу | Старт на большой базе не ждёт сборки |
| 4 | Два сервера стартуют вместе | Сессионная блокировка `pg_advisory_lock` с постоянным ключом на отдельном соединении. Второй ждёт первого, потом видит готовые индексы и ничего не строит | Нет двух одновременных `CONCURRENTLY` на одной таблице |
| 5 | Недостроенный индекс (сервер убили посреди сборки) | Найден `indisvalid = false` → `DROP INDEX CONCURRENTLY`, потом сборка заново | Иначе `IF NOT EXISTS` оставит нерабочий индекс навсегда, а запись его всё равно обновляет |
| 6 | Какой путь поиска выбирать, пока индексов нет | У `Store` флаг «индексы готовы». Пока он не поднят — прежний проход по истории (ветка `default` в `queueNarrow`). Флаг поднимается при старте, если оба индекса уже есть и рабочие, или после фоновой сборки | Путь через `found` без индекса может быть медленнее прежнего прохода |
| 7 | Индексы строятся по очереди или вместе | По очереди: сначала `idx_incidents_search_number`, потом `idx_events_search_alarm` | Два `CONCURRENTLY` одновременно ждут друг друга |
| 8 | Ошибка сборки | Предупреждение в журнал, сервер работает, поиск медленный, новая попытка — при следующем старте. Повторов внутри одного запуска нет | Ничего нового не ломается; повторы в цикле — лишняя нагрузка |
| 9 | Уровень журнала | `info` для «готово, построено за N с», `warn` для «нет `pg_trgm`» и ошибок | Строки `debug` в бою не видны (урок плана 93) |
| 10 | Остановка сервера во время сборки | Отдельной обработки нет: соединение закрывается, сборка обрывается, индекс остаётся недостроенным, следующий старт его чинит (решение 5) | Проще и уже покрыто |
| 11 | Что показывает «Состояние системы» | Новое обязательное поле `searchIndex` в `SystemDatabase`, строка из пяти: `ready` — индексы рабочие, поиск по ним; `building` — проверка или сборка идёт (в том числе ждём другой сервер); `no_extension` — нет `pg_trgm`; `failed` — сборка упала, повтор при следующем старте; `unknown` — фоновая проверка ещё не начиналась (только у `Store` без `InitInfrastructure`, то есть в тестах) | Пользователь (2026-11-20): видеть, используется индекс, не используется или строится |
| 12 | Чьё это состояние | Того сервера, который ответил на запрос. Блок и так помечен «общий для сервера». На нескольких серверах после сборки все приходят к `ready`: второй ждёт блокировку и видит готовые индексы | Хранить общее состояние в базе — лишняя таблица ради секунд сборки |
| 13 | Подписи на экране | Строка «Индекс поиска (pg_trgm)» после «Хватит при текущем приросте», до частей базы. Значения: `ready` — «используется»; `building` — «строится»; `no_extension` — «не используется: нет расширения pg_trgm»; `failed` — «не используется: ошибка сборки, повтор при перезапуске»; `unknown` — «нет данных». Подсказка-пояснение у `no_extension`: «Суперпользователь базы выполняет CREATE EXTENSION pg_trgm, потом сервер МИ перезапускают» | Слова — для администратора поста, без внутренних имён индексов |

## Общие ограничения

- Postgres 9.6: `CREATE INDEX CONCURRENTLY` — только вне транзакции; `DROP INDEX CONCURRENTLY IF EXISTS` есть с 9.2.
- Тексты двух `CREATE INDEX CONCURRENTLY IF NOT EXISTS` переносятся из нынешней 081 **дословно**: выражения должны совпадать с `queueNumberText`, иначе запрос не попадёт в индекс.
- Ключ блокировки — константа `searchIndexesLockKey int64 = 0x494d5f7472676d` («IM_trgm»).
- Down миграции 081 не меняется: удаляет оба индекса, расширение оставляет.
- Смысл поиска не меняется. Все тесты `queue_search_test.go` проходят, с индексами и без.
- Тесты — на `IM_TEST_DB_URL` (implementer — 55432, ревьюер — 55433), тяжёлые прогоны — под `systemd-run --user --scope -p MemoryMax=12G`.
- `ac_db` на стенде общий с облаком: не перезапускать, конфиг не менять.

## Что проверить особо

1. **Нет `pg_trgm`.** Миграции проходят, сервер стартует, поиск находит то же, что с индексами. Отчёт сборки: «расширения нет», ничего не построено. Тест — задача 1.
2. **Расширение включили позже.** Повторный вызов сборки строит оба индекса и поднимает флаг. Тест — задача 1.
3. **Недостроенный индекс.** Удаляется и строится заново, после — рабочий. Тест — задача 1.
4. **Два сервера сразу.** Каждый индекс строится ровно один раз, оба сервера в итоге с поднятым флагом. Тест — задача 1.
5. **Индексы уже есть** (стенд, где 081 прошла по-старому). Ничего не строится, флаг поднят сразу при создании `Store`, до фоновой проверки. Тест — задача 1.
6. **Состояние на экране отражает каждое из пяти значений.** Тест сервера на `systemDatabase` и тест конфигуратора на подписи — задача 3.

**Интерфейсы (что появляется):**
- `type SearchIndexesReport struct { Extension bool; Built []string; Rebuilt []string }`. `Built` — построенные с нуля, `Rebuilt` — пересобранные недостроенные, имена индексов.
- `func (s *Store) EnsureSearchIndexes(ctx context.Context, logger logrus.FieldLogger) (SearchIndexesReport, error)` — синхронная. Берёт отдельное соединение (`s.dbc.DB.Conn(ctx)`), на нём `pg_advisory_lock(searchIndexesLockKey)`. Проверяет расширение. Для каждого индекса по очереди: рабочий — пропустить; недостроенный — `DROP INDEX CONCURRENTLY IF EXISTS`, затем `CREATE`; нет — `CREATE`. В конце снимает блокировку и поднимает флаг, если оба рабочие.
- `type SearchIndexState string` с константами `SearchIndexReady = "ready"`, `SearchIndexBuilding = "building"`, `SearchIndexNoExtension = "no_extension"`, `SearchIndexFailed = "failed"`, `SearchIndexUnknown = "unknown"`. В `Store` — `atomic.Value` с текущим значением; начальное — `unknown`, или `ready`, если при создании оба индекса рабочие.
- `func (s *Store) SearchIndexState() SearchIndexState` и `func (s *Store) SearchIndexed() bool` (`== ready`). `EnsureSearchIndexes` ставит `building` в начале (до ожидания блокировки), в конце — `ready`, `no_extension` или `failed`.
- `queueNarrow(scope QueueScope, args []any, trigram bool)`. Ветка `case queueSearchIndexed(scope.Search)` становится `case trigram && queueSearchIndexed(scope.Search)`. Вызывающие передают `s.SearchIndexed()`; свободные функции между ними получают тот же параметр.
