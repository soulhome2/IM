# План 99. Два экземпляра сервера МИ на одной базе

> **Для агентов-исполнителей:** обязательный навык — superpowers:subagent-driven-development (рекомендуется) или superpowers:executing-plans. Шаги — чекбоксы `- [ ]`. Сервер — по superpowers:test-driven-development: сначала тест, он падает, потом код. Пункт из таблицы решений — в работу, только когда заполнено «Решение»; чего в плане нет — не придумывать, а остановиться и спросить.

Статус: **выполнен** (2026-11-22), решения приняты 2026-11-21. Что сделано и замеры — раздел «Итог» после задач.

**Опирается на план [98](98-coordination-seams.md):** замки, будильник ленты и лидер вынесены там за интерфейсы `Locker`, `Listener`, `Leader` пакета `service/coord`. Задачи этого плана пишут новые замки и лидера только через них, прямых `pg_advisory_*` и `LISTEN` в логике не добавляют.

**Цель:** два и больше процессов сервера МИ на одной базе за nginx, который раздаёт запросы по очереди (схема «оба активны»). Оператор видит одно и то же, на какой бы узел ни попал запрос. Ни одно действие не выполняется дважды. Упал один узел — второй продолжает без потери данных.

**Откуда:** стенд Bezeq Test2 (2026-11-20): два узла облака, dc1-c1 и dc2-c1, на каждом свой процесс `imbackend`, база общая. Nginx берёт группу `im-backend` из Consul и шлёт туда запросы по очереди ([15, п. 1](15-deploy-configurator.md#1-боевой-конфиг-шлюза-где-apiv1monitoring-есть-ли-im-и-apiv1im-backend)). INC-0002 в состоянии `new`. dc2 показывает его в «Открытых» и в счётчике, dc1 — нет (`total=0`, `open=0`). С `deviceTypeId=camera` запрос идёт в базу мимо `LiveSlice`, и dc1 тоже отдаёт 1. У оператора сработка то появляется, то исчезает.

**Причина:** сервер рассчитан на один процесс на базу (решение 2026-11-13, комментарий `LiveSlice`; ADR-005, раздел «Before the public launch»). Часть данных он держит в памяти процесса и сбрасывает её вызовом внутри процесса. Второй узел о записи не узнаёт.

## Что уже работает между узлами

- **Лента и поток.** Лента — таблица `stream_events`. Запись берёт замок `pg_advisory_xact_lock` заказчика и шлёт `pg_notify('im_stream')`, хаб слушает `LISTEN` (`storing/stream_queries.go`, `stream/hub.go`). Поток оператору приходит, с какого бы узла ни была запись.
- **Переходы инцидентов в `LiveSlice`.** Каждая запись называет инцидент в ленте в своей транзакции (Н-12), и срез дочитывает ленту перед ответом. Пока запись идёт через ленту, срезы узлов сходятся.
- **Люди и сессии** — `operator_sessions` (план 62).
- **Замки в базе:** сборка индексов поиска (план 96), сброс и восстановление (`im-backup:`), запись настроек (`lockWorkflowSettingsSQL`).

## Задачи

### Задача 1. Сброс кэшей через ленту (П1–П3)

- [x] **Шаг 1: тест с двумя экземплярами.** Помощник в `handler/test`: два `AppServices` (A и B) на одной тестовой базе, у каждого свой `LiveSlice`, `AccessCache`, дерево. Падающие тесты, по одному на путь записи мимо ленты: загрузка стенда, правка через тестовый стенд, сброс МИ, восстановление из копии, создание, правка и удаление группы устройств, состав группы, правило доступа. Запись на A — очередь, счётчики и дерево на B сразу совпадают с SQL (`IM_LIVE_SLICE=off`).
- [x] **Шаг 2: строка ленты `cache.invalidated`.** Тип в `service/stream/feed.go` с полем `kind` (`live`, `access`, `tree`, `all`). Внутренняя: `render` её не отдаёт клиентам, по ней только сбрасываются копии. Пишется последней в транзакции (как `Feed.Append`).
- [x] **Шаг 3: запись строки.** Во всех путях из шага 1 — вместо или рядом с вызовом `Invalidate`/`InvalidateAll`. Путь без транзакции (стенд пишет пачками) — отдельной транзакцией сразу после.
- [x] **Шаг 4: чтение строки.** `LiveSlice.readFeed` по строке `live`/`all` перестраивает срез заказчика. `AccessCache` и дерево — по строке `access`/`tree`/`all`: у каждой свой курсор ленты (решение 13). Перед ответом про доступ копия сверяет свой курсор с концом ленты заказчика (`Feed.Last`, одно чтение), как срез. Хаб (`service/stream/hub.go`, уведомления через `coord.Listener`) только будит сверку, данных из него копия не берёт.
- [x] **Шаг 5: дерево.** Версия дерева уже хранится в базе: таблица `source_group_tree_meta`, растёт при каждой правке (`storing/source_group_tree.go`, сброс, восстановление, загрузка стенда). Процесс читает её только при старте (`LoadAllTrees`). По строке `tree`/`all` узел перечитывает дерево и версию заказчика из базы, и `AccessCache` на B видит смену дерева на A.
- [x] **Шаг 6:** тесты шага 1 зелёные; старые тесты среза, доступа и дерева зелёные; `-race`.
- [x] **Шаг 7: замер.** Цена сверки с концом ленты на запрос очереди на стенде (план 90, 100 операторов) — не больше 1 мс p95 к нынешнему.

### Задача 2. Страж и сверка (П1–П3)

- [x] **Шаг 1: страж по коду.** Расширить `TestAccessWritesInvalidate` (план 80): каждая функция, которая пишет в таблицы инцидентов, групп, правил, настроек не через `Feed.Append` перехода, пишет строку `cache.invalidated` в своей транзакции. Новый путь без неё — тест красный.
- [x] **Шаг 2: сверка в фоне.** `IM_LIVE_SLICE_VERIFY` по умолчанию 1 мин. Нашла расхождение — сбросить срез заказчика (а не только посчитать в `Mismatches`) и написать `Warn` с числом записей. Тест: SQL руками мимо ленты на A — через одну сверку срез на B совпадает с базой.
- [x] **Шаг 3:** число расхождений — в «Состоянии системы» рядом с остальными показателями сервера.
- [x] **Шаг 4: цена сверки.** Время одной сверки на копии базы стенда (174 тыс. инцидентов) и p95 очереди под нагрузкой плана 90 с сверкой и без — в отчёт задачи 7. Сверка дольше 1 с или прибавка к p95 очереди больше 1 мс — интервал по умолчанию 5 мин вместо 1. Сверку делает каждый процесс: срез у каждого свой, сверка лидера чужой срез не исправит.

### Задача 3. Машина заказчика на всех узлах (П4)

- [x] **Шаг 1: падающий тест.** Публикация настроек поста на A — следующий переход на B идёт по новой машине (новый таймер, новый приоритет, новый сценарий).
- [x] **Шаг 2:** читатель ленты на каждом узле по строке `workflow.schema_published` вызывает `Settings.Reload(customer)`. То же после сброса МИ и восстановления из копии (строку пишут и они, проверить).
- [x] **Шаг 3:** переход, начатый на B до перечитывания, идёт по старой машине (решение 11), без новой ошибки. Закрепить тестом: публикация на A во время перехода на B — переход проходит, следующий на B идёт по новой машине.
- [x] **Шаг 4:** планировщик на B после перечитывания пересчитывает таймеры организации (как после `Load`).

### Задача 4. Лидер планировщика (П5, решение 209)

- [x] **Шаг 1: падающий тест.** Два планировщика на одной базе: за 30 тактов переходы делает только один, второй не ждёт замков строк.
- [x] **Шаг 2:** такт берёт `coord.Leader` плана 98 (в PostgreSQL — замок на отдельном соединении сессии). Не лидер — такт пропускает, пробует на следующем. Соединение порвалось — замок снят базой.
- [x] **Шаг 3:** курсор обхода доступа (план 79) и отметка последнего такта — в базе, чтобы новый лидер продолжил с того же места.
- [x] **Шаг 4:** `Restart` считает простой по отметке последнего такта лидера в базе, а не по времени остановки своего процесса.
- [x] **Правило (ADR-008, «The leader saves work, it does not guard»):** лидер — экономия, не защита. Такт должен оставаться правильным, если лидеров на миг два или такт идёт на всех узлах; от двойного действия защищают замки строк и версии. Тест шага 1 — ещё и с двумя лидерами сразу: переходов не больше, чем с одним.
- [x] **Шаг 5: тест переключения.** Лидер остановлен — второй узел берёт такт не позже чем через 2 такта; просроченные реакции разобраны.

### Отклонения и почему

- **Раздача на стенде.** Раздача идёт через второй nginx в сети машины, а не через `upstream` в `ac_nginx`. Порты 5001–5004 из Docker закрыты (`vpn-killswitch`), а их открытие требует root. `apply-nginx-dev.sh N` написан, но не применён.
- **`api.html` на пяти процессах.** Он гонялся только с `ip_hash`: тестовые часы и сброс тестовой сборки живут в одном процессе. Падений 44 на одном процессе против 43 на пяти, на ±1 расходится случайный тест `im-fsm: … закрытие × молчание`. Причину внутри теста не выяснили.
- **Ключи повторов.** Решение 6 называет столбцы `key, request_hash, answer`, сделан один `key_hash` (метод + путь + значение) по решению 112 плана 57. Отпечатка тела нет, как и раньше: повтор того же ключа с другим телом получает старый ответ.
- **Потолки запросов.** Потолки решения 69 подняты на одно чтение (`Feed.Last`) — это требование решения 13.
- **`Restart`.** Решает по лидерству: роль взята — сброс активности как раньше, держит другой — сброс только при отметке старше 30 с. Так на одном процессе поведение прежнее (RULE-113).
- **Сверка среза.** По замеру шага 2.4 сверка идёт раз в 5 мин. SQL руками мимо ленты виден до 5 мин.
- **Команды агенту на стенде.** Проверены только на тестовой сборке: в боевой сборке команду ставит лишь тестовый маршрут, исполнителя макросов ещё нет.
