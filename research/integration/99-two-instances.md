# План 99. Два экземпляра сервера МИ на одной базе

> **Для агентов-исполнителей:** обязательный навык — superpowers:subagent-driven-development (рекомендуется) или superpowers:executing-plans. Шаги — чекбоксы `- [ ]`. Сервер — по superpowers:test-driven-development: сначала тест, он падает, потом код. Пункт из таблицы решений — в работу, только когда заполнено «Решение»; чего в плане нет — не придумывать, а остановиться и спросить.

Статус: **черновик для обсуждения** (2026-11-21). Решения не приняты.

**Опирается на план [98](98-coordination-seams.md):** замки, будильник ленты и лидер вынесены там за интерфейсы `Locker`, `Listener`, `Leader` пакета `service/coord`. Задачи этого плана пишут новые замки и лидера только через них, прямых `pg_advisory_*` и `LISTEN` в логике не добавляют.

**Цель:** два и больше процессов сервера МИ на одной базе за nginx, который раздаёт запросы по очереди (схема «оба активны»). Оператор видит одно и то же, на какой бы узел ни попал запрос. Ни одно действие не выполняется дважды. Упал один узел — второй продолжает без потери данных.

**Откуда:** стенд Bezeq Test2 (2026-11-20): два узла облака, dc1-c1 и dc2-c1, на каждом свой процесс `imbackend`, база общая. Nginx берёт группу `im-backend` из Consul и шлёт туда запросы по очереди ([15, п. 1](15-deploy-configurator.md#1-боевой-конфиг-шлюза-где-apiv1monitoring-есть-ли-im-и-apiv1im-backend)). INC-0002 в состоянии `new`. dc2 показывает его в «Открытых» и в счётчике, dc1 — нет (`total=0`, `open=0`). С `deviceTypeId=camera` запрос идёт в базу мимо `LiveSlice`, и dc1 тоже отдаёт 1. У оператора сработка то появляется, то исчезает.

**Причина:** сервер рассчитан на один процесс на базу (решение 2026-11-13, комментарий `LiveSlice`; ADR-005, раздел «Before the public launch»). Часть данных он держит в памяти процесса и сбрасывает её вызовом внутри процесса. Второй узел о записи не узнаёт.

## Что уже работает между узлами

- **Лента и поток.** Лента — таблица `stream_events`. Запись берёт замок `pg_advisory_xact_lock` заказчика и шлёт `pg_notify('im_stream')`, хаб слушает `LISTEN` (`storing/stream_queries.go`, `stream/hub.go`). Поток оператору приходит, с какого бы узла ни была запись.
- **Переходы инцидентов в `LiveSlice`.** Каждая запись называет инцидент в ленте в своей транзакции (Н-12), и срез дочитывает ленту перед ответом. Пока запись идёт через ленту, срезы узлов сходятся.
- **Люди и сессии** — `operator_sessions` (план 62).
- **Замки в базе:** сборка индексов поиска (план 96), сброс и восстановление (`im-backup:`), запись настроек (`lockWorkflowSettingsSQL`).

## Решения

| № | Вопрос | Варианты | Рекомендация | Решение |
|---|---|---|---|---|
| 1 | Нужен ли режим «оба активны» вообще | а) да, доделать сервер по этому плану; б) нет: в Consul и nginx режим «основной + резервный», сервер не трогаем; в) сейчас б, план — к публичному запуску | в: б снимает баг Test2 без кода и даёт отказоустойчивость; «оба активны» нужен только для деления нагрузки, а её пока держит один узел. Задать вопрос DevOps (см. «Вопросы к DevOps») | |
| 2 | Как узел узнаёт о записи мимо ленты (П1–П3) | а) счётчик поколений в базе: таблица `cache_generations (customer, kind, gen)`, запись мимо ленты увеличивает его в своей транзакции, узел сверяет перед ответом одним лёгким чтением; б) строка ленты нового типа `cache.invalidated`: узлы уже читают ленту, отдельной таблицы не надо; в) только `NOTIFY` без записи в таблицу | б: лента уже упорядочена и уже читается срезом перед ответом; строка ложится в ту же транзакцию, что и запись. ## Задачи

### Задача 1. Сброс кэшей через ленту (П1–П3)

- [ ] **Шаг 1: тест с двумя экземплярами.** Помощник в `handler/test`: два `AppServices` (A и B) на одной тестовой базе, у каждого свой `LiveSlice`, `AccessCache`, дерево. Падающие тесты, по одному на путь записи мимо ленты: загрузка стенда, правка через тестовый стенд, сброс МИ, восстановление из копии, создание, правка и удаление группы устройств, состав группы, правило доступа. Запись на A — очередь, счётчики и дерево на B сразу совпадают с SQL (`IM_LIVE_SLICE=off`).
- [ ] **Шаг 2: строка ленты `cache.invalidated`.** Тип в `stream/feed.go` с полем `kind` (`live`, `access`, `tree`, `all`). Внутренняя: `render` её не отдаёт клиентам, по ней только сбрасываются копии. Пишется последней в транзакции (как `Feed.Append`).
- [ ] **Шаг 3: запись строки.** Во всех путях из шага 1 — вместо или рядом с вызовом `Invalidate`/`InvalidateAll`. Путь без транзакции (стенд пишет пачками) — отдельной транзакцией сразу после.
- [ ] **Шаг 4: чтение строки.** `LiveSlice.readFeed` по строке `live`/`all` перестраивает срез заказчика. `AccessCache` и дерево — по строке `access`/`tree`/`all`: им нужен свой курсор ленты или подписка на хаб (`stream/hub.go` уже получает уведомления через `coord.Listener`). Перед ответом про доступ копия сверяет свой курсор с концом ленты заказчика (`Feed.Last`, одно чтение), как срез.
- [ ] **Шаг 5: дерево.** Версия дерева становится общей: хранится в базе (или берётся из курсора ленты), а не своя у процесса. Иначе `AccessCache` на B не видит смены дерева на A.
- [ ] **Шаг 6:** тесты шага 1 зелёные; старые тесты среза, доступа и дерева зелёные; `-race`.
- [ ] **Шаг 7: замер.** Цена сверки с концом ленты на запрос очереди на стенде (план 90, 100 операторов) — не больше 1 мс p95 к нынешнему.

### Задача 2. Страж и сверка (П1–П3)

- [ ] **Шаг 1: страж по коду.** Расширить `TestAccessWritesInvalidate` (план 80): каждая функция, которая пишет в таблицы инцидентов, групп, правил, настроек не через `Feed.Append` перехода, пишет строку `cache.invalidated` в своей транзакции. Новый путь без неё — тест красный.
- [ ] **Шаг 2: сверка в фоне.** `IM_LIVE_SLICE_VERIFY` по умолчанию 1 мин. Нашла расхождение — сбросить срез заказчика (а не только посчитать в `Mismatches`) и написать `Warn` с числом записей. Тест: SQL руками мимо ленты на A — через одну сверку срез на B совпадает с базой.
- [ ] **Шаг 3:** число расхождений — в «Состоянии системы» рядом с остальными показателями сервера.

### Задача 3. Машина заказчика на всех узлах (П4)

- [ ] **Шаг 1: падающий тест.** Публикация настроек поста на A — следующий переход на B идёт по новой машине (новый таймер, новый приоритет, новый сценарий).
- [ ] **Шаг 2:** читатель ленты на каждом узле по строке `workflow.schema_published` вызывает `Settings.Reload(customer)`. То же после сброса МИ и восстановления из копии (строку пишут и они, проверить).
- [ ] **Шаг 3:** что будет с переходом, начатым на B до перечитывания: решить в тесте и записать в журнал (переход в транзакции читает версию машины из базы и при расхождении отказывает `409` или идёт по старой).
- [ ] **Шаг 4:** планировщик на B после перечитывания пересчитывает таймеры организации (как после `Load`).

### Задача 4. Лидер планировщика (П5, решение 209)

- [ ] **Шаг 1: падающий тест.** Два планировщика на одной базе: за 30 тактов переходы делает только один, второй не ждёт замков строк.
- [ ] **Шаг 2:** такт берёт `coord.Leader` плана 98 (в PostgreSQL — замок на отдельном соединении сессии). Не лидер — такт пропускает, пробует на следующем. Соединение порвалось — замок снят базой.
- [ ] **Шаг 3:** курсор обхода доступа (план 79) и отметка последнего такта — в базе, чтобы новый лидер продолжил с того же места.
- [ ] **Шаг 4:** `Restart` считает простой по отметке последнего такта лидера в базе, а не по времени остановки своего процесса.
- [ ] **Шаг 5: тест переключения.** Лидер остановлен — второй узел берёт такт не позже чем через 2 такта; просроченные реакции разобраны.

### Задача 5. Повторы в базе (П6, Task 20–22 плана 57)

- [ ] **Шаг 1:** перенос пакета `handler/operator/idempotency` в `internal/im/service/idempotency`, ключ с заказчиком (Task 20).
- [ ] **Шаг 2:** таблица и миграция (номер — следующий свободный), захват ключа со сроком (лиза), ответ сохраняется (Task 21, наброски 4–5).
- [ ] **Шаг 3:** чистка по сроку пачками, предел ключей на пользователя, сбой между фиксацией и сохранением закреплён тестом (Task 22, наброски 6–7).
- [ ] **Шаг 4: тест.** Запрос на A, повтор того же ключа на B — тот же ответ, действие одно.

### Задача 6. Опрос агента (П7, А-7)

- [ ] **Шаг 1: падающий тест.** Команда записана на A, агент ждёт на B — получает за время меньше 1 с.
- [ ] **Шаг 2:** `Enqueue` шлёт уведомление по каналу `im_agent_commands` в своей транзакции, каждый узел слушает его через `coord.Listener` плана 98 и будит своих `waiters`. Переподключение `LISTEN` — будить всех ждущих (они перечитают базу).

### Задача 7. Стенд из двух экземпляров и прогон

- [ ] **Шаг 1: стенд.** Второй процесс сервера на том же стенде на другом порту, nginx `upstream im-backend` с обоими, раздача по очереди. Скрипт запуска — в `~/Work/stand/`, копия в `IM/tools/stand-load`.
- [ ] **Шаг 2:** `tests/api.html` через nginx — зелёный с теми же исключениями, что на одном узле.
- [ ] **Шаг 3: «запись на A — чтение на B».** Скрипт по каждому пути таблицы «Что только в памяти процесса»: записать через A напрямую, прочитать через B напрямую, сравнить с SQL.
- [ ] **Шаг 4: нагрузка.** Прогон плана 90 (100 операторов) через nginx на двух узлах. Счётчики и очередь у всех операторов совпадают с базой, расхождений сверки 0, 5xx 0.
- [ ] **Шаг 5: падение узла.** Во время нагрузки остановить один процесс: операторы продолжают через второй, такт подхватывается, повторы не дают двойных действий.
- [ ] **Шаг 6:** П8 — проверить на стенде `seen_ms` и список адресатов передачи, если расходятся — в «Итог» отдельным пунктом.
- [ ] **Шаг 7:** отчёт `research/integration/load-<дата>-plan99.md`; ADR-005, раздел «Before the public launch» — убрать сделанное; комментарий «one process on a base» в `live_slice.go` — переписать.
