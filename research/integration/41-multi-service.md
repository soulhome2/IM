# Одно событие — несколько служб: итог консилиума

Дата: 2026-10-28. Вопрос пользователя: одна тревога (пожар) должна обрабатываться пожарной и медицинской службами, у каждой свой сценарий. Модель пользователя: события проходят через фильтры (правила), у каждого фильтра свой сценарий, каждый сработавший фильтр порождает свой инцидент — одно событие может дать несколько инцидентов.

Мнения: [архитектор машины](41-consilium/architect.md), [предметная область — диспетчерские и PSIM](41-consilium/domain.md), [UX оператора](41-consilium/ux.md). Сравнивались М1 — инцидент на правило с адресацией дежурной группе правила; М2 — инцидент на правило в общей очереди (модель пользователя); М3 — один инцидент с заданиями служб внутри; М4 — один инцидент и ручное «создать смежный».

## Общий вывод

Все трое — за модель пользователя (М2) как основу. М3 отвергнута: удобна за пультом и принята внутри одного центра, но ломает «у инцидента одно состояние и один владелец» — пересборка машины, §4, §8, §11 и модели Quint (объём L). М4 отвергнута: смежный инцидент появится, только если оператор вспомнит его создать; пропуск не ловит ни таймер, ни эскалация.

Машина почти не меняется: переход `create` остаётся, ни один инвариант модели Quint не зависит от числа инцидентов на событие (архитектор).

## Что нужно к модели, чтобы она работала

| # | Что | Почему | Кто говорит |
|---|---|---|---|
| 1 | Ключ уникальности — **событие + сценарий** (не событие + правило) | пересекающиеся фильтры одной службы («любой пожар» и «пожар в серверной» с одним сценарием) иначе дадут два инцидента; повтор события ничего не досоздаёт (одна транзакция, уникальный индекс). Внутри одного сценария правило выбирается ранжированием §14.5 — открытый вопрос §15 сужается до этого случая | архитектор; предметник — «событие + служба» (то же, если служба = сценарий) |
| 2 | Нельзя закрыть «Дубликатом» соседний инцидент того же события | §2.2 сейчас прямо разрешает («то же событие уже разбирается»), оператор так и сделает | UX, предметник |
| 3 | Соседи знают друг о друге: в карточке «По этому событию: INC-13 — Медики, в работе», в строке очереди — отметка «событие: ещё N»; при закрытии соседа как ложной тревоги — уведомление, без автозакрытия | ложная тревога у одной службы иначе не дойдёт до другой; автозакрытие опасно | все трое |
| 4 | Соседи видны только тем, у кого к ним есть доступ; число считать по видимым | правило видимости §5: без доступа — ни номера | архитектор |
| 5 | Один звук на событие | иначе оператор двух групп и старший получат по два сигнала на одну тревогу | UX |
| 6 | «Массовый сбой» на выборке не должен закрывать инциденты чужой службы | выборка по зданию захватит соседей | UX |
| 7 | Фильтр очереди по сценарию (или службе) | у соседей совпадают состояние, группа, тип события, тип устройства — различает только сценарий | архитектор, UX |

## Где мнения расходятся — решить пользователю

| # | Вопрос | Варианты | Мнения |
|---|---|---|---|
| A | Разделять службы адресацией: у правила необязательное поле «дежурная группа», инцидент сразу «Ожидает принятия» этой группой | сейчас / вторым шагом | UX и предметник — нужно сразу: доступ выдаётся по устройству, без адресации медик может взять инцидент пожарных. Архитектор — необязательное поле и второй шаг: новый переход `route_on_create`, правила «в группе никто не может принять» и «после Отклонить — в общую очередь» |
| B | Сквозной номер тревоги — общий для всех инцидентов одного события, в очереди, карточке и отчётах; два счётчика: тревоги и инциденты | сейчас / позже | предметник — нужен для учёта и «кто отвечает за тревогу целиком» (так в CAD и 112); статус тревоги вычисляется из её инцидентов, без нового состояния машины |
| C | Нормативы и цепочка эскалации — по службе (сценарию) или общие | общие / по сценарию | все трое: сейчас одна цепочка на схему — не взятый вовремя медицинский инцидент уйдёт старшему пожарной смены. Норматив по сценарию — малая правка; цепочка по службе — больше. Записать в §15 |
| D | Вызов службы «сразу» или «по подтверждению» (сначала проверяют тревогу, потом вызывают службу; кнопка «Вызвать службу X» из карточки) | сейчас / вторым этапом | предметник — так принято в охране, иначе ложные тревоги умножаются на число служб; вторым этапом |

## Предложение

Принять модель пользователя с пунктами 1–7. Из спорных: A — необязательное поле «дежурная группа» у правила, сделать вместе с моделью (без него службы не разделены); B — сквозной номер тревоги сделать сразу (дёшево, нужен для учёта); C — норматив по сценарию сделать, цепочку эскалации по службе — в §15; D — вторым этапом.

## Решение пользователя (2026-10-28)

- Модель — пользователя: событие проходит через фильтры (правила), каждый сработавший фильтр со сценарием порождает свой инцидент с этим сценарием; одно событие — несколько инцидентов. Пункты 1–7 выше — принимаются.
- A. Адресация дежурной группе фильтра — **вторым шагом**; пока все инциденты в общей очереди, службы различают по фильтру сценария (п. 7).
- B. Сквозной номер тревоги — **сразу**.
- C. Норматив реакции и закрытия — **по сценарию**; цепочка эскалации по службе — открытый вопрос в §15.
- D. Вызов службы «по подтверждению» — **не нужен**: все сработавшие фильтры создают инциденты сразу.
- Приоритет инцидента задаёт правило (решение № 9 в [40-plan.md](40-plan.md)).
