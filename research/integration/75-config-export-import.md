# Резервная копия настроек МИ: сохранить в файл и восстановить

Дата: 2026-11-10. Статус: сделано 2026-11-10 (сервер, конфигуратор, эмулятор), кроме автокопии перед загрузкой — её отменили, см. «Решения». План — [76-plan-config-export-import.md](76-plan-config-export-import.md).

## Зачем

Если настройки МИ слетели (испортили правило, удалили группу, пересобрали базу), их нужно вернуть одним действием. Сейчас резервной копии настроек нет, а стенд собирается из нескольких скриптов (`demo-config`, `rules`) и ручной работы.

Задача — **восстановить ту же систему**, а не переносить настройки на другую. Поэтому в файле хранятся сами идентификаторы (GUID): каждый объект возвращается на своё место, а история инцидентов и событий снова ссылается на те же записи (решение пользователя).

## Что должно получиться

В конфигураторе на странице настроек — две кнопки, только для администратора:

- **«Сохранить в файл»** — скачивается JSON со всеми объектами и настройками. На сервере ничего не меняется.
- **«Загрузить из файла»:**
  1. Администратор выбирает файл.
  2. Открывается окно предпросмотра: по каждому разделу — что будет восстановлено, изменено и удалено; что оставлено, потому что на него ссылается история; изменится ли машина инцидента и сколько открытых инцидентов это затронет.
  3. Администратор нажимает «Восстановить».
  4. Сервер применяет файл одной транзакцией: либо всё, либо ничего.

Кнопки «Вернуть как было» нет (решение пользователя 2026-11-10): копию перед загрузкой сохраняют сами — «Сохранить в файл».

**Режим один — замена.** После загрузки объекты и настройки МИ такие, как в файле.

**Не делаем:**
- перенос на другую систему или другого заказчика: файл чужого заказчика отклоняется;
- слияние и выбор частей файла;
- копию на сервере перед загрузкой и историю копий;
- загрузку по расписанию.

**Провал, даже если всё работает:**
- после восстановления открытый инцидент или его журнал ссылаются на пропавший объект;
- файл смог загрузить не администратор;
- загрузка прошла наполовину;
- в файл попал секрет в открытом виде.

## Что входит в файл

Все объекты и настройки заказчика, по GUID, как в базе:

| Раздел | Таблицы |
|---|---|
| `agents` | `agents` (без ключей) |
| `sourceTypes`, `sourceEventTypes` | `source_types`, `source_event_types` |
| `sources` | `sources` |
| `sourceGroups` | `source_groups`, `source_group_memberships` |
| `priorities`, `statuses` | `priorities`, `statuses` |
| `scenarios` | `scenario_definitions`, все версии `scenarios`, связь `scenarios_customers` |
| `rules` | `incident_rules`, `incident_rule_scenarios`, `incident_rules_conditions` (таблицы назначений групп в базе нет) |
| `accessRules`, `accessRuleGroups` | `access_rules`; `access_rule_groups` — группы живых правил доступа, не удаляются |
| `dutyGroups` | `duty_groups` |
| `helpLinks`, `cameraLinks` | `help_links`, `camera_links`, `camera_link_items` |
| `workflowSettings` | `workflow_settings`: опубликованная версия |

Ссылки на группы пользователей облака хранятся как в базе (идентификатор группы облака). В той же системе они те же.

**Чего в файле нет:**
- **События, инциденты, журнал, аудит, сессии операторов.** Это рабочие данные, их размер — гигабайты. Для них есть резервная копия базы.
- **Ключи агентов (`agent_api_keys`).** Это секреты. Восстановление их не трогает: у агента, который остался в базе, ключ прежний. Если агент пропал из базы вместе с ключом, он регистрируется заново.

**Заголовок файла:**
```json
{ "format": "im-backup", "version": 1, "customerGuid": "…", "exportedAt": "…", "exportedBy": "…", "serverVersion": "…" }
```
Отклоняется до предпросмотра, если:
- чужой `format`;
- `version` новее, чем знает сервер;
- `customerGuid` не совпадает с заказчиком администратора.

## Как работает восстановление

Сравнение идёт **по GUID**:

| Случай | Что делает восстановление |
|---|---|
| объект есть в файле и в базе | обновляет до состояния из файла |
| есть в файле, нет в базе (или помечен удалённым) | возвращает с тем же GUID |
| есть в базе, нет в файле: устройство, тип, агент | помечает удалённым (`deleted_at`), как сверка агента |
| есть в базе, нет в файле, на него ссылаются инциденты или события (приоритет, статус, сценарий) | **оставляет**, в предпросмотре — «оставлено: на него ссылается история» |
| есть в базе, нет в файле, остальное | удаляет |
| версии сценария | недостающие версии возвращаются; существующие не меняются: их могут проходить инциденты |
| `workflowSettings` | нет раздела — не трогается. Совпадает с опубликованной — ничего. Отличается — черновик, проверка, публикация новой версией, как при ручной правке; не прошла проверку — отклоняется всё восстановление |

**Агент после восстановления.** Агент шлёт сверку раз в несколько секунд. Если в базе после восстановления что-то расходится с тем, что у агента на самом деле, следующая сверка это поправит. Источник правды по устройствам — агент.

**Предупреждение о машине.** Если меняются настройки машины инцидента, предпросмотр показывает это отдельной заметной строкой с числом открытых инцидентов: они продолжат работу по новым настройкам.

**Резервная копия перед загрузкой — отменена** (решение пользователя 2026-11-10). Сервер копии не держит; перед загрузкой администратор сохраняет файл сам.

**Устарел предпросмотр.** Если между предпросмотром и нажатием «Восстановить» кто-то изменил настройки, загрузка отклоняется с просьбой повторить предпросмотр.

**Аудит.** Восстановление — одна запись в аудите настроек: кто, когда, имя файла, дата файла, сводка.

**Права.** Экспорт, предпросмотр и восстановление — право администратора `incident:schema:admin`. Без права — 403.

## Варианты

- **А. Полная копия по GUID, восстановление в ту же систему — выбран.** Восстанавливается всё одним файлом и одним действием. Не нужно искать по именам, ждать агента и разбирать «не найдено». Переноса между системами нет, и он не нужен.
- Б. Перенос по естественным ключам (`uid`, имена). Подходит для переноса, но на голой системе правила на устройствах не восстанавливаются до прихода агента. Нужны повторная загрузка или ожидающие ссылки. Отвергнут: сложно ради ненужного сценария.
- В. Дамп базы (`pg_dump`). Уже есть для полной копии, но тянет гигабайты рабочих данных, требует доступа к серверу и не отделяет настройки.

## Решения

1. Цель — восстановление той же системы, копия по GUID (решение пользователя).
2. Режим — только замена (решение пользователя).
3. Кнопки и все действия — только администратор (решение пользователя).
4. Настройки машины инцидента входят: публикуются обычным путём с проверкой, нет раздела — не трогаются (решение пользователя).
5. Обязательный предпросмотр, восстановление одной транзакцией. Автокопию перед загрузкой и «Вернуть как было» пользователь отменил 2026-11-10.
6. Рабочие данные и ключи агентов в файл не входят. Объекты, на которые ссылается история, не удаляются (решение автора проекта).
7. Тестовые наборы стенда (демо, вышки) — файлы этого формата в `tools/agent-emulator/testdata/backup/`; эмулятор загружает их тем же API. `demo-config` и `rules` устаревают.

## Что остаётся исполнителю

- Имена методов API и место блока на странице настроек.
- Порядок разделов и форматирование JSON: так, чтобы файл удобно сравнивать в git.
- Тексты окна предпросмотра, на четырёх языках интерфейса.

## Как сделано

- Методы: `exportBackup` (`GET /operator/admin/backup`), `previewRestore` (`POST …/preview`), `applyRestore` (`POST …/apply`, `planHash` из предпросмотра; иначе 409 `BACKUP_STALE`). Плохой файл — 400 `BACKUP_INVALID`, ошибка применения — 422 `BACKUP_APPLY_FAILED`, ничего не меняется.
- Раздела нет в файле — раздел не трогается (как `workflowSettings`); экспорт пишет все разделы.
- Сценарий в файле проверяется тем же разбором, что у сервера; настройки машины публикуются тем же кодом, что ручная правка (черновик, проверка, публикация).
- Аудит — запись журнала настроек `objectType: backup`, `action: restore` с именем файла и сводкой.
- Конфигуратор: своя вкладка «Резервная копия» в настройках поста, последняя, только для администратора (сначала блок стоял внизу «Хранения» — неудобно листать).
- Эмулятор: `backup export`, `backup restore [--yes]`; наборы — `tools/agent-emulator/testdata/backup/`.
