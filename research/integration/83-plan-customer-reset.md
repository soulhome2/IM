# План: сброс МИ клиента с записью в журнале

Черновик, 2026-11-13.

> **Для исполнителя-агента:** выполнять по задачам через superpowers:subagent-driven-development или superpowers:executing-plans. Шаги отмечаются `- [ ]`.

**Цель:** в настройках резервной копии рядом с «Сохранить в файл» и «Загрузить из файла» — кнопка «Сбросить». Она удаляет все данные МИ **одного клиента** (`customer_guid`): инциденты и настройки. Перед сбросом сервер проверяет пароль. Запись о сбросе остаётся в журнале настроек: сброс её не стирает, по ней видно, кто, когда и что удалил.

**Зачем:** сейчас вернуть систему к чистому виду можно только загрузкой файла. Пустой системы так не получить. При этом след сброса должен остаться, даже если сбросил кто-то по ошибке или со злым умыслом.

**Основа, которая уже есть:**
- журнал настроек `settings_audit` (миграция 043): в него только добавляют, UPDATE, DELETE и TRUNCATE запрещены триггерами. Очистка по сроку `retention.auditDays` идёт в обход триггера;
- запись `backup / restore` в журнале (миграция 058, план 76);
- `internal/im/stand/wipe.go` — очистка всех таблиц одного клиента по шагам. Собирается только с тегом `imtest` и вызывается только из сброса стенда.

**Репозитории:** IM (контракт), `~/Work/incident-manager-server`, `~/Work/incident-manager`, ветка `feature/im_operator`. Коммиты — только по просьбе. Перед коммитом сервер и конфигуратор собираются на стенд.

## Решения

| № | Вопрос | Решение |
|---|---|---|
| 1 | Граница сброса | Один клиент. Другие клиенты не затрагиваются. |
| 2 | Что удаляется | Всё, что входит в резервную копию (таблица «Что входит в файл» проекта 75), плюс инциденты, события, действия операторов, очереди и счётчики. |
| 3 | Что остаётся | Журнал настроек `settings_audit`, журнал действий операторов `operator_actions`, ключи агентов. |
| 4 | Подтверждение | Пароль облачного аккаунта текущего пользователя (проверяет сервер) и слово «СБРОСИТЬ» в поле ввода. |
| 5 | Право | `incident:schema:admin`, проверка на сервере. |
| 6 | Защита от ошибки | Перед сбросом конфигуратор предлагает скачать резервный файл. Отказаться можно, но кнопка «Скачать и сбросить» стоит первой. |
| 7 | След | Одна запись `settings_audit`: `object_type = 'customer'`, `action = 'reset'`, в `before` — сколько строк было в каждой таблице. Неверный пароль — запись `action = 'reset_denied'`. |
| 8 | Срок хранения следа | Очистка по сроку не удаляет записи `reset` и `reset_denied` моложе 365 дней, даже если `auditDays` меньше. Иначе можно сбросить, уменьшить срок и дождаться, пока след уйдёт. |

## Решения по открытым вопросам (2026-11-13)

1. **Журнал действий операторов (`operator_actions`)** — при сбросе остаётся, как и журнал настроек. Его строки могут ссылаться на удалённые инциденты.
2. **Ключи агентов** — при сбросе остаются, как и при загрузке из файла. Агентов не нужно регистрировать заново.
3. **Пароль** — сервер МИ проверяет повторным входом в облако (вариант А задачи 0); метод облака для сервисов (Б) просим заранее. Пользователи SAML/SSO подтверждают только словом «СБРОСИТЬ», а в запись `reset` пишется, что пароль не проверялся.
4. **Запись о сбросе** хранится только в `settings_audit` в базе сервера МИ, наружу (в журнал облака) не отправляется. Удалить её через приложение нельзя. Владелец базы может отключить триггер и удалить её — это допустимо.

## На что смотреть при проверке

1. **Два клиента, сбросили первого.** У второго не изменилось ничего, ни одной строки. Тест — задача 3.
2. **После сброса.** Списки инцидентов и настроек первого клиента пусты, журнал настроек на месте, в нём последняя запись — `reset` с числом строк. Тест — задача 3.
3. **Неверный пароль.** 403, база не изменилась, в журнале запись `reset_denied`. Тест — задача 3.
4. **Без права администратора.** 403 `PERMISSION_DENIED`, записи `reset_denied` нет: до проверки пароля дело не дошло. Тест — задача 3.
5. **Сброс, затем загрузка файла, сохранённого до сброса.** Настройки вернулись с прежними GUID. Тест — задача 3.
6. **Очистка журнала по сроку с `auditDays = 1`.** Запись `reset` трёхдневной давности осталась. Тест — задача 2.
7. **Ошибка посреди сброса.** Откат всего, записи `reset` нет. Тест — задача 3.

### Задача 0: выяснить проверку пароля

**Даёт:** ответ на вопрос 3 из «Решений по открытым вопросам» — каким методом облака сервер МИ проверяет пароль пользователя. Результат — абзац в этом плане вместо вопроса 3.

- [x] Найти в облаке метод проверки пароля или повторного входа.
- [x] Согласовать вариант с пользователем — **решено 2026-11-13: делаем А, Б заранее просим у команды облака.**
- [ ] Отправить команде облака просьбу о методе Б.

**Итог (2026-11-13, axxoncloudgo `epic/CLOUD-23284-perms-i18n`).** Отдельного метода «подтвердить пароль» облако не даёт ни снаружи, ни для сервисов (`/ac/v1/…`). Внутри облака проверка есть: `UserService.CheckPassword` (`services/user/service.go:822`) — пароль облака или LDAP. Наружу она открыта только через вход `POST /users/login` (`handler/rest/auth.go:379`, `LoginByEmail`): email и пароль → пара токенов, неверный пароль → 401, частые попытки ограничивает `limiter`.

Сервер МИ уже ходит в облако (`internal/externalclient/cloud/client.go`) и умеет узнать email пользователя по id (`GetUserInfo`, `/ac/v1/users/{id}`).

Варианты:
- **А. Повторный вход.** Сервер МИ берёт email через `GetUserInfo` и вызывает `POST /users/login` с паролем: 200 — пароль верный, 401 — нет. Полученные токены сразу выбрасывает. Делается без облака. Минусы: в облаке появляется лишний вход (новая пара токенов, отметка активности); неудачи считаются в блокировку входа — для защиты это скорее плюс; пользователь без пароля (вход через SAML/SSO) так подтвердить не сможет.
- **Б. Метод в облаке для сервисов** — `POST /ac/v1/users/{id}/check-password` поверх `CheckPassword`. Без побочных эффектов, работает и с LDAP. Нужна доработка у команды облака.
- **В. Без пароля** — только слово «СБРОСИТЬ», в записи `reset` отметка «пароль не проверялся».

Предложение: сейчас А; Б попросить у облака и перейти на него, когда появится (строка в `TECH-DEBT.md`). Для пользователей SAML/SSO — В с отметкой в журнале.

**Капча.** `CheckPassword` перед проверкой пароля смотрит капчу, если включено `AXXONCLOUD_AUTH_USE_CAPTCHA`, причём с пустым id клиента — белый список клиентов не поможет. На стенде (`dev.env`) капча выключена, вариант А работает без правок облака. В рабочем облаке с включённой капчей А не пройдёт — поэтому Б просим заранее, не дожидаясь отказа. Состояние капчи в рабочем облаке не проверялось.

### Задача 3: сервер — сброс

**Файлы:** `internal/im/service/reset/reset.go` (новый), обработчик в `handler/operator/admin.go` (или рядом с `backup.go`); шаги очистки — общие с `stand/wipe.go`.

**Даёт:** `Reset(ctx, customer, user, password) (map[string]int64, error)`.
1. Проверка права (до пароля).
2. Ограничение попыток: не больше 5 неудачных за 15 минут на пользователя (счётчик — по записям `reset_denied` в журнале, отдельной таблицы не нужно). Превышено — 429 `TOO_MANY_ATTEMPTS`, пароль в облако не отправляется.
3. Проверка пароля (задача 0). Неверный — запись `reset_denied` в своей транзакции и 403.
4. Одна транзакция:
   - `pg_advisory_xact_lock` по клиенту — второй сброс того же клиента ждёт или получает 409;
   - подсчёт строк по таблицам;
   - очистка по шагам — список и порядок вынести из `stand/wipe.go` в общий пакет без тега `imtest`; `settings_audit`, `operator_actions` и ключи агентов — исключить и проверить тестом, что их нет в списке;
   - запись `reset` с числами в `before`.
5. После транзакции — сбросить кэши клиента: кэш доступа (план 80), счётчики очереди.
