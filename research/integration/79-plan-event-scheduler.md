# План 79: планировщик без зависаний (фаза 1 планировщика на событиях)

> **Для агентов-исполнителей:** обязательный навык — superpowers:subagent-driven-development (рекомендуется) или superpowers:executing-plans. Шаги — чекбоксы `- [ ]`.

**Цель:** планировщик сервера МИ не зависает при любом размере базы и любой волне эскалаций. Такт разбирает тысячи переходов за секунды, а не часами.

**Устройство:**
- Такт перестаёт после каждого перехода перепроверять весь набор. Он помнит готовый переход каждого инцидента и пересчитывает только затронутую семью — так обещал ADR-006, п. 3.
- Независимость семей закрепляется проверкой машины.
- У такта появляется бюджет времени и предупреждение о долгом такте.
- Обход доступа идёт порциями по кругу, а не весь за раз.

**Технологии:** Go (сервер `~/Work/incident-manager-server`, ветка `feature/im_operator`), Python (`tools/check_machine.py` в IM), PostgreSQL стенда.

**Спецификация:** [78-adr-draft-event-scheduler.md](78-adr-draft-event-scheduler.md) — разделы 3, 4.5, 7 (шаги 0–1), 8. Решения пользователя 2026-11-12 по разделу 9:
- 1а — начинать с шагов 0–1, без временной заплатки;
- 2а — очередь в памяти, это фаза 2;
- 3 — порядок между семьями может отличаться;
- 4 — Н-4 исправить после шага 0;
- 5 — расхождение ADR-006 записать сразу.

**Повод:** [load-burst-soak-2026-11-12.md](load-burst-soak-2026-11-12.md).

## Почему уверены, что это поможет, — и что, если нет

**Уверенность опирается на три факта, не на догадку:**
1. **Где стоит процессор — замерено.** Снимок горутин зависшего такта: `Core.Tick → ticker.best → ticker.next`, `runnable` (2026-11-12, 11:15). То есть время уходит на перепроверку условий, а не на базу.
2. **Почему перепроверка квадратичная — видно в коде.** `best` после каждого `fire` заново вызывает `next` для каждой строки набора (`tick.go`, `Core.Tick` и `best`).
3. **Почему её можно не делать — проверяется машиной и тестом.**
   - Задача 1: ни одно условие системного перехода не читает чужие инциденты, кроме семьи.
   - Задача 2: на всех векторах и 200 случайных наборах новый такт даёт **тот же** результат и порядок, что старый.

**Чего мы ещё не знаем** — какая доля времени такта уходит на эту перепроверку, а какая — на что-то другое: чтение семьи из базы после перехода (`Around`), сборку миров. Если не перепроверка, задача 2 даст меньше, чем ждём. Поэтому первой идёт **задача 0: замер до правок**, с условием остановки.

## Общие ограничения

- Машина (`workflow_schema.v1.json`), правила, контракт `openapi.json` и прототип **не меняются**. Задача 1 добавляет только проверку в `tools/`.
- Ожидаемое в векторах `transition-vectors.json` не меняется. Порядок и итог такта на векторах совпадают с нынешними **точно** (задача 2 это доказывает).
- Транзакция на переход, блокировка семьи, `lock_timeout` 1 с, отметка `fired`, предел 50 переходов на инцидент за такт (`tickCap`) — как есть (решения 200, 202 плана 60).
- Коммиты — по одному на задачу. Сообщения на русском, простыми словами, с префиксом `План 79, задача N:`. Пуш — только по просьбе пользователя.
- Сервер стенда перезапускается только в задаче 5, под замком `~/Work/stand/lock-server`.
- Тесты сервера — на тестовой базе (`make test-db-up`, `IM_TEST_DB_URL`), никогда на `imdb` стенда.

## Где опасно (Review Focus)

1. **Переход, который сделал готовым переход другого инцидента той же семьи.** Например, закрыли основной, и `close_linked` у связанных должен сработать в этом же такте. Задача 2: тест `TestTickMemoFamilyChain`.
2. **Инцидент, у которого после перехода появился следующий шаг цепочки** (эскалация → новый срок реакции, уже истёкший). Он должен пересчитаться сразу, а не ждать следующего такта. Задача 2: тест `TestTickMemoChainSameIncident`.
3. **Бюджет кончился посреди волны.** Остаток должен уйти в следующий такт, без потерь, без двойных переходов, в том же порядке. Задача 3: тест `TestTickBudgetLeavesRest`.
4. **Обход по кругу: инцидент с номером меньше курсора, у которого адресат потерял доступ, пока курсор был дальше.** Он должен найтись на следующем круге. Задача 4: тест `TestSweepCursorWraps`.
5. **Будущая правка машины добавит в системный переход условие, читающее чужие инциденты** (например, `countMine`). Тогда пересчёт по семье станет неверным. Задача 1 должна такую правку отклонить, мутация `system-guard-reads-others`.

- `clear(t.worlds)` после перехода остаётся: миры дешёвые, а свежие факты сессий нужны пересчитываемым строкам.
- Записи `since` невыбранных строк не трогаются. Для строки, которая не пересчитывается, `since` и не нужен.

### Задача 3: бюджет такта и предупреждения

Сервер.

**Файлы:**
- Изменить: `internal/im/service/transition/tick.go` — `TickOp.Budget`.
- Изменить: `internal/im/appservice/operator/scheduler.go` — `SchedulerConfig`, `DefaultSchedulerConfig`, `tickOf`, `Tick`.
- Тесты: `tick_test.go`, `appservice/operator/scheduler_test.go`.

**Интерфейсы:**
- Даёт:
  - `TickOp.Budget time.Duration` — 0 значит без предела;
  - `SchedulerConfig.TickBudget time.Duration` = `500 * time.Millisecond`;
  - `SchedulerConfig.SlowTick time.Duration` = `5 * time.Second`;
  - `SchedulerConfig.DueFullWarn int` = `60` (тактов подряд).
- Использует: `TickResult.More` — уже есть.

**Поведение:**
- `Core.Tick` перед каждым `fire` смотрит, сколько прошло с начала такта. Если больше `Budget` — возвращает результат с `More = true`, как при `MaxRuns`. Часы такта — `time.Now` процесса, не `now` машины: бюджет — про процессор, а не про время правил.
- `Scheduler.Tick` пишет `Warn` `scheduler: the tick took long`, если такт шёл дольше `SlowTick`. Поля: `customer`, `took_ms`, `fired`, `pool`.
- Если `DueIncidents` вернул ровно `candidateLimit` строк `DueFullWarn` тактов подряд — `Warn` `scheduler: due incidents keep the limit full` с числом тактов. Это сигнал долга без лишнего запроса `count(*)`. После предупреждения счётчик тактов сбрасывается, чтобы не писать каждую секунду.
