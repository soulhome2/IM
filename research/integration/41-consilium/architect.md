# Консилиум «одно событие — несколько служб»: взгляд архитектора машины

Дата: 2026-10-28. Роль: архитектор машины состояний. Основная модель — задуманная пользователем: **М2** (событие проходит через фильтры-правила, у каждого правила свой сценарий, сработало N правил — N инцидентов). Отдельно: нужна ли сверху адресация дежурной группе (М1) и как не плодить дубли.

Обозначения: **[факт]** — проверено по правилам, машине, коду; **[мнение]** — моя оценка.

## 1. Что уже есть и на что опираемся (факты)

- **[факт]** `create` — единственный переход без исходного состояния, `to: new`, без условий; ставит пустых владельца и адресата, уровень 0, запускает реакцию (`workflow_schema.v1.json`, переход `create`; §6.2; RULE-61). У перехода одно `to` — условного «куда» машина не знает.
- **[факт]** Доступ оператора — **по устройству-источнику**: «Оператору видны только инциденты, устройство-источник которых доступно хотя бы одной из его ролей» (§5). У всех инцидентов одного события одно устройство.
- **[факт]** Фильтры очереди — по состоянию (§7), группе устройств (§19.1), типу события и типу устройства (§19.2). У инцидентов одного события всё это совпадает. Отличает их в строке очереди только название сценария (BUG-41, §14.5).
- **[факт]** Нормативы — по типу события, приоритету и группе устройств (§4, правило 2; `timers[].overrides`: `eventType?`, `priority?`, `sourceGroup?`). Цепочка эскалации — одна на схему (`escalation.levels`), схема выбирается по типу события, группе и приоритету (§14.4).
- **[факт]** Объединение (§11.3) — только у одного сценария; инвариант Quint `linkedSameScenario`. Пожарный и медицинский инциденты не объединить никак.
- **[факт]** Сервер сейчас: событие × подошедшие правила × **подошедшие условия одного правила** × сценарии правила; отметка «обработано» вне транзакции; уникальности по событию нет; после миграции 010 инцидент не знает своего правила ([14, п. 4](../14-im-backend-operator.md)). То есть сервер уже ближе к М2, чем к §14.5, но с дублями.
- **[факт]** В модели Quint доступ задан абстрактно — множество инцидентов на оператора (`core.qnt`, `access`), появление — `create(i, sc, prio)` со своим сценарием. Несколько инцидентов на событие модель уже допускает: связи «одно событие» в ней просто нет.

## 2. Сравнение моделей

| | М2 (база) | М2 + М1: адресат при создании | М3: задания служб в инциденте | М4: один + ручной «смежный» |
|---|---|---|---|---|
| Машина | `create` без изменений. Нормативам — ключ `scenario` (или `rule`) в `overrides` | + новый переход появления: `route_on_create` (`new` → `pending_acceptance`, `trigger: event`, условие «группа правила может принять и кто-то на месте»), эффекты как у передачи, но без `transfer_count +1` | Новая сущность «задание» со своим состоянием, владельцем, таймерами, ходом сценария. По сути машина переезжает на задание, инцидент становится контейнером. Лимиты, объединение §11, «Перехватить», эскалация, перерыв — всё переопределять | Новое ручное действие `spawn_sibling` (без смены состояния исходного) + второй вход в `create` с ручным триггером |
| Правила | §14.5 переписать («одно событие — один инцидент» → «инцидент на сценарий»); §15 — закрыть вопросы ранжирования и приоритета; §2.2 — поля события и правила; §4 — ключ норматива; §19.2 — фильтр по сценарию | то же + §8.1 (адресация при появлении), §6.2 (строка перехода), §8.3 (что если группа недоступна) | переписать §2–§11 почти целиком | §6.1, §6.3, §14.5 |
| Контракт | `IncidentSummary`: `eventGuid`, `ruleId`/`ruleTitle`, `siblingCount`; карточка: `siblings[]`; фильтр очереди `scenario` | то же; `assignmentGroup` при появлении уже есть | новые схемы заданий, переходы по заданию | `siblings[]`, переход `spawn_sibling` с формой «служба» |
| Сервер МИ | переписать обработчик событий (нужно и так): все инциденты события — в одной транзакции с отметкой, уникальность, ссылка на правило | + дежурная группа у правила (новое поле правила) | очень много | средне |
| Quint | новых инвариантов почти не нужно; поле `eventGuid` для отчёта, по желанию | `create` в `core.qnt` с выбором группы; инвариант «при появлении — только группе, которая может принять, иначе в очередь»; `pendingAddresseeCanAccept` уже покрывает итог; порчи нового перехода | модель переписать | новое действие; инвариант «смежный — другого сценария» |
| Объём | **M** (машина S, правила M, сервер M) | **M+** (машина M) | **L** | **M** |
| Главный риск | службы не разделены ни доступом, ни очередью (дыры Д1, Д2) | отклонённый уходит в общую очередь и теряет службу (Д10) | всё переделать; ни одна проверка не переживёт без переписывания | человек забыл нажать — медики не вызваны; потеря времени реакции |

**[мнение]** М3 отпадает по цене: это вторая машина внутри первой, а все механизмы (§8–§12) завязаны на одного владельца инцидента. Плюс М3 — один закрывающий результат и одна карточка — достигается в М2 дешевле: смежные видны в карточке (ниже). М4 противоречит задумке пользователя («фильтры порождают инциденты») и держит безопасность на памяти оператора.

## 3. Как М2 (и М1) взаимодействуют с существующими механизмами

| Механизм | М2 | М2 + М1 |
|---|---|---|
| Передача дежурной группе §8.1 | не задействована; служба берёт «Взять» из общей очереди — кто первый | инцидент сразу «Вашей группе» (§2.4), фильтр «Мне на принятие» (§7) — это и есть очередь службы. Чужая служба принять не может (`isTarget`), только «Перехватить» по `incident:reassign` |
| Автоэскалация §9 | одна цепочка на всех: не взятые вовремя пожарный и медицинский уходят одному старшему (Д4) | реакция при маршрутизации продолжается, как при передаче из `new` (RULE-82 по смыслу). Уровень 0 у «Ожидает принятия» уже бывает (после ручной передачи) — эскалация на уровень 1 работает как есть; правило «не тому же адресату» (RULE-93) тоже |
| Выборка и привязанные §11 | разные сценарии не объединить (`linkedSameScenario`) — это правильно. «Выделить по фильтру» с «Одинаковый сценарий» — готовый инструмент службы для пачки своих событий | то же; чужие и ожидающие принятия в объединение не входят (§11.2) — адресованные группе берут «Принять», потом объединяют |
| «Массовый сбой» | N служб — N инцидентов на событие: закрывать в N раз больше, `limits.maxBulk` наступает раньше | то же; закрыть адресованное группе из очереди можно (`pending_acceptance` в списке «Откуда», §2.2) |
| Нормативы реакции | у смежных одинаковы, кроме различий по приоритету правила; свой норматив службы не задать (Д3) | то же |
| Счётчики дерева §19.1 | считают инциденты, а не тревоги: пожар у одного датчика — «2» | то же |

## 4. Дыры, которых не видно сразу

- **Д1. Доступом службы не разделить.** [факт] Доступ — по устройству (§5), а у смежных инцидентов устройство одно. Фраза М2 «службы разбирают сами по группам доступа» не работает: пожарный и медик видят оба инцидента одинаково. Варианты: (а) ничего не прятать — смежный виден как ситуационная картина; (б) группы доступа по правилу/сценарию — новое измерение доступа. Для модели Quint (б) бесплатно (доступ там абстрактный), для сервера и §5 — средне, а `linked_lost_access`, проверки «адресат может принять» и поток событий поедут за ним автоматически. [мнение] Достаточно (а) + Д2.
- **Д2. Очередью службы не разделить.** [факт] Все фильтры §7/§19 у смежных совпадают. Нужен фильтр по сценарию (или по «службе» правила) в §19.2 — дёшево, только интерфейс и контракт. Без него М2 — общая очередь, где пожарный может по ошибке «Взять» медицинский.
- **Д3. Нормативы службы.** [факт] Ключа `scenario`/`rule` в `overrides` нет. Без него у медицинского тот же срок реакции, что у пожарного. Правка машины — S: новый необязательный ключ, правило «самая специфичная строка» уже есть.
- **Д4. Одна цепочка эскалации на всех.** [факт] `escalation.levels` одна на схему; схема выбирается без правила (§14.4). Не взятый медицинский уйдёт старшему пожарной смены. Варианты: схема по правилу/сценарию (§14.4 — добавить измерение) или уровни эскалации у правила. [мнение] Отложить до первой жалобы, но записать в §15: это не S.
- **Д5. Дубли от пересекающихся фильтров.** [факт] Ключ М1 «событие + правило» не ловит два правила одного смысла: «Пожар в здании А» и «Пожар — любой» оба сработают, сценарий один, инцидентов два. Ещё один источник — несколько подошедших условий одного правила (сегодня в коде). Предложение — **ключ уникальности «событие + сценарий»** (`UNIQUE(event_guid, scenario_guid)`): правила с одним сценарием сводятся в один инцидент, а какое из них главное (приоритет, дежурная группа) — по уже записанному ранжированию §14.5 (точность условия → приоритет → раньше созданное). Открытый вопрос §15 о ранжировании сужается: он нужен только внутри одного сценария. Плюс предупреждение при сохранении правила: «сценарий X уже есть у правила Y с пересекающимся условием». Следствие: две службы не могут делить один сценарий — нужен свой сценарий на службу; это записать в §14.5.
- **Д6. Повтор события.** [факт] Сегодня повтор — 500 или второй набор. Нужно: все инциденты события и отметка «обработано» — одна транзакция, всё или ничего; уникальный индекс из Д5; повтор того же `event_guid` — без изменений, 200. Если правила поменяли между первой доставкой и повтором — повтор ничего не досоздаёт (иначе набор зависит от времени доставки). Отдельно (вне этой темы): повторная тревога с **новым** `event_guid` даёт новый набор из N — шум множится на число служб.
- **Д7. Ложная тревога в одной службе.** [мнение, решение нужно] Пожарный выяснил «ложная» — медицинский остаётся открытым, медик едет. Автоматически закрывать смежные нельзя (службы независимы, у каждой свой результат и своё право), но медик должен узнать: событие потока смежным «INC-N закрыт: Ложная тревога» и плашка в карточке. Это не переход машины — `ui.observerNotice` и новый адресат «владельцы смежных».
- **Д8. Что видит оператор без доступа к смежному.** [факт] По §5 невидимое не видно никак, даже номером. Если введут Д1(б), список смежных в карточке показывает только видимые; «есть ещё, но вам не видно» показывать нельзя — это утечка. Счётчик `siblingCount` считать по видимым.
- **Д9. Два правила адресуют одну группу (М1).** [мнение] Разные сценарии → группа получает два инцидента одного события, каждый «Принять» отдельно, оба занимают `maxActive`, объединить нельзя. Для малого поста (один человек на обе службы) М2 удваивает работу — тут М3 был бы удобнее, но не ценой L. Одинаковый сценарий → по Д5 инцидент один.
- **Д10. Отклонение и возврат теряют службу (М1).** [факт] «Отклонить», «Вернуть в очередь», уход адресата без группы, потеря доступа — инцидент в общей очереди `new`, адресация правила забыта. Дальше его может взять другая служба. Варианты: оставить (как сейчас при передаче) / «возврат в очередь службы» — новый смысл `assignment_group` без «Ожидает принятия», что ломает инвариант `ownerByState` и §8.1 («группа только в `pending_acceptance`»). [мнение] Оставить; фильтр по сценарию (Д2) и так покажет его службе.
- **Д11. Группа службы недоступна при появлении (М1).** [мнение] Ручная передача отсутствующей группе разрешена (§8.1), эскалация такую пропускает (§8.3, RULE-100). Появление — системное действие, поэтому как эскалация: если в группе никто на месте не может принять — в общую очередь `new` + запись в журнал; иначе реакция пройдёт у пустой группы. Это условие нового перехода и новый инвариант Quint.
- **Д12. Почему маршрутизация — отдельный переход, а не эффект `create`.** [факт] `create` ведёт в `new`, а `assignment_group` бывает только в `pending_acceptance` (§8.1; Quint `ownerByState`). Второй переход с `from: []` нарушит RULE-61 и проверку «ровно одно начальное» (`check_machine.py`). Значит — `create` → `new`, сразу за ним `route_on_create` (`trigger: event`, исполнитель — диспетчер) в той же транзакции. В `check_machine.py` (`automatic()`) появление уже исключено из планировщика — второй переход `trigger: event` надо так же исключить из проверок одновременных таймеров.
- **Д13. Отчёты.** [факт] «Сколько тревог» ≠ «сколько инцидентов». Нужны `event_guid` и правило у инцидента (вернуть ссылку, удалённую миграцией 010). Нарушения нормативов — на инцидент, как сейчас: у каждой службы свои, и это правильно — суммировать нарушения по событию нельзя.
- **Д14. Приоритет у смежных разный** (решение пользователя: приоритет — от правила). Очередь по приоритету разнесёт смежные далеко — пожарный вверху, медицинский внизу. [мнение] Это верно по смыслу; связь показывает `siblings[]` в карточке. Строка §2.5 «У инцидента» о числе от источника — переписать.

## 5. Рекомендация

**Принять М2 с ключом уникальности «событие + сценарий»; адресацию М1 сделать необязательным полем правила («дежурная группа службы»), не обязательной частью модели.** [мнение]

Обоснование:
1. М2 — задумка пользователя и почти то, что сервер делает сегодня; машина почти не меняется: `create` как есть, состояний и переходов не добавляется. Quint не ломается: ни один инвариант не зависит от того, сколько инцидентов на событие.
2. Без М1 службы не разделены ничем (Д1, Д2). Самое дешёвое разделение — **фильтр очереди по сценарию** (только интерфейс и контракт). М1 сверху даёт настоящую очередь службы («Вашей группе»), защиту от чужого «Взять» и уведомление группе — за цену одного нового перехода. Делать М1 вторым шагом, после фильтра, если службам на посту реально нужна адресация.
3. Ключ «событие + сценарий» (Д5) убирает дубли от пересекающихся фильтров и сужает открытый вопрос ранжирования §15.

Порядок работ:
- **Шаг 1 (обязательно, M):** §14.5 — «инцидент на каждый сценарий подошедших правил, один на пару событие + сценарий; главное правило пары — по ранжированию»; закрыть оба вопроса §15 (ранжирование — только внутри сценария; приоритет — от правила, переписать §2.5 и описание `create`); §2.2 и контракт — `eventGuid`, `ruleId`, `siblings[]`; сервер — одна транзакция, `UNIQUE(event_guid, scenario_guid)`, ссылка на правило; шаг самопроверки — два инцидента на одно событие, повтор события не создаёт третьего.
- **Шаг 2 (S):** фильтр очереди по сценарию (§19.2); ключ `scenario` в `overrides` нормативов (Д3); уведомление смежным о закрытии (Д7).
- **Шаг 3 (по необходимости, M):** М1 — `route_on_create` с правилом Д11, новый инвариант Quint, порчи, §8.1/§6.2.
- **В §15 записать:** цепочка эскалации на службу (Д4); группы доступа по правилу (Д1б); повторная тревога с новым `event_guid`.
