# Эмулятор агента для тестов

Дата: 2026-11-10. Статус: проект, кода нет.

> Протокол, который реализует эмулятор, описан в сервере: `docs/agent-api/` (README, `agent.openapi.yaml`, примеры), 2026-11-12.

## Зачем

Вход агентов в МИ ещё не решён: регистрация должна быть по схеме `updateagent` ([72, п. 2.1](72-remaining-work.md)). Ждать её мы не хотим: систему нужно тестировать и отдать на тестирование уже сейчас. Эмулятор агента нужен только для этого. Потом его сводим с настоящим агентом в один, поэтому топологию и события он передаёт так, как будет передавать настоящий агент, а не через временные методы.

## Что должно получиться

- Все тестовые данные лежат в одном JSON-файле: агент, типы устройств, типы событий, устройства и их идентификаторы. Файл сначала смотрит и правит человек.
- Группы в файл не входят: их ведут в конфигураторе МИ.
- Раз в 10 секунд эмулятор перечитывает файл и отправляет топологию. Типы устройств, типы событий и устройства появляются в базе МИ и видны в конфигураторе, руками их не заводят.
- Раз в секунду эмулятор отправляет одно событие. Устройства перебираются по порядку, у каждого все его типы событий, затем всё повторяется сначала.
- Запуск из командной строки, остановка по Ctrl+C. В консоль выводится, что ушло и что ответил сервер.

**Не делаем:** интерфейс эмулятора, паузу, ручную отправку, сценарии и последовательности событий, макросы (канал «сервер → агент»), настоящую регистрацию агента.

**Провал, даже если всё работает:** тестовый вход доступен где-то кроме локального стенда; формат топологии и событий расходится с API агента, и при сведении придётся всё переписывать.

## Что уже есть на сервере МИ

`incident-manager-server`, `api/im/backend.openapi.yaml`. Все методы ниже требуют вход агента по HMAC (`security: Agent`):

| Метод | Тело | Что делает |
|---|---|---|
| `POST /sync/sources/types` | `[{uid, name}]` | сверка типов устройств агента |
| `POST /sync/sources/event-types` | `[{uid, name, sourceTypeUid}]` | сверка типов событий |
| `POST /sync/sources` | `[{uid, name, typeUid, isOnline}]` | сверка устройств |
| `POST /events` | `guid, sourceUid, eventTypeUid, payload` | событие → правила → инциденты |

Как работает сверка (`internal/im/appservice/sync/`): сервер берёт полный список от агента, новое заводит, существующее обновляет (сравнивает по `uid`), пропавшее помечает удалённым (`deleted_at`). Строку не стирает, история остаётся.

## Варианты

- **А. Настоящие методы агента и тестовый вход на сервере — выбран.** Эмулятор шлёт в sync-методы и `/events`. На сервере есть настройка, которая включает вход без подписи и работает только локально. При переходе на `updateagent` у эмулятора меняется только вход.
- Б. `/test/events` и методы конфигуратора (`/sources`, `/sources/types`). Сервер не трогаем, но методы не агентские, сверки с удалением нет, при сведении всё переписывается.
- В. Честно проходить текущий HMAC (токен, `POST /agents`, подпись). Сервер не трогаем, но это работа, которую выбросим после перехода на `updateagent`.

## Решения

1. **Прямой вход (сервер), без токенов и регистрации** — решение joynickray 2026-11-10. Настройка `IM_AGENT_DEV_AUTH`, по умолчанию выключена. Включена — запрос агента с заголовком `X-Dev-Agent: <GUID агента>` пускается без подписи HMAC, но **только с адреса этой же машины** (127.0.0.1, ::1). Агента с таким GUID сервер заводит сам при первом запросе, у заказчика установки. Выключена или запрос не с этой машины — заголовок ничего не значит, работает обычная проверка HMAC. При включённой настройке сервер при старте пишет в журнал предупреждение. Вход HMAC через токен остаётся как был.
2. **Повторный запуск и пропавший датчик.** Используем сверку, которая уже есть: пропал из файла — помечен удалённым, история остаётся. Чего не хватает, записываем в техдолг, к эмулятору это не относится:
   - датчик вернулся (тот же `uid`) — нужно снять отметку, а не заводить новую запись (проверить, что делает сервер сейчас);
   - у правил, которые ссылаются на удалённый датчик, — предупреждение в конфигураторе; выбрать такой датчик в новых правилах нельзя.
3. **Идентификаторы в файле постоянные.** Сменили `uid` — для МИ это другой датчик.
4. **Порядок отправки топологии:** типы устройств → типы событий → устройства. Каждый запрос опирается на предыдущий.
5. **Событие:** новый `guid` у каждого, время — текущее. `payload` берётся из файла, если он задан у типа события, иначе пустой. На выбор правил `payload` не влияет.
6. **Интервалы** — в файле (`eventIntervalSec: 1`, `topologyIntervalSec: 10`), их можно переопределить ключами запуска.
7. **Где живёт:** эмулятор уже есть — `~/Work/incident-manager-server/tools/agent-emulator/`, ветка `feature/im_operator` (этап 3: `enroll`, `sync`, `event`, `replay`, `demo-config` на данных `demo.json` прототипа, вход HMAC). Дорабатываем его в этой же отдельной папке: своя команда `run`, свой файл `testdata/agent-emulator.json`, свой `README.md`. Прежние команды не трогаем.

## Формат тестового файла (черновик)

```json
{
  "agentGuid": "0193f000-0000-7000-8000-000000000e01",
  "eventIntervalSec": 1,
  "topologyIntervalSec": 10,
  "sourceTypes": [
    {
      "uid": "door-sensor",
      "name": "Датчик двери",
      "eventTypes": [
        { "uid": "door-forced", "name": "Дверь взломана", "payload": { "zone": "Склад" } },
        { "uid": "door-held",   "name": "Дверь удерживается" }
      ]
    },
    {
      "uid": "smoke-detector",
      "name": "Датчик дыма",
      "eventTypes": [
        { "uid": "smoke", "name": "Задымление" },
        { "uid": "fault", "name": "Неисправность" }
      ]
    }
  ],
  "sources": [
    { "uid": "door-01",  "name": "Дверь склада, ворота 2", "typeUid": "door-sensor",    "isOnline": true },
    { "uid": "smoke-01", "name": "Дым, серверная",         "typeUid": "smoke-detector", "isOnline": true }
  ]
}
```

Типы событий вложены в тип устройства: так в файле видно, какие события у какого датчика. В запрос `sync/sources/event-types` эмулятор разворачивает их в плоский список с `sourceTypeUid`. Адрес сервера — ключ `--server` эмулятора (по умолчанию `127.0.0.1:5000`), в файл не входит.

## Порядок работ

1. Черновик тестового файла. Его смотрит человек, правит состав датчиков и событий.
2. Сервер: тестовый вход по настройке, тесты на «включено / выключено».
3. Эмулятор: чтение файла, отправка топологии по таймеру, перебор событий по таймеру, вывод в консоль.
4. Проверка на стенде:
   - после запуска датчики и типы видны в конфигураторе;
   - события доходят, по ним создаются инциденты, если есть правила;
   - убрали датчик из файла — через 10 секунд он помечен удалённым, история на месте;
   - без настройки сервер отвечает 401.
5. Техдолг: пункты из решения 2, плюс «убрать тестовый вход после перехода на `updateagent`».

## На усмотрение исполнителя

Имя настройки и заголовка, где в сервере проверять вход (рядом с проверкой HMAC), формат вывода в консоль, ключи командной строки.
