# План 85: срез живых инцидентов в памяти сервера

> **Для исполнителя:** навыки superpowers:executing-plans и superpowers:test-driven-development. В каждой задаче сначала тест, он должен упасть, потом код, потом тест проходит. Шаги — чекбоксы `- [ ]`.

**Цель:** дерево групп со счётчиками, счётчики очереди и страница живой очереди считаются из памяти сервера, а не запросом по всем живым с проверкой правила доступа. Цифры при 50 операторах и 45 тыс. живых:
- p95 очереди ≤ 300 мс;
- приём событий ≥ 160 в секунду;
- время базы за 4 мин кратно меньше 1 922 с;
- срез и база расходятся 0 раз.

## Как устроен срез

- **Запись** — одна на живой инцидент. Живой — не удалён и не в состоянии «завершено» машины. В записи:
  - номер, состояние, владелец, группа назначения, `linked_to`;
  - сценарий, приоритет (guid);
  - срок реакции (`due`, `fired`);
  - источник, тип источника, тип события, время события.
- **Постройка** — при первом запросе заказчика. Сначала берётся курсор (последняя строка ленты), потом одним запросом читаются все живые.
- **Догонка ленты** — перед каждым ответом, синхронно: строки ленты после курсора. Новые guid перечитываются из базы одним запросом. Так клиент сразу видит свою же запись: сначала запись, потом чтение. Запросы одного заказчика, пришедшие во время догонки, ждут её, если она началась после их прихода.
- **Перестройка:**
  - разрыв ленты (`Feed.From` → `ok=false`);
  - другие состояния «завершено» у машины;
  - хуки: сброс МИ, стенд, восстановление настроек — рядом с `Access.InvalidateAll()`.
- **Видимость** — из кэша доступа плана 80, по ключу события. Сам срез видимость не хранит.
- **Сверка** — в фоне раз в `IM_LIVE_SLICE_VERIFY` (по умолчанию 5 мин). Пересчёт из базы сравнивается со срезом. Инциденты, которые за время сверки изменились по ленте, не сравниваются. Расхождение — в лог (warn) и в счётчик расхождений, затем перестройка.
- **Запасной путь** — запрос в базу, как сейчас. По нему идут: поиск, фильтр по типу устройства, списки с завершёнными, `IM_LIVE_SLICE=off`.

## Решения по ходу

Сделано по задачам 0–3 (2026-11-13), подробности — в отчёте:
- тесты сервера: полный прогон после задачи 0 — 27 пакетов, 0 падений; тесты обработчиков со срезом — зелёные после правок шести старых тестов, которым нужен путь без среза или сброс среза после записи мимо ленты;
- сравнительные тесты «срез = SQL» (`live_slice_equiv_test.go`) написал отдельный агент по описанию, не видя кода среза: 10 тестов, 3 324 сравнения, 0 расхождений;
- тестовые записи прямым SQL (`testDB`) сбрасывают срез через трассировщик pgx: сервер мимо ленты не пишет, тесты — пишут.

1. **Догонка ленты синхронно, перед ответом, а не фоновым читателем.** Тесты и клиент ждут, что после своей записи сразу видят новые счётчики. Цена — один короткий запрос ленты по индексу на запрос оператора, если в ленте ничего нового.
2. **Страница живой очереди целиком из памяти** (порядок, страница, `focus`). В базу уходят только строки страницы. Вариант «передать список видимых в SQL» хуже: 45 тыс. guid в параметре на каждый запрос, и сортировка всех живых всё равно остаётся в базе.
3. **Значения приоритетов срез держит у себя** вместе со справочником всех уровней заказчика, удалённые тоже: у инцидента может остаться такой уровень. Перечитывает их по строке ленты `reference.priorities_changed`. Её пишут правка уровней (оба API), стенд, а теперь и восстановление из копии (задача 0). Лишнего запроса на каждый ответ нет.
4. **Фильтр по типу устройства и поиск остаются в базе.** Тип устройства берётся из текущей записи источника, а не из события. Поиск — по тексту из трёх таблиц. Обе ветки редкие.
5. **Фоновая сверка — только на время приёмки** (пользователь, 2026-11-13: «думаю, не нужно будет в итоге»). На замерах она включена: по ней видно, что расхождений 0. После приёмки — `IM_LIVE_SLICE_VERIFY=0` по умолчанию; код остаётся и включается переменной.
6. **Хвост приёма под блокировкой счётчика короче (Н-13).** Резерв номеров, номера инцидентов и отметка события «обработано» — один запрос (`NumberIncidents`) вместо трёх. Блокировка ленты и NOTIFY — один запрос вместо двух: NOTIFY уходит только при коммите, так что его можно запросить до INSERT. Журнал действий остаётся после номеров: таблица только на добавление (миграция 045), номер берётся при записи строки, а правка строки запрещена. Перенести журнал в общий запрос — значит отказаться от правила «сбой журнала не валит приём» (точка сохранения), это не делал.
7. **Дерево и счётчики — по готовым суммам среза, а не по записям.** После замера 2 дерево отвечало за 110 мс при 45 тыс. живых, хотя в базу почти не ходило: на каждый запрос сервер дважды проходил по всем записям среза (классы и счёт по источникам) — 12–17 мс процессора, а под 50 операторами процессор общий с базой и нагрузкой. Теперь срез держит суммы по ключу «источник, тип источника, тип события, сценарий, приоритет, состояние, владелец, группа» и обновляет их вместе с записями. Дерево и счётчики идут по суммам: сотни–тысячи ключей вместо десятков тысяч записей. Замер в тесте (`BenchmarkLiveSliceTree`, 45 тыс. записей): 12–17 мс → 0,08 мс. Страница очереди по-прежнему проходит по записям: ей нужен порядок.
