# План 80: постоянный кэш доступа в памяти

> **Для агентов-исполнителей:** обязательный навык — superpowers:subagent-driven-development (рекомендуется) или superpowers:executing-plans. Шаги — чекбоксы `- [ ]`.

**Цель:** вопрос «видит ли человек этот инцидент» в сервере МИ отвечается из памяти, без запроса `AccessMatrix` к базе. Планировщик разбирает долг эскалаций за минуты, а не за десятки часов.

**Устройство:**
- В сервере появляется один на процесс `AccessCache`: по заказчику — правила доступа, состав групп устройств, версия дерева групп. Ответ «группа пользователя × ключ события → да/нет» считается в Go.
- Кэш живёт постоянно и обновляется при изменениях: каждое место записи правил, дерева и состава групп вызывает `Invalidate(customer)` напрямую. При старте процесса кэш пуст и загружается при первом вопросе. Перечитывания по времени нет (решение пользователя 2026-11-12): вместо него — проверка по коду, что любая запись идёт через функции со сбросом.
- Чтение под `sync.RWMutex`. Сброс собирает новую неизменяемую копию заказчика вне блокировки и под `Lock` подменяет указатель.
- `AccessMemo` берёт указатель на копию один раз и держит его всю попытку — решение 70 сохраняется.
- Группы человека — как сейчас, из справочника (`peopleSnapshot`/`Seen`). Кэш их не хранит.

**Технологии:** Go (сервер `~/Work/incident-manager-server`, ветка `feature/im_operator`, голова `c560f58`), PostgreSQL стенда.

**Спецификация:** [80-access-cache-research.md](80-access-cache-research.md) — разделы «Из чего складывается доступ», «Проект», «Что нельзя отловить», «Риски». Решения пользователя 2026-11-12:
- кэш постоянный, в памяти, обновляется при изменениях, под `sync.RWMutex`; подмена указателя на неизменяемую копию допустима;
- кэш на один такт (одна память доступа на весь такт) — отвергнут;
- сервер один; второй экземпляр — только абзац «на будущее» (ниже);
- группы пользователя берутся из справочника, как сейчас.

**Повод:** [отчёт задачи 5 плана 79](../../.superpowers/sdd/79-plan-event-scheduler/task-5-report.md), раздел «Почему разбор медленный». После плана 79 такт разбирает ~1,3 перехода/с, долг 100 тыс. просроченных уйдёт за ~42 ч. На каждый переход `ticker.fire` строит новый мир (`operator/scheduler.go:473`, `NewSchedulerWorld` в `operator/scheduler_world.go:30`), в нём новый `NewAccessMemo`, и первый вопрос о доступе идёт в базу: `AccessMemo.Access` → `readKeys`/`readKnown` → `Store.AccessMatrix` (`storing/access_queries.go:100`, `WITH rules AS …`), 100–900 мс.

## На какие образцы опираемся

| Что в плане | Образец | Что берём |
|---|---|---|
| Задачи 1, 3: кэш, который сбрасывается при записи | Обычный приём «cache-aside с инвалидацией при записи» (кэши прав в Keycloak, Spring Security ACL cache) | Сброс в месте записи — единственный путь обновления; срок жизни не берём |
| Задача 1: неизменяемая копия и подмена указателя | Read-copy-update; `atomic.Value`/`RWMutex` в Go для снимков настроек | Читатель держит свой снимок, писатель не ждёт читателей |
| Задача 2: один смысл в двух местах — сверка тестом | Дифференциальное тестирование (сверка двух реализаций на случайных входах, как `TestTickMemoSameAsFullRandom` плана 79) | Векторы + случайные наборы, SQL и Go дают один ответ |
| Задача 3: защита от забытого места записи | Архитектурные тесты по коду (ArchUnit, `go/analysis`): правило «запись в таблицу — только через разрешённые функции» проверяется в CI | `TestAccessWritesInvalidate` вместо перечитывания по времени |

Своё у нас только одно число — предел ответов. Их проверяет задача 6 на стенде.

## Почему уверены, что это поможет, — и что, если нет

**Уверенность опирается на факты:**
1. На стенде такт не упирается в процессор: CPU 14–24 %, Warn `the tick took long` — 0. Время уходит на ожидание базы (отчёт задачи 5).
2. В `pg_stat_activity` видны запросы `WITH rules …` по 100–900 мс, по одному и больше на переход.
3. Ответ доступа зависит только от правил, дерева, состава групп устройств (всё это пишет сам МИ) и групп человека (уже берутся из справочника). Проверка правила в памяти — микросекунды.

**Чего мы не знаем:** сколько именно `AccessMatrix` приходится на переход и какая доля времени такта на них уходит. После снятия этого запроса такт может упереться в другое: чтение семьи (`Around`), `EventKeys`, запись журнала. Поэтому первой идёт **задача 0: замер до правок**, с условием остановки. Ожиданий по скорости без замера не обещаем.

## Общие ограничения

- Машина (`workflow_schema.v1.json`), правила, контракт `openapi.json`, прототип **не меняются**. Ожидаемое в `transition-vectors.json` не меняется.
- SQL-условие `accessRuleMatch` остаётся: им пользуются очередь, счётчики, `VisibleIncidentIDs`, v1. План переводит на кэш только `AccessMemo`.
- Решение 70 сохраняется: в одной попытке перехода ответы доступа не меняются (одна копия на попытку). Решения 67, 206, 214 — как есть. Обход доступа (sweep) остаётся.
- Ошибка загрузки кэша — ошибка вопроса, как сейчас ошибка `AccessMatrix`. Ответа «нет доступа» по ошибке не бывает, старое после неудачной загрузки не отдаётся.
- Коммиты — по одному на задачу. Сообщения на русском, простыми словами, с префиксом `План 80, задача N:`. Пуш — только по просьбе пользователя.
- Тесты сервера — на тестовой базе (`make test-db-up`, `IM_TEST_DB_URL`), никогда на `imdb` стенда.
- Сервер стенда перезапускается только в задаче 6, под замком `~/Work/stand/lock-server`.

## Где опасно (Review Focus)

1. **SQL и Go разошлись.** Условие записано дважды. Особенно: правило без полей (не даёт ничего), правило с группой устройств и подгруппами, мягко удалённое правило, чужой заказчик. Задача 2: `TestAccessCacheSameAsSQL` на векторах и случайных наборах.
2. **Забытое место записи.** Новое место, которое пишет `access_rules`, `source_groups` или `source_group_memberships`, не вызывает сброс — доступ устаревает **до перезапуска процесса** (перечитывания по времени нет). Задача 3: тест на каждый маршрут и `TestAccessWritesInvalidate`: запись в эти таблицы — только из функций, которые вызывают `Invalidate`.
7. **Правка базы руками мимо сервера** (SQL, миграция данных). Кэш её не увидит до перезапуска. Это **принятое ограничение** (решение пользователя 2026-11-12), записывается в ADR-006 (задача 7). Опция — тестовый маршрут сброса только в сборке `imtest` (задача 3, шаг 6).
3. **Сброс посреди попытки.** Если `AccessMemo` спросит кэш дважды и между вопросами прошёл сброс, решение 70 нарушится. Задача 4: `TestAccessMemoKeepsCopy`.
4. **Ошибка перечитывания.** После сброса загрузка упала — нельзя отдать прежнюю копию. Задача 1: `TestAccessCacheLoadErrorDropsOld`.
5. **Потерянный сигнал шины.** `EventBus.Publish` (`infrastructure/eventbus/eventbus.go:26-37`) выбрасывает событие, если буфер (10) полон. Кэш на шину не полагается: сброс — прямым вызовом. Задача 3.
6. **Гонки.** Параллельные вопросы и сбросы — `go test -race` (задача 5).

### Задача 1: `AccessCache` — загрузка, проверка в Go, поколение

**Файлы:**
- Создать: `internal/im/appservice/operator/access_cache.go`, `access_cache_test.go`.
- Изменить: `internal/im/service/storing/access_queries.go` — два запроса загрузки по заказчику: живые правила и состав групп устройств.

**Интерфейсы:**
- Даёт:

  ```go
  type AccessCache struct { /* mu sync.RWMutex; by map[uuid.UUID]*accessCopy */ }
  func NewAccessCache(store AccessCacheStore, tree SourceTree) *AccessCache
  func (c *AccessCache) Copy(ctx model.AppContext, customer uuid.UUID) (*AccessCopy, error)
  func (c *AccessCache) Invalidate(customer uuid.UUID)
  func (c *AccessCache) InvalidateAll()
  func (a *AccessCopy) Grants(group int64, key model.AccessKey) bool
  ```

  `AccessCacheStore`: `AccessRulesOf(ctx, customer)`, `SourceMembershipsOf(ctx, customer)`.
- `AccessCopy` неизменяема после сборки: правила по группе пользователя, «устройство → прямые группы», версия дерева (`ClosurePairs()`), `loadedAt`, поколение. Готовые ответы `(группа, ключ) → bool` — по замеру: либо не хранить (проверка дешёвая), либо держать в отдельной карте с пределом (например, 1 млн, при превышении очистить).

**Правило проверки** (тот же смысл, что `accessRuleMatch`, `access_queries.go:12-55`): правило живое, того же заказчика и той же группы пользователя; каждое заполненное поле (устройство, тип устройства, тип события) совпадает с ключом; если у правила есть группа устройств — одна из прямых групп устройства равна ей или её потомку (`IsSelfOrAncestor` дерева, ADR-001 п. 5); у правила заполнено хотя бы одно поле.

- [ ] **Шаг 1.** Тесты (красные): `TestAccessCacheGrants` (по пункту правила на случай), `TestAccessCacheLazyLoad`, `TestAccessCacheInvalidate` (после сброса — новая копия, старая у держателя не меняется), `TestAccessCacheTreeVersion` (версия дерева не совпала — пересборка), `TestAccessCacheLoadErrorDropsOld` (сброс, загрузка упала → `Copy` возвращает ошибку, не прежнюю копию; следующий `Copy` пробует снова).
- [ ] **Шаг 2.** Код. `Copy` под `RLock` смотрит указатель; если её нет или не совпала версия дерева — собирает новую копию **вне** блокировки и под `Lock` ставит её. Одновременные загрузки одного заказчика схлопнуть (`singleflight` или флаг под `Lock`). `Invalidate` убирает указатель (а не помечает), так старое после ошибки загрузки не отдаётся. Сброс во время загрузки: поколение растёт при `Invalidate`, загрузка, начатая до сброса, свой результат не ставит.
- [ ] **Шаг 3.** `go test ./internal/im/appservice/operator/ -run AccessCache` — зелёные.
