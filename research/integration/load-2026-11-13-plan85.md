# Нагрузка 2026-11-13: итог плана 85 — срез живых инцидентов в памяти

[План 85](85-plan-memory-slice.md), [анализ](85-memory-counters-analysis.md). Сравнение — с [итогом плана 84](load-2026-11-13-plan84.md).

## Коротко

- **Очередь уложилась в цель.** p95 при ~25 тыс. живых — 409 → 184 мс, при ~43 тыс. — 2 091 → 271 мс. Цель ≤ 300 мс.
- **Время базы кратно меньше.** За 4 мин при ~25 тыс. живых — 871 → 208 с, при ~45 тыс. — 1 922 → 305 с (в 6,3 раза).
- **Дерево групп со счётчиками — в 36 раз быстрее.** Один запрос на спокойном стенде при 43 тыс. живых — 126 → 3,5 мс. В базу дерево больше не ходит.
- **Приём событий под 50 операторами — 92–110 → 142–149 в секунду.** Цель 160 не взята, остаток — ожидание блокировки счётчика номеров (Н-13).
- **Срез и база не расходились ни разу:** сверка раз в 5 мин, в логе сервера 0 расхождений, сравнительные тесты — 0.

## Что сделано

1. **Пробелы ленты (Н-12):**
   - строка `incident.updated` на каждый изменённый инцидент без шага, в том числе на детей объединения;
   - убран маршрут `DELETE /api/v1/incidents/{guid}`;
   - восстановление настроек из копии пишет `reference.priorities_changed`.
2. **Срез в памяти.** На каждого заказчика — запись на каждый живой инцидент:
   - строится из базы при первом запросе;
   - перед каждым ответом догоняет ленту и перечитывает изменённые инциденты пачкой;
   - на разрыве ленты и на массовых хуках строится заново;
   - сверка с базой — в фоне.
3. **Дерево и счётчики очереди — из среза, по готовым суммам** (Н-11, Н-1). Суммы — по ключу «источник, тип источника, тип события, сценарий, приоритет, состояние, владелец, группа». Обновляются вместе с записями.
4. **Страница живой очереди — из среза** (Н-2). Порядок, листание и `focus` считаются в памяти, из базы читаются только строки страницы.
5. **Хвост приёма короче (Н-13):**
   - резерв номеров, номера и отметка события — один запрос;
   - блокировка ленты и NOTIFY — один запрос.

Через базу, как раньше, идут:
- поиск;
- фильтр по типу устройства;
- списки с завершёнными;
- запросы внутри транзакции;
- `IM_LIVE_SLICE=off`.

Под нагрузкой ответ — в основном ожидание: сервер, база, 50 операторов и генератор событий делят одну машину. Сессия, где считать нечего, тоже 16 мс против 3 мс в покое. Поэтому сам запрос дерева мерили ещё и отдельно, на спокойном стенде и той же базе. Каждый сервер — 60 запросов, медиана:

Подсчёт в памяти по суммам — 0,08 мс на 45 тыс. записей. По записям, до сумм, было 12–17 мс (`BenchmarkLiveSliceTree`).

### Что осталось в топе базы

При 45 тыс. живых в топе остались запросы с поиском и с фильтром по типу устройства. В нагрузке это ~6 % действий («текст», «тип»). Они идут через базу, так задумано: решение 4 плана.

Хвост приёма: при 25 тыс. живых в окне s1 ожидание блокировки счётчика — 362 с из 657. Под блокировкой остались:
- журнал действий — точка сохранения и строка на каждый инцидент;
- запись ленты;
- коммит.

## Проверки

- Тесты сервера, итоговая сборка:
  - все пакеты, кроме тестов обработчиков, — зелёные (26 пакетов);
  - пакет тестов обработчиков — два полных прогона. Первый: одно падение `TestQueuePriorityState`, подробностей нет: вывод был отфильтрован. Второй — целиком зелёный, 872 с;
  - отдельно этот тест прошёл 3 раза из 3, вместе с тестами очереди и приоритетов — 2 раза из 2;
  - причину не нашли: совпадения случайных значений приоритета исключены. Записано в техдолг Н-14, п. 6.
- Что пришлось поправить в старых тестах:
  - запись ленты теперь один SELECT, а не два (`feedSelects`);
  - перед лентой в приёме теперь идёт журнал (`TestFeedCreatedOnIntake`).
- Сравнительные тесты «срез = SQL» (`live_slice_equiv_test.go`):
  - 10 тестов, 3 324 сравнения, 0 расхождений;
  - написал агент, не видевший кода среза.
- Тесты среза под `-race`.
- `verify_ops.py` по `load45k-85d` — **0 FAIL**. По остальным прогонам его не гоняли сразу, а база потом откатывалась. Поздний прогон по `loadP-85c` дал «нет события»: событий того замера в базе уже не было. Это не ошибка сервера.
- Ревью кода агентом: замечаний с уверенностью выше 80 % нет. Мелкие — в техдолге.
