# 80. Доступ в памяти: исследование кэша

Дата: 2026-11-12. Сервер МИ `~/Work/incident-manager-server`, ветка `feature/im_operator`, голова `c560f58`. Облако — `~/Work/axxoncloudgo`, ветка `epic/CLOUD-23284-perms-i18n` (не переключал). Только чтение кода, ничего не менял.

Повод: после плана 79 планировщик разбирает долг ~1,3 перехода/с. На каждый переход такт строит новый мир (`NewSchedulerWorld`, `internal/im/appservice/operator/scheduler_world.go:30` — новый `NewAccessMemo`), и первый же вопрос о доступе идёт в базу: `AccessMemo.Access` → `readKeys`/`readKnown` → `Store.AccessMatrix` (`internal/im/service/storing/access_queries.go:100`, CTE `WITH rules AS …`), 100–900 мс на запрос.

Проектируем под **один экземпляр сервера**: второго до публичного запуска не будет (уточнение пользователя).

## Ответ на утверждение пользователя

**Подтверждается почти полностью.** Ответ «есть ли у человека доступ к инциденту» зависит от четырёх вещей. Три из них — правила доступа, дерево групп устройств и состав групп устройств — хранит и меняет сам МИ. У каждой есть свои места записи, их можно перечислить, а для двух уже есть сигнал в шине событий. Четвёртая вещь — группы пользователя — приходит из облака вместе с токеном. Облако не сообщает, что состав группы пользователей изменился: в шине NATS есть только темы «пользователь создан» и «пользователь удалён». Но МИ и сейчас знает группы человека только по его последнему запросу (строка `operator_sessions`, память `Seen`). Поэтому кэш, у которого ключ — **группа пользователя**, а не человек, этой части вообще не касается: человек → группы берётся так же, как сейчас, из справочника. Что поймать нельзя: правку таблиц мимо кода МИ (SQL руками, загрузка стенда) и ошибку, если новое место записи забыли подключить к сбросу. Поэтому страховка нужна — перечитывать всё по таймеру (например, раз в 60 с) и сверять версию. Обход доступа (sweep) остаётся: он не кэш, а реакция на потерю доступа.

## Из чего складывается доступ

Условие одно — `accessRuleMatch` (`access_queries.go:12-55`). Правило `ar` даёт ключ события `e = (source, source_type, event_type)`, если:
- правило живое (`deleted_at IS NULL`), того же заказчика и одной из групп человека (`access_queries.go:18-22`);
- каждое заполненное поле правила совпадает с ключом: устройство, тип устройства, тип события (`:36-48`);
- если у правила есть группа устройств, то устройство события входит в эту группу или в любую её подгруппу: замыкание дерева `closure` × `source_group_memberships` (`:23-31`, `:39-41`);
- у правила заполнено хотя бы одно поле (`:49-54`).

Ответ для человека — «ИЛИ» по его группам: `AccessMatrix` разворачивает человека в пары «человек, группа» (`access_queries.go:103-115`, `:89`). Ключ события берётся из `events` (`GetEventKeys`, `:150`); инцидент без живого события не видит никто (`operator/access.go:130-150`).

Что в ответ **не** входит: права облака (`Permissions`, `PermManage` и т. п.). Они проверяют действия и админку, а не видимость инцидента. Флага «активен» нет. Удалённый пользователь просто не приходит с токеном. Решения: 67 — одна матрица на запрос, 70 — память доступа держится всю попытку и под блокировкой, потому что ответы доступа не зависят от записей ядра (`operator/access.go:53-56`, `docs/adr/005-transitions-in-transaction.md:130`); 214 — список людей памяти берётся из `Seen`, таблица не читается (`operator/access.go:26-29`, `operator/directory.go:39-41`); 206 — обход доступа раз в 10 с (`docs/adr/006-scheduler-and-scenarios.md:20`); 209 — второй экземпляр (`docs/adr/006…:22`).

## Проект

**Что держать.** Не готовую матрицу, а сами данные условия: по заказчику — правила, состав групп устройств, версию дерева. Ответ считать в Go. Готовые ответы запоминать:

```go
type AccessCache struct {
    mu  sync.RWMutex
    by  map[uuid.UUID]*customerAccess // заказчик
}
type customerAccess struct {
    gen      uint64                         // номер поколения; растёт при любом сбросе
    tree     uint64                         // версия дерева, с которой собрано
    loadedAt time.Time
    rules    map[int64][]rule               // группа пользователя → её правила
    member   map[uuid.UUID][]uuid.UUID      // устройство → его прямые группы
    answers  map[groupKey]bool              // (группа пользователя, ключ) → даёт ли
}
```

- Проверка `rule × key`: поля совпали, и (группы у правила нет, или одна из прямых групп устройства — это группа правила или её потомок; спросить дерево `IsSelfOrAncestor`, ADR-001 п. 5). Тот же смысл, что у `accessRuleMatch`. Чтобы не было двух текстов условия, тест сверяет оба.
- Человек: `Access(person, key) = OR по person.UserGroupIDs answers[(g,key)]`; группы — из `peopleSnapshot`/`Seen`, как сейчас.
- Объём. Правил — сотни (~100 Б на правило). Состав групп — по строке на устройство в группе: 10 тыс. устройств ≈ 1 МБ. Ответы: групп пользователей G × ключей K; на стенде G ≈ 10–20, K — тысячи ключей событий → ≤ 100 тыс. записей по ~60 Б ≈ 6 МБ. От числа людей **не зависит**: 51 человек или 10 тыс. — разница только в G (групп обычно десятки–сотни). Чтобы ответы не росли без конца, вычислять их дёшево и держать с ограничением (например, сброс `answers`, когда их больше 1 млн) или не хранить вовсе: проверка в памяти — микросекунды.
- Блокировка: `RLock` на чтение. Сброс — собрать новый `customerAccess` вне блокировки, затем под `Lock` заменить указатель. Читатель в `AccessMemo` берёт указатель один раз на запрос — так держится решение 70: в одной попытке ответы не меняются.

**Как обновлять.**

| Что изменилось | Действие |
|---|---|
| правило (Create/Update/Delete) | после коммита — новое событие `EventAccessRulesUpdated(customer)` в шину → перечитать правила заказчика, `answers` очистить |
| дерево | уже есть `EventSourceGroupTreeUpdated`; кэш слушает → очистить `answers`, запомнить версию дерева; при чтении сверять `tree` с `ClosurePairs()` и пересобирать при расхождении |
| состав групп | уже есть `EventSourceGroupMembersUpdated` → перечитать состав заказчика, очистить `answers` |
| резервная копия | `AfterApply` (`appservice.go:450`) — добавить событие правил |
| стенд (`stand/load_*`, `wipe`) | позвать сброс заказчика целиком |

Сброс всегда целиком по заказчику: данные малы, перечитать — два запроса по десяткам миллисекунд. Точечный сброс не окупается.

Нюанс шины: `Publish` неблокирующий и **выбрасывает** событие, если буфер (10) полон (`eventbus.go:26-37`). Для кэша это недопустимо. Либо подписчик кэша с отдельным неблокирующим флагом «грязно» (атомарный счётчик поколения), либо вызывать сброс кэша напрямую из сервисов, а не через шину. Советую прямой вызов `cache.Invalidate(customer)` плюс счётчик.

**Старт.** Ленивая загрузка заказчика при первом вопросе; ошибка — вопрос получает ошибку, как сейчас при ошибке `AccessMatrix` (нет ответа «нет доступа» по ошибке).

**Ошибка перечитывания.** Старое поколение не оставлять: если сброс был, а загрузка упала, заказчик помечается «не загружен», следующий вопрос пробует снова и при ошибке возвращает ошибку. Так устаревшее не отдаётся.

**Ограничение возраста.** `loadedAt` старше X (60 с) → перечитать при следующем вопросе. Это страховка от того, что нельзя поймать (ниже). Итог: устаревшие права живут не дольше X; при правках через API — 0 с.

**Обход доступа (sweep).** Остаётся. Он не кэш, а обработка «человек потерял доступ» (адресат, связанный инцидент), и ему нужно, чтобы источник правды был свежим. С кэшем он станет дешевле: 500 инцидентов страницы — без SQL матрицы.

**Тесты.**
- эквивалентность: случайные правила, дерево, состав → ответ кэша = `AccessMatrix` (на базе в тестах сервера);
- каждое место записи сбрасывает кэш (тест на маршрут: создать правило → доступ появился без ожидания);
- ошибка загрузки не отдаёт старое; возраст > X перечитывает;
- решение 70: в одной попытке ответ не меняется при сбросе посередине;
- `-race`: параллельные вопросы и сбросы;
- замер такта планировщика до и после (как в задаче 0 плана 79).

## Что нельзя отловить и что делать

1. Группы пользователя в облаке — облако не сообщает. Кэш по группам этого не хранит. Как и сейчас, МИ узнаёт о смене при следующем запросе человека (до 30 с память токена, `session.go:431-434`). У людей без запросов (планировщик видит их по строке `operator_sessions`) группы устаревают до их следующего входа. Это уже так и кэшем не ухудшается. Улучшить можно отдельно: периодически читать `GetUserGroupsWithMembers` (`cloud/client.go:223`) или договориться с облаком о теме NATS `user.groups.changed`.
2. Правка таблиц мимо кода (SQL руками, миграция данных) — ловит только ограничение возраста X.
3. Новое место записи, которое забыли подключить, — тоже X; плюс проверка в CI: grep на `INSERT/UPDATE/DELETE` по `access_rules`, `source_group_memberships`, `source_groups` вне известных файлов.

## Риски

- **Два текста одного условия** (SQL и Go) разойдутся при правке правила. Мера — тест эквивалентности обязателен; SQL-условие остаётся для очереди и v1.
- **Шина теряет события** при полном буфере. Мера — прямой вызов сброса и счётчик поколения, а не канал.
- **Забытое место записи** → устаревший доступ до X. Мера — ограничение возраста и проверка в CI.
- **Решение 70**: если подменить поколение посреди попытки, ответы в одной попытке станут разными. Мера — указатель на поколение фиксируется в `AccessMemo` при первом вопросе.
- **Узкое место может сдвинуться**: после снятия `AccessMatrix` такт упрётся в другое (чтение семьи, `EventKeys`). Мера — замер до и после, ожидания по скорости не обещать без замера.
- **Второй экземпляр** без `pg_notify` сделает кэш неверным. Сейчас не актуально, но записать в ADR-006 рядом с решением 209.
