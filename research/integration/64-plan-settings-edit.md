# Правка «Настроек поста» — план

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** администратор меняет настройки поста (разделы `adminSettings.sections` машины) своей организации во вкладке «Настройки поста» конфигуратора: черновик → проверка → публикация → откат; сервер применяет опубликованное сразу, без перезапуска.

**Architecture:** сервер хранит у организации версии настроек как JSON Merge Patch поверх общей машины и держит ядро (`transition.Core`, ручка со снимками, решение 188) на каждую организацию; публикация собирает новый снимок и ставит его атомарно, место оператора перечитывает машину по `workflow.schema_published`. Операции — уже описанные в контракте `/operator/workflow/schemas…`; схема в них — полная `WorkflowDefinition`, сервер принимает в ней изменения только внутри `adminSettings.sections`. Конфигуратор правит значения по `adminSettings.tabs[].items[].path`, своего списка настроек не держит.

**Tech Stack:** Go (gin, oapi-codegen, PostgreSQL 9.6), React + TypeScript + MUI + TanStack Query + zod.

**Spec:** решение пользователя 2026-11-05 — «только настройки» (вопрос шага 4 [плана 63](63-plan-admin-tabs.md)); [SETTINGS.md](../../Specification/Workflow_machine/SETTINGS.md); контракт [openapi.json](../../Specification/Workflow_machine/openapi.json) — `listWorkflowSchemas`, `createWorkflowSchema`, `getWorkflowSchema`, `updateWorkflowSchema`, `validateWorkflowSchema`, `publishWorkflowSchema`, `getActiveWorkflow`, событие `workflow.schema_published`; правила §9 (настройки администратора), §14.6 (версии), §14.7 (проверка); сервер — `internal/im/appservice/machine_patch.go` (`checkPatchSections`), `internal/im/service/transition/core.go`, `pin.go`, `core_swap_imtest.go` (`Prepare`, `Install`).

## Решения (2026-11-05)

- **0.** «Организация» — заказчик в облаке (`customer_guid`): у неё свои пользователи, операторы, устройства, справочники. Один сервер МИ обслуживает несколько организаций; настройки поста у каждой свои и действуют на всех её операторов.

- **1.** Меняются только разделы `adminSettings.sections` (`timers`, `reasonCatalogs`, `escalation`, `alerts`, `limits`, `session`, `queueSort`). Состояния, переходы, формы, права — нет; поэтому сопоставление состояний при публикации не нужно, `stateMapping` не используется, открытые инциденты переводить не надо.
- **2.** Версия настроек организации — патч поверх общей машины (вендоренная, на стенде — после `IM_MACHINE_PATCH`). У организации без опубликованной версии — общая машина, как сейчас.
- **3.** `schema.version` машины под настройками не меняется (как решение 175 у патча стенда): это версия логики. Номер версии настроек — `version` в `WorkflowSchemaSummary` списка и карточки; `ETag` `getActiveWorkflow` меняется с каждой публикацией.
- **4.** Откат — новый черновик из архивной версии и его публикация; своей операции не нужно.
- **5.** `simulateWorkflowSchema` в этот план не входит — остаётся заглушкой.
- **6.** Сервер работает в одном экземпляре (40-plan). Публикация ставит снимок в своём процессе; другие экземпляры — когда будет «два сервера» (Task 23–25 плана 57).
- **7.** Показ на стенде пишет в `imdb` (версии настроек организации стенда) — только после дампа `imdb-before-p64-*.sql`; в конце показа опубликованное откатывается к общей машине.

## Global Constraints

- Ветки `feature/im_operator`: сервер `~/Work/incident-manager-server`, конфигуратор `~/Work/incident-manager`, IM — контракт в `main` (`~/Work/IM-main`), затем `cherry-pick` в `feature/im_operator`.
- Право на все операции схем — `incident:schema:admin`, без него — `403 PERMISSION_DENIED`; `getActiveWorkflow` — без права, как сейчас.
- Изменение вне `adminSettings.sections` — `422 FORM_FIELD_INVALID`, `details.field` — путь первого такого ключа через точку (`transitions`, `states`…).
- Машина организации после патча проходит то же, что `Prepare` тестовой сборки: `machine.Load`, `checkLimits`, `storing.CheckQueueOrders`, сборка ядра; не прошла — черновик не публикуется (`422`), ядро не меняется.
- Один запрос и одна операция планировщика — на одном снимке своей организации (решение 188): `transition.WithCore` с ядром клиента.
- Тесты сервера — на своей базе (`ensure-test-dbs.sh`), не на `imdb`; полный прогон `go test -race ./...` — после каждой задачи сервера.
- Язык интерфейса задаётся снаружи; полей по языкам нет; тексты конфигуратора — ru/en/kk/zh.
- `openapi.json` IM — CRLF.

## Review Focus

- Две организации с разными настройками: таймеры, лимиты, эскалация и очередь каждого идут по своим, планировщик не смешивает (Task 1).
- Публикация во время перехода: переход, начатый на старом снимке, доигрывает на нём; следующий — на новом (Task 2).
- Перезапуск сервера: опубликованные настройки клиентов подхватываются при старте (Task 2).
- Черновик, ставший невалидным после правки общей машины (новая вендоренная версия): проверка показывает ошибку, публикация — `422`, место оператора остаётся на последней опубликованной (Task 2).
- Пустое значение «без ограничения» (`null`) у лимита: JSON Merge Patch удаляет ключ — сервер должен хранить и отдавать `null`, а не значение общей машины (Task 2, Task 3).
