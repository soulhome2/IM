# План 93. Очередь на базе с миллионом закрытых

> **Для агентов-исполнителей:** обязательный навык — superpowers:subagent-driven-development (рекомендуется) или superpowers:executing-plans. Шаги — чекбоксы `- [ ]`. Сервер — по superpowers:test-driven-development: сначала тест, он падает, потом код. Решения ниже приняты, их не пересматривать; чего в плане нет — не придумывать, а остановиться и спросить.

Статус: **расписан** (2026-11-20), решения заполнены.

Порядок: **делается раньше плана [92](92-stats-sql.md)**. Номера планов — имена, не очередь. Поиск, «Все» и выделение — рабочее место оператора, а медленный «За период» плана 92 тормозит в том числе очередь; дамп и разбор медленных запросов отсюда пригодятся 92-му.

**Цель:** на базе с миллионом закрытых инцидентов очередь, поиск и «Выделить → Все в фильтре» отвечают так же быстро, как на маленькой базе, и не грузят базу для остальных операторов.

**Подход:** сначала разбор — EXPLAIN каждого медленного запроса на наполненной базе, потом исправление по одному семейству запросов: поиск, «Все» и подсчёт с правами, фильтр по типу устройства, выделение. После каждого — замер того же запроса, в конце — прогон как A2 плана 90. Смысл ответов не меняется: старые тесты сервера — страховка, что после переписывания запрос находит то же самое.

**Где:**
- IM — `/mnt/hgfs/VmWareShared/soul2home/IM` (план, правила, если решения их меняют, отчёт замера);
- сервер — `~/Work/incident-manager-server`: запросы `internal/im/service/storing/queue_queries.go`, `access_queries.go`, выделение `internal/im/handler/operator/selection.go`, миграции `internal/im/service/storing/migrations/` (последняя — 080);
- рабочее место — `~/Work/incident-manager`, только если решение 2 меняет ответ выделения;
- стенд — `~/Work/stand/load` (скрипты нагрузки), `~/Work/stand/load/plan90G/run_G.sh`, `~/Work/stand/load/explain_queue.py`.

Ветка везде `feature/im_operator`.

## Что не так

Замер: [load-2026-11-19-plan90.md](load-2026-11-19-plan90.md), раздел 4, прогон A2 (1 млн закрытых, 100 операторов, без блока «За период»). По сравнению со ступенью 100 плана 86 (база ~500 инцидентов, 0 ошибок):
- поиск по номеру — p50 49 с, по тексту — 46 с, часть — 504 через 60 с от прокси;
- сверка страницы — p50 27 с, 91 ответ 504;
- очередь по событию потока — p95 55 с;
- вкладка «Все» и фильтр по типу устройства — десятки секунд;
- база занята ~8,7 ядра против ~4,5.

Самый дорогой запрос по `pg_stat_statements` — подсчёт очереди с проверкой прав: ~1 400 вызовов, в среднем 3,2–3,5 с.

«Выделить → Все в фильтре» (стенд 2026-11-19, 51 020 открытых, `limits.maxBulk` = null): `POST /operator/incidents/selection` отвечает 55–60 с и присылает ~7 МБ. Экран ждёт 30 с (`SELECTION_LIMIT_MS`) — оператор видит пустоту, потом «сервер не ответил».

## Почему так (по коду, до EXPLAIN)

Сверка страницы и очередь по событию потока — это тот же `GET /operator/incidents` с фильтрами, что сейчас на экране. Медленные они тогда, когда на экране «Все» или поиск, поэтому чинятся вместе с ними.

1. **Поиск идёт по каждой строке истории.** `queueSearchHit` склеивает номер, номер тревоги и тип события и сравнивает `LIKE '%…%'` у каждого инцидента, плюс название и адрес устройства через `LEFT JOIN sources`. Индекса под это нет. Поиск по номеру — `filter=all`, значит по всему миллиону. Классы для счётчиков с поиском не берутся из `queue_closed_counts` (поиск — не колонка счётчика), так что подсчёт тоже идёт по миллиону строк.
2. **«Все» и подсчёт с правами.** Страница «Все» (`queueListedSQL`) группирует все строки выбранных классов по трём колонкам события, проверяет права у групп и только потом сортирует и берёт 50. На миллионе закрытых это полный проход для каждой страницы.
3. **Фильтр по типу устройства** — `ev.source_guid IN (подзапрос по sources)`: на «Все» тот же полный проход, что в п. 2.
4. **Выделение.** `filterRows` без `maxBulk` берёт всю очередь, `ViewPage` строит вид каждой строки, `selectionActions` спрашивает машину о каждом ручном переходе для каждой строки, `snapshotOf` кладёт в ответ снимок каждой строки — отсюда 7 МБ.

## Общие ограничения

- Postgres на стенде и в облаке — 9.6: нет сгенерированных столбцов, нет `INCLUDE` в индексах, нет `DROP DATABASE … WITH (FORCE)`.
- Индексы на `incidents` и `events` — `CREATE INDEX CONCURRENTLY` в отдельной миграции без транзакции, как `idx_incidents_closed_at`. Миграция на миллионе строк должна пройти на стенде; время записать в журнал (это «к выкату»).
- Опыты — на `imdb` стенда, восстановленной из `~/Work/stand/backup/imdb-G-filled-20261119-0922.dump` (`plan90G/restore_dump.sh`); перед первым опытом — свежая копия нынешней `imdb` в `~/Work/stand/backup/imdb-before-p93-<дата>.sql.gz`.
- Тяжёлое — через `systemd-run --user --scope -q -p MemoryMax=12G -p MemorySwapMax=0 …`.
- Язык документов, коммитов — русский; коммиты кончаются строкой `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`; push — только по просьбе.
- В конце каждой задачи с кодом — сборка сервера на стенд (`~/Work/stand/bin/im-p93-<N>`), потом коммит.

## Что проверить особо

1. **Поиск находит то же, что раньше.** Подстрока номера («184» → INC-1847, INC-11840), номер тревоги («INC-1847» → все видимые инциденты тревоги), тип удалённого события по uid, удалённое устройство — не ищется ни по названию, ни по адресу, адрес из МИ важнее адреса устройства, символы `%`, `_`, `\` в запросе — как обычные. Тесты — в задаче 2.
2. **Поиск в привязанных** (`linked_found`): найденный привязанный выводит строку основного, и только если основной виден правилами.
3. **Права после переписывания «Все».** Оператор не видит строк, которых не дают правила, ни в странице, ни в подсчёте; два правила на одну строку не считают её дважды. Тесты — в задаче 3.
4. **Короткий запрос поиска** (1–2 символа): `pg_trgm` по нему не ищет, запрос не должен откатиться в полный проход на 60 с. Тест — в задаче 2.
5. **Миграция индексов на живой базе** — без блокировки записи инцидентов (лавина идёт во время `CREATE INDEX CONCURRENTLY`). Проверка — в задаче 2, шаг стенда.
