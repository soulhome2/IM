# План 93. Очередь на базе с миллионом закрытых

Заготовка плана (2026-11-19). Попутная находка замера части Г плана 90; решение пользователя — отдельным планом. Задачи расписать перед началом.

Замер: [load-2026-11-19-plan90.md](load-2026-11-19-plan90.md), раздел 4, прогон A2 (1 млн закрытых, 100 операторов, без блока «За период»).

## Что не так

По сравнению со ступенью 100 плана 86 (база ~500 инцидентов, 0 ошибок):
- поиск по номеру — p50 49 с, по тексту — 46 с, часть — 504 через 60 с от прокси;
- сверка страницы — p50 27 с, 91 ответ 504;
- очередь по событию потока — p95 55 с;
- вкладка «Все» и фильтр по типу устройства — десятки секунд;
- база занята ~8,7 ядра против ~4,5.

Самый дорогой запрос по `pg_stat_statements` — подсчёт очереди с проверкой прав: в среднем 3,2–3,5 с.

«Выделить → Все в фильтре» (найдено на стенде 2026-11-19, 51 020 открытых, `limits.maxBulk` = null): `POST /operator/incidents/selection` отвечает 55–60 с и присылает ~7 МБ. Экран ждёт 30 с (`SELECTION_LIMIT_MS`) — оператор видит пустоту, потом «сервер не ответил». Без предела сервер берёт всю очередь и для каждой строки спрашивает машину о каждом ручном переходе (`selectionRows` → `selectionActions` в `internal/im/handler/operator/selection.go`).

## Что сделать

1. EXPLAIN каждого медленного запроса на наполненной базе (`~/Work/stand/backup/imdb-G-filled-20261119-0922.dump`).
2. Индексы и переписывание запросов: поиск по номеру и тексту, «Все», фильтр по типу устройства, сверка страницы, подсчёт с правами.
3. Выделение «Все в фильтре» на десятках тысяч строк: ответ в пределах 30 с экрана. Варианты — доступность действий считать один раз на одинаковые строки (состояние, приоритет, адресат), а не на каждую; отдавать список номеров без лишних полей; при `maxBulk` = null — разумный предел по умолчанию. Предел — это правила (§11, RULE-117), значит решение пользователя.
4. Если поиск по всей истории не ускоряется — решение пользователя (например, ограничить «Все» и поиск периодом); это правила, а не только сервер.
