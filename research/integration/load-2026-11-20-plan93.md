# Нагрузка 2026-11-20: очередь на миллионе закрытых после плана 93

План — [93-queue-big-db.md](93-queue-big-db.md), задача 6. Для сравнения — прогон A2 из [load-2026-11-19-plan90.md](load-2026-11-19-plan90.md), раздел 4: та же база, те же операторы, тот же скрипт.

Стенд — та же машина на 16 ядер: сервер МИ, база (PostgreSQL 9.6, настройки по умолчанию: shared_buffers 128 МБ, work_mem 4 МБ), облако и генератор нагрузки. Сервер — `im-p93-5` (сервер b3d4f94 + 04bddc2, все задачи плана 93), машина IM b99af71 (`limits.maxBulk` = 1000 по умолчанию).

## Коротко

- **Ошибок больше нет.** 5xx и сбоев сети — **0** (в A2 — 305 ответов 504). Ни один запрос не дошёл до 60 с прокси. Сервер ни разу не бросил запрос из-за ожидания слота тяжёлых чтений.
- **Цели по времени не достигнуты.** Поиск, сверка страницы, очередь по событию потока, фильтр по типу устройства: p95 — **4,3–7,9 с** вместо десятков секунд и 504, но цель — меньше 1–3 с.
- **База — 6,2 ядра** (медиана) вместо 8,7. Цель — не больше 5.
- **«Все в фильтре» уложилось:** под нагрузкой 3,6–5,2 с до ответа (цель меньше 10 с), всегда 1000 строк.
- **«Взять», «Закрыть», «Открытые» — p95 на 10–19 % хуже A2.** Но операторы сделали вдвое больше переходов (6 066 против 2 985) и втрое больше запросов очереди: в A2 они по минуте ждали 504.
- **Почему не уложились.** Один оператор на спокойном стенде получает поиск по номеру за 30 мс, а под нагрузкой p50 — 1,3 с. У всех запросов очереди p50 ~0,2 с, а p95 — 4,5–5 с, даже у простых «следующая страница» и «обновить». Значит, запросы ждут один из 6 слотов тяжёлых чтений (`heavyReadSlots`). Слоты держат несколько запросов по 1–5 с. Самый дорогой — страница с фильтром по приоритету на длинных списках («Все», «Выполненные»): в среднем 5,3 с, 20 % всего времени базы. Его план 93 не трогал. Подробно — в разделе 4.

## 5. Что не уложилось и почему

**Главное — очередь к слотам тяжёлых чтений, а не сами поиски.** Под нагрузкой и без неё:

| Запрос | Один оператор, спокойный стенд | Под нагрузкой p50 / p95 |
|---|---|---|
| Поиск по номеру на «Все» | 30 мс | 1,3 / 5,9 с |
| «Вкладка», «следующая», «обновить» | 0,05–0,14 с | 0,19 / 4,6–4,8 с |
| Очередь по событию потока | — | 0,24 / 4,5 с |

Каждая страница и каждый подсчёт очереди идут через `heavyRead` (6 слотов). Пока слоты заняты запросами по 1–8 с, лёгкие запросы стоят в очереди за ними. Отсюда одинаковый «хвост» 4,5–6 с почти у всех видов запросов очереди. Сколько запрос ждал слота, сервер не пишет: в журнале есть только отказы, их 0. Ожидание выведено из разницы «спокойно / под нагрузкой» и из занятости слотов по `pg_stat_statements` (раздел 4).

Кто держит слоты, по убыванию:

1. **Фильтр по приоритету на длинных списках — запрос №1, 20 % времени базы.** У `test@` на спокойном стенде — 2,1–2,2 с на любой приоритет («Все» и «Выполненные»). Под нагрузкой — 5,3 с в среднем. Планом 93 этот запрос не разбирался. Вероятная причина (EXPLAIN не делали): обход по индексу каждого приоритета (`unnest(prio) CROSS JOIN LATERAL`) идёт и для приоритетов, которых нет в фильтре. Такой обход проходит по всем 200–250 тыс. строк приоритета и ничего не находит.
2. **Подсчёт классов с поиском по всей истории — запрос №2, 17 %.** Он вызывается часто: 4 661 раз (страница + счётчики при поиске). В среднем 0,29 с, но на широком слове — до 6 с. Широкий текст («предмет», 110 тыс. найденных) у одного оператора — 1,7 с: цель < 1 с не выполняется и на спокойном стенде. Это объём найденного, а не способ поиска (вывод задачи 2). Один и два знака на «Все» — 1,5 и 1,2 с.
3. **Страница поиска (№5) и страница с фильтром по типу устройства (№7) — 1,0 и 1,5 с в среднем.** У одного оператора «Все» + камеры, стр. 20 — 0,1 с, малый тип (датчики дыма), стр. 1 — 0,13 с. Под нагрузкой медленнее в 10 раз: это общая очередь и ожидание процессора.
4. **Планировщик (№3) — 0,6 с раз в ~1,3 с, около 0,5 ядра.** Он ищет инциденты с наступившими сроками среди всех. В журнале сервера всё время «due incidents keep the limit full». К очереди операторов отношения не имеет, но процессор базы занимает. Планом 93 не разбирался.

Сколько не хватает до цели:
- поиск по номеру p95 — 5,9 с, нужно меньше 3 с (в 2 раза больше); p50 — 1,3 с, нужно меньше 1 с;
- поиск по тексту p95 — 7,9 с, нужно меньше 3 с (в 2,6 раза);
- сверка страницы, очередь по событию потока, тип устройства p95 — 4,5–6 с, нужно меньше 1 с (в 4,5–6 раз);
- база — 6,2 ядра, нужно не больше 5 (на 1,2 ядра больше).

Что могло бы помочь (не делалось, решает контролёр): разобрать запрос №1 (фильтр по приоритету); решение 1 «б» (период) для широкого текста и коротких запросов на «Все»; разделить слоты, чтобы лёгкие страницы не стояли за тяжёлыми подсчётами с поиском; посчитать, сколько запросы ждут слотов (сейчас это не пишется); число `heavyReadSlots` — по процессору базы (решение «общее» задачи 1).
