# Этап 6: таймеры и планировщик, исполнитель сценариев, журнал действий оператора — план работ

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Сервер МИ сам выполняет переходы по таймеру и системные переходы (нормативы, автоэскалация, молчание оператора, потеря доступа, закрытие привязанных), проводит оператора по сценарию из конфигуратора шаг за шагом и ведёт журнал действий оператора (§12.4). Сервер остаётся в одном процессе, но планировщик не мешает второму.

**Architecture:** Сначала в IM правятся долги прототипа и записываются эталоны: векторы `tick` на ядре прототипа и векторы сценариев на `scenario.js`. Затем на Go — чистый исполнитель сценариев с JSONLogic (пакет без базы), хранение прохождения и три маршрута сценария. Потом ядро получает `Core.Tick` — перенос `tick` из `engine.js`: общий порядок по времени, каждый переход — свой `Core.Run` в своей транзакции. Планировщик в процессе раз в секунду берёт кандидатов запросами по индексу и вызывает `Core.Tick`; перед действием оператора догоняет семью, после — доделывает системные переходы. Журнал действий — своя таблица только на добавление и представление по ней.

**Tech Stack:** Go 1.27.1, gin v1.11.0, oapi-codegen (`operatorgen`), `mgutz/dat`, cel-go, PostgreSQL 9.6, pgx v5.7.6, testify `require`, kin-openapi v0.133.0 (только тесты), golangci-lint v2.14.0. IM: Node (vm, без Chrome) для векторов сценариев, Chrome для `cel_vectors.mjs --update`.

- **197.** Прохождение хранится в `incidents.scenario_result` (столбец есть с миграции 001), курсор показа — новый `incidents.scenario_cursor TEXT NOT NULL DEFAULT ''` (миграция 024). `scenario_result IS NULL` — прохождение `Start(script)`, вычисляется на чтении и **не пишется**, пока нет первого ответа, курсора или переноса: так старые строки стенда получают «0 из M» без записи в базу. Пустой курсор или курсор не на пути — `Cursor(script, result)`. Сценарий версии читается `GetScenariosAtVersions` и хранится в памяти процесса по `(guid, version)`: версия сценария не меняется (`InsertScenario` — единственная запись `script`), до 1024 ключей; при переполнении память очищается целиком. Сценарий, который не разбирается, запоминается как битый под своим ключом — `Warn` один раз на ключ; в строке очереди прогресс `{filled: 0, total: null}`, `getIncidentScenario` — `500 INTERNAL_ERROR`. Приём события на битом сценарии не падает: строка `create` журнала — `filledSteps 0`, `totalSteps null`, `Warn`, событие принимается.
- **198.** Мир. `Progress`, `StepNumber`, `SetCursor`, `ShareAnswers` и факт `stepsFilled` в `appservice/operator/world.go` работают по-настоящему. **Память прохождений живёт одну попытку, а не одну операцию** (C-1 ревью): ядро повторяет операцию при `ErrFamilyChanged` до трёх раз (`family.go`, `familyAttempts`), а мир один на весь `Core.Run`. Каждая попытка читает прохождения семьи заново под блокировкой — `LockFamily`, затем `IncidentScenarioRuns` в той же транзакции; память привязана к транзакции попытки, новая транзакция — память пуста. Внутри попытки `SetCursor` и `ShareAnswers` пишут столбцы в её транзакции и видят то, что записали раньше в ней же. Так выполняется контракт `World` (`core.go:202-208`): `ShareAnswers` откатывается вместе с Repo. Чтения очереди и карточки не добавляют запроса на строку: прохождения набора — один запрос, сценарии — из памяти или один запрос на недостающие ключи. Перенос ответов с `n > 0` поднимает версию основного и без `logKey` (долг ADR-005, «Stage 6»).
- **199.** Маршруты сценария. Видимость и `If-Match` сервер проверяет общим слоем до обработчика, как у переходов (решение 47), поэтому порядок `404 → 428 → 403 → 412`. У прототипа `403` раньше `428` — отличие записывается в итог.

| Шаг | Отказ |
|---|---|
| инцидент не виден или нет его | `404 NOT_FOUND` |
| `answer`: нет `If-Match` | `428` |
| `scenarioEdit` машины не выполнен (кроме `GET`) | `403 PERMISSION_DENIED`, `workflow.error.read_only` |
| `answer`: версия не та | `412` с карточкой |

| `revisitable: false` у пройденного | `409 STEP_NOT_EDITABLE`, `workflow.error.scenario.not_editable` |
| ответ не подходит | `422 INVALID_ANSWER`, `workflow.error.scenario.invalid_answer` с `{step}`, `details.reason` |

`answer` — под блокировкой семьи, в одной транзакции: `scenario_result`, `scenario_cursor` (шаг пути после отвеченного), версия +1, строки журнала макросов, лента `incident.updated` с `{stepIds: [stepId]}`; ответ `200` с `ETag` новой версии. У прототипа кадр `delivered` — отличие в итог. Макрос, которому `run_macro` недоступен, остаётся событием `macro` в `history` и больше ничего. `cursor` — без `If-Match`, версия не меняется, как у прототипа. Идемпотентного ключа у маршрутов сценария в контракте нет.

## Review Focus

1. **Перезапуск с просроченными таймерами.** Сервис лежал, у одних истекла реакция, у других — норматив закрытия, операторы «на месте». Ждём: ни одного `system_hold_idle` от простоя, норматив закрытия срабатывает, порядок общий по времени, нарушение на дедлайн. `TestSchedulerRestartCatchUp`, `TestSchedulerStartRestarts`, Task 11.
2. **Скачок часов.** Часы ушли вперёд на час (сон машины) или назад на минуту. Ждём: вперёд — `Warn`, `now` такта — новые часы, активность не сброшена (правило не меняется, решение 203), просроченное срабатывает по своему дедлайну; назад — ничего не срабатывает дважды, `now` такта равен прошлому, `at` строк журнала не раньше прошлого такта. `TestSchedulerClockJumpForward`, `TestSchedulerClockBack`, Task 11; подделка часов двигает и скачок, и `now`.
3. **Долгая блокировка.** Массовое `hold` на 200 держит семью 30 с. Ждём: такт не встаёт, другие просроченные срабатывают вовремя, занятый — в первом такте после освобождения. `TestSchedulerLongLockSkips`, Task 11, такт ограничен фикстурой (решение 204а).
4. **Два таймера сразу.** Два инцидента с одним `due`; основной и привязанный; таймер и системный переход на один момент. ## Решения этого плана — обоснования

- **193.** Проверка по индексу разрешает разрыв и запрещает вставку снизу. Взять 022 и 023 значило бы, что отложенные задачи всё равно переедут, а старые ссылки поменяют смысл.
- **194.** Ядро уже сверяется векторами; планировщик без них разошёлся бы с прототипом в порядке, а порядок и есть его смысл (ARCH-13). Предел 50 на настоящей машине не наступает, поэтому эталона ему нет — есть тест на подделке.
- **195.** Исполнитель сценариев — чистые функции; запись без Chrome дешёвая, а 1008 случаев проверяют только условия, не путь. Генератор с ошибкой дал бы неверный эталон без сигнала — поэтому порчи.
- **196.** Перенос один к одному: требования — машина сценариев и профиль МИ, `scenario.js` их уже исполняет и закреплён тестами. Где `scenario.js` расходится со спецификацией, правится он, а не Go.
- **197.** Писать прохождение каждой старой строке значило бы трогать данные стенда без нужды; вычисление на чтении даёт то же. Версия сценария неизменна, поэтому память безопасна.
- **198.** Мир — единственный шов двух машин (§14.5, стык). Без версии +1 у переноса второй оператор не узнал бы об изменении сценария. Память дольше попытки пережила бы откат и тихо потеряла ответы.
- **199.** Видимость и `If-Match` проверяет общий слой сервера, тот же у переходов; коды — прототип и `tests/api-junction.js`. Кадр «в очереди» обманул бы клиента: по контракту `macro.completed` — это результат.
- **200.** Транзакция на переход — как `SessionMoves` и решение 61: семья своя, а сбой одного не отменяет другие. Окно у системных — ошибка, найденная в 5а (RULE-67).
- **201.** Каждую секунду считать 5000 открытых в CEL нельзя. Функция в индексе живёт в одном месте с данными и не требует писать новый столбец при каждом переходе.
- **202.** Массовое `hold` держит семьи десятки секунд (итог 5б); такт без предела стоял бы столько же у всех. Предел на ленте терял бы переходы на чужой фиксации, а не на долгой семье.
- **203.** Дедлайны — метки настенного времени (§4, правило 1). Сон машины похож на простой, но правила этого не говорят; сброс активности при скачке был бы новым правилом.
- **204.** RULE-113, RULE-119 и §9, пункт 5: так правила, без исключений. 204а: на общей тестовой базе такт по всему клиенту выполнил бы переходы чужих тестов.
- **205.** §14.3: без догона действие стирает нарушение (BUG-82). Ответ после фиксации не может стать ошибкой: действие уже есть, повтор не должен выполнить его снова. Свои инциденты действующего решают его лимит — без их догона лимит считался бы по прошлому.
- **206.** Сервер узнаёт о смене ролей только при обращении или сверке (§5, `BACKEND.md`); раз в 30 с — то, что дёшево и не теряет случая.
- **207.** Решение 80 обещало этот остаток планировщику; один запрос по людям закрывает и его, и M-4.
- **208.** §12.4: журнал только дополняется. Строки журнала инцидента ядро законно правит (`once`), поэтому журнал оператора — копия в своей таблице, правило не меняется.
- **209.** Пользователь оставил один экземпляр; замок без второго экземпляра проверить нечем.
- **210.** Без настоящего адресата уровня критерий «сам эскалируется» на стенде не выполним: эскалация упёрлась бы в потолок. Ограничение разделами `adminSettings` оставляет машину единственным источником логики: патч меняет только то, что §9 и так отдаёт администратору.
- **211.** Как решение 69: равенства важнее времени, время уточняется замером.
- **212.** Пункты ревью 57, раздел 7, и предварительного ревью: поведение прототипа — образец сервера, и ошибка в нём перешла бы в Go.
