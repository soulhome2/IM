# Чек‑лист формальной проверки машины состояний

Закрытый список: каждый прогон проходит **все** пункты, ни один не пропускается молча. У пункта — способ проверки:

- **[скрипт]** — `python3 tools/check_machine.py`: его ошибка — находка с ✅, руками не повторять;
- **[сценарий]** — тесты API «im-fsm: …» в `tests/api-fsm.js` (встроенный сервер, CI, бэкенд): их «FAIL» — находка с ✅;
- **[чтение]** — вручную, по выводу вспомогательного скрипта из [SKILL.md](SKILL.md) или по названным файлам, с доказательством: путь в графе, контрпример, строка.

В отчёте — таблица покрытия: пункт → чем проверен → результат. Пункт, который проверить нельзя, — «не проверяется статически» с причиной, а не пропуск. Находку не записывать, пока не пройдены все пункты: первая находка — не повод остановиться.

Уверенность вывода: **высокая** — скрипт или сценарий; **средняя** — чтение машины и кода без запуска; **низкая** — зависит от того, чего статически не видно.

## 1. Синтаксис и структура

- [ ] **[скрипт]** JSON машины и контракта валиден; все ссылки — на состояния, формы, условия, эффекты, права, таймеры, настройки — существуют.
- [ ] **[скрипт]** Нет дубликатов идентификаторов состояний и переходов.
- [ ] **[скрипт]** Нет двух переходов с одним исходным состоянием и одинаковыми условиями.
- [ ] **[скрипт]** Поля по виду перехода: у автоматических нет полей ручных (`form`, `bulk`, `requiredStepSet`, `labelKey`, `hint`, `concurrency`).
- [ ] **[скрипт]** Записи реестра условий и эффектов используются.
- [ ] **[чтение]** Именование: состояния и переходы — `snake_case`, функции реестра — `camelCase`. Одно понятие — одно слово в идентификаторах и подписях: владелец (`owner`), адресат (`addressee`), оператор (`agent`), группа (`group`). Список идентификаторов выводит вспомогательный скрипт.

## 2. Описание против поведения

Описательные поля исполнитель не читает; если они расходятся с эффектами, бэкенд, построенный по описанию, поведёт себя иначе, чем прототип.

- [ ] **[скрипт]** Состояния: ровно одно `initial`, оно не терминальное; `owner` — из перечня; `activeTimer` — таймер машины или пусто.
- [ ] **[скрипт]** Таймеры: `startsOnEnter`, `resumesOnEnter` (продолжается, только если шёл), `stopsOnEnter`, `pausedInStates` совпадают с эффектами переходов в обе стороны — что обещает описание, делают эффекты, и что делают эффекты, есть в описании; исключения — `continuesOn`.
- [ ] **[чтение]** Владелец каждого состояния совпадает с тем, что оставляют в нём эффекты всех входящих переходов (`setOwner`, `setAssignmentGroup`), и с инвариантами случайных прогонов (`tests/api-properties.js`).
- [ ] **[чтение]** Подписи переходов и записи журнала (`appendLog`) говорят ровно то, что проверяют условия: не «потолок», если срабатывает и без потолка; не «у владельца», если и у адресата. Таблицу «переход — условия — подпись — запись журнала» выводит вспомогательный скрипт.
- [ ] **[чтение]** Правила §4 (таймеры), §6.1–6.2 (переходы), §8.1 (адресаты) говорят то же, что машина, включая исключения. Таблицы §6 и диаграмму §3 сверяет скрипт.
- [ ] **[чтение]** Остальные места правил, где названа функция реестра (§11, §12, §14.5, §14.8 и др.), говорят то же, что машина: у каких переходов эффект и что он делает. Строки выводит вспомогательный скрипт; поведение подтвердить запуском.
- [ ] **[чтение]** Запись журнала берёт нужное значение: новое — после эффекта, который его ставит, прежнее — до эффекта, который его очищает. Переходы, где значение из записи меняется до неё, выводит вспомогательный скрипт; находку подтвердить текстом журнала после запуска. Пустая таблица при записях с переменными — повод проверить сам скрипт: так он молчал после перехода журнала на ключи каталога (PROC-29).
- [ ] **[чтение]** Привязанные события (§11.4): связь `linked_to` есть только у привязанного и у закрытого вместе с основным. Каждый переход, после которого у основного другой адресат, который переоткрывает, закрывает или объединяет, — что станет со связью и с доступом к привязанным: ручная передача проверяет доступ условием (`targetHasAccessToLinked`), автоматическая — системным переходом `linked_lost_access`; переоткрытое событие связь снимает (BUG-42, RULE-71). Таблицу «переход — меняет адресата — доступ к привязанным — связь» выводит вспомогательный скрипт; находку подтвердить запуском: основной с привязанным, переход для основного, что у привязанного.
- [ ] **[чтение]** Эффекты сверх §14.8 (`extendsBaseRegistry`): у каждого описано, что он делает с данными инцидента (`$comment` в реестре или README машины; функции без `$comment` выводит вспомогательный скрипт), и исполнитель (`engine.js`) делает всё это — например, `clearLink` с шаблонами пишет в журнал события и основного, только если связь была (§11.4).

## 3. Граф

- [ ] **[скрипт]** Все состояния достижимы из начального.
- [ ] **[скрипт]** У каждого нетерминального состояния есть переход в другое.
- [ ] **[чтение]** Из терминальных — только задуманные выходы (`closed` → `reopen`, §10.1).
- [ ] **[чтение]** Тупики по условиям: выход есть в графе, но при настройках по умолчанию и типовых наборах прав (`validation.typicalPermissionSets`) невыполним.

## 4. Ручные переходы

- [ ] **[чтение]** Одна кнопка — один переход; у перехода из нескольких состояний эффекты верны для каждого (`TRANSITIONS.md`).
- [ ] **[скрипт]** В «В работе» — только по праву взятия или принятия; у каждого типового набора прав с ними есть выход из карточки (§10.3).
- [ ] **[чтение]** Отказ — код `Problem` контракта: у условия есть код или `GUARD_FAILED` (README машины, «Коды ошибок перехода»).

## 5. Автоматические переходы

- [ ] **[скрипт]** Перебор настроек: для каждой группы переходов одного таймера и каждого сочетания значений настроек из перечня — срабатывает ровно один переход или задуманное «ничего». Пустая ветка при нарушении — находка (RULE-40, RULE-45).
- [ ] **[скрипт]** Карта пересечений: для каждого состояния — пары автоматических переходов, которые могут быть готовы одновременно, и какой выполнится первым по §14.3. Пары с разным итогом — проверить сценарием.
- [ ] **[сценарий]** Прыжок часов против шагов: для пар из карты пересечений итог одинаков (RULE-41, RULE-48).
- [ ] **[сценарий]** Повторный вход: каждый таймер — «истёк → выход из состояния → возврат любым переходом» не даёт нового срабатывания (RULE-50).
- [ ] **[сценарий]** Переходы без смены состояния (`to: null`) не срабатывают повторно на один и тот же дедлайн.
- [ ] **[сценарий]** Системный переход в окне после дедлайна: переход по таймеру выполняется первым, нарушение записано на момент дедлайна — для каждого таймера, у которого есть переход с нарушением (RULE-67).
- [ ] **[сценарий]** Ручной переход в окне после дедлайна, после которого таймер продолжается (`continuesOn`, `startTimer … ifStopped`): срабатывание не отменяется — дальше срабатывает то же, что при действии до дедлайна, автоматика не замолкает (RULE-83). Список таких переходов печатает `check_machine.py --fsm`, сценарии — набор `CONTINUING`, тест «покрытие» сверяет одно с другим (PROC-26).
- [ ] **[чтение]** Циклы без выхода: при бездействии людей ничего не крутится бесконечно (эскалация упирается в потолок).

## 8. Машина сценариев

Для каждого сценария эталонного набора (каждой версии); примеры исходника — замечаниями.

- [ ] **[скрипт]** Схема (формат редактора продукта); проверки редактора с его кодами — первый шаг, `goto` на существующие шаги, `goto: null` только у финального, хотя бы один финальный шаг, id не повторяются, границы Checkbox, ссылки условий на варианты и списки; проверки МИ — правила только у шагов с выбором, белый список операторов, `var` — ответ своего шага, значения по умолчанию из вариантов (`check_scenarios.py`).
- [ ] **[скрипт]** Граф: каждый шаг достижим из первого (`STEP_NOT_REACHABLE`), из каждого достижимого — путь до финального шага.
- [ ] **[скрипт]** Перебор ответов своего шага: каждое правило срабатывает хоть при одном ответе и не заслонено более ранним; `default` срабатывает хоть при одном ответе — иначе шаги за ним недостижимы по ответам.
- [ ] **[скрипт]** Набор: `scenario.id` и `version` совпадают с guid и версией строки, имя файла — по ним; у типа события — существующий сценарий; прохождения инцидентов — на существующих версиях и шагах.
- [ ] **[сценарий]** Прохождения набора такие, какие даёт исполнитель; исполнитель и вычислитель проверки сходятся на крайних случаях (`tests/scenario.html`).
- [ ] **[сценарий]** Стык §14.5 — тесты API из `tests/api-junction.js`: набор «закрытие», прогресс, курсор, переответ, макрос исхода, переходы инцидента и прохождение, объединение версий.
- [ ] **[чтение]** Шаги, которые `--fsm` не перебирает (слишком много вариантов): условие выполнимо и не заслонено — по самим выражениям.
- [ ] **[чтение]** Исход по смыслу: ветка, куда ведёт ответ, соответствует ответу (по карте `--fsm`: «ложная тревога» не ведёт в шаги вызова наряда); макрос исхода — на тех ответах, где он нужен, и не на тех, где вреден.
- [ ] **[чтение]** Обязательность: шаг, без ответа на который обработка неполна, — обязательный; необязательный шаг не стоит единственным перед финальным там, где пропуск всё обесценивает.
- [ ] **[чтение]** Циклы из `--fsm`: переход назад на пройденный шаг конечен — у оператора есть ответ, который ведёт вперёд.
- [ ] **[чтение]** Стык: правила §14.5, профиль МИ (README машины сценариев) и исполнитель говорят одно и то же — набор «закрытие», курсор, прогресс, перенос ответов, макрос исхода.
