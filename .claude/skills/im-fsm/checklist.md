# Чек‑лист формальной проверки машины состояний

Закрытый список: каждый прогон проходит **все** пункты, ни один не пропускается молча. У пункта — способ проверки:

- **[скрипт]** — `python3 tools/check_machine.py`: его ошибка — находка с ✅, руками не повторять;
- **[сценарий]** — тесты API «im-fsm: …» в `tests/api-fsm.js` (встроенный сервер, CI, бэкенд): их «FAIL» — находка с ✅;
- **[чтение]** — вручную, по выводу вспомогательного скрипта из [SKILL.md](SKILL.md) или по названным файлам, с доказательством: путь в графе, контрпример, строка.

В отчёте — таблица покрытия: пункт → чем проверен → результат. Пункт, который проверить нельзя, — «не проверяется статически» с причиной, а не пропуск. Находку не записывать, пока не пройдены все пункты: первая находка — не повод остановиться.

Уверенность вывода: **высокая** — скрипт или сценарий; **средняя** — чтение машины и кода без запуска; **низкая** — зависит от того, чего статически не видно.

## 1. Синтаксис и структура

- [ ] **[скрипт]** JSON машины и контракта валиден; все ссылки — на состояния, формы, условия, эффекты, права, таймеры, настройки — существуют.
- [ ] **[скрипт]** Нет дубликатов идентификаторов состояний и переходов.
- [ ] **[скрипт]** Нет двух переходов с одним исходным состоянием и одинаковыми условиями.
- [ ] **[скрипт]** Поля по виду перехода: у автоматических нет полей ручных (`form`, `bulk`, `requiredStepSet`, `labelKey`, `hint`, `concurrency`).
- [ ] **[скрипт]** Записи реестра условий и эффектов используются.
- [ ] **[чтение]** Именование: состояния и переходы — `snake_case`, функции реестра — `camelCase`. Одно понятие — одно слово в идентификаторах и подписях: владелец (`owner`), адресат (`addressee`), оператор (`agent`), группа (`group`). Список идентификаторов выводит вспомогательный скрипт.

## 2. Описание против поведения

Описательные поля исполнитель не читает; если они расходятся с эффектами, бэкенд, построенный по описанию, поведёт себя иначе, чем прототип.

- [ ] **[скрипт]** Состояния: ровно одно `initial`, оно не терминальное; `owner` — из перечня; `activeTimer` — таймер машины или пусто.
- [ ] **[скрипт]** Таймеры: `startsOnEnter`, `stopsOnEnter`, `pausedInStates` совпадают с эффектами переходов в обе стороны — что обещает описание, делают эффекты, и что делают эффекты, есть в описании; исключения — `continuesOn`.
- [ ] **[чтение]** Владелец каждого состояния совпадает с тем, что оставляют в нём эффекты всех входящих переходов (`setOwner`, `setAssignmentGroup`), и с инвариантами случайных прогонов (`tests/api-properties.js`).
- [ ] **[чтение]** Подписи переходов и записи журнала (`appendLog`) говорят ровно то, что проверяют условия: не «потолок», если срабатывает и без потолка; не «у владельца», если и у адресата. Таблицу «переход — условия — подпись — запись журнала» выводит вспомогательный скрипт.
- [ ] **[чтение]** Правила §4 (таймеры), §6.1–6.2 (переходы), §8.1 (адресаты) говорят то же, что машина, включая исключения. Таблицы §6 и диаграмму §3 сверяет скрипт.
- [ ] **[чтение]** Группа сценария (§11): у членов группы общие владелец и ответы. Каждый переход, после которого владелец инцидента другой или его нет, выводит инцидент из группы (`clearGroup`) или действует на всю группу (`bulk.mode: group`). Таблицу «переход — меняет владельца — `clearGroup` — режим выборки» выводит вспомогательный скрипт; находку подтвердить запуском: группа из двух, переход для одного, что у второго.
- [ ] **[чтение]** Эффекты сверх §14.8 (`extendsBaseRegistry`): у каждого описано, что он делает с данными инцидента (README машины), и исполнитель (`engine.js`) делает всё это — например, выход из группы (`clearGroup`) отделяет ответы, как ручное исключение (§11).

## 3. Граф

- [ ] **[скрипт]** Все состояния достижимы из начального.
- [ ] **[скрипт]** У каждого нетерминального состояния есть переход в другое.
- [ ] **[чтение]** Из терминальных — только задуманные выходы (`closed` → `reopen`, §10.1).
- [ ] **[чтение]** Тупики по условиям: выход есть в графе, но при настройках по умолчанию и типовых наборах прав (`validation.typicalPermissionSets`) невыполним.

## 4. Ручные переходы

- [ ] **[чтение]** Одна кнопка — один переход; у перехода из нескольких состояний эффекты верны для каждого (`TRANSITIONS.md`).
- [ ] **[скрипт]** В «В работе» — только по праву взятия или принятия; у каждого типового набора прав с ними есть выход из карточки (§10.3).
- [ ] **[чтение]** Отказ — код `Problem` контракта: у условия есть код или `GUARD_FAILED` (README машины, «Коды ошибок перехода»).

## 5. Автоматические переходы

- [ ] **[скрипт]** Перебор настроек: для каждой группы переходов одного таймера и каждого сочетания значений настроек из перечня — срабатывает ровно один переход или задуманное «ничего». Пустая ветка при нарушении — находка (RULE-40, RULE-45).
- [ ] **[скрипт]** Карта пересечений: для каждого состояния — пары автоматических переходов, которые могут быть готовы одновременно, и какой выполнится первым по §14.3. Пары с разным итогом — проверить сценарием.
- [ ] **[сценарий]** Прыжок часов против шагов: для пар из карты пересечений итог одинаков (RULE-41, RULE-48).
- [ ] **[сценарий]** Повторный вход: каждый таймер — «истёк → выход из состояния → возврат любым переходом» не даёт нового срабатывания (RULE-50).
- [ ] **[сценарий]** Переходы без смены состояния (`to: null`) не срабатывают повторно на один и тот же дедлайн.
- [ ] **[чтение]** Циклы без выхода: при бездействии людей ничего не крутится бесконечно (эскалация упирается в потолок).

## 6. Контракт

- [ ] **[скрипт]** Настройки, от которых зависят ветви (`escalation.enabled`, `onResolutionOverdue`, `alerts.target`), заданы и из перечня; в контракте — обязательные.
- [ ] **[скрипт]** Ответы встроенного сервера, включая схему, сверяются с контрактом — это тесты API; при их падении — находка.
