# Чек‑лист формальной проверки машины состояний

Пункты с пометкой **[скрипт]** проверяет `tools/check_machine.py`: руками не повторять, его ошибки — находки с ✅. Остальное — вручную, с доказательством: путь в графе, контрпример или запуск на встроенном сервере.

Для каждого вывода указать уверенность: **высокая** — проверено скриптом или запуском; **средняя** — прочитано в машине и коде, запуском не подтверждено; **низкая** — зависит от того, чего статически не видно.

## Синтаксис и структура

- [ ] **[скрипт]** JSON машины и контракта валиден; при ошибке — строка и символ.
- [ ] Ключи переходов единообразны: `id`, `from`, `to`, `trigger`, `guards`, `effects`; необязательные (`form`, `bulk`, `labelKey`, `scope`, `actor`) — по виду перехода, а не вразнобой. Рассинхрон названий полей — находка.
- [ ] **[скрипт]** Нет дубликатов идентификаторов состояний и переходов.
- [ ] Нет дубликатов по сигнатуре: два перехода с одним `from`, одним событием (для ручных — одна кнопка) и пересекающимися условиями.
- [ ] Типы полей: `id` — строка, `from` — массив состояний, `to` — состояние или `null`, `guards` и `effects` — массивы записей с `fn`, аргументы — по описанию в реестре.
- [ ] Именование в одном стиле: состояния и переходы — `snake_case`, функции реестра и настройки — `camelCase`, без пробелов.

## Логическая корректность

- [ ] **[скрипт]** Все `from` и `to` ссылаются на объявленные состояния.
- [ ] **[скрипт]** Ровно одно начальное состояние (`initial`), и оно не терминальное.
- [ ] Терминальные состояния: какие переходы из них ведут и задумано ли это (у `closed` — только `reopen`, §10.1).
- [ ] **[скрипт]** Все состояния достижимы из начального. Для недостижимого — обход графа как доказательство.
- [ ] **[скрипт]** У каждого нетерминального состояния есть переход в другое состояние.
- [ ] Тупики по условиям: выход есть в графе, но при настройках по умолчанию и типовых наборах прав (`validation.typicalPermissionSets`) его условия невыполнимы.
- [ ] Ручные переходы детерминированы: одна кнопка — один переход; если переход доступен из нескольких состояний, его эффекты описаны для каждого.
- [ ] Автоматические переходы одного состояния: для каждой пары — пересекаются ли условия. Если да — какой выполнится первым по §14.3 (время наступления, затем «сразу следом», затем порядок в массиве) и совпадает ли итог с правилами. Контрпример — сценарий с моментами.
- [ ] Итог не зависит от частоты планировщика: сценарий «прыжок часов» и «шаги» дают одно и то же (тесты RULE-41, RULE-48 — образец).
- [ ] Переходы с `to: null` (в себя): осознанные ли, не срабатывают ли повторно на один и тот же дедлайн.
- [ ] Иерархии, параллельных регионов и истории в машине нет; если появились — проверить вход, выход и конфликты событий.

## Полнота

- [ ] События: в каждом состоянии для каждой кнопки есть переход либо кнопка скрыта или недоступна с причиной (`onFail`, `actions` в ответе сервера).
- [ ] Отказ перехода — код `Problem` контракта: у каждого условия реестра есть код или `GUARD_FAILED` (README машины, «Коды ошибок перехода»).
- [ ] **Ветви условий автоматических переходов покрыты.** Для каждой группы переходов одного состояния и одного таймера разобрать все комбинации настроек и условий: при какой комбинации не сработает ни один — и это задумано или нарушение пропадает молча (RULE-40, RULE-45 — образцы).
- [ ] **[скрипт]** Настройки, от которых зависят ветви, заданы и из допустимого перечня (`escalation.enabled`, `onResolutionOverdue`, `alerts.target`).
- [ ] **[скрипт]** Каждая запись реестра где‑то используется.

## Семантика

- [ ] Названия состояний и переходов соответствуют смыслу; подписи (`label`) — те же слова, что в правилах.
- [ ] Циклы без выхода: есть ли цикл, который при бездействии людей крутится бесконечно (автоэскалация ограничена потолком).
- [ ] Условия: аргументы существуют (состояния, таймеры, настройки, справочники), нет взаимоисключающих условий в одном переходе, нет условий, которые всегда истинны.
- [ ] Обращения к пустому: условие или эффект над пустым владельцем, адресатом, группой, таймером — что вернёт исполнитель.
- [ ] Эффекты не меняют состояние в обход `to`; внешние эффекты (`notify`, `externalCommand`) — после транзакции.
- [ ] Таймеры: каждый дедлайн срабатывает один раз; перезапуск таймера эффектом не создаёт вечного цикла.
- [ ] Права и роли: переход в «В работе» — только с правом взятия или принятия (§10.3); у каждого типового набора прав есть выход из карточки.

## Сравнение с аналогами

- [ ] Структура машины не изменилась с последней проверки (те же виды полей и триггеров, нет вложенности и регионов) — тогда сравнение с SCXML, XState, UML — ссылкой на таблицу в [SKILL.md](SKILL.md), без повторения.
- [ ] Если изменилась — обновить таблицу сравнения в SKILL.md и отметить отличия от SCXML: три и больше — осознанное отклонение или находка.

## Доказательства и самопроверка

- [ ] У каждого утверждения о достижимости, детерминизме, недостижимости — путь или контрпример.
- [ ] Нет ссылок на поля, которых в машине нет.
- [ ] То, что зависит от внешней системы, времени, связи, реальных прав, — «не проверяется статически» с причиной, а не ошибка.
- [ ] Вердикт не противоречит таблице проблем.
