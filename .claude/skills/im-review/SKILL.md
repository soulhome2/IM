# Ревью IM

Цель ревью — чтобы прототип и правила, которые уйдут разработчикам, были без ошибок и противоречий, а всё, что не готово, было явно названо.

Ревью только находит и фиксирует. Прототип и правила во время ревью не правятся: исправления идут отдельно, по плану.

## Контекст репозитория

- `Specification/` — Vision, сверка покрытия Vision `Vision coverage.md` и правила перехода состояний `State_rules/States rules IM.md`. Это действующие правила: один файл, правится на месте, номер версии — в шапке, журнал изменений — в §16. Прошлые версии лежат в `State_rules/archive/` и не правятся: их не ревьюить, ошибки в них не записывать.
- `prototype/` — кликабельный прототип: `index.html`, интерфейс в `app.js`, встроенный сервер по `openapi.json` в `server.js` с исполнителем машины `engine.js` на эталонных данных `Specification/State_machine/fixtures/demo.json`, клиент API `api.js`, переводы в `i18n-*.js`, оформление в `styles.css` и `bridge.css`.
- `reviews/` — прошлые ревью и планы. Указатель и договорённости — `reviews/README.md`. Образец результата — `reviews/2026-10-01/`.
- `Specification/State_machine/` — машина состояний: `workflow.v4.json` (JSON-модель workflow) и `openapi.json` (контракт API). Её ведёт программист. Формат не изобретать заново. Расхождения машины с правилами и прототипом — находки ревью. Решения по правилам считать предварительными, пока их не внесли в машину.
- В репозитории работают двое и пушат прямо в `main`, без pull request. Коммитить и пушить — только по просьбе пользователя.

## Порядок

### 1. Подготовка

1. Выполнить `git fetch`. Если на GitHub есть новые коммиты — сказать пользователю и предложить подтянуть их до начала ревью.
2. Определить проверяемый коммит: `git rev-parse --short HEAD`. Все ссылки в ревью ведут на него.
3. Выбрать режим:
   - **изменения** (по умолчанию, если прошлый цикл есть) — то, что поменялось с коммита прошлого ревью из таблицы в `reviews/README.md`: `git diff --stat <прошлый>..HEAD`. Плюс разделы правил, которые затрагивает изменённый код, и наоборот;
   - **полное** — весь репозиторий. Если пользователь просит полное ревью или прошлого цикла нет.
4. Выбрать роли:
   - **все** (по умолчанию) — архитектор, тестировщик, продакт, UX / оператор, дизайнер, разработчик, по очереди;
   - **одна роль**, если пользователь её назвал: `/im-review продакт`, «посмотри как архитектор». Тогда проверяется только её раздел чек‑листа.

   Автоматические проверки выполняются всегда, при любом выборе ролей.
5. Прочитать `plan.md` прошлых циклов: какие пункты открыты (без `[x]`) и какие решения приняты в таблице этапа 2. Принятые решения — часть требований наравне с правилами.

### 2. Автоматические проверки

Всё, что они находят, сразу идёт в ревью с пометкой ✅.

**Самопроверка прототипа.** Прогнать в headless‑браузере и прочитать отчёт:

```bash
google-chrome --headless=new --disable-gpu --no-first-run \
  --user-data-dir=<временная папка> --virtual-time-budget=30000 \
  --dump-dom "file://$PWD/prototype/index.html?selftest" > <временная папка>/selftest.html
```

- Отчёт — содержимое `<pre id="selftest-log">`, итог — атрибут `data-selftest="pass|fail"` у `<html>`. Один из шагов сверяет ответы встроенного сервера со схемами `openapi.json`: его падение — расхождение прототипа с контрактом.
- Временные файлы — в scratchpad, если он есть, иначе в системной временной папке. Не в репозитории.
- При открытии через `file://` браузер скрывает текст ошибок JS («Script error.»). Чтобы увидеть полный текст, поднять сервер `python3 -m http.server` из корня репозитория и открыть `http://127.0.0.1:<порт>/prototype/index.html?selftest`.
- Если headless‑браузера нет (на Windows это `msedge` или полный путь к Chrome), попросить пользователя открыть `prototype/index.html?selftest` и вставить отчёт из угла страницы.

**Тесты API:** открыть `tests/api.html` тем же способом, что самопроверку (`--virtual-time-budget=120000`); отчёт — `<pre id="apitest-log">`, итог — `data-apitest="pass|fail"`. Сценарии по правилам, случайные прогоны с инвариантами, сверка ответов с `openapi.json`, покрытие маршрутов.
**Тесты API по сети:** `python3 tools/check_loopback.py` — те же тесты через петлю: клиент говорит со встроенным сервером по `fetch` и SSE. Режим `--dump-dom` для них не годится — в нём не регистрируется Service Worker.

**Машина состояний:** `python3 tools/check_machine.py` — целостность `workflow.v4.json` и `openapi.json`, граница слоёв прототипа, значения справочников машины не зашиты в код, эталонный набор данных, таблицы §6 правил против машины. Переходы машины словами — `Specification/State_machine/TRANSITIONS.md`, по нему правила сверяются глазами.

**Правила только в машине:** `python3 tools/check_mutations.py` — мутации машины меняют поведение прототипа. Мутация со статусом BAD — находка: правило продублировано в коде прототипа.

**Мутации кода:** `python3 tools/check_code_mutations.py` — тесты ловят порчу исполнителя, сервера и интерфейса. Выжившая мутация — находка: дыра в тестах.

**Словари перевода:** `python3 tools/check_i18n.py` — лишние ключи и расхождение языков.

**Ссылки в документах:** `python3 tools/check_links.py`.

**Покрытие самопроверки.** Для каждого нового или изменённого перехода, кнопки, формы проверить, есть ли шаг в `prototype/selftest.js`. Нет шага — это находка: новый функционал не защищён от поломки.

### 3. Внимательное чтение

Пройти [checklist.md](checklist.md) по ролям, по очереди. У каждой роли свой вопрос — сначала ответить на него, потом пройти её пункты:

| Роль | Вопрос |
|---|---|
| архитектор | модель целостна, однозначна и переносится в продукт без переделки? |
| тестировщик | всё работает так, как написано, и заметим ли мы, если сломается? |
| продакт | сделано то, что нужно, и ничего важного не потеряно? |
| UX / оператор | оператору под нагрузкой удобно и понятно? |
| дизайнер | интерфейс собран по дизайн-системе и одинаков во всех состояниях? |
| разработчик | можно ли взять это в работу без устных пояснений? |

Роль — это угол зрения, а не отдельная проверка. Одна и та же проблема, замеченная двумя ролями, — одна находка с двумя метками.

Продакт не знает бизнес‑контекста: ценность и приоритеты решают люди. Его находки — чаще вопросы в таблицу решений плана, чем ошибки.

В режиме «изменения» — пункты, которые касаются изменённого. Но расхождение с правилами проверять в обе стороны: правка в прототипе может разойтись с разделом правил, который не менялся.

Для нового функционала отдельно:

- есть ли он в действующих правилах (раздел, таблица переходов, кнопки, права, горячие клавиши);
- записан ли он в журнал изменений правил (§16);
- совпадает ли поведение прототипа с правилами — на всех состояниях и для всех владельцев: я, моя группа, другой, никто;
- покрыт ли он самопроверкой.

### 4. Проверка каждой находки перед записью

- Утверждение о коде или документе проверить по конкретным строкам на проверяемом коммите.
- Утверждение о поведении по возможности подтвердить запуском (пометка ✅). Временный тест — в scratchpad, не в репозитории.
- Не преувеличивать. «Работает частично», «при настройках по умолчанию», «при таком‑то условии» — если это так.
- Отделять ошибку в правилах от ошибки в прототипе и от расхождения между ними.
- Если нашлась системная причина нескольких находок — оформить её отдельным пунктом `ARCH` и сослаться на неё из частных.

### 5. Запись результата

Создать `reviews/<YYYY-MM-DD>/review.md` и `plan.md` по [templates.md](templates.md) и добавить строку в таблицу `reviews/README.md`.

Если папка этого дня уже есть — повторное ревью, в том числе одной ролью, дописывается в её `review.md` и `plan.md` с пометкой «найдено вторым проходом». Новую папку не заводить.

**Номера пунктов** сквозные между циклами: найти наибольший номер каждого префикса во всех `reviews/*/review.md` и `plan.md` и продолжить с него. Так номер в сообщении коммита однозначен.

| Префикс | Что |
|---|---|
| `ARCH` | системная причина нескольких ошибок |
| `BUG` | ошибка прототипа или его расхождение с правилами |
| `RULE` | противоречие или пробел в правилах |
| `DOC` | неточность в README и сопроводительных документах |
| `DATA` | демо-данные противоречат правилам или сами себе |
| `PROC` | процесс: коммиты, проверки, договорённости |

Префикс `D-` не использовать: так нумеруются решения дизайн-кита.

**Важность** — у каждого пункта:

- **[блокер]** — не работает основной сценарий;
- **[высокий]** — ошибка в модели или в частом сценарии, тихая порча данных;
- **[средний]** — заметная ошибка или пробел, есть обходной путь;
- **[низкий]** — неточность, на работу не влияет.

**Роль** — курсивом сразу после важности: *архитектор*, *тестировщик*, *продакт*, *UX*, *дизайнер*, *разработчик*. Если находка касается нескольких ролей — через запятую. Пример: `- **BUG-NN** [высокий] *тестировщик, UX* ✅ **Заголовок.** …`

**Ссылки** — постоянные, на проверяемый коммит: `https://github.com/soulhome2/IM/blob/<коммит>/<путь>#L<строка>`. Для `.md` добавлять `?plain=1` перед `#L`, иначе GitHub не прокрутит к строке. Пробелы в путях — `%20`.

**Открытые пункты прошлых циклов** заново не записывать. В начале ревью — раздел со списком их номеров и одним словом о состоянии: «не исправлено», «исправлено, но не отмечено в плане», «стало хуже». Если исправление сломало что‑то другое — это новая находка со ссылкой на старый номер.

**Текст:**

- по‑русски, простыми словами, без внутреннего жаргона;
- одна находка — одна проблема: что не так, где (ссылка), почему это важно;
- в ревью нет исправлений. Предложение — в `plan.md`;
- решения, которые принимают люди (выбор между вариантами), — в таблицу решений плана: варианты и предложение. Поля «Решение» и «Кто, дата» оставить пустыми.

### 6. Ответ пользователю

Коротко в чате:

- сколько находок каждой важности;
- главное — 3–5 пунктов;
- какие роли смотрели и у каких ролей находок нет — это тоже результат;
- что не проверялось;
- ссылки на `review.md` и `plan.md`.

Ничего не коммитить без просьбы.
