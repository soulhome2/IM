# Чек‑листы ревью IM по ролям

Один проход, но через каждую роль по очереди: архитектор, тестировщик, продакт, UX / оператор, дизайнер, разработчик. У каждой роли свой вопрос к прототипу и правилам. Находку можно найти глазами одной роли, а записать — с меткой всех, кого она касается.

Пункты собраны из ошибок, которые уже встречались в этом репозитории. Новый тип ошибки, найденный в ревью, стоит добавлять в раздел той роли, которая его нашла.

## Архитектор

*Вопрос: модель целостна, однозначна и переносится в продукт без переделки?*

**Состояния**

- [ ] У каждого нетерминального состояния есть вход и выход. Терминальные выходят только через «Переоткрыть».
- [ ] У каждого состояния указаны категория и владелец. Владелец определён однозначно: человек, группа или никто, и связь `owner` с `assignment_group` описана.
- [ ] Для каждого состояния есть бейдж для каждого смотрящего: я, моя группа, другой.

**Переходы**

- [ ] У каждого перехода в таблице указаны: откуда, куда, право, условия и все эффекты — владелец, таймеры, уровень эскалации, причина удержания, журнал, уведомления.
- [ ] Эффекты описаны для каждого исходного состояния, а не «в общем». Например, перехват из «Отложен» и из «Ожидает принятия» действует по‑разному.
- [ ] Диаграмма совпадает с таблицей переходов, включая автоматические переходы.
- [ ] Каждое правило достижимо при настройках по умолчанию.
- [ ] Таблицы кнопок для очереди и для карточки покрывают все сочетания «состояние × владелец» и согласованы с таблицей переходов.

**Права**

- [ ] Ключи в одном формате `ресурс:действие:область`. Третий сегмент — только область `own` или `any`.
- [ ] Действие над чужим инцидентом требует права с областью `any`. Это правило одинаково для всех действий.
- [ ] Описание права совпадает с тем, из каких состояний оно применяется.
- [ ] Каждый переход в «В работе» требует права взятия: Взять, Принять, Возобновить, Перехватить, Переоткрыть, групповая обработка.

**Лимиты и инварианты**

- [ ] Каждый переход в «В работе» учитывает лимит активных. Для групповой обработки явно сказано, считается группа одной единицей или каждый инцидент отдельно.
- [ ] Лимит отложенных описан для ручных и для системных удержаний.
- [ ] Гарантия выхода из карточки выполняется и при исчерпанных лимитах.
- [ ] Передача на себя запрещена, включая группы, в которые входит сам оператор.
- [ ] Ни одним действием, в том числе повторяющимся, нельзя обнулить норматив: передача туда‑обратно, возврат в очередь, переоткрытие.
- [ ] У каждого поля один смысл. Например, счётчик передач и ступень иерархии — разные вещи.

**Устройство прототипа**

- [ ] Переход атомарен: состояние меняется только после того, как эффекты выполнились без ошибки.
- [ ] Набор кнопок берётся из описания переходов, а не из списков, которые ведутся вручную.
- [ ] Эмуляция коллег и автоматические переходы идут через те же переходы и проверки прав и лимитов.
- [ ] Нормативы и адресаты берутся из настроек, а не из чисел в коде.
- [ ] Если у нескольких находок общая причина, она названа отдельным пунктом `ARCH`.

**Версии правил**

- [ ] Новое и изменённое записано в журнал изменений (§16) с номером пункта или решения.
- [ ] Ссылки «§N» ведут туда, куда сказано.
- [ ] Номер версии в шапке правил совпадает с тегом `rules-vN` последней выпущенной версии.

## Тестировщик

*Вопрос: всё ли работает так, как написано, и заметим ли мы, если сломается?*

**Самопроверка**

- [ ] `index.html?selftest` проходит. Каждое падение сопоставлено с номером пункта.
- [ ] Новый или изменённый переход, кнопка, форма покрыты шагом самопроверки.
- [ ] Шаги самопроверки не зависят друг от друга и от того, что осталось после прошлого шага.

**Поведение**

- [ ] Функция получает всё, что использует: нет обращений к переменным, которых нет в её области.
- [ ] Поведение совпадает с правилами на всех состояниях и для всех владельцев: я, моя группа, другой, никто.
- [ ] Что выбрано в форме, то и записано: варианты, списки, текст.
- [ ] Фоновое обновление не сбивает ввод и не закрывает открытый список.
- [ ] Флаг, который записывается, где‑то читается. При переоткрытии и сбросе поля очищаются.
- [ ] Отметки нарушений не смешивают разные причины.
- [ ] Граничные случаи: лимит активных и отложенных исчерпан, перерыв, норматив истёк, потолок эскалации, выборка из разных состояний.

**Демо-данные**

- [ ] Начальные данные не нарушают правил: лимиты, уровни эскалации, адресаты уровней.
- [ ] Журнал каждого инцидента — цепочка переходов, которые возможны по правилам.
- [ ] Место, устройства и план объекта совпадают: этаж, корпус, помещение.
- [ ] Термины в журналах — из действующей версии правил.

## Продакт

*Вопрос: сделано то, что нужно, и ничего важного не потеряно?*

Продакт не знает за вас, что ценно для заказчика. Его находки — чаще вопросы в таблицу решений плана, чем ошибки.

- [ ] Каждое требование Vision есть в `Specification/Vision coverage.md`, и его состояние совпадает с тем, что на самом деле в правилах и прототипе.
- [ ] Для каждого типа события сценарий оператора доходит до конца: от появления в очереди до закрытия или отмены.
- [ ] Итог сценария ведёт к правильному переходу: ложная тревога — к отмене, ожидание наряда — к удержанию.
- [ ] Отчётные данные нельзя исказить штатными действиями: передачей, возвратом в очередь, переоткрытием.
- [ ] Нет функций, для которых нет требования в Vision или в правилах.
- [ ] У открытых вопросов правил (раздел «Открытые вопросы») есть владелец или срок. Открытые вопросы Vision перенесены туда же.
- [ ] Решения из таблиц прошлых планов перенесены в правила, а не остались только в плане.
- [ ] Название продукта и термины одинаковые везде: Vision, правила, README, интерфейс.
- [ ] Раздел «соответствие прототипу» в правилах честно перечисляет расхождения, а не заявляет полное соответствие.

## UX / оператор

*Вопрос: оператору под нагрузкой удобно и понятно?*

- [ ] Типовой инцидент разбирается за разумное число действий. Массовый сбой — без повторения одного и того же для каждого события.
- [ ] Каждая кнопка и подпись совпадают с таблицами кнопок в правилах и понятны без документации.
- [ ] Недоступная кнопка объясняет почему, в том числе на телефоне. Когда кнопка скрыта, а когда заблокирована, — одно правило для всех.
- [ ] Сообщения и подсказки на языке оператора, без внутренних терминов и ключей прав.
- [ ] Горячие клавиши без дублей, не перехватывают стандартные клавиши браузера, не срабатывают в полях ввода, при открытых окнах и на кнопке в фокусе.
- [ ] Всё доступно с клавиатуры. У элементов без текста есть подписи для экранного диктора, на всех языках.
- [ ] На телефоне очередь, карточка и видео доступны. Кнопки видны без наведения.
- [ ] Пустые состояния (нет событий, нет камер, ничего не найдено) объясняют, что происходит.

## Дизайнер

*Вопрос: интерфейс собран по дизайн-системе и выглядит одинаково во всех состояниях?*

Правила дизайн-кита ONE PSIM лежат в его отдельном репозитории. Здесь проверяется то, что видно из этого.

- [ ] Цвета берутся из переменных темы (`theme/one-psim.css` через `bridge.css`), а не из чисел в CSS. Исключения перечислены в `prototype/README.md`.
- [ ] У каждого значения перечисления — приоритета, состояния, бейджа — есть стиль в светлой и тёмной теме.
- [ ] У элементов управления есть все состояния: обычное, наведение, нажатие, фокус, недоступное.
- [ ] Цвет действия один и тот же везде: в очереди, в карточке, в форме. Например, «Передать» — один акцент.
- [ ] Скриншоты в `prototype/shots/` соответствуют текущему интерфейсу, скрипт съёмки работает.

## Разработчик

*Вопрос: можно ли взять это в работу без устных пояснений?*

- [ ] Есть явный список того, что в прототипе только демонстрация и не переносится: эмуляция коллег, таймеры в браузере, права‑константы, данные в коде.
- [ ] Понятно, к какой версии правил приведён прототип и где он от неё отступает.
- [ ] Поля инцидента и их смысл описаны в правилах, а не только в коде прототипа.
- [ ] Каждая ошибка в ревью воспроизводится по описанию.
- [ ] Один ключ перевода — один перевод. Нет ключей, которые нигде не используются.
- [ ] Ссылки в документах работают: `python3 tools/check_links.py`.
- [ ] README описывает текущий прототип: раскладку, кнопки, проверки, версию правил.
- [ ] README и `prototype/README.md` не противоречат друг другу.
- [ ] Скрипты работают с текущими селекторами и не зависят от путей одного человека.
