# Пункт плана IM

Цель — пункт плана сделан так, как в нём записано, ничего лишнего не задето, и проверки это показывают.

## Порядок

### 1. Найти пункт

1. `git fetch`. Есть новое на GitHub — сказать и предложить подтянуть: план мог измениться.
2. Найти пункт по номеру во всех `reviews/*/plan.md` и его находку в `review.md` того же цикла. Прочитать шапку плана «Как вести» — она задаёт, как вести шаги, и ей следовать. Расходится с `CLAUDE.md` — главнее `CLAUDE.md`; сказать о расхождении и спросить.
3. Пункт из таблицы решений — в работу, только если заполнено «Решение». Пусто — остановиться и спросить. Решили не так, как предложено, — вписать решение в таблицу и делать по нему.
4. «Этап N» — все открытые пункты этапа по порядку, каждый как отдельный пункт.

### 2. Понять, где причина

Назвать место причины до правки:

| Пункт | Где причина | Где правка |
|---|---|---|
| RULE — правило противоречиво или неполно | правила, машина | правила + `State_rules/CHANGELOG.md` (§16), машина, если правило в ней |
| BUG — прототип не по правилам | машина, если правило там записано не так; иначе `engine.js`, `server.js`, `app.js` | там, где причина. Правило в коде прототипа не дублировать: условие или эффект — в машине |
| DOC | документ | документ; сгенерированные `TRANSITIONS.md`, `SETTINGS.md` — через исходник и сборку |
| DATA | `fixtures/demo.json`, `fixtures/scenarios/` | эталонный набор, затем сборка |
| PROC | `tools/`, CI, договорённости | там |

Поведение подтвердить запуском до правки: временная страница в scratchpad по образцу `tests/api-fsm.js` — `IMServer.create({ … testSupport: true })`, `POST /test/reset` с `workflowPatch` / `fixturePatch`, `POST /test/clock`, переходы. Не воспроизводится — сказать, а не чинить наугад.

### 3. Исправить

- Только то, что в пункте. Нашлось другое — назвать, не чинить попутно.
- Сгенерированные файлы не править (список — `CLAUDE.md`); после правки машины, контракта, эталонного набора, строк или примеров сценариев — `python3 tools/build_workflow.py`, после машины ещё `node tools/gen_quint.mjs`.
- `Specification/Workflow_machine/README.md` и `openapi.json` — CRLF.
- Новое поведение — с тестом: правило — сценарий в `tests/api-*.js`; кнопка, форма, экран — шаг в `prototype/selftest.js`. Тест должен падать до правки — проверить, а не предполагать.

### 4. Проверить

Проверки — по таблице «Что поменял → что проверить» в `CLAUDE.md`. Дополнительно:

- **Правка в `prototype/*.js` или в машине** — порчи не устарели: место порчи должно встречаться ровно один раз — в файле прототипа, а у порч машины (общий список `tools/mutations/machine.json`) — в самой машине.

  ```bash
  python3 -c "
  import sys; sys.path.insert(0, 'tools'); import check_code_mutations as m
  bad = m.stale()
  print(len(m.MUTATIONS), 'порч, устаревших:', len(bad), bad)"
  ```

  Устаревшую — поправить строку поиска в той же правке: порчу кода — в `tools/check_code_mutations.py`, порчу машины — в `tools/mutations/machine.json` (по ней же судит и модель Quint). Затем — только порчи изменённых файлов: `python3 tools/check_code_mutations.py <имя> …`. Полный прогон — предложить, запускать по просьбе.
- **Правка правила в машине** — затронутые мутации машины: `python3 tools/check_mutations.py <имя> …`. Статус BAD — правило продублировано в коде прототипа.
- Проверку, которую не прогнал, назвать с причиной.

### 5. Ответ

- что сделано по пункту и где (файлы);
- вывод проверок — итоговые строки, как есть; что не прогонялось и почему;
- что нашлось попутно и не чинилось.

### 6. Коммиты — только по просьбе

Два коммита:

1. Исправление. Сообщение начинается с номера пункта: `BUG-01: Принять — передать payload`; несколько пунктов — через запятую.
2. Отметка в плане: `- [ ]` → `- [x]`, в пункте — `Коммит: \`<хэш>\``. Сообщение — `Хэш <хэш> в плане ревью <дата>`; если в том же коммите хэш вписан в журнал правил — `… и журнале изменений правил`.
