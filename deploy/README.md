# Локальный стенд: облако и модули к нему

Как на своей машине быстро поднять облако AxxonSoft, а поверх него — модуль облака. Сейчас модуль один: Менеджер инцидентов (МИ). Стенд сделан так, чтобы и другие модули подключались к облаку тем же способом.

Всё делают скрипты из [stand/](stand/). Вы только указываете пути в двух файлах настроек и запускаете команды по порядку.

Порядок всегда такой: **сначала целиком облако, потом модули.**

```
stand/
  cloud/            облако — общее для всех модулей
    cloud.env.example   пути и пользователь стенда
    up.sh               всё облако одной командой
    01-prereq.sh … 04-gateway.sh, check.sh, after-reboot.sh
  modules/
    im/             модуль «Менеджер инцидентов»
      im.env.example    пути к репозиториям МИ, база, порты
      nginx.conf        маршруты МИ в шлюзе облака
      up.sh             весь модуль одной командой
      01-db.sh … 05-demo.sh, check.sh, stop.sh
```

## Что нужно заранее

- Linux (проверено на Ubuntu 26.04), от 16 ГБ памяти, около 40 ГБ свободного места.
- Docker CE с `buildx` и `compose`. Ваш пользователь должен быть в группе `docker`.
- Go, Node.js 20+, `jq`, `python3`, `curl`, `git`, `make`, `unzip`.
- Клоны репозиториев. Держите их на диске машины, а не в общей папке VMware: там сборка и Docker работают медленнее.

| Репозиторий | Ветка | Нужен для |
|---|---|---|
| `PROJ/axxoncloudgo` | `epic/CLOUD-23284-perms-i18n` | облака |
| `NEW/incident-manager-server` | `feature/im_operator` | МИ |
| `PROJ/incident-manager` | `feature/im_operator` | МИ (настройки и место оператора) |

- Интерфейс облака — `ui-AxxonNet.zip` из Bamboo (план `ASIP-AX`). Есть и другой вариант: каталог своей сборки `axxoncloud-ui`, об этом ниже.
- Образ `uploader.img` из Bamboo (план `ASIP-UP`). Модулям он не нужен, без него можно обойтись.
- Без корпоративного VPN приватные Go-модули `src.axxonsoft.dev` не скачиваются. Их берут из локального прокси, который собирают из архива `libs.zip`; архив дают коллеги. Подключается он файлом вида `~/go/offline-env.sh`. Путь к этому файлу указывается в `GO_ENV_FILE`. С VPN оставьте `GO_ENV_FILE` пустым.

## Часть 1. Облако

1. Настройки:

   ```bash
   cd deploy/stand/cloud
   cp cloud.env.example cloud.env
   nano cloud.env          # пути к клону облака, ui-AxxonNet.zip, uploader.img, рабочему каталогу
   ```

2. Пароль пользователя стенда. Он хранится только в файле, в скрипты не вписывается:

   ```bash
   printf '%s' 'ПридумайтеПароль' > ~/Work/stand/test-operator.pass
   chmod 600 ~/Work/stand/test-operator.pass
   ```

3. Запуск:

   ```bash
   ./up.sh              # первый раз, около 15 минут
   ./up.sh --no-build   # если образы уже собраны
   ```

4. Проверка: `./check.sh` должен вывести `итого FAIL: 0`. После этого откройте `https://axxonnet.test/dev-login.html`: вход выполнится сам, под пользователем стенда.

Что делают шаги (каждый можно запустить отдельно, повторный запуск безопасен):

| Скрипт | Что делает |
|---|---|
| `01-prereq.sh` | проверяет программы и клон, включает Docker Swarm, добавляет `127.0.0.1 axxonnet.test` в `/etc/hosts` (спросит `sudo`) |
| `02-build-deploy.sh` | собирает образы облака (`make build-all`), раскладывает интерфейс, запускает стек `ac` (`make deploy`), ждёт ответа портала |
| `03-users.sh` | заводит пользователя стенда в группе `cloud-admin` прямо в базе облака и ставит страницу входа без пароля |
| `04-gateway.sh` | собирает шлюз облака (`ac_nginx`) с маршрутами модулей, см. «Как подключить свой модуль» |
| `check.sh` | портал отвечает, пользователь входит, нет остановленных сервисов |
| `after-reboot.sh` | поднимает облако после перезагрузки машины |

Что скрипты обходят сами, руками делать ничего не нужно:

- Debian 11 переехал в архив, и сборка `ac/backend` падала на `apt`. Скрипт собирает локальный `debian:bullseye`, который берёт пакеты из `archive.debian.org` (файл `bullseye-archive.Dockerfile`).
- `make dep` и `gen-bp-prepare` не вызываются: в них жёстко прописан корпоративный прокси.
- Сервис `ac_uploader` останавливается: без хранилища он падает, а модулям не нужен.
- `make create-db-users` устарел, поэтому пользователь заводится по новой схеме: `users` → `user_nodes` → `users_user_groups`.
- `make deploy` сбрасывает шлюз. Маршруты модулей `02-build-deploy.sh` после этого возвращает сам.

## Часть 2. Модуль «Менеджер инцидентов»

Облако из части 1 должно быть уже поднято: `up.sh` модуля проверяет это первым делом.

```bash
cd deploy/stand/modules/im
cp im.env.example im.env
nano im.env             # пути к incident-manager-server и incident-manager
./up.sh                 # или ./up.sh --demo — сразу с демо-данными
```

`check.sh` должен вывести `итого FAIL: 0`. Адреса:

| Что | Адрес |
|---|---|
| Настройки МИ под шапкой облака | `https://axxonnet.test/dev-login.html?to=/incident-manager/` |
| Настройки МИ напрямую | `https://axxonnet.test/dev-login.html?to=/im/` |
| Место оператора | `https://axxonnet.test/dev-login.html?to=/im/operator/` |

| Скрипт | Что делает |
|---|---|
| `01-db.sh` | роль и база МИ в контейнере `ac_db`; таблицы сервер создаёт сам при старте |
| `02-server.sh` | собирает сервер МИ и запускает его в фоне (`--no-build` — без сборки, `stop` — остановить). Журнал — `$STAND_DIR/im-server.log` |
| `03-web.sh` | `npm ci` и Vite в фоне (`stop` — остановить). Журнал — `$STAND_DIR/vite.log` |
| `04-permissions.sh` | выдаёт группе `cloud-admin` права `incident_manager.*` из машины МИ |
| `05-demo.sh` | по желанию: агент-эмулятор, устройства, приоритеты, сценарии и правила из `demo.json`; `--replay` — ещё и события |
| `check.sh` | сервер МИ отвечает напрямую и через шлюз, Vite отвечает через шлюз |
| `stop.sh` | останавливает сервер и Vite; `--remove` ещё и убирает маршруты МИ из шлюза |

Важно: Vite запускается с `VITE_API_URL=https://axxonnet.test`. Без этой переменной прокси конфигуратора по умолчанию смотрит в боевое облако заказчика.

**Страница МИ под шапкой облака** (`/incident-manager/`) есть только в своей сборке `axxoncloud-ui` с правкой из ветки `feature/im_operator`. В архиве Bamboo её нет. Чтобы она появилась, соберите `axxoncloud-ui` и укажите каталог сборки в `UI_BUILD_DIR` файла `cloud.env`, затем выполните `cloud/02-build-deploy.sh --no-build`. Скрипта для самой сборки нет: без VPN закрытый пакет `@axxon-web/cloud-menu` приходится собирать из исходников `axxon-web`. Как это сделано — в [TECH-DEBT.md](../research/integration/TECH-DEBT.md) и [67-im-under-cloud-header.md](../research/integration/67-im-under-cloud-header.md). Без этой сборки настройки МИ открываются по адресу `/im/`.

## После перезагрузки машины

```bash
deploy/stand/cloud/after-reboot.sh        # облако
deploy/stand/modules/im/up.sh --restart   # модуль: сервер и Vite без сборки
```

## Как подключить свой модуль

Модуль работает на машине (сервер и интерфейс в режиме разработки), а облако ведёт к нему запросы через свой шлюз. Чтобы так же подключить новый модуль:

1. Сделайте каталог `stand/modules/<модуль>/` по образцу `im/`: файлы `<модуль>.env.example`, `up.sh`, `check.sh`. В начале каждого скрипта:

   ```bash
   MOD="$(cd "$(dirname "$0")" && pwd)"
   source "$MOD/../../cloud/lib.sh"      # CLOUD, CA, D (docker), login → $TOKEN, psql_root, say, die …
   load_module_env "$MOD" <модуль>
   ```

2. Опишите маршруты модуля в `nginx.conf`: `location`-блоки, а вместо адреса машины — `@HOST@`, например `proxy_pass http://@HOST@:5100;`. В `up.sh` положите этот файл в `$GATEWAY_D/<модуль>.conf` и вызовите `"$CLOUD_KIT/04-gateway.sh"`. Шлюз соберёт куски всех модулей и откроет в фоновом фаерволе `vpn-killswitch` (если он стоит) проход из Docker к их портам.
3. Если модулю нужна своя база — заведите её в `ac_db` через `psql_root`, как в `im/01-db.sh`.
4. Если модулю нужны права в облаке — выдайте их группе `cloud-admin` через `PATCH /api/v3/ac-backend/roles/global`, как в `im/04-permissions.sh`. Тело запроса — массив всех ролей, список прав роли заменяется целиком.

## Если что-то не так

| Признак | Что делать |
|---|---|
| `https://axxonnet.test/` не открывается после перезагрузки | `cloud/after-reboot.sh` |
| `/im/` даёт 502 | Vite не запущен (`modules/im/03-web.sh`) или фаервол не пускает Docker к машине (`cloud/04-gateway.sh` ещё раз) |
| Через шлюз 401/403 у сервера МИ | `modules/im/04-permissions.sh`; если сервер перезапускался — проверить конец `im-server.log` |
| Сервер МИ упал при старте | конец `$STAND_DIR/im-server.log`. Часто причина в том, что облако не приняло каталог прав, или в том, что база новее сборки (откат — [30-local-stand.md](../research/integration/30-local-stand.md#откат-сборки)) |
| После `make deploy` пропали маршруты МИ | `cloud/04-gateway.sh` |

Подробная история стенда со всеми находками — [30-local-stand.md](../research/integration/30-local-stand.md).

## Только для локального стенда

Страница `dev-login.html` хранит пароль пользователя стенда открытым текстом, а сервер МИ и Vite слушают все сетевые интерфейсы. Это допустимо лишь на своей машине. Не ставьте так стенд, доступный другим людям; страницу входа можно не ставить: `DEV_LOGIN=0` в `cloud.env`.
